# Orchestration: delegating and the Orchestra board

## Delegating to subagents

For independent, well-scoped tasks (a single feature, a page, a test suite, a self-contained refactor), spin up subagents on a lower model, Sonnet 5.5 (`model: "sonnet"`), and run independent ones in parallel. Keep the work that needs judgment yourself: architecture, prompts, cross-cutting design and final review.

- **Start agents from the templates in `~/.claude/agents/`** (pass it as `subagent_type`): `lane-builder` for build lanes, `test-porter` for porting acceptance tests before launch, `browser-checker` for the phone and desktop check after hand-back, `art-reviewer` for every batch of integrated art (packs or commissioned) before the owner sees it, `researcher` for read-only research. The templates already carry the model, the shared-tree rules, the self-check list and the report format, so a brief states only the task. If a template doesn't fit, use `general-purpose` with `model: "sonnet"`.
- **Name lanes for their work**, not by letter: owner ids like `leeches`, `activity-log`, `tutor-lessons`, with the model in each step's `model` field. The board shows "Leeches · Sonnet". Use the same name as the agent's `description` so hand-backs are easy to place.
- **Split lanes by coupling, not by file list.** Before fixing lanes, list the interfaces each would need. If two lanes would need the same interface, or one would change something the other calls, make them one lane, or have the orchestrator build that interface as a contract first. Measured elsewhere: grouping tightly coupled files under one agent beat naive file-by-file parallelism, which gained little and cost 44-60% more; cross-agent merge conflicts run at about twice the rate of single-agent ones.
- **Parallelize only independent work.** Measured elsewhere, multi-agent setups gain a lot on tasks that split cleanly and lose 39-70% on sequential ones. Give a chain of dependent steps to one agent in order rather than to several. Three or four lanes is the usual sweet spot. The exception is work with no shared interfaces at all, like art assets (one folder each): there, run as many lanes as the assets justify (6 to 10 is fine), limited by the review load and the GPU and CPU rather than merge risk.
- Give each agent strict file ownership (which files it may create or edit) so parallel agents don't collide, plus the conventions to follow and how to run the tests.
- **Every brief has an "Assumptions and decisions" section**: each choice already made that the agent could otherwise guess differently, such as the user's answers, which file owns a shared piece, date and text formats, what to leave alone, and which tests are expected to stay red. Conflicting assumptions between parallel agents are a top cause of multi-agent failure.
- **Onboard through the context file, not the codebase.** Tell each agent to rely on the project `CLAUDE.md` and to open only the files its brief names; don't ask it to "read the project".
- **Contracts before launch.** Before parallel lanes start, the orchestrator makes the shared changes they depend on (schema and migrations, shared models) and writes the interfaces each lane builds against (function signatures, stubs, data shapes). Agents then read one interface, not the code behind it, and never edit shared contracts in parallel. When a spec comes with acceptance tests, port them into the repo before launch so each lane starts with its own red tests; lanes may adapt a test to the codebase but never weaken an assertion.
- **Reuse working code before rebuilding it.** Before planning lanes, look for an existing implementation of the same spec (an experiment's run, a prototype branch, an earlier attempt). Merging and reviewing it is far cheaper than a lane rebuilding it (measured: about 10 minutes against roughly 200k agent tokens), and it gets the same review as a lane's work. Offer it to the user as a plan field when the choice is theirs.
- **Keep shared entry points out of lanes.** Pre-create and register anything several lanes would otherwise add to one file (empty routers in the app entry point, menu or registry entries at the gate), so no two lanes edit the same file. A migration whose data step depends on a lane's code (a backfill) belongs to that lane, appended at a marked spot: registered early with a stub, a database migrated in between records it as done with no data.
- **Reuse agents for related steps.** Group a phase's steps into lanes by shared code, and send follow-on steps to the same agent (SendMessage) so it keeps its context; a fresh agent spends most of its first step learning the codebase (measured: follow-on steps cost 60-80% less).
- **Time-box every lane.** Each brief asks for a status hand-back at least every 60 minutes of work (what is done, what is left, an estimate); at each one, decide to continue, narrow, split or fan out. Never leave a lane unchecked for more than an hour, especially one holding a shared resource (a real game, a device, a database). Measured: one unchecked Sonnet lane spent 5.5 hours on a restore rewrite that should have taken about 2.
- **Diagnose, then plan the fix.** When a lane's diagnosis shows the fix is a rewrite or bigger than the brief, it hands back with the diagnosis and an estimate before starting it, so the orchestrator can re-plan.
- **Fan out open-ended work.** Reverse-engineering, hunting a divergence, performance archaeology: run several investigators in parallel, one per hypothesis or subsystem, each with its own copy of any shared resource (a separate install, port range or database copy), and merge the findings; or use one or two Opus agents (`model: "opus"`), whose fewer wrong guesses pay off where each guess costs a slow build or test. Keep Sonnet for well-specified builds.
- **Make every guess cheap.** Before a lane iterates on a slow loop (a rebuild plus a real-environment probe), make the loop fast: incremental builds, a probe script that checks one hypothesis in seconds, the affected test only. A guess that costs minutes is the first thing to fix.
- **Shared working tree rules, in every brief:** never `git stash`, `checkout`, `reset` or `restore` (the other lanes' uncommitted work lives in the same tree), never commit, and if the suite fails in files you don't own, report it rather than fix it. Each lane runs its own live server on its own port and stops it by PID.
- **Concise briefs without losing content.** Give exact file pointers and paste the few relevant lines of a pattern or interface rather than saying "read file X". Cut repetition and spec restatement, but keep every requirement, constraint, acceptance criterion and gotcha: shorter wording, never fewer facts.
- Review every agent's result before committing, then send it back for one improvement round:
  1. Check: run the tests, read the diff (not whole files), and click through any UI in the browser at 375px and desktop width, including opening menus and dialogs. Build lanes skip "optional" live checks, so the browser check is the review's job. For a phase with several UI lanes, run one `browser-checker` over all of them, then spot-check its findings and the riskiest pages yourself. Review against the checklist that catches what green suites miss:
     - the user's own data is never silently overwritten;
     - dates and numbers read naturally;
     - no sideways scroll or cramped layout at 375px;
     - helpful empty states;
     - inline errors with a retry;
     - the project's content rules.
  2. Score it 1-5 on correctness, fit to the spec, code quality and UX (where there is a UI), in one line each.
  3. Send the agent (SendMessage to the same agent, so it keeps its context) a short list of must-fix issues and at most a few should-fix ones, with file:line pointers. Fix a trivial one-liner yourself when that's cheaper than a round trip, and tell the agent so it doesn't redo it.
  4. Re-check only what it changed. One round is the norm; a second only if must-fix issues remain.
- Run the whole suite at the gate, not only each lane's tests: suites that pass alone can break together (test helper modules with the same name in different folders, shared fixtures).
- **Keep the test loop fast** (see the lifecycle skill's "slow inner loop" pitfall). Lanes and review rounds run only the affected tests, under about 3 minutes. The full suite runs once per gate, alone on the machine, and reviewers read that result instead of re-running it. A full suite over about 10 minutes gets a planned step to speed it up. Write the rule into every brief ("run only <these tests> while iterating; the full suite once, at the end"): a lane that re-runs a 10 to 15 minute suite after each change spends most of its time waiting (measured: about a third of one 5.5-hour lane).
- Keep reviews lean: no separate reviewer agent unless the change is large or risky, no re-reading unchanged code, no restating the spec back to the agent.

## Orchestra board

Orchestrated work is tracked on the Orchestra board, a private claude.ai artifact with its own database: https://claude.ai/artifact/Eqis6DgyZMefwhzFM1KNta (one board for all projects). Overture stays for reviewing small, single-agent plans; it is unreliable for lanes (in-memory state, forks read as choices, counters only count updates the open page received).

Write to it with the `ArtifactData` tool (`url` above), batching writes and pinning `if_version` on updates. Data model:
- `projects/<project-id>`: `{name, repo, repoUrl (e.g. the GitHub URL, so committed files link to the repo), updatedAt}`.
- `phases/<prefix>~<phase>`: `{project, order, short, title, kind: discovery|build (default build), deliverables: [{title, path or url}], status: draft|planned|active|closed, deps: [phase doc ids], startedAt, endedAt, notes, metrics: {orchestratorTokens, defectsCaught, lines}}`.
- `steps/<prefix>~<step>`: `{project, phase, order, owner ("orchestrator" or a lane named for its work, e.g. "leeches": one lane per owner), model ("sonnet", "haiku"...), code, title, status: pending|active|review|returned|accepted, startedAt, endedAt, deps: [step doc ids], description, expected, risks (text), complexity and riskLevel (low|medium|high, shown as meters on each tile), fields, options: [{id, title, description, complexity, riskLevel}] for alternatives the user chooses between, changes: [{at, reason}] for edits after approval, rerunsHandled: [request at], files: [{path, status: A|M|D|R, added, removed}], commit (sha once committed), checks: [{id, label, status: pass|fail|warn|pending, detail, at}], commentsHandled: [comment at], agentTokens, summary, gate: true for the review gate, rounds: [{n, at, verdict: returned|accepted, scores: {correctness, spec, quality, ux}, notes}]}`. Times are ISO 8601 UTC, read from the clock (`date -u +%Y-%m-%dT%H:%M:%SZ`) at the moment of the event, never estimated: a time in the future pushes the step off the Score timeline.

Draft review (before any launch): write the new phase as `status: "draft"` with every step `pending`, its `deps`, and for each step `description`, `expected`, `risks`, `complexity`, `riskLevel` and, where the user should decide something, `fields: [{id, label, type: text|longtext|select|boolean|number, options, required, help}]`. Phases also carry `deps: [phase doc ids]` for the board's "All phases" tree. Tell the user the plan is ready to review on the board (its Plan view shows the draft tree top to bottom with one column per lane, then every question in one section, then the approval; "All phases" shows phase dependencies) and to say so in chat when they have approved, since nothing notifies you. Then read `approvals/<phase doc id>` (`{status: pending|approved|changes, note}`) and `inputs/<step doc id>` (`{answers: {fieldId: value}, note}`) with ArtifactData. Launch only when the approval says `approved`; apply every answer and note to the briefs; on `changes`, revise the draft and ask again. When a step has alternatives, give it `options` (two or three) instead of a select field: the board draws them side by side, the user's pick arrives as `inputs/<step>.choice` (an option id), and approval is blocked until every step with options has one. Build only the chosen option. The user's inputs live in their own documents, so never write to `inputs`, `approvals`, `controls` or `comments`.

When to write: plan the phase (draft as above; after approval set the phase `planned` or straight to `active`); on launch (phase `active`, `startedAt`, steps `active`); when an agent hands back (`review`); after each review round (append the round; `returned` or `accepted`; `endedAt` on acceptance; `agentTokens` from the task notification, which is cumulative per agent, so record an agent's latest total once rather than adding rounds; when one agent builds several steps in a single run, record its tokens on the first step and say so in the others' summaries); at the gate (gate step `accepted` only when every lane step is accepted, then phase `closed` with `endedAt` and metrics). For `metrics.orchestratorTokens`, run `python ~/.claude/tools/phase_tokens.py --since <phase startedAt> --until <gate time>` from the project folder. It adds up this session's transcript (fresh input plus output) and its subagents' transcripts for the window; record the orchestrator figure, and the agents' total in the phase notes. Bump the project's `updatedAt`. Tell the user the board link when a phase starts.

Events (the command center's live feed and each agent's milestone note on the network view; the owner wants it constantly active, so every agent, the orchestrator included, posts often): `events/<prefix>~<UTC time as 20261010T163557Z>-<agent>-<n>` (n counts up, so two events in one second never overwrite each other) with `{project, phase, step, agent ("orchestrator" or the lane name), kind, text, at}`. `kind` is one of `dispatch`, `relay`, `thought`, `review`, `breach`, `secured`, `command`, `info`. `text` is one plain sentence under 160 characters; `at` is clock time. The orchestrator posts `dispatch` when it launches a step, `relay` when a lane hands back, `review` (accepted) or `breach` (returned, or a check failing) after each round, `secured` when a step is accepted, `command` when it needs the user's decision, and `thought` as it works: what it is planning, what it is checking during a review (tests, the diff, the browser check, each finding), and each judgment call. Batch them with the step writes they accompany, and post at least every few minutes while any lane is running. Every lane brief gives the board URL, project id, phase id, step id and lane name and asks the lane to narrate its work: an event at every notable action, roughly every few minutes or every two or three tool steps, typically 10 to 30 per step (the `lane-builder` template says how; other agent types get the same instruction in their brief). Never write secrets into events.

Files per step (the board shows them as a folder tree on each step): write `files` with `python ~/.claude/tools/step_files.py --out <file>`, then pass that file to ArtifactData as the update's `file_path`.
- At each hand-back and after each round: use `--paths <the lane's owned globs>` in a shared tree, or `--worktree <lane dir>` in a worktree.
- After the gate commit: rerun each step with `--commit <sha>` (plus its `--paths`) so its files and `commit` link to the repo.
- Ownership check: at each hand-back, a file changed in the tree that no lane owns, or that belongs to another lane, is an ownership violation to raise in the review.

Checks per step (mechanical gates, shown as pills; the gate counts a failing check as blocking): at each hand-back and after each round, run `<the project's venv python> ~/.claude/tools/step_checks.py` (the project's own interpreter, e.g. `.venv/Scripts/python.exe`, not the system `python`: on this machine that is the Microsoft Store build, whose child processes can't start uv-managed Pythons) with `--tests "<the project's test command>" --owned <lane globs> [--others <other lanes' globs> | --worktree <lane dir>] --out <file>`, and write the result to the step with ArtifactData `file_path`. It records tests, ownership and diff size. Add your own entries the same way, such as `{id: "browser", label: "Browser check", status, detail}` after the browser check. Never set a step `accepted` while any check is `fail`: fix it, return it, or record why in a `warn` with the reason.

File comments (the user's, in `comments/<step doc id>`: `{items: [{path, text, at}]}`, written from the step's file tree): read them with the controls at every check. Every comment whose `at` is not in the step's `commentsHandled` goes to the lane's agent as part of its next round: quote the path and the comment, and treat each as a must-fix unless it conflicts with the spec, in which case ask the user. When sending, append each comment's `at` to `commentsHandled`; the board then shows it as sent. A comment on an accepted step reopens it as `returned`. Never write to `comments`.

Changes after approval: whenever you edit an approved step's scope, description, deps or owner (not its status or rounds), append `{at, reason}` to its `changes` with a one-line reason. The board flags it "changed" until the user marks changes as seen.

Run controls (the user's, in `controls/<phase doc id>`: `{mode: run|pause, stopAfter: step doc id or "", reruns: [{step, note, at}]}`): read it before launching any step, at every agent hand-back and before every review round, then set the phase's `controlsCheckedAt` (clock time) so the board shows when you last looked.
- `pause`: let running agents finish their current step, then launch nothing new and send no return rounds until the mode is `run` again. Tell the user in chat that you have paused.
- `stopAfter`: once that step is accepted, stop the phase (as with pause) and tell the user.
- A rerun request whose `at` is not yet in the step's `rerunsHandled`: send the step back to its agent (or redo it yourself) with the note as the brief, set the step `active`, then append the request's `at` to `rerunsHandled`.
