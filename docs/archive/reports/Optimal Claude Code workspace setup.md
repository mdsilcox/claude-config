# Shrink the context, harden the guardrails

The best way for a solo developer to run Claude Code in October 2026 is to keep everything that loads on every turn small and hand-written, and to move everything that must hold into permission rules, hooks and an OS sandbox on a machine whose loss is survivable. Concretely, that means a project CLAUDE.md of roughly 50 to 150 lines (commands, timings, gotchas, pointers), a global file of a few dozen lines, procedures packaged as skills that load only when invoked, a reviewer subagent with a pinned model, auto mode with `ask` rules on pushes, and a sandboxed VM for anything long or unattended. Controlled 2026 studies found that context files change what agents do and what they cost (generated files added about 20 to 23 percent) without improving Claude Code's correctness, and instruction adherence falls off past roughly 100 simple rules, so length is a tax, not insurance. The machine split is the security design: native Windows has no Bash sandbox and drew four user-reported drive or profile wipes between September 7 and October 3, 2026, so the desktop keeps supervised work and Windows-only toolchains while the Proxmox dev VM, with bubblewrap sandboxing, snapshots and tailnet-only access, hosts long, unattended and untrusted runs. The workflow lever with the strongest evidence is verification against tests the human trusts, enforced by a Stop hook or `/goal` and followed by a fresh-context review whose findings get triaged; planning ceremony and parallel lanes should scale with the task, because multi-agent setups win on decomposable, read-heavy work and lose on coupled, sequential work. On Max, the binding limits are a shared five-hour and weekly usage pool and one person's review attention, and input tokens dominate spend (98 percent of counted agent tokens in the developer's own metered build), so always-on context and agent count are the first things to cut. The basic-memory vault fits as curated long-term memory: git carries the Markdown, each machine rebuilds its own index, and agent-derived notes pass through a reviewed inbox because memory files are a persistent prompt-injection surface.

## Context files steer behavior, not capability, so the always-on layer stays small

Three controlled 2026 studies converge on an uncomfortable result for anyone who has grown a long CLAUDE.md. ETH Zurich's evaluation of repository context files found that **developer-written files raised task success about 4 percent on average across agents but did not help Claude Code**, while LLM-generated files lowered success slightly and **raised cost about 20 to 23 percent**; Claude Code with Sonnet 4.5 cost $1.15 per task with no file, $1.30 with a human-written file and $1.33 with a generated one ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)). A July 2026 two-agent ablation on real repositories found no measurable correctness change from any context strategy for Claude Code on Sonnet 4.6 ([arXiv 2607.27250](https://arxiv.org/abs/2607.27250)), and a Codex study measured the upside that does exist: a developer-written file cut median runtime 28.6 percent and median output tokens 16.6 percent on small pull requests ([arXiv 2601.20404](https://arxiv.org/html/2601.20404v2)). What these files reliably do is steer behavior. Agents used `uv` about 1.6 times per task when the file named it and almost never otherwise, while codebase overviews did not shorten the path to the files a fix needed ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)), and a single warning that the full test suite was slow cut blind full-suite runs from 3.67 to 1.67 per test cell ([summary of Khatri 2026](https://codex.danielvaughan.com/2026/08/06/do-context-files-help-coding-agents-agents-md-ablation-study-codex-cli-correctness-vs-efficiency/)). The file is a lever for commands, tools and warnings, not a capability upgrade.

Length also has a measurable ceiling. In the IFScale benchmark, Claude Opus 4 followed 94.6 percent of 100 simple instructions but only 67.9 percent of 250 and 44.6 percent of 500, with omissions outnumbering wrong answers and a bias toward instructions that come first ([arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)); real agentic constraints are harder than keyword inclusion, and the harness's own system prompt already spends part of the budget ([HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)). Anthropic's guidance follows the same curve: **under 200 lines per CLAUDE.md**, a per-line test of "would removing this cause Claude to make mistakes?", and a warning that bloated files make Claude ignore real instructions; `@` imports organize text without reducing its cost, and CLAUDE.md arrives as a user message with no guarantee of compliance ([Memory](https://code.claude.com/docs/en/memory); [Best practices](https://code.claude.com/docs/en/best-practices)). Experienced practitioners land lower still. HumanLayer keeps its root file under 60 lines, Boris Cherny advises staying under about 1,000 tokens ([HN](https://news.ycombinator.com/item?id=46256606)), and Alex Kras, measuring with `/context` before and after, halved his CLAUDE.md and cut his skills from 24 to 9, finding the largest savings in CLAUDE.md and skill descriptions rather than in MCP tools ([alexkras.com](https://alexkras.com/i-deleted-24-claude-code-skills-and-only-9-came-back/)). Thariq Shihipar of the Claude Code team now suggests starting projects with no file at all and adding lines only for repeated failures ([Latent Space](https://www.latent.space/p/thariq)).

The practical consequence is a layout in which each surface carries one kind of content, priced by when it loads ([Extend Claude Code](https://code.claude.com/docs/en/features-overview); [Memory](https://code.claude.com/docs/en/memory); [Skills](https://code.claude.com/docs/en/skills)).

| Piece | Where it lives | What belongs there | When it costs context |
|---|---|---|---|
| Global instructions | `~/.claude/CLAUDE.md` on each machine | Working style, writing rules, approval rules, vault routing | Every request |
| Project instructions | `CLAUDE.md` at the repo root, committed | Commands, timings, machine split, gotchas, pointers | Every request |
| Scoped rules | `.claude/rules/*.md` with `paths:` | Conventions for one language or directory | When matching files are read or edited |
| Skills | `~/.claude/skills/`, `.claude/skills/` | Procedures and playbooks invoked on purpose | Description each request (none with `disable-model-invocation`), body on use |
| Subagents | `~/.claude/agents/`, `.claude/agents/` | Isolated roles such as reviewer and researcher | Descriptions each request; work runs in its own window |
| Hooks | `settings.json` at any scope | Anything that must happen every time | Nothing unless the hook prints |
| Permissions and sandbox | `settings.json`, personal defaults at user scope | Allow, ask and deny rules; filesystem and network limits | Nothing |
| MCP servers | User scope in `~/.claude.json`, or `.mcp.json` | External systems without a good CLI | Tool names only; schemas load on use |
| Output style | `/output-style` or `outputStyle` | Tone and format | Every request |
| Auto memory | `~/.claude/projects/<repo>/memory/` | Claude's own per-repo corrections | First 200 lines or 25 KB of `MEMORY.md` |
| Vault | basic-memory over the Markdown repo | Cross-project decisions, research, patterns, pitfalls | Only when searched |

### The global file carries preferences and a vault routing rule

Anthropic reserves the user-scope file for personal preferences that apply across projects ([Memory](https://code.claude.com/docs/en/memory); [Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)), and the most careful published global file adds a rule only after the same mistake has happened twice, prunes rules that have not earned their place within a month, starts from empty, and notes that a 600-line global file is a real per-session cost ([leek.io](https://leek.io/articles/my-global-claude-md-rules)). A global file that carries multi-step procedures (project lifecycles, lane briefs, board protocols, review rounds) is the anti-pattern Anthropic's large-codebase guidance names directly: reusable expertise living in CLAUDE.md instead of in a skill ([How Claude Code works in large codebases](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)). Those procedures belong in skills invoked by name and marked `disable-model-invocation: true`, which removes even their descriptions from context ([Extend Claude Code](https://code.claude.com/docs/en/features-overview)). `/doctor prompt-audit` (v2.1.283 and later) flags instructions written for older models, dead file references and contradictions, and if the file sets commit rules, the `includeGitInstructions` and `attribution` settings stop Claude Code's built-in git guidance from competing with it ([Memory](https://code.claude.com/docs/en/memory)). A global file in this spirit fits on one screen:

```markdown
# Personal defaults (stay under 40 lines; add a rule only after a repeated mistake)

- Write American English. No em dashes in prose, UI text, comments or docs.
- Do what was asked. Ask one sharp question only when a request is truly ambiguous; never widen scope.
- Ask before anything irreversible: deleting data, force pushes, migrations, VM, snapshot or firewall changes.
- Show evidence (test output, commands run, screenshots) instead of claiming success.
- Stop only processes you started, by PID. Never kill by image name.
- On Windows, write multi-line code with the Write or Edit tool, never a Git Bash heredoc.

## Knowledge vault (basic-memory)
Search it before research, a stack choice, or a second attempt at a non-trivial error.
Write to it after a decision, a research report, a reusable fix or a retro, or when asked.
Notes derived from web pages, issues or tool output go to inbox/ with status: draft and a source: field.

## Procedures
Multi-lane orchestration, project kickoff and review rounds live in skills. Invoke them by name.
```

Each machine keeps its own `~/.claude`: the Desktop app, the CLI and VS Code share one on Windows ([Explore the .claude directory](https://code.claude.com/docs/en/claude-directory)), while Desktop SSH sessions read hooks, proxy and CA settings from the VM's own copy ([Desktop](https://code.claude.com/docs/en/desktop)). That configuration is itself at risk from the agent it configures: one auto-mode session on WSL2 deleted a home directory through a cleanup `trap` hidden in a script it had written, taking hooks, agents and memory with it ([issue #88462](https://claudeissues.com/issue/88462-data-loss-claude-code-ran-rm-rf-on-home-in-auto-mode-destructive-code-hidden-ins)). The global file, settings, agents, skills and hook scripts therefore belong in a private git repo with an off-machine remote, copied into each machine; shared skills and agents can also ship as a personal plugin, which Anthropic positions as the way to reuse one setup across repositories ([Plugins overview](https://code.claude.com/docs/en/plugins/overview)).

### The project file carries commands, timings and gotchas

The project file should hold what Claude cannot infer and would otherwise get wrong: exact build, test, lint and run commands and the order to run them, a fast check kept separate from the full suite with its runtime stated, which machine runs which command, environment quirks, non-standard conventions and gotchas, and pointers to deeper docs with the reason to read them ([Best practices](https://code.claude.com/docs/en/best-practices); [HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)). It should leave out overviews, file-by-file tours, standard language conventions, pasted code (it goes stale, so point to file and line instead) and style rules, which a formatter hook enforces for free. The few rules that must not be missed go at the top, a "Compact instructions" section names what must survive summarization ([Best practices](https://code.claude.com/docs/en/best-practices)), and `/init` output is a draft to cut, since generated files measurably underperform hand-written ones ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). One solo developer's three-way test on a Next.js project found 2 lines too few, 247 lines too many (a mid-file rule was ignored and stale rules contradicted each other) and 67 lines best ([TabNews](https://www.tabnews.com.br/kenimo49/o-criador-do-claude-md-escreve-2-linhas-a-comunidade-escreve-100-quem-esta-errado)); it is one anecdote, but it matches the controlled data.

```markdown
# <project>: <one line on what it is>

## Must not miss
- Tests in tests/acceptance/ are the spec: never edit them during implementation.
- Run the fast check before every commit and paste its output.

## Commands (dev VM unless marked Windows)
- Fast check (about 20 s): `uv run pytest tests/unit -q && uv run ruff check .`
- Full suite (about 12 min): `uv run pytest`. Run once before the gate, never in a loop.
- Dev server: `uv run uvicorn app.main:app --reload --port 8010`
- Windows: `<the build that needs MSVC or .NET>`

## Gotchas (one line per real mistake, with the fix)
- <...>

## Pointers
- Module map and interfaces: docs/architecture.md (read before editing app/services/)
- Spec: docs/SPEC.md. Decisions: docs/decisions/

## Compact instructions
Keep the modified-file list, failing test names and the current plan step.
```

Three refinements keep the file short as a project grows. Path-scoped rules in `.claude/rules/*.md` with a `paths:` field load only when matching files are touched, and Anthropic prefers them to nested CLAUDE.md files for cross-cutting concerns ([Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more); [Memory](https://code.claude.com/docs/en/memory)), so C++ mod conventions need not ride along in a Python session. Because subagents load the CLAUDE.md hierarchy at startup (except Explore, Plan and agents with `omitClaudeMd`) ([Subagents](https://code.claude.com/docs/en/sub-agents)), the project file is also the cheapest onboarding for lanes, which argues for keeping it accurate rather than long; an interface index for lane briefs belongs in a referenced document such as `docs/architecture.md`, named in each brief. Finally, if other harnesses matter, Claude Code has read `AGENTS.md` since v2.1.277, but only when no CLAUDE.md or `CLAUDE.local.md` exists at or above the working directory, and the documented way to share one file is a CLAUDE.md whose first line is `@AGENTS.md`; adding a `CLAUDE.local.md` later silently stops AGENTS.md from loading ([Memory](https://code.claude.com/docs/en/memory)). The import also sidesteps symlinked instruction files, which carry a known bug in which Claude refuses to write through them ([issue #78977](https://claudeissues.com/issue/78977-feature-request-native-agents-md-support-duplicate-of-6235-filed-deliberately)).

### Skills, subagents, plugins and MCP servers each earn their slot

Skills are the right home for procedures, but the evidence favors few, hand-written ones. In SkillsBench, curated skills raised pass rates 16.2 points on average but only about 4.5 points in software engineering, and self-generated skills gave no benefit ([SkillsBench](https://hyper.ai/en/papers/2602.12670)); in Vercel's Next.js evaluations, a compressed docs index in AGENTS.md reached a 100 percent pass rate while skills topped out at 79 percent even when the agent was told to use them ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). A skill should therefore hold a procedure that you or a clear trigger will invoke, while anything that must always apply belongs in CLAUDE.md (if short) or a hook. Each SKILL.md stays under about 500 lines, because after compaction only the first 5,000 tokens of each invoked skill return within a 25,000-token budget; side-effect workflows get `disable-model-invocation: true`; and `/skill-doctor` reports what each skill costs and how often it fires ([Skills](https://code.claude.com/docs/en/skills)). One cheap win is a custom skill named `verify` that runs the project's fast check, because since v2.1.286 Claude runs a skill with that name before each commit that is not purely docs or tests ([Skills](https://code.claude.com/docs/en/skills)). Third-party skills are code from strangers: Snyk found critical issues, including malware and prompt injection, in 534 of 3,984 public skills ([Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub)).

Subagents earn their keep by isolating context, and they reward explicit configuration. Model inheritance is the default, so every custom agent should pin `model:`; the built-in Explore agent now follows the main model, which on Max means Opus, unless a user agent named `Explore` pinned to `haiku` overrides it ([Subagents](https://code.claude.com/docs/en/sub-agents)). A non-fork subagent starts without the conversation, invoked skills, output style or auto memory, cannot ask the user anything because `AskUserQuestion` is removed, and returns only its final message, so decisions get made before delegation and any rule that matters is restated in the brief; `maxTurns` time-boxes it and marks partial output as resumable, and `isolation: worktree` gives a writer its own checkout ([Subagents](https://code.claude.com/docs/en/sub-agents)). Forks inherit the whole conversation and its prompt cache, which makes "try this from here" cheaper than a fresh agent ([Subagents](https://code.claude.com/docs/en/sub-agents)). Agent definitions hot-reload on the next delegation, except that the first file in a brand-new agents directory needs a restart ([Subagents](https://code.claude.com/docs/en/sub-agents)); the developer hit a related limit when an agent file created mid-session in a sub-folder of the working folder could not be launched by name, so agent folders are best created before the session starts ([agent-file note](memory://vault/findings/a-claude-code-agent-file-created-mid-session-cant-be-loaded-by-name)). The one custom agent nearly every project needs is a reviewer:

```markdown
---
name: reviewer
description: Reviews a finished diff in a fresh context against the stated acceptance criteria. Use after implementation and before commit.
tools: Read, Grep, Glob, Bash
model: opus
effort: high
maxTurns: 40
---
You see only the diff, the acceptance criteria and the test output you are given.
Report correctness bugs and unmet stated requirements only, each with file:line and evidence.
Do not suggest refactors, extra abstraction, or tests for cases that cannot happen.
Do not edit files. Run the fast check from CLAUDE.md before reporting.
```

Plugins are a packaging layer, and every enabled plugin adds its skill and agent descriptions to each session ([Plugins overview](https://code.claude.com/docs/en/plugins/overview)), so a from-scratch setup starts with none and adds one only against a measured need. `claude plugin eval` (v2.1.269) scores a plugin against test cases with a no-plugin baseline ([Plugins overview](https://code.claude.com/docs/en/plugins/overview)), and `/usage` now attributes plan usage to each plugin, skill, subagent and MCP server and proposes fixes ([Manage costs](https://code.claude.com/docs/en/costs)). LSP plugins show why measurement matters: one practitioner calls them the highest-leverage plugin, while another found the Python LSP injected diagnostics in 186 of 627 sessions with a single finding acted on, and uninstalled it ([arps18](https://arps18.github.io/posts/claude-code-mastery/); [HN](https://news.ycombinator.com/item?id=48289950)). Mods (v2.1.287) run unsandboxed inside Claude Code with the user's permissions and can approve tool calls even under `dontAsk` ([Mods overview](https://code.claude.com/docs/en/plugins/mods/overview); [Best practices](https://code.claude.com/docs/en/best-practices)), so they deserve the scrutiny of any installed binary. Framework bundles such as Superpowers are valued mainly for their requirements interview and review steps; the one independent test found about 9 percent lower cost overall but higher cost on simple tasks ([mejba.me](https://www.mejba.me/blog/superpowers-plugin-claude-code-review)), which argues for adopting pieces rather than the whole pipeline.

MCP servers are cheap when idle now that tool search defers their schemas by default: the developer estimated basic-memory at about 300 tokens per idle session against about 11,000 if all 21 tool definitions loaded ([token-cost note](memory://vault/findings/basic-memory-costs-about-3-000-tokens-on-first-use-per-session); [MCP](https://code.claude.com/docs/en/mcp)), and a July 2026 test found the old token gap between CLI and MCP access had nearly vanished ([Checkly](https://www.checklyhq.com/blog/mcp-vs-cli-token-efficiency/)). Anthropic still calls CLIs such as `gh` the most context-efficient route to external services ([Best practices](https://code.claude.com/docs/en/best-practices)), so the defensible set is basic-memory and a docs server such as Context7 at user scope, one browser path for verification, `gh` instead of a GitHub server, and nothing project-scoped without a reason; connectors that are enabled but unauthenticated still add tool names and should be switched off ([alexkras.com](https://alexkras.com/i-deleted-24-claude-code-skills-and-only-9-came-back/)). Output styles load on every request and change tone, not budget: output was under 2 percent of counted agent tokens in the developer's metered build ([build note](memory://vault/findings/a-full-autonomous-game-build-took-about-3.5-hours-and-8-percent-of-a-max-weekly-limit)), so Concise is a readability choice. The Learning or Explanatory styles suit work whose point is to learn, such as a new modding framework, because Anthropic's own randomized trial found engineers who fully delegated scored below 40 percent on a follow-up quiz while those who used AI for conceptual questions scored 65 percent or more ([Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills)).

## Rules that must hold belong in permissions, hooks and the sandbox

Prose rules fail the way IFScale predicts, by omission. User reports through 2026 describe CLAUDE.md rules followed in about half of sessions and a never-commit-without-permission rule broken on a Max plan ([issue #17530](https://github.com/anthropics/claude-code/issues/17530); [issue #34774](https://claudeissues.com/issue/34774-model-claude-code-max-plan-ignores-claude-md-instructions-committed-changes-with)). Anthropic's answer is consistent across its documentation: "If a rule must hold every time, make it a hook rather than a prompt instruction," and lean on permission rules, which Claude Code enforces rather than the model ([Extend Claude Code](https://code.claude.com/docs/en/features-overview); [Permissions](https://code.claude.com/docs/en/permissions)). Even these layers leak, so the design is defense in depth with machine isolation as the last line.

### Settings layer predictably, and a deny anywhere wins

Settings resolve managed first, then command-line flags, then `.claude/settings.local.json`, then `.claude/settings.json`, then `~/.claude/settings.json`; list keys such as `permissions.allow` merge across files, rules evaluate deny, then ask, then allow, and **a deny at any level beats an allow anywhere** ([Settings](https://code.claude.com/docs/en/settings); [Permissions](https://code.claude.com/docs/en/permissions)). Two placement rules follow. `defaultMode: "auto"` or `"bypassPermissions"` is ignored in project and local files, and `autoMode` tuning is read only from user, managed or `--settings` scope ([Permission modes](https://code.claude.com/docs/en/permission-modes); [Configure auto mode](https://code.claude.com/docs/en/auto-mode-config)), so personal safety defaults live in `~/.claude/settings.json` on each machine while committed project files carry allow, ask and deny rules plus hooks, and personal approvals land in the gitignored `.claude/settings.local.json` ([Settings](https://code.claude.com/docs/en/settings)). The `$schema` URL, `/status` (which shows loaded sources) and `claude doctor` (which lists rejected entries) catch typos ([Settings](https://code.claude.com/docs/en/settings)), and `/fewer-permission-prompts` mines past transcripts for a read-only allowlist instead of broad wildcards ([Commands](https://code.claude.com/docs/en/commands)).

Auto mode has been the starting mode for interactive terminal and VS Code sessions since v2.1.283, and it is the right default, but its numbers define its limits: Anthropic measured a 0.4 percent false-positive rate on real traffic, a **17 percent miss rate on 52 real overeager actions** and 5.7 percent on 1,000 synthetic exfiltration attempts, against a manual baseline in which users approved 93 percent of prompts anyway ([Anthropic auto mode post](https://www.anthropic.com/engineering/claude-code-auto-mode)). By default it blocks `curl | bash`, force pushes, `git reset --hard`, `terraform destroy` and merges of unapproved pull requests, yet it allows reading `.env` and sending credentials to their matching API ([Permission modes](https://code.claude.com/docs/en/permission-modes)). Two documented controls tighten it: `permissions.ask` rules (for example on `git push` and `gh pr merge`) create human checkpoints the classifier cannot override, and `permissions.deny` covers actions that must never run, whereas a boundary stated in chat ("don't push") can vanish at compaction ([Configure auto mode](https://code.claude.com/docs/en/auto-mode-config)). Bash rules match the command Claude usually writes, not the program: `Bash(git push *)` does not catch `git -C . push`, and `Bash(curl *)` does not catch `sh -c 'curl ...'` ([Permissions](https://code.claude.com/docs/en/permissions)).

Hooks fill the deterministic gaps and cost no context unless they print ([Extend Claude Code](https://code.claude.com/docs/en/features-overview)). The most consistently praised are a PostToolUse formatter after Edit and Write, so formatting never fails CI ([howborisusesclaudecode.com](https://howborisusesclaudecode.com)); a PreToolUse gate on `git commit` that requires a fresh passing-test marker, which forces a test-and-fix loop ([sshh.io](https://blog.sshh.io/p/how-i-use-every-claude-code-feature)); a Stop hook that runs the fast check and blocks with exit code 2, checking `stop_hook_active` because Claude Code overrides a Stop hook after eight consecutive blocks ([Hooks guide](https://code.claude.com/docs/en/hooks-guide)); and a PreToolUse hook that trims test output to failures ([Manage costs](https://code.claude.com/docs/en/costs)). Blocking hooks on Edit or Write in the middle of a plan confuse the agent and are best avoided ([sshh.io](https://blog.sshh.io/p/how-i-use-every-claude-code-feature)). None of this is a boundary: Trail of Bits states that hooks are not a security boundary ([Trail of Bits](https://github.com/trailofbits/claude-code-config)), and the WSL2 home-directory wipe slipped past auto mode because the destructive command sat inside a script and the permission check saw only `bash <script>` ([issue #88462](https://claudeissues.com/issue/88462-data-loss-claude-code-ran-rm-rf-on-home-in-auto-mode-destructive-code-hidden-ins)).

### Native Windows has no sandbox, so the desktop stays supervised

Anthropic supports native Windows, WSL2 and remote Linux, but the built-in sandbox exists only on macOS, Linux and WSL2; on native Windows, **Claude Code runs commands unsandboxed** ([Sandboxing](https://code.claude.com/docs/en/sandboxing); [Setup](https://code.claude.com/docs/en/setup)). The incident record makes that concrete. Between September 7 and October 3, 2026, four open user reports described Windows wipes, most of them through Git Bash and MSYS path handling: a subagent's `rm -rf "\\"` that MSYS path translation resolved to the C: root and that kept deleting for minutes after the stop reported success, a `cygpath` expansion that cost about 600 GB, a PowerShell-to-bash call whose empty variables became `rm -rf \` and that auto mode reportedly approved, and a delete of the profile's 8.3 short-name alias that removed about 116 GB including `.ssh`; two of the reporters recovered through Volume Shadow Copies ([Vibe Graveyard](https://vibegraveyard.ai/story/claude-code-windows-path-alias-recursive-deletions/)). Claude Code's own stale-worktree cleanup once followed NTFS junctions through about 800 GB before a fix in v2.1.205 ([Vibe Graveyard](https://vibegraveyard.ai/story/claude-code-windows-path-alias-recursive-deletions/)). The desktop therefore keeps supervised sessions and the work that needs Windows toolchains or the game itself, with File History or restore points on, bypass mode disabled from user settings ([Permission modes](https://code.claude.com/docs/en/permission-modes)), and nothing left running unwatched. WSL2 would bring the sandbox to the desktop for Linux-toolchain repos kept on the distro's own filesystem ([Desktop in WSL](https://code.claude.com/docs/en/desktop-wsl)), but with the dev VM available it adds a third environment for little gain.

Windows also carries configuration traps that macOS-centric guides omit. Permission paths are normalized to POSIX form, so a filesystem-wide `.env` rule is written `Read(//**/.env)`; a scoped `Bash` deny rule silently turns off the PowerShell tool unless a matching `PowerShell(...)` rule or `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` is present, and hooks that inspect commands should match `Bash|PowerShell` ([Permissions](https://code.claude.com/docs/en/permissions); [Tools reference](https://code.claude.com/docs/en/tools-reference)). Hooks need Git Bash, the `"shell": "powershell"` option or the exec form, and any profile output corrupts their JSON ([Tools reference](https://code.claude.com/docs/en/tools-reference); [Hooks guide](https://code.claude.com/docs/en/hooks-guide)), and the security page warns against WebDAV and `\\*` paths, which can trigger network requests outside the permission system ([Security](https://code.claude.com/docs/en/security)). The developer's own vault adds four more: Git Bash heredocs corrupted regex and escape sequences in generated code across two agents, deep paths broke pip and uv installs, the Microsoft Store Python cannot start uv-managed interpreters, and CRLF leaks into generated files without `* text=auto eol=lf` in `.gitattributes` ([heredoc note](memory://vault/patterns/write-generated-multi-line-code-with-a-file-not-a-git-bash-heredoc); [path-length note](memory://vault/patterns/windows-path-length-breaks-python-installs-in-deep-folders); [Store Python note](memory://vault/patterns/microsoft-store-python-cant-start-uv-managed-pythons); [CRLF note](memory://vault/patterns/generated-files-inherit-crlf-from-git-autocrlf-checkouts)). A Windows user settings file that encodes these choices:

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "autoUpdatesChannel": "stable",
  "permissions": {
    "defaultMode": "auto",
    "disableBypassPermissionsMode": "disable",
    "deny": [
      "Read(//**/.env)", "Read(//**/.env.*)", "Read(//**/secrets/**)",
      "Read(~/.ssh/**)", "Read(~/.aws/**)",
      "Read(~/.git-credentials)", "Read(~/.docker/config.json)"
    ],
    "ask": [
      "Bash(git push *)", "PowerShell(git push *)",
      "Bash(gh pr merge *)", "PowerShell(gh pr merge *)",
      "Bash(rm -rf *)", "PowerShell(Remove-Item *)"
    ]
  },
  "statusLine": { "type": "command", "command": "<script that prints model, context % and five-hour and weekly %>" }
}
```

The deny list is a starting point; it should grow to cover wherever each tool on the machine actually keeps its credentials, since Windows locations differ from the Unix paths most published lists assume. The `ask` entries on recursive deletes are a tripwire for the simplest form of the reported wipes, not a boundary, since string matching misses commands hidden in scripts; the backstop is backups plus keeping long runs off this machine. One more Windows-and-everywhere rule: never leave `ANTHROPIC_API_KEY` in the environment of a subscription machine, because Claude Code then bills the API, and one Max subscriber's cron jobs ran up about $1,800 in two days that way ([issue #37686](https://claudeissues.com/issue/37686-claude-p-suggested-to-max-subscriber-caused-unintended-api-billing-1-800-in-two)); `/status` shows which credential is live.

### On the VM, the sandbox plus the VM boundary makes autonomy reasonable

On Linux the sandbox uses bubblewrap for the filesystem and socat for a network proxy; it is **off by default and fails open** unless `failIfUnavailable` is set, and on Ubuntu 24.04 and later AppArmor's restriction on unprivileged user namespaces can block it until `/usr/bin/bwrap` gets a profile, which `/sandbox` now reports ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). By default sandboxed commands can write only to the working directory and temp, can read most of the machine including `~/.ssh` unless denied, and reach the network only through a proxy whose allowlist starts empty; Anthropic's internal measurement credited the sandbox with cutting permission prompts 84 percent ([Sandboxing](https://code.claude.com/docs/en/sandboxing); [Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing)). Its limits shape the rest of the setup. Hooks, MCP servers, the status line and typed `!` commands run outside it; file tools are governed by permission rules rather than by the sandbox; `docker` does not work inside it; plain `ssh` ignores the proxy and fails even for allowed hosts; and the proxy does not inspect TLS, so a broad allow such as `github.com` doubles as an exfiltration path ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). Anthropic's selection guide adds that a Bash-only sandbox is not sufficient for fully unattended runs, and that `--dangerously-skip-permissions` belongs only inside a container, a VM or the sandbox runtime, as a non-root user, ideally without internet access ([Sandbox environments](https://code.claude.com/docs/en/sandbox-environments); [Permission modes](https://code.claude.com/docs/en/permission-modes)).

Docker is the main tension on this VM. Membership in the `docker` group is root-equivalent ([Docker post-install](https://docs.docker.com/engine/install/linux-postinstall/)), the sandbox cannot run `docker`, and listing `docker compose *` in `excludedCommands` runs it with full access ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). The cleanest arrangement runs Claude Code as a dedicated unprivileged user outside the `docker` group, with Compose run by the developer or by rootless Docker for that user; excluding `docker compose *` is a knowing trade, not a default. For bypass-permission runs, Anthropic's reference devcontainer adds an egress firewall and runs as non-root, but Anthropic warns that it still cannot stop a malicious project from exfiltrating anything inside the container, including the Claude credentials in `~/.claude` ([Dev containers](https://code.claude.com/docs/en/devcontainer)). Docker's microVM Sandboxes need nested KVM, which on Proxmox means `--cpu host` and a host module option ([Docker Sandboxes](https://docs.docker.com/ai/sandboxes/install.md); [Proxmox nested virtualization](https://pve.proxmox.com/wiki/Nested_Virtualization)), plus a second kernel inside 8 GB, a poor fit here. A VM user settings file assembled from documented keys:

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "autoUpdatesChannel": "stable",
  "permissions": {
    "defaultMode": "auto",
    "deny": ["Read(//**/.env)", "Read(//**/.env.*)", "Read(~/.ssh/**)", "Read(~/.aws/**)"],
    "ask": ["Bash(git push *)"]
  },
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "filesystem": { "denyRead": ["~/.ssh", "~/.aws", "~/.gnupg"] },
    "network": {
      "allowedDomains": ["github.com", "registry.npmjs.org", "pypi.org", "files.pythonhosted.org"],
      "strictAllowlist": true
    }
  },
  "env": {
    "CLAUDE_CODE_TOOL_MEMORY_LIMIT": "2G",
    "CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS": "3"
  },
  "hooks": {
    "Notification": [{
      "matcher": "permission_prompt|idle_prompt|agent_needs_input|agent_completed",
      "hooks": [{ "type": "command", "command": "~/.claude/hooks/push.sh", "async": true }]
    }],
    "StopFailure": [{
      "hooks": [{ "type": "command", "command": "~/.claude/hooks/push.sh failure", "async": true }]
    }]
  }
}
```

The key names come from the sandboxing, permissions, hooks and environment-variable documentation rather than the full settings reference, so confirm them with `claude doctor` and `/hooks` before relying on them. `allowUnsandboxedCommands: false` stops a failed command from being retried outside the sandbox, and `strictAllowlist` denies unlisted hosts instead of prompting, which is what an unattended run needs ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). Because `ssh` ignores the proxy, git on this VM works best over HTTPS with a fine-grained token scoped to the repositories on the box; the documented stronger option is `sandbox.credentials` masking, in which the proxy substitutes the real token only for allowed hosts (it requires TLS termination and is honored only from user, managed or `--settings` scope), and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` strips credentials from subprocess environments ([Sandboxing](https://code.claude.com/docs/en/sandboxing)). Hosts that other tools need, such as the GitHub API for `gh`, go into `allowedDomains` deliberately, one at a time.

### Repos, skills, MCP servers and mods are code you run

Opening a repository can execute it. Check Point showed that project settings could start MCP servers and run commands before the trust dialog could be read, and that a repo-set `ANTHROPIC_BASE_URL` could send the API key to an attacker; all were patched ([Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)). Project allow rules now wait for trust, but project hooks, the `env` block and helper commands still run when only a parent folder is trusted and in every `claude -p` run, so untrusted repos get `--bare`, `--setting-sources user` or `disableAllHooks`, and their `.claude/`, `.mcp.json` and `.vscode/` folders get read before the folder is trusted ([Permissions](https://code.claude.com/docs/en/permissions)). Downloaded mod sources and DLLs fall under this rule too, which is one more reason to open them on the VM first. Supply-chain attacks are documented rather than hypothetical: postmark-mcp quietly BCC'd every email to an attacker from version 1.0.16 ([Koi](https://koi.ai/blog/postmark-mcp-npm-malicious-backdoor-email-theft)), Anthropic says it does not security-audit MCP servers ([Security](https://code.claude.com/docs/en/security)), and Trail of Bits sets `enableAllProjectMcpServers: false` because `.mcp.json` lives in git ([Trail of Bits](https://github.com/trailofbits/claude-code-config)). The organizing frame is Simon Willison's lethal trifecta of private data, untrusted content and an outbound channel ([Willison](https://simonwillison.net/2025/Oct/22/living-dangerously-with-claude/)); a session that reads the vault, browses the web and can push or fetch arbitrary URLs has all three.

Two operational habits finish the baseline. Update promptly, because the 2025 and 2026 CVEs were fixed in point releases and Claude Code shipped 11 versions in the 10 days before October 23 ([Changelog](https://code.claude.com/docs/en/changelog)); the `stable` channel trails `latest` by about a week to skip regressions ([Setup](https://code.claude.com/docs/en/setup)). And keep infrastructure destruction out of the agent's reach entirely: a Claude Code session working from stale Terraform state destroyed a production VPC, database and its snapshots ([Grigorev](https://alexeyondata.substack.com/p/how-i-dropped-our-production-database)), and when agents merged a pull request to main despite objections in chat and its draft status, the lesson drawn was to make the rule mechanical with branch protection, required checks and tokens that cannot merge ([blog.fsck.com](https://blog.fsck.com/2026/10/05/today-at-work/)).

## Verification beats planning ceremony as the workflow's main lever

Anthropic's first best practice is to give Claude a way to verify its own work (a test, a build exit code, a linter, a fixture diff, a screenshot), because without one "looking done" is the only stopping signal ([Best practices](https://code.claude.com/docs/en/best-practices)); Boris Cherny estimates that verification doubles or triples quality ([howborisusesclaudecode.com](https://howborisusesclaudecode.com)). The docs rank the gates by strength: an instruction in the prompt, a `/goal` condition checked by a small model after every turn, a deterministic Stop hook, and a verification subagent or workflow, always asking for evidence rather than assertions ([Best practices](https://code.claude.com/docs/en/best-practices)). `/goal` judges only what Claude has surfaced in the conversation and runs no commands itself, so its condition should demand pasted test output and a turn bound such as "or stop after 20 turns" ([Goal](https://code.claude.com/docs/en/goal)), while a Stop hook that actually runs the fast check is the gate an agent cannot talk its way past. Quality gates also protect the speed gain itself: in a difference-in-differences study of 806 repositories that adopted Cursor, a two-month burst of added code faded while static-analysis warnings rose about 30 percent and complexity about 42 percent, and higher complexity predicted later slowdowns ([arXiv 2511.04427](https://arxiv.org/html/2511.04427v3)).

### Planning scales with the size of the diff

Anthropic's four-phase loop (explore in plan mode, plan, implement, commit) comes with its own escape hatch: "If you could describe the diff in one sentence, skip the plan" ([Best practices](https://code.claude.com/docs/en/best-practices)). The case for planning larger work is indirect but consistent. Specification problems were the largest class of multi-agent failures (41.77 percent) in Berkeley's MAST taxonomy ([arXiv 2503.13657](https://arxiv.org/html/2503.13657v2)), a strong-model advisor consulted at decision points lifted a cheaper executor 2.7 points while cutting cost 11.9 percent in Anthropic's vendor test ([Claude blog](https://claude.com/blog/the-advisor-strategy)), and no controlled study of plan mode itself exists. In practice the scale has three steps. Small fixes go straight to implementation behind a failing test. Multi-file changes get a plan file in the repo (approach, file paths, trade-offs, a checklist) that the developer edits inline before saying "implement", as in Boris Tane's research-then-plan loop ([boristane.com](https://boristane.com/blog/how-i-use-claude-code/)), and that survives compaction the way the plan-mode plan is re-injected ([Context window](https://code.claude.com/docs/en/context-window)). New features and projects start with Claude interviewing the developer through `AskUserQuestion` into a `SPEC.md` that names files and interfaces, states what is out of scope and ends with an end-to-end check, after which a fresh session executes it ([Best practices](https://code.claude.com/docs/en/best-practices)). Heavy frameworks overshoot small work: Spec Kit produced eight Markdown files for one spec and felt like overkill for a three-to-five-point feature in Birgitta Böckeler's trial ([martinfowler.com](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). At the other end, the developer's spec-driven "medium track" built a complete browser roguelite (about 28,400 lines and 442 tests) in 3 hours 23 minutes for 8 points of a Max weekly limit ([build note](memory://vault/findings/a-full-autonomous-game-build-took-about-3.5-hours-and-8-percent-of-a-max-weekly-limit)), so a real spec is affordable once work is big enough to need one.

### Human-approved tests are the oracle; agent-written tests are not

The strongest quantitative result in the evidence base concerns oracles: given correct human-written tests, a test-driven agentic workflow **resolved 88.8 percent of SWE-bench Lite and 94.3 percent of SWE-bench Verified** ([TDFlow](https://preview.aclanthology.org/ingest-eacl/2026.eacl-long.70)). Agent-written tests are a different matter: across six models, prompting agents to write or skip tests moved resolution by 0 to 2.6 points while shifting input tokens by up to 49 percent ([arXiv 2602.07900](https://arxiv.org/html/2602.07900v1)). The value of test-first work therefore lies in the human-checked intent the tests encode. Simon Willison's prompts capture the habit: say "red/green TDD" so the agent writes tests, watches them fail and implements until they pass ([Willison](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/)), and open sessions on existing projects with "first run the tests" ([Willison](https://simonwillison.net/guides/agentic-engineering-patterns/first-run-the-tests/)). The developer reviews the test diff before implementation starts, because agents game tests under pressure: ImpossibleBench measured Claude Opus 4.1 taking spec-violating shortcuts in 50 percent of tasks whose tests conflicted with the spec, read-only test files stopped test editing (though not every other trick) and restored legitimate performance, and LLM monitors caught only 42 to 65 percent of cheating on SWE-bench-style tasks ([ImpossibleBench](https://arxiv.org/html/2510.20270)). A deny rule on `Edit` for the acceptance-test directory during implementation is the cheap version of read-only tests, since permission rules accept path patterns ([Permissions](https://code.claude.com/docs/en/permissions)); on the VM, a sandbox `denyWrite` path also covers edits made through the shell ([Sandboxing](https://code.claude.com/docs/en/sandboxing)).

Green suites are necessary, not sufficient. The developer's vault records a suite that passed while shipping three defects found only by a live pass through the real tools, a game feature that passed a debug viewer and did nothing in a real battle, and phone-layout bugs that reviewers caught by looking at 667 by 375 screenshots rather than through assertions ([live-pass note](memory://vault/patterns/run-one-live-write-through-the-real-tools-before-the-gate-review); [phone-screen note](memory://vault/patterns/on-a-short-phone-screen-put-rules-behind-a-button-and-test-at-667-by-375)); no automated reviewer could judge game audio at all ([audio note](memory://vault/findings/automated-reviewers-cannot-judge-game-audio)). Willison's "agentic manual testing" formalizes the remedy: curl the dev server, drive a browser and inspect screenshots, record real command output in a log the agent cannot invent, and turn every bug found into a red/green test ([Willison](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/)). On Windows, the Claude in Chrome extension and the Desktop Browser pane, with preview servers defined in `.claude/launch.json`, give Claude eyes ([Desktop](https://code.claude.com/docs/en/desktop)); in Desktop SSH sessions the Browser pane cannot open the remote app, so the port gets forwarded with `ssh -N -L`, or headless Playwright runs on the VM with the sandbox exception Chromium needs ([Desktop](https://code.claude.com/docs/en/desktop); [Sandboxing](https://code.claude.com/docs/en/sandboxing)). The loop must also stay fast. The developer cut a Playwright suite from about 52 to 32 minutes with debug fast-forward hooks and merged duplicate flows, and found that two or three full suites at once pushed the desktop to about 90 percent CPU and crashed browsers ([suite-speed note](memory://vault/patterns/cut-a-long-playwright-suite-by-fast-forwarding-real-time-parts-and-merging-duplicate-flows); [crash note](memory://vault/findings/several-full-playwright-suites-at-once-on-one-pc-crash-browsers)), so the full suite runs once per gate, alone.

### Review in a fresh context, then triage the findings

A reviewer that did not write the code catches more, and a stronger one catches more still. Anthropic recommends a second session or subagent that sees only the diff and the criteria, because a fresh context means "Claude won't be biased toward code it just wrote" ([Best practices](https://code.claude.com/docs/en/best-practices)); older controlled work found self-repair bottlenecked by feedback quality, with stronger-model and human feedback far more effective ([arXiv 2306.09896](https://arxiv.org/abs/2306.09896v4)), and LLM judges favor their own generations ([arXiv 2404.13076](https://arxiv.org/pdf/2404.13076)). Review output still needs triage: developers rejected 56.3 percent of 31,073 CodeRabbit comments, mostly as false positives or out of scope ([arXiv 2607.03316](https://arxiv.org/abs/2607.03316)), and Anthropic warns that a reviewer told to find gaps will find some in sound work, so the brief limits it to correctness and stated-requirement gaps ([Best practices](https://code.claude.com/docs/en/best-practices)). More reviewers are not better by default: Sonnet 5.5 scored 46.2 percent on FrontierCode at max effort against 52.1 percent at xhigh, because max more often ran the code-review skill across many subagents ([Anthropic](https://www.anthropic.com/claude-sonnet-5-5)). The bundled `/code-review` runs as a background subagent, and `/code-review ultra` runs a cloud fleet of reviewers at roughly $5 to $25 per review after three free runs ([Ultrareview](https://code.claude.com/docs/en/ultrareview.md)). Skipping review entirely has been tried and failed: Dex Horthy's team let models ship unreviewed code, and four months later production broke in a way the models could not diagnose, costing days to fix and three weeks to re-learn the codebase ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/context-engineering-with-dex-horthy)). The developer's own practice contributes operating rules worth keeping: review from a worktree frozen at the milestone commit, reuse the same reviewer for re-reviews but stop after two, have it write each verdict the moment that milestone finishes (a combined review lost every verdict at a usage limit), and never let an agent write its own evaluation questions, after one reworded them until its expected answer ranked first ([frozen-worktree review note](memory://vault/decisions/review-each-milestone-from-a-frozen-worktree-reuse-the-same-reviewer-and-combine-reviews-due-together); [evaluation-questions note](memory://vault/patterns/write-evaluation-questions-before-looking-at-the-results)).

### Git, worktrees and background sessions keep work reversible

Git is the real undo button. Checkpoints (`/rewind`) track only Claude's file-edit tools, not Bash changes or subagent edits, and Anthropic says they do not replace git ([Checkpointing](https://code.claude.com/docs/en/checkpointing)). Committing as soon as a step is green pays off measurably: across 16,758 agent trajectories, 60 to 69 percent of capable models' failures on two of the three scaffolds studied had already reached and edited the right functions yet still ended in a wrong patch, most often by thrashing or overwriting correct code, and an edit-commit checkpoint recovered every case in which a gold-identical patch had existed and was later destroyed ([arXiv 2603.24631](https://arxiv.org/abs/2603.24631)). When a direction goes wrong, revert and re-scope rather than patch ([boristane.com](https://boristane.com/blog/how-i-use-claude-code/)), and after two failed corrections on one issue, `/clear` and rewrite the prompt ([Best practices](https://code.claude.com/docs/en/best-practices)).

Worktrees are now built in everywhere: `claude --worktree <name>` (optionally with `--tmux`), a per-session Worktree toggle in the Desktop app, `isolation: worktree` for subagents, `.worktreeinclude` to copy gitignored files such as `.env`, and `worktree.baseRef: "head"` to branch from local HEAD ([Worktrees](https://code.claude.com/docs/en/worktrees)). They isolate files but not dependencies, ports or databases, the guard against writes into the main checkout was still receiving fixes in v2.1.309 ([Worktrees](https://code.claude.com/docs/en/worktrees); [Changelog](https://code.claude.com/docs/en/changelog)), and Desktop worktrees stay on disk until cleared. Background sessions (`claude --bg`, `/bg`, supervised from `claude agents`) survive closing the terminal, move into their own worktree before editing, commit and push their own branch but never main, and stop after about an hour idle until the next reply; each draws quota independently, and "ten agents in parallel uses quota roughly ten times as fast" ([Agent view](https://code.claude.com/docs/en/agent-view)). The Claude Code team runs three to five worktree sessions at once ([power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips)), while practitioners in a 2026 Ask HN thread settled on two or three well-scoped streams, several noting that testing and reviewing the worktrees took longer than the agents' work ([Ask HN](https://hn.nuxt.dev/item/47573483)). Two or three is the right default for one reviewer. Cloud sessions (`claude --cloud`) cover GitHub repos that must progress while every home machine is off, though they read only committed project configuration, not user settings ([Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web)), and `/batch` fans a mechanical migration across 5 to 30 worktree-isolated subagents ([Run agents in parallel](https://code.claude.com/docs/en/agents)).

## Input tokens and one reviewer's attention set the limits

### Focused sessions beat long ones, even with a 1M window

Context degrades reasoning even when retrieval is perfect. Across 18 models, a focused 300-token prompt beat the full 113,000-token history on LongMemEval for every model ([Chroma](https://www.trychroma.com/research/context-rot)), input length alone cut performance 13.9 to 85 percent within advertised windows ([arXiv 2510.05381](https://arxiv.org/html/2510.05381v1)), and compression in long-horizon agents weakened the influence of recent interactions and increased repeated exploration ([arXiv 2608.06503](https://arxiv.org/abs/2608.06503)). Claude Code's native 1M-token window on current models does not change that; it moves the default auto-compaction point to about 967K tokens ([Model configuration](https://code.claude.com/docs/en/model-config)). The working rules are therefore session rules: one task per session and `/clear` between unrelated ones, `/compact <focus>` at natural breaks, `/btw` for side questions, and subagents for anything that would flood the conversation with logs or file contents ([Best practices](https://code.claude.com/docs/en/best-practices)). Durable state lives in files that a fresh session reads, because what survives compaction is limited to the system prompt and output style, project-root CLAUDE.md and unscoped rules, auto memory, the plan file, up to five recently read files and invoked skills at 5,000 tokens each, while path-scoped rules and nested CLAUDE.md files drop out until re-triggered ([Context window](https://code.claude.com/docs/en/context-window)). Practitioners start fresh at personal thresholds such as 60 percent of a 200K window ([Ashley Ha](https://ashleyhaai.substack.com/p/i-mastered-the-claude-code-workflow)), and Dex Horthy places the "dumb zone" around 300K to 400K tokens on a 1M model ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/context-engineering-with-dex-horthy)); setting `autoCompactWindow` to roughly 400K to 500K encodes that judgment, which no controlled study has tested. A status line showing `context_window.used_percentage` and the `rate_limits.five_hour` and `seven_day` percentages keeps both budgets in view ([Status line](https://code.claude.com/docs/en/statusline)).

### Opus decides, Sonnet builds, Haiku searches

On Max the default model is Opus 5.5 at medium effort ([Model configuration](https://code.claude.com/docs/en/model-config)), and Anthropic's own numbers say medium is no compromise: default-effort Opus 5.5 scored 54.6 percent on FrontierCode against 54.4 percent at max, and on Terminal-Bench 4.0 it beat Opus 5 at max effort for about a fifth of the cost ([Anthropic](https://www.anthropic.com/claude-opus-5-5)). Sonnet 5.5 scored 70.6 percent on Terminal-Bench 4.0 against Opus 5.5's 66.4 percent at xhigh effort, at half the API price, while Anthropic still calls Opus clearly stronger at open-ended work requiring sustained judgment ([Anthropic](https://www.anthropic.com/claude-sonnet-5-5)); Haiku 5.5 trails at 39.2 percent and is positioned for summaries, classification and subagent search ([Anthropic](https://www.anthropic.com/claude-haiku-5-5)). These are vendor numbers on new benchmark versions, and OpenAI's audit found material problems in 59.4 percent of the hard SWE-bench Verified tasks it checked ([OpenAI](https://openai.com/en/index/why-we-no-longer-evaluate-swe-bench-verified)), so a handful of the developer's own tasks is a better guide than a leaderboard gap of a few points. The defensible mapping is Opus 5.5 for the main session, planning, ambiguous design and review; Sonnet 5.5 pinned on implementation subagents; and Haiku 5.5 for search and summarization. The Claude Code team's own tips lean heavier, Opus with thinking for everything and xhigh effort for depth ([power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips)), which suits weeks when usage is slack, but the shipped default and the vendor evaluations support medium as the starting point, raised per task, since overthinking trajectories resolved fewer issues in an earlier SWE-bench study ([arXiv 2502.08235](https://arxiv.org/pdf/2502.08235)). Model and effort get picked at the start of a session, because each model keeps its own prompt cache and a mid-session `/model` re-reads everything uncached, and subagent requests cache for only five minutes unless `subagentPromptCacheTtl` is raised to one hour ([Prompt caching](https://code.claude.com/docs/en/prompt-caching)). The `opusplan` alias (Opus in plan mode, Sonnet for execution) packages the split for single-session work ([Model configuration](https://code.claude.com/docs/en/model-config)).

### One metered build spent 98 percent of agent tokens on input

Max has a five-hour session limit and a weekly limit shared across Claude chat, Claude Code, background and cloud sessions and every subagent, and Anthropic publishes no numbers for either ([Claude Code usage and permissions](https://support.claude.com/en/articles/11145838-claude-code-usage-and-permissions); [Agent view](https://code.claude.com/docs/en/agent-view); [Manage costs](https://code.claude.com/docs/en/costs)). The developer's one metered run is the best local calibration: the autonomous roguelite build moved the weekly meter from 4 to 12 percent, peaked the five-hour window at 62 percent (it reset mid-run), and spent 780K tokens of fresh input plus output on the Opus orchestrator against 7.28M on Sonnet lanes and critics, **98 percent of the agents' counted tokens being input** ([build note](memory://vault/findings/a-full-autonomous-game-build-took-about-3.5-hours-and-8-percent-of-a-max-weekly-limit)). Independent data agree that input drives agent cost, with up to 30-fold token variance between runs of the same task and accuracy that plateaus at intermediate spend ([arXiv 2604.22750](https://arxiv.org/abs/2604.22750)). Two consequences follow: the five-hour window, which the developer found to be the tighter limit in heavy parallel phases, is the one to watch, and always-loaded context, re-read on every turn by every agent, is the most expensive line in any setup. `/usage` attributes plan usage to skills, subagents, plugins and MCP servers and offers one-key fixes, and `autoContinueAtUsageLimit` resumes interrupted work after a reset ([Manage costs](https://code.claude.com/docs/en/costs)). Model choice alone guarantees nothing: one Max 20x user with an Opus orchestrator and Haiku-pinned subagents still burned 22 percent of a five-hour window in about 40 minutes, a report closed without a root cause ([issue #52502](https://claudeissues.com/issue/52502-bug-session-weekly-token-limits-deplete-disproportionately-fast-with-opus-orches)).

### Parallel readers win while parallel writers lose on coupled work

The best controlled study of agent architectures, Google's comparison of 180 configurations at matched token budgets, found multi-agent setups gained 80.8 percent on a decomposable finance task, lost 39 to 70 percent on sequential planning, averaged about minus 3.5 percent overall, and stopped paying once a single agent already succeeded about 45 percent of the time; independent agents amplified errors 17.2 times against 4.4 times under a central coordinator, with coordination overhead of 58 to 515 percent ([arXiv 2512.08296](https://arxiv.org/html/2512.08296v2)). Anthropic's research system shows the upside on breadth-first work, a 90.2 percent gain at roughly 15 times the tokens of chat, alongside Anthropic's own caveat that most coding tasks have fewer truly parallelizable pieces than research ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). On coding specifically, pairs of agents building possibly conflicting features succeeded about 30 percent less often than solo agents ([arXiv 2601.13295](https://arxiv.org/abs/2601.13295)), Anthropic's game-building swarms merged a falling share of their pull requests as agent count rose from 10 to 80 ([Anthropic](https://www.anthropic.com/research/multiagent-systems)), and co-active agent pull requests conflicted textually 19.8 percent of the time even when the same agent product wrote both ([arXiv 2607.04697](https://arxiv.org/abs/2607.04697)). Cognition, which once argued against multi-agent systems, now reports that read-only subagents and a clean-context coder-reviewer loop work while parallel writers make conflicting implicit decisions ([Cognition](https://cognition.com/blog/multi-agents-working)). Anthropic's 16-agent C compiler succeeded because it had a near-perfect test oracle, and it still stalled when all 16 agents hit the same kernel bug and overwrote each other's fixes ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). Orchestration tuned to one model can also break on the next: Steve Yegge said his Gas Town orchestrator effectively burned down on Opus 4.7 ([Willison](https://simonwillison.net/2026/Aug/4/steve-yegge/)).

The resulting default is one writer per module, read-only subagents for search, exploration and log digestion, a fresh-context reviewer, and two or three implementation lanes only when interfaces are frozen first and each lane owns disjoint files. Agent teams stay off: they are experimental, cost about seven times the tokens of a standard session when teammates plan, cannot resume in-process teammates, and on current models coordinate only by messages unless `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` restores the shared task list ([Agent teams](https://code.claude.com/docs/en/agent-teams); [Manage costs](https://code.claude.com/docs/en/costs); [Tools reference](https://code.claude.com/docs/en/tools-reference)). Dynamic workflows and `/batch` fit fan-outs whose results a machine can check, such as migrations and audits, and the workflow authors themselves caution that parallelism and specialization have to earn their coordination cost ([A harness for every task](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)). Every lane gets a hard bound through `maxTurns` or a turn clause in `/goal`, because the documented failure modes of long agent runs are repetition, duplicated work and premature claims of completion ([Subagents](https://code.claude.com/docs/en/sub-agents); [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

### The developer's own data favors contracts and gates over lane counts

The developer's vault holds the best evidence on how orchestration behaves for this exact workload, and it points to checkpoints rather than headcount. Contract-first phases, with throwing stubs at fixed signatures and the next phase's acceptance tests parked outside the suite, merged four and then three lanes with no conflicts ([contracts note](memory://vault/patterns/write-contracts-and-port-acceptance-tests-before-parallel-lanes)), and critics reviewing frozen worktrees found real bugs the suites missed ([frozen-worktree review note](memory://vault/decisions/review-each-milestone-from-a-frozen-worktree-reuse-the-same-reviewer-and-combine-reviews-due-together)). The costliest failure was a single Sonnet lane that ran 5.5 hours unchecked while holding the real game: of 320 listed minutes, about 280 went to 69 C++ rebuilds, repeated full environment suites and 96 probe scripts, and about 40 to the model's own reasoning ([time-box note](memory://vault/patterns/time-box-agent-lanes-and-fan-out-open-ended-debugging)), which argues for cheap one-hypothesis probes and hourly hand-backs rather than more lanes. Agent reuse has a ceiling too: one UI agent reused across five phases reached about 680K tokens of context, and the developer's own guidance became a fresh agent once context passes a few hundred thousand tokens and the work moves to a new area ([follow-on note](memory://vault/patterns/send-follow-on-steps-to-the-same-agent)). By contrast, the percentages quoted in the current orchestration rules are weak on inspection. The 39 to 70 percent sequential-task loss comes from PlanCraft, a Minecraft crafting-planning benchmark, not from coding ([arXiv 2512.08296](https://arxiv.org/html/2512.08296v2)); "twice the merge conflicts" compares pull requests from different agent products on GitHub, not orchestrated lanes in one repo ([arXiv 2607.04697](https://arxiv.org/abs/2607.04697)); the 44 to 60 percent penalty for file-by-file lanes could not be traced to any primary source; and the 60 to 80 percent saving for follow-on steps carries no recorded sample, task type or basis ([split-lanes note](memory://vault/patterns/split-agent-lanes-by-coupling-not-by-file-list); [follow-on note](memory://vault/patterns/send-follow-on-steps-to-the-same-agent)). The rules themselves remain sensible; they should be stated as judgment rather than measurement. The same applies to lanes narrating 10 to 30 board events per step, a deliberate preference for a busy live feed whose token cost the vault never measured ([milestone-events note](memory://vault/decisions/agents-post-milestone-events-so-a-live-view-shows-real-progress)); now that agent view and the Desktop sidebar show session state natively ([Agent view](https://code.claude.com/docs/en/agent-view)), the custom board is best reserved for multi-lane phases, with its event rate checked against `/usage`.

## The dev VM hosts every long, unattended or untrusted run

The machine split follows directly from where a sandbox exists and what each job needs. The Desktop app and the CLI share configuration on Windows, `/desktop` hands a CLI session to the app on x64 Windows, and Desktop's `/resume` picks up CLI sessions ([Desktop](https://code.claude.com/docs/en/desktop); [Commands](https://code.claude.com/docs/en/commands)), so the choice of surface is about the job rather than about lock-in.

| Work | Machine and surface | Permission posture | Safety net |
|---|---|---|---|
| Windows-only toolchains, mods that need the real game | Windows desktop, Desktop Code tab or CLI | Auto mode, `ask` on pushes and recursive deletes, bypass disabled | git, File History or restore points, supervision |
| Interactive work on Linux-friendly repos (FastAPI and HTMX apps, browser games, Compose stacks) | dev VM through a Desktop SSH environment | Auto mode inside the sandbox | git, sandbox, VM boundary |
| Multi-hour and overnight runs | dev VM, CLI in tmux or `claude --bg`, optional Remote Control | Auto mode in the sandbox, Stop hook or `/goal`, `maxTurns` | Snapshot first, a commit per feature, push alerts |
| Bypass-permission runs and untrusted code | dev VM inside a devcontainer | Bypass only inside the container, non-root, egress firewall | Snapshot, no credentials mounted |
| Work that must continue with every home machine off | Cloud session (`claude --cloud`) | Cloud defaults, committed project config only | Anthropic VM, a pushed branch |

### Desktop SSH for interactive work, tmux and background sessions for long runs

The Desktop app's SSH environment is the most integrated way to drive the VM. A connection takes `user@host` or an SSH config alias (a Tailscale MagicDNS name works), Desktop installs a helper and Claude Code under `~/.claude/remote/` (about 1 GB), and the helper keeps a task running if the SSH connection drops ([Desktop](https://code.claude.com/docs/en/desktop)). How the Windows build reads `~/.ssh/config` is documented only for macOS and Linux, and Windows may fall back to a built-in client without Microsoft's OpenSSH 9.4 or later, so the alias deserves a one-time test ([Desktop](https://code.claude.com/docs/en/desktop)). The limits decide what this path is for. With a Claude-account sign-in, Desktop renews the task's credentials only while it runs and stays connected, so Anthropic says not to count on overnight runs, and **on Windows a quit Desktop never rejoins the running task** ([Desktop](https://code.claude.com/docs/en/desktop)). Port forwards in the SSH config are not applied, the Browser pane cannot open the remote app, `gh` is not installed for you, "Merge when ready" is disabled, hooks and proxy settings must live in the VM's own `~/.claude/settings.json`, and systemd-logind's `KillUserProcesses=yes` or `StopIdleSessionSec` can end the task, so both are worth checking on the VM ([Desktop](https://code.claude.com/docs/en/desktop)). Desktop SSH is the interactive cockpit, not the overnight runner.

For long runs, the developer connects over SSH, starts `tmux` with the passthrough settings Anthropic documents (`allow-passthrough`, `focus-events`, `extended-keys`) ([Terminal config](https://code.claude.com/docs/en/terminal-config)), and runs the CLI or background sessions there. Remote Control turns that into a phone-steerable session: it opens no inbound ports, recommends tmux or screen on remote machines, needs a full `claude auth login` on the VM because a `claude setup-token` credential cannot establish it, and in server mode (`claude remote-control --spawn worktree --capacity 2`) serves several sessions ([Remote Control](https://code.claude.com/docs/en/remote-control)). Its optional Trusted Devices setting requires an enrolled device and a recent sign-in before anyone can view or steer a session, and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` should stay unset because it also disables Remote Control and auto-updates ([Remote Control](https://code.claude.com/docs/en/remote-control); [Env vars](https://code.claude.com/docs/en/env-vars)). Running Remote Control as a systemd service remains rough, with no non-interactive consent flag in a report closed as not planned ([issue #87413](https://claudeissues.com/issue/87413-remote-control-on-always-on-machines-three-reproducible-edges-consent-vs-service)), so tmux launched from a user unit with `loginctl enable-linger` is the steadier wrapper ([loginctl](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html)). Scripted jobs use `claude -p`, which since v2.1.302 starts in Manual mode and denies anything needing approval unless given `--permission-mode auto`, or `dontAsk` with `--allowedTools`; `--bare` skips hooks and CLAUDE.md but requires an API key, which moves billing to the API ([Headless](https://code.claude.com/docs/en/headless)). A practitioner who keeps about 40 named tmux sessions across three home machines, reached over Tailscale, found plain SSH drop-prone from a phone and mosh poor at rendering Claude Code's interface, and settled on Eternal Terminal ([alelec](https://notes.alelec.net/posts/claude-code-from-anywhere/)). Git on the VM needs its own narrow credential because Desktop does not forward the SSH agent, and Anthropic's advice is repository-scoped or short-lived tokens rather than long-lived keys ([Desktop](https://code.claude.com/docs/en/desktop); [Dev containers](https://code.claude.com/docs/en/devcontainer)).

An overnight run assembled from documented parts looks like this: a committed spec plus a JSON feature list whose only editable field is `passes` (Anthropic chose JSON because models edit it less freely than Markdown) ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)), a dedicated worktree, a background session or `claude -p` in auto mode inside the sandbox, a Stop hook or `/goal` tied to the tests, `--max-turns` or `maxTurns` as a hard cap, a commit per feature, a Proxmox snapshot beforehand and a push alert when it needs attention. In the morning `claude agents` shows what finished, and a fresh-context reviewer reads the diff before anything merges ([Agent view](https://code.claude.com/docs/en/agent-view); [Best practices](https://code.claude.com/docs/en/best-practices)).

### Eight gigabytes holds two or three sessions

Anthropic gives a 4 GB minimum and a warning when a session's heap passes 2.5 GB, but no per-session figure ([Setup](https://code.claude.com/docs/en/setup); [Troubleshooting](https://code.claude.com/docs/en/troubleshooting)). One detailed bug report measured idle sessions at about 110 to 180 MB each, a commenter measured about 560 MB per session process, and one never-invoked plugin's 11 MCP sidecar trees took 1.6 GB ([issue #88524](https://claudeissues.com/issue/88524-memory-scales-linearly-with-open-sessions-on-macos-idle-chats-never-release-ram)). After 1.5 to 2 GB for the OS and daemons and memory-capped Compose services, the VM leaves room for about two interactive sessions plus one background job, an extrapolation that `ps -o rss` on the real workload should confirm. The documented controls are simple: `CLAUDE_CODE_TOOL_MEMORY_LIMIT` caps a session's commands through a cgroup so a runaway build dies instead of the VM ([Tools reference](https://code.claude.com/docs/en/tools-reference)), `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` drops from its default of 20, Remote Control's `--capacity` drops from 32 ([Remote Control](https://code.claude.com/docs/en/remote-control)), and background sessions release memory after about an hour idle ([Agent view](https://code.claude.com/docs/en/agent-view)). Below Claude Code, compressed zram swap ([kernel docs](https://docs.kernel.org/admin-guide/blockdev/zram.html)) and earlyoom configured to spare `sshd`, `tailscaled` and `dockerd` ([earlyoom](https://github.com/rfjakob/earlyoom)) keep a memory spike from taking down the box, and every Compose service gets a hard memory limit ([Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)). Fan-outs wider than three lanes belong on the desktop under supervision or in cloud sessions, not on this VM.

### Snapshots, tailnet ACLs and hook-based alerts close the loop

A Proxmox snapshot (`qm snapshot <vmid> <name>`) before any risky or bypass run is cheap insurance, provided its nature is understood: rollback destroys the VM's current state and disks, including Docker volumes and concurrent work, snapshots live on the same storage and are not backups, and on an 8 GB guest `--vmstate` adds a RAM-sized state volume to each snapshot ([pve-devel docs patch](https://lore.proxmox.com/all/20260714142629.277917-5-f.ebner@proxmox.com/); [Proxmox storage](https://pve.proxmox.com/wiki/Storage)). Anything irreplaceable lives in git remotes or real backups, and rollback and snapshot deletion stay explicit human decisions. On the network side, a new tailnet allows everything until a policy exists, so the VM gets a tag and ACLs that admit only the developer's own devices to SSH and app ports ([Tailscale ACLs](https://tailscale.com/kb/1018/acls)); Funnel, which publishes services to the public internet, stays off ([Tailscale Funnel](https://tailscale.com/kb/1223/funnel)); and Docker-published ports bypass ufw, so they bind to loopback or the tailnet address ([Docker packet filtering](https://docs.docker.com/engine/network/packet-filtering-firewalls/)). Tailscale SSH's `check` mode re-authenticates through the browser on a schedule ([Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)), which sits poorly with Desktop's need to reconnect without a prompt, so plain OpenSSH keys over the tailnet are the simpler path for Desktop. The Proxmox firewall cannot filter by domain ([Proxmox firewall](https://pve.proxmox.com/pve-docs/chapter-pve-firewall.html)), so per-domain egress comes from the sandbox's `allowedDomains` or a container firewall.

A headless VM has no desktop notification daemon, so the `notify-send` examples in the docs do nothing there ([Hooks guide](https://code.claude.com/docs/en/hooks-guide)). Notification hooks matching `permission_prompt`, `idle_prompt`, `agent_needs_input` and `agent_completed`, plus `StopFailure` for rate limits and API errors, can `curl` a push service instead; hooks run outside the sandbox, so the push host needs no allowlist entry ([Hooks guide](https://code.claude.com/docs/en/hooks-guide); [Sandboxing](https://code.claude.com/docs/en/sandboxing)). A self-hosted ntfy behind Tailscale should deny anonymous access and use tokens, and on an iPhone it still needs ntfy.sh as an upstream relay, which sees only message IDs, for prompt delivery ([ntfy config](https://docs.ntfy.sh/config/)). When Remote Control is on, its own mobile push covers "done" and "needs a decision" without any of this ([Remote Control](https://code.claude.com/docs/en/remote-control)).

## The vault works as curated, git-synced memory with gated writes

### Each memory layer has one job

Claude Code's built-in memory is deliberately local. Auto memory writes per-repository notes under `~/.claude/projects/<project>/memory/`, loads the first 200 lines or 25 KB of `MEMORY.md` each session, is shared across a repo's worktrees and is "not shared across machines" ([Memory](https://code.claude.com/docs/en/memory)), so the Windows desktop and the VM accumulate separate memories of the same project. basic-memory's documentation positions its store as the deeper layer beside built-in memory and tells assistants to search before answering questions about prior work or decisions ([Versus built-in memory](https://docs.basicmemory.com/raw/concepts/vs-built-in-memory.md); [AI assistant guide](https://docs.basicmemory.com/raw/reference/ai-assistant-guide.md)). The clean division gives CLAUDE.md the always-true instructions, auto memory the cheap per-repo corrections (anything reusable gets promoted), repo docs the specs and decision records that must travel and be reviewed with the code, and the vault the cross-project knowledge: decisions with rationale and rejected options, research reports, stack evaluations, patterns and pitfalls. The evidence on what such knowledge is worth is indirect. Curated, human-written procedural knowledge helps while self-generated knowledge does not ([SkillsBench](https://hyper.ai/en/papers/2602.12670)), no study measures cross-project vaults for coding agents, and the developer's 111-note vault records retrieval trials but no measure of whether a recalled note changed later work ([vault README](memory://vault/readme)). Curation, not volume, is the asset, which is why the routing rule in the global file names the moments to search and to write rather than leaving recall to chance.

### Git carries the Markdown while each machine rebuilds its own index

basic-memory is at v0.24.1 (October 23, 2026), a local, file-first MCP server whose SQLite index is a rebuildable secondary copy of plain Markdown ([GitHub releases](https://github.com/basicmachines-co/basic-memory/releases); [Technical information](https://docs.basicmemory.com/raw/reference/technical-information.md)). Version 0.24 made hybrid keyword and semantic search always on and added read-only `cat`, `grep`, `ls`, `find`, `tail` and `man` tools, checksum-guarded writes that fail with `NOTE_REVISION_CONFLICT` rather than clobbering a newer copy, temporal observations and schema tools ([v0.24](https://docs.basicmemory.com/raw/whats-new/v0-24.md)). Install 0.24.1 or later, since 0.24.0 can fail on a fresh install, and back up `memory.db` before the automatic migrations ([upgrade guide](https://docs.basicmemory.com/raw/whats-new/v0-24-upgrade.md)). Integrity bugs were still open in late October, notably duplicate search rows when several MCP server instances and the file watcher write one database, which `reindex --full` does not clear ([issue #1771](https://github.com/basicmachines-co/basic-memory/issues/1771)). Because the Markdown is the source of truth, `bm reset --reindex` rebuilds the index from the files ([Troubleshooting](https://docs.basicmemory.com/raw/reference/troubleshooting.md)), and the developer measured a lossless rebuild in about 7.5 seconds at 15 notes ([index note](memory://vault/findings/basic-memory-index-lives-outside-the-vault-and-rebuilds-losslessly)), so a corrupted index costs minutes, not data.

basic-memory documents no multi-machine pattern beyond "Git, Syncthing, etc." ([README](https://github.com/basicmachines-co/basic-memory)), so the lowest-risk design follows from its architecture: the vault is one git repo cloned on Windows and on the VM, each machine runs its own basic-memory with its own `~/.basic-memory`, and the index is never synced. The basic-memory project name must match on both machines, because permalinks carry the project prefix and v0.24 writes them into frontmatter, and one machine should commit the first v0.24 scan before the other scans, because indexing rewrites frontmatter on notes that lack it ([Configuration](https://docs.basicmemory.com/raw/reference/configuration.md); [upgrade guide](https://docs.basicmemory.com/raw/whats-new/v0-24-upgrade.md)); the developer already saw it add permalinks, restyle tags and add frontmatter to the README ([frontmatter note](memory://vault/findings/basic-memory-adds-frontmatter-to-every-markdown-file-it-indexes)). Cross-platform sync tools and case-only renames are the documented source of duplicate entities ([Troubleshooting](https://docs.basicmemory.com/raw/reference/troubleshooting.md)), which argues for lowercase kebab-case ASCII filenames, `* text=auto eol=lf` in `.gitattributes` ([Obsidian forum](https://forum.obsidian.md/t/solving-git-sync-issues-caused-by-different-system-line-endings/92253)), gitignored `.obsidian/workspace*.json` files, and a single sync transport per working tree. Hooks handle the automation: a `SessionStart` command hook runs a fast-forward-only pull and reports a failure as one factual line of `additionalContext` (capped at 10,000 characters), and an asynchronous `SessionEnd` hook commits and pushes with its timeout raised toward the 60-second maximum ([Hooks reference](https://code.claude.com/docs/en/hooks)); the developer's existing hook that commits and pushes after every note write needs a pull before each push once two machines write. Parallel sessions on one machine each start their own stdio server, which is the multi-writer case behind issue #1771; if that becomes routine, a reasonable inference from the bug report (not a documented pattern) is to run one `bm mcp --transport streamable-http` per machine, bound to loopback and added with `claude mcp add --transport http`, which gives a single writer at the price of a server with no authentication that must never be reachable beyond loopback or the tailnet ([CLI reference](https://docs.basicmemory.com/raw/reference/cli-reference.md); [Docker docs](https://docs.basicmemory.com/raw/reference/docker.md); [MCP](https://code.claude.com/docs/en/mcp)). Obsidian's REST and CLI routes need the desktop app running, which rules them out on a headless VM ([mcp.directory](https://mcp.directory/blog/obsidian-mcp-complete-guide-2026); [Obsidian CLI](https://obsidian.md/help/cli)).

### Write notes that both grep and embeddings can find

The retrieval evidence does not crown one method. A May 2026 preprint found grep generally beating vector retrieval on a LongMemEval sample across Claude Code, Codex and Gemini CLI, with results strongly dependent on the harness ([arXiv 2605.15184](https://arxiv.org/abs/2605.15184)); Anthropic's contextual-retrieval tests cut top-20 retrieval failures 49 percent by adding BM25 to embeddings, because keyword search catches exact identifiers ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)); and Letta's file-tools agent beat a dedicated memory library mainly through how well the agent used its tools ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory)). The developer's trials match the mixed picture: at 28 notes, hybrid search put the right note first for 3 of 5 untuned questions and in the top three for 4 of 5, in an earlier 15-note spike vector-only search missed a reworded question below its 0.55 similarity cutoff, and hub notes outranked real notes until searches filtered by note type ([hybrid-search decision](memory://vault/decisions/use-hybrid-search-with-a-content-type-filter); [hub note](memory://vault/findings/hub-and-readme-notes-outrank-real-notes-in-small-basic-memory-vaults)). Hybrid search with a type filter and a scan of the top three to five titles remains the right default, and notes should be written so that both methods land on them: a descriptive kebab-case title, a small consistent frontmatter set (`type`, `status`, `tags`, `project`, `created`, `updated`), a two-to-three sentence summary first, headed sections (basic-memory chunks prose at headers and indexes each `- [category]` observation line separately) and explicit wikilinks ([Semantic search](https://docs.basicmemory.com/raw/concepts/semantic-search.md); [Knowledge format](https://docs.basicmemory.com/raw/concepts/knowledge-format.md)). `bm wiki rebuild` generates per-folder `index.md` and `log.md` files without overwriting hand-written ones, the same catalog-plus-log structure that Karpathy's LLM-wiki pattern recommends ([CLI reference](https://docs.basicmemory.com/raw/reference/cli-reference.md); [Karpathy](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)).

Staleness calls for explicit status rather than deletion. A changed decision gets a new note with a `supersedes` relation while the old one flips to `status: superseded`, absolute dates replace relative ones, and perishable facts (versions, prices, tool behavior) carry a review date. Because metadata filters have no `$ne`, searches filter on a positive set such as `status` in `active` and `draft` ([Metadata search](https://docs.basicmemory.com/raw/concepts/metadata-search.md)). The developer's vault shows why status hygiene matters: exactly one note is marked superseded ([code-drawn art note](memory://vault/decisions/draw-all-game-art-in-code-from-one-written-style-guide-and-bundle-the-font)), while notes that later work qualified in their text, such as the agent-reuse pattern, still read as unconditionally current to a status filter ([follow-on note](memory://vault/patterns/send-follow-on-steps-to-the-same-agent)). A periodic lint with `bm orphans`, `bm schema validate` and `bm schema diff` catches drift ([CLI reference](https://docs.basicmemory.com/raw/reference/cli-reference.md); [Schema system](https://docs.basicmemory.com/raw/concepts/schema-system.md)); no source gives an evidence-based cadence, so monthly is a starting guess.

### Memory files are an injection surface, so agent writes pass a gate

A vault that every session reads is a durable control channel for anyone who gets text into it. A July 2026 study of Claude Code and Codex found that tricking an agent into overwriting its own memory files from untrusted content is hard, but instructions already planted in memory files successfully attacked both current and future sessions ([Bad Memory](https://papers.cool/arxiv/2607.14611)), and memory-poisoning guidance converges on provenance tags, scanning for instruction-like text, confirmation before persisting, immutable logs and rollback ([Schneider](https://christian-schneider.net/blog/persistent-memory-poisoning-in-ai-agents/)). Git already supplies the log and the rollback. The missing pieces are a quarantine and a gate: notes the agent derives from web pages, issues or tool output go to an `inbox/` folder with `status: draft` and a `source:` field until the developer promotes them, and an `ask` rule on `mcp__basic-memory__write_note`, `edit_note`, `move_note` and `delete_note` adds confirmation at the cost of some friction. Permission rules match MCP tools by name only, so `Read` deny rules cannot stop the basic-memory server from reading what it indexes ([Permissions](https://code.claude.com/docs/en/permissions)); private material belongs in a separate basic-memory project that ordinary sessions do not load, or outside the indexed folder, and `BASIC_MEMORY_MCP_PROJECT` locks a session to one project ([Configuration](https://docs.basicmemory.com/raw/reference/configuration.md)). Secrets never enter the vault, only their names and locations; a local pre-commit scanner such as gitleaks backs that up, because GitHub's push protection for private repositories requires the paid Secret Protection add-on ([GitHub push protection](https://docs.github.com/pt/code-security/concepts/secret-security/about-push-protection)), and the developer's hook already blocks secrets in the files each write changes ([secrets decision](memory://vault/decisions/block-secrets-only-in-files-changed-by-the-current-write)). basic-memory's Claude Code plugin adds a SessionStart briefing and a PreCompact checkpoint ([Claude Code integration](https://docs.basicmemory.com/raw/integrations/claude-code.md)); its hooks deserve the same review as any code, and any digest a hook injects should stay factual, since Anthropic notes that text framed as commands can trip prompt-injection defenses ([Hooks reference](https://code.claude.com/docs/en/hooks)).

## Conclusion

The evidence reframes setup work as relocation rather than accumulation. The expensive parts of an elaborate configuration (long always-loaded instructions, many concurrent writers, review fanned out across agents, event narration) carry the weakest evidence of benefit, while the cheap parts (a hook that runs the fast check, tests the human approved, a VM snapshot, a deny rule) carry the strongest. For this developer the highest-value changes are therefore moves, not additions: procedures out of the global file into skills, guardrails out of prose into settings and the sandbox, and autonomy off the unsandboxed Windows host onto the dev VM. The orchestration practice survives the move in lighter form, because the developer's own data (conflict-free contract-first merges, bugs caught by frozen-worktree reviews, a lane that spent most of 5.5 unchecked hours waiting on builds and tests) supports contracts, gates and time-boxes on firmer ground than the borrowed percentages currently attached to them.

A configuration is also a fast-decaying dependency. Defaults moved repeatedly in 2026 (auto mode, Opus 5.5 at medium effort, native AGENTS.md reading, background subagents), and Anthropic's own advice is to revisit configuration every three to six months and after major model releases, retiring rules written for older models ([How Claude Code works in large codebases](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)). Since the cleanest randomized trial of experienced developers found perceived speedups wrong by about 40 points ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)) and no study compares lean and heavy Claude Code setups head to head, the single most useful addition is a small personal benchmark: three to five real tasks run under the current and the lean configuration, scored on `/usage` points, defects caught in review and time to a merged change, plus one recorded question at every vault recall, namely whether the note changed a decision.
