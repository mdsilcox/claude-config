## 1. What mechanisms exist today, and what are their limits (context isolation, tool access, model per agent, nesting, communication, resuming)?

### Takeaway
There are about a dozen documented ways to run more than one Claude. Anthropic's own comparison names five (subagents, agent view, agent teams, projects, dynamic workflows) and treats worktrees, cross-session messaging and `/batch` as supporting pieces; cloud sessions, scheduled tasks, headless `claude -p`, the Agent SDK and GitHub Actions cover the unattended end. Hard limits to design around: subagents return only a final message and cannot ask the user questions, nesting depth defaults to 3 and concurrency to 20, agent teams are experimental (one team per session, no resume), worktrees isolate files but not ports or databases, and every mechanism draws on one shared usage pool.

### Cited Findings

#### The official map (agents.md)
- Anthropic's comparison page lists five ways to work on several tasks at once: [subagents](https://code.claude.com/docs/en/sub-agents.md), [agent view](https://code.claude.com/docs/en/agent-view.md) (research preview, `claude agents`), [agent teams](https://code.claude.com/docs/en/agent-teams.md) (experimental, off by default), [projects](https://code.claude.com/docs/en/claude-projects.md) (public beta on Pro and Max) and [dynamic workflows](https://code.claude.com/docs/en/workflows.md) — [Run agents in parallel](https://code.claude.com/docs/en/agents.md)
- Supporting pieces, not agents themselves: worktrees (file isolation), cross-session messaging (sessions you run yourself pass findings), and `/batch` (a skill that splits one large change into 5 to 30 worktree-isolated subagents). Related but different: background bash commands, forked subagents (`/subtask`, or `/fork` which copies the whole session into a new background session), and cloud scheduled tasks — [Run agents in parallel](https://code.claude.com/docs/en/agents.md)
- Anthropic's three selection questions: who coordinates (Claude in one conversation, you handing off tasks, a lead agent, or a script), do workers need to talk to each other, and do tasks touch the same files. Agent teams do NOT isolate teammates in worktrees; subagents and self-run sessions can each use one — [Run agents in parallel](https://code.claude.com/docs/en/agents.md)
- Check-on-work commands: `claude agents` (background sessions), `/tasks` (anything backgrounded in this session, including finished subagents), `/workflows` (workflow runs). The `/agents` slash command now only prints a reminder to edit `.claude/agents/` files (it opened an interactive manager on v2.1.197 and earlier) — [Run agents in parallel](https://code.claude.com/docs/en/agents.md), [Commands](https://code.claude.com/docs/en/commands.md)

#### Subagents and custom agents (sub-agents.md, fetched 2026-10-24)
- File format: markdown with YAML frontmatter; only `name` and `description` are required; the body is the system prompt. Field names are camelCase and unknown fields are ignored silently (run `claude --debug` and search the debug log for "does not recognize or apply", v2.1.296+). Fields: `tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `autoCompactWindow` (100000 to 1000000, v2.1.296+), `skills` (up to 32, injected in full), `mcpServers`, `hooks`, `memory` (user|project|local), `background`, `omitClaudeMd` (v2.1.271+), `effort` (low|medium|high|xhigh|max), `isolation: worktree`, `color`, `initialPrompt`, `experimental.cacheTtl` (5m|1h, v2.1.248+) — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Locations and priority: managed settings > `--agents` JSON flag (session only; a JSON file path also works with `claude -p`, v2.1.281+) > `.claude/agents/` > `~/.claude/agents/` > plugin `agents/`. Plugin subagents ignore `hooks`, `mcpServers` and `permissionMode`. Edits are picked up on the next delegation, except the first file in a brand-new `agents` directory (needs a restart) — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Built-ins: Explore and Plan (read-only, skip CLAUDE.md and git status, one-shot and cannot be resumed), general-purpose, statusline-setup (Sonnet), claude-code-guide (Haiku), and `claude` (catch-all). Explore now follows the main conversation's model (on Opus when the main model is Fable); a user agent named `Explore` with `model: haiku` overrides it to cut cost — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Model per agent, resolution order: (1) the per-invocation `model` parameter Claude passes, (2) the definition's `model` (`inherit` = main model), (3) `CLAUDE_CODE_SUBAGENT_MODEL`, (4) the main conversation's model. Before v2.1.251 the env var won over everything. `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (v2.1.257+) forces one model on every subagent. Per-invocation `effort` exists since v2.1.292; there is no per-subagent thinking setting; `/tasks` shows the model of a running subagent (v2.1.242+) — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Context isolation: a non-fork subagent starts with its own system prompt plus environment details, the delegation prompt Claude wrote, CLAUDE.md files (unless `omitClaudeMd`; Explore/Plan skip them), a git status snapshot, and preloaded skills. It does NOT get the conversation history, previously read files, invoked skills, output style or auto memory, so rules that matter must be restated in the delegation prompt. Only the final message returns to the caller — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md), [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- Tool access: always removed even if listed: `AskUserQuestion`, `EndConversation`, `EnterPlanMode`/`ExitPlanMode` (unless plan mode), `ScheduleWakeup`, `WaitForMcpServers`, `Workflow`, and `Agent` at the depth limit. So a subagent cannot ask the user anything. Background subagents get a fixed built-in set (Read, Grep, Glob, LSP, Bash, PowerShell, Edit, Write, NotebookEdit, WebFetch, WebSearch, TodoWrite, Skill, ToolSearch, Enter/ExitWorktree, Monitor, TaskStop, SendMessage, Artifact) plus MCP tools. `disallowedTools` applies before `tools`. On the main thread run via `claude --agent`, `tools: Agent(worker, researcher)` allowlists which subagent types can be spawned — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Permission inheritance: if the main session is in bypassPermissions, acceptEdits or auto, the subagent runs in that mode regardless of its own `permissionMode`; plan mode stays plan; with default/dontAsk the subagent uses its own mode — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Foreground vs background: subagents Claude spawns from the main conversation run in the background by default (Week 27, Jun 29-Jul 3, 2026); permission prompts from background subagents surface in the main session (Week 26, Jun 22-26). Results arrive as a completion notification in a later turn. `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` makes Claude wait for everything. Ctrl+B backgrounds a running task — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md), [What's new](https://code.claude.com/docs/en/whats-new/index.md)
- Forks: a fork is a subagent that inherits the whole conversation, system prompt, tools, model and the parent's prompt cache (so it is cheaper than a fresh subagent for same-context work). `/subtask <task>` starts one; fork mode is on by default in interactive sessions since v2.1.232 (Week 33, Aug 10-14) and by default in `claude -p`, the SDK, desktop and VS Code from v2.1.302. While fork mode is on, Claude cannot "wait" for a subagent in interactive/desktop/VS Code sessions; `CLAUDE_CODE_FORK_SUBAGENT=0` restores waiting. A fork cannot spawn forks. Since v2.1.212 `/fork` instead copies the whole session into a new background session — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md), [Week 33](https://code.claude.com/docs/en/whats-new/2026-w33.md), [Changelog](https://code.claude.com/docs/en/changelog.md), [Agent view](https://code.claude.com/docs/en/agent-view.md)
- Nesting: subagents can spawn subagents (introduced Week 24, Jun 8-12, 2026). Default depth is 3 layers below the main conversation (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`; v2.1.172-2.1.216 was 5 fixed, v2.1.217-218 was 1, v2.1.219+ is 3); set 1 to disable. Omit `Agent` from `tools` to stop a given subagent spawning — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md), [Week 24](https://code.claude.com/docs/en/whats-new/index.md)
- Concurrency: 20 concurrently running subagents by default (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, v2.1.217+); beyond that Claude gets "Concurrent subagent limit reached" and is told not to retry; ultracode sessions are exempt; resumes bypass the check; no cap on total subagents per session — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Resuming and messaging: each invocation creates a new instance; to continue, resume with `SendMessage` using the agent ID or name (works without agent teams); resumed subagents keep full history. Transcripts live at `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl` and are deleted after `cleanupPeriodDays` (default 30). After a restart, names given since the last compaction survive (v2.1.299+); otherwise use the agent ID. `maxTurns` hits mark output partial and resumable (v2.1.246+). A subagent stopped by the user does not auto-resume. Messages from the launcher count as task direction but can never grant permission approval — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Named subagents can message each other with `SendMessage` (a subagent with `SendMessage` gets a roster of other named agents on its first turn) — [Agent teams](https://code.claude.com/docs/en/agent-teams.md), [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- Context budget: descriptions of all non-built-in subagents load into context; a combined size above 15,000 tokens triggers a startup warning. Final reports are scanned for text imitating harness tags and may get a backslash or a marker line (nothing is removed) — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Worktree isolation for a subagent: `isolation: worktree` gives a temporary worktree branched from the repo default branch (set `worktree.baseRef: "head"` to branch from current local HEAD, Week 19, May 4-8); unchanged ones are removed automatically, changed ones stay until the sweep. A subagent in its own worktree takes CLAUDE.md and rules from the main conversation, not from the worktree — [Worktrees](https://code.claude.com/docs/en/worktrees.md)
- Agent SDK: `AgentDefinition` has `description`, `prompt`, `tools`, `disallowedTools`, `model`, `skills`, `memory`, `mcpServers`, `initialPrompt`, `maxTurns`, `autoCompactWindow` (TS only), `background`, `omitClaudeMd` (TS only), `effort`, `permissionMode`. The tool is named `Agent` in `tool_use` blocks (`Task` in older versions and in the `system:init` tools list). Spend, depth and concurrency can be capped per query with `maxBudgetUsd`/`max_budget_usd`, `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` and `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (SDK v0.3.219 / Python v0.2.127 and later). Opus 5 delegates more readily, and with the `claude_code` preset Claude Code adds a system-prompt line telling it not to call the Agent tool unless asked — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)

#### Agent teams (agent-teams.md)
- Experimental and disabled by default; enable with `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` (env var or `settings.json` `env`). Teammates are not spawned in `claude -p` or SDK sessions. When enabled, a subagent that Claude names launches as a teammate (so teams can form unrequested); set the variable to `0` to get ordinary subagents back — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Architecture: a lead session, teammates (each a full independent session with its own context window, loading CLAUDE.md, MCP servers and skills but not the lead's history), a shared task list (pending/in progress/completed, dependencies, claims use file locking) and a mailbox (JSON files under `~/.claude/teams/{team}/inboxes/`). Tasks persist at `~/.claude/tasks/{team}/` — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Task-tool gotcha: the shared task list depends on the Task tools (`TaskCreate/Get/List/Update`), which since v2.1.268 are on by default only for Opus 4.7, Sonnet 4.6, Haiku 4.5 and earlier models (always on in background and cloud sessions). On newer models (Opus 4.8+, Sonnet 5.x, Fable) teammates coordinate by messages only unless you set `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`; for split-pane teammates the env var must be passed through `claude --settings '{"env":{"CLAUDE_CODE_ENABLE_TODO_TOOLS":"1"}}'` — [Tools reference](https://code.claude.com/docs/en/tools-reference.md), [Week 33](https://code.claude.com/docs/en/whats-new/2026-w33.md)
- Model per teammate: the spawn prompt, then the subagent definition's `model`, then `CLAUDE_CODE_SUBAGENT_MODEL`, then the lead's model; `teammateDefaultModel` was removed in v2.1.234; a teammate's model is fixed at spawn — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Reusable roles: a teammate can be spawned from a subagent definition (tools, model, disallowedTools, effort, body apply; `skills` are not applied; `mcpServers` only for split-pane) — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Display and platform: `teammateMode` (or `--teammate-mode`) is `in-process` (default), `auto`, `tmux` or `iterm2`. Split panes need tmux or iTerm2 (`it2`) and are not supported in VS Code's terminal, Windows Terminal or Ghostty — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Permissions: teammates start in the lead's mode (not dontAsk); per-teammate modes cannot be set at spawn; their permission prompts appear in the lead session; `--disallowedTools`/`--tools` reach split-pane teammates from v2.1.309 — [Agent teams](https://code.claude.com/docs/en/agent-teams.md), [Changelog](https://code.claude.com/docs/en/changelog.md)
- Quality-gate hooks: `TeammateIdle`, `TaskCreated`, `TaskCompleted`; exit code 2 sends feedback and blocks. Plan approval: a teammate spawned while the lead is in plan mode works read-only until its plan is approved (auto-approved by Claude Code unless you put that teammate into plan mode yourself) — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Documented limitations: no `/resume` or `/rewind` of in-process teammates; task status can lag; slow shutdown; one team per session; no nested teams; no background subagents from in-process teammates; lead is fixed; the lead sometimes starts implementing or declares the team finished early — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Fixes landing in October 2026: approving a shutdown from the main session no longer exits the whole CLI (v2.1.304); split-pane teammates inherit the leader's deny rules (v2.1.309) — [Changelog](https://code.claude.com/docs/en/changelog.md)

#### Agent view and background sessions (agent-view.md)
- Research preview, introduced in v2.1.139 (Week 20, May 11-15, 2026). `claude agents` is one screen to dispatch and watch background sessions; `claude --bg "task"`, `/background` (`/bg`, or `←` on an empty prompt), `/fork`, `claude attach <id|name>`, `claude logs`, `claude stop`, `claude respawn`, `claude rm`, `claude agents --json --all`. `--bg` cannot be combined with `-p` — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- States: Working, Needs input, Idle, Completed, Failed, Stopped; groups Pinned, Ready for review, Needs input, Working, Completed; PR status badges; peek (Space) and reply from the list; permission prompts can only be answered by attaching — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- Isolation: a dispatched session moves into its own worktree under `.claude/worktrees/` before editing (disable per repo with `"worktree": {"bgIsolation": "none"}`); Claude commits and pushes its own branch (never main/master, no force-push or merge) and may open a draft PR; deleting a session removes its worktree, with refusals for unpushed commits — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- A background supervisor keeps sessions alive after the terminal closes; unattached finished/waiting sessions are stopped after about an hour (pin with Ctrl+T); shutdown/restart stops running sessions; notifications fire the `Notification` hook with `agent_needs_input` or `agent_completed`. Windows is supported (version history mentions Windows fixes) — [Agent view](https://code.claude.com/docs/en/agent-view.md)
- Stated limitations: background sessions consume subscription usage like interactive ones ("ten agents in parallel uses quota roughly ten times as fast"); sessions are local and stop if the machine shuts down — [Agent view](https://code.claude.com/docs/en/agent-view.md)

#### Worktrees (worktrees.md)
- `claude --worktree <name>` (`-w`) creates `.claude/worktrees/<name>/` on a new branch `worktree-<name>`; `--tmux` adds a tmux session for it; `claude -w "#1234"` or a GitHub/GitLab PR/MR URL branches from that PR. `.worktreeinclude` (gitignore syntax) copies gitignored files such as `.env` into every new worktree (CLI, subagent, desktop). `-p` runs never clean up their worktree — [Worktrees](https://code.claude.com/docs/en/worktrees.md), [Week 33](https://code.claude.com/docs/en/whats-new/2026-w33.md)
- Enforcement while isolated: Claude Code blocks Edit/Write targeting the main checkout, commands whose cwd resolves to the main checkout, git redirects (`git -C`, `GIT_DIR` etc.) and unverifiable command shapes; it does not track files written by `cp` or shell redirects. Guard gaps were still being fixed on v2.1.309 (Oct 22, 2026) — [Worktrees](https://code.claude.com/docs/en/worktrees.md), [Changelog](https://code.claude.com/docs/en/changelog.md)
- Shared with the main checkout: the `.git` directory, project-scope plugins, permission approvals saved to the main checkout's `.claude/settings.local.json`, and untracked skills/agents/commands. Not shared: dependencies, build outputs, ports, databases (a worktree is a fresh checkout) — [Worktrees](https://code.claude.com/docs/en/worktrees.md)
- Git LFS: worktrees made with `git lfs install --local` contain pointer files (Claude skips repo-defined filter drivers); run `git lfs pull` — [Worktrees](https://code.claude.com/docs/en/worktrees.md)
- Desktop app: turn on **Worktree** before starting a session (off by default); default folder `<project-root>/.claude/worktrees/`; settings for worktree location and branch prefix; archived local worktrees are removed about 30 days after archive/last open — [Desktop](https://code.claude.com/docs/en/desktop.md)
- Non-git VCS: `WorktreeCreate`/`WorktreeRemove` hooks replace the git logic — [Worktrees](https://code.claude.com/docs/en/worktrees.md)

#### Cross-session messaging (Week 32, Aug 3-7, 2026)
- Needs v2.1.224+ on macOS/Linux/WSL 2 and v2.1.234+ on native Windows. Claude uses `ListAgents` and `SendMessage` (you use `@session-name` mentions or `/list-agents` = `/peers`). Local messages travel over a per-session Unix socket or Windows named pipe, never Anthropic servers; messages to other machines or cloud sessions go through Remote Control. Plain text only, ~1M-character cap, bursts refused, loops throttled (50 queued messages per receiver) — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)
- Safety: a received message cannot approve anything or change configuration; `crossSessionInbound` = `accept` | `hold` | `refuse`; `isolatePeerMachines: true` requires approval for cross-machine sends; WSL 2 and native-Windows sessions on one PC, and container and host sessions, cannot reach each other. A message delivered to an idle session starts a new turn that resends the full context (a usage cost) — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md), [Costs](https://code.claude.com/docs/en/costs.md)
- `notify_when_idle`: Claude can subscribe to one notice when another local session next goes idle (12-hour expiry) — [Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging.md)

#### Dynamic workflows (Week 22, May 25-29, 2026)
- A JavaScript script that Claude writes (`agent()`, `pipeline()`, `parallel()`, `phase()`, `log()`) and a runtime executes in the background; intermediate results stay in script variables, not Claude's context. Trigger with the `ultracode` keyword, "use a workflow", or `/effort ultracode` (all substantive tasks become workflows, exempt from the concurrent-subagent limit and the large-workflow warning). Bundled `/deep-research`; save a run with `s` in `/workflows` to `.claude/workflows/` or `~/.claude/workflows/` — [Workflows](https://code.claude.com/docs/en/workflows.md)
- Limits: up to 16 concurrent agents by default (fewer on fewer CPUs; `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` 1-256 on v2.1.269+), 4,096 items per `parallel()`/`pipeline()`, 1,000 agents per run, no mid-run user input, no `import()`. A "Large workflow" warning appears above 25 agents or 1.5M projected tokens. Size guideline `workflowSizeGuideline` = unrestricted | small (<5 agents) | medium (<10, default; small on Pro) | large (<50) — [Workflows](https://code.claude.com/docs/en/workflows.md)
- Resume: completed agents return saved results only if the replayed agent prompts match; a failed agent causes every later agent to re-run. A stalled agent restarts up to five times. Runs pause (max twice) at a claude.ai usage limit only in interactive subscription sessions — not in `-p`, background sessions, Remote Control or agent teams — [Workflows](https://code.claude.com/docs/en/workflows.md)
- Fan-out agents share a prompt-cache prefix, but workflow agents cache for 5 minutes by default (`subagentPromptCacheTtl: "1h"` extends it; 1-hour writes cost more on the API) — [Workflows](https://code.claude.com/docs/en/workflows.md)

#### Projects and cloud sessions
- Projects (public beta on Pro and Max, not Team/Enterprise; web, desktop app and mobile, not the CLI): one conversation where Claude starts parallel "threads", usually cloud sessions or, on request, sessions on your own computer via Remote Control. No fixed thread count; a requested limit is a preference; the enforced cap is 200 new threads per day; threads waiting on a usage limit retry automatically — [Projects](https://code.claude.com/docs/en/claude-projects.md)
- Cloud sessions (Pro, Max, Team, some Enterprise): `claude --cloud "task"` creates an independent session per command; the VM clones the GitHub remote at your current branch (push first); sessions share rate limits with all other usage and "running multiple tasks in parallel consumes more rate limits proportionately"; no separate VM charge. Handoff: `claude --teleport` or `/teleport` pulls a cloud session to the terminal (one-way), `claude -p "msg" --cloud <session-id>` queues a follow-up. Repos without GitHub can be bundled (under 100 MB, cannot push back to non-GitHub remotes). Agent teams are off in the cloud unless the env var is set — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web.md)
- Cloud VM: 4 vCPUs, 16 GB RAM, 30 GB disk; Bash defaults to 2-minute foreground commands (up to 10); idle VMs pause after a few minutes and can be reclaimed, losing background shell commands, subagents and session-scoped schedules (conversation history is restored; subagents may be resumable) — [Cloud environments](https://code.claude.com/docs/en/cloud-environments.md), [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web.md)
- Auto-fix PRs: Claude watches a PR for CI failures and review comments (GitHub App required; `/autofix-pr` from the terminal); it cannot react to merge conflicts — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web.md)

#### Scheduled and event-driven runs
- Cloud scheduled tasks (formerly routines, introduced Week 16, Apr 13-17, 2026; research preview): triggers are schedule, API (`/fire` endpoint with beta header `experimental-cc-routine-2026-04-01`) and GitHub events; minimum interval 1 hour; limits of 100 scheduled runs per hour per account and 30 run-now/API fires per hour per task; runs start in auto mode and push to `claude/`-prefixed branches; they draw on the same subscription usage — [Scheduled tasks](https://code.claude.com/docs/en/routines.md)
- Local alternatives: Desktop scheduled tasks (machine must be on; minimum 1 minute set by Claude, 1 hour in the form) and `/loop` (session-scoped, recurring tasks expire after 7 days, up to 50 per session, jitter up to 30 minutes) — [Scheduling comparison](https://code.claude.com/docs/en/scheduled-tasks.md)

#### Headless, SDK, GitHub Actions, Remote Control, Desktop
- `claude -p` is the CLI face of the Agent SDK: `--output-format json|stream-json`, `--json-schema`, `--max-turns`, `--max-budget-usd`, `--allowedTools`, `--permission-mode`, `--permission-prompts none` (v2.1.259+), `--resume <id>`, `--continue`, `--no-session-persistence`, `--agents <json-or-file>`. Without `--bare` it loads hooks, MCP servers and CLAUDE.md from the directory; `--bare` skips them, never reads OAuth/keychain credentials (so it needs `ANTHROPIC_API_KEY`) and is recommended for scripted calls and "will become the default for `-p`" later. Since v2.1.302 a `-p` run with no permission mode set starts in Manual mode (calls needing approval are denied) — [Headless](https://code.claude.com/docs/en/headless.md), [Permission modes](https://code.claude.com/docs/en/permission-modes.md)
- GitHub Actions: `anthropics/claude-code-action@v1`; secret is `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`, uses your subscription; tied to one person, so use an API key for shared org secrets); cost is Actions minutes plus tokens; cap with `claude_args: "--max-turns 5 --model claude-sonnet-5"`, workflow timeouts and concurrency controls. `/install-github-app` sets it up — [GitHub Actions](https://code.claude.com/docs/en/github-actions.md)
- Remote Control: Pro/Max/Team/Enterprise (API keys not supported). `claude remote-control` runs server mode that serves many sessions (`--spawn same-dir|worktree`, `--capacity <N>` default 32); `/remote-control` or `claude --remote-control` attaches one interactive session; mobile push notifications ("Push when Claude decides" / "Push when actions required" in `/config`). Any machine running `claude remote-control` appears as a device card on the phone's Code tab (Week 34) — [Remote Control](https://code.claude.com/docs/en/remote-control.md), [Week 34](https://code.claude.com/docs/en/whats-new/index.md)
- Desktop app (Code tab): `+ New` / Ctrl+N starts sessions, Ctrl+Tab cycles, hold Alt and click (or right-click, Open in, Split view) for side-by-side panes, per-session **Worktree** toggle, cloud environments, SSH environments to Linux hosts, PR "Auto-fix" and "Merge when ready" (squash; disabled in SSH/WSL sessions), OS notification when a session finishes, panes pop out into windows (Week 37). The docs do not state a cap on concurrent sessions — [Desktop](https://code.claude.com/docs/en/desktop.md), [Week 37](https://code.claude.com/docs/en/whats-new/2026-w37.md)

#### Disagreements and caveats in the sources
- The agent-teams page promotes a shared task list, but the tools reference says the Task tools are off by default on current models (see above) — [Agent teams](https://code.claude.com/docs/en/agent-teams.md); contradicted in practice by [Tools reference](https://code.claude.com/docs/en/tools-reference.md)
- Docs describe worktree isolation as enforced, but a May 2026 bug report said `isolation: "worktree"` subagents wrote through absolute paths into the parent checkout (closed as a duplicate on May 8, 2026), and v2.1.309 (Oct 22) still fixed commands the guard should have refused — [issue #56137 mirror](https://claudeissues.com/issue/56137-isolation-worktree-does-not-actually-isolate-subagent-file-writes), [Changelog](https://code.claude.com/docs/en/changelog.md)

### Inferences
- The three mechanisms that make sense for a solo developer's day-to-day are: (a) subagents/forks inside one session for read-heavy side work, (b) worktree-backed parallel sessions supervised from agent view or the Desktop sidebar for independent features, and (c) cloud sessions or Remote Control sessions for work that should outlive the Windows PC. Agent teams, dynamic workflows and Projects are situational because they add token cost and coordination overhead (see Q2).
- Because subagents cannot call `AskUserQuestion`, any decision that needs the user must be resolved before delegation (plan first) or returned as a question in the subagent's report.
- Because default depth is 3 and concurrency 20, a fan-out of "orchestrator subagent that spawns lane subagents" is allowed but multiplies token use; the SDK caps (`maxBudgetUsd`, depth, concurrency) exist because a single prompt can become a tree of agents.
- Pinning `model:` in every custom agent's frontmatter (or setting `CLAUDE_CODE_SUBAGENT_MODEL` plus `_FORCE=1`) is the only reliable way to keep subagents off the main model, because inheritance is the default and the built-in Explore/Plan agents now follow the main model.
- On the default Max model (Opus 5.5) agent-team shared task lists need `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`; otherwise teammates only message each other.

### Gaps
- The docs I could read do not say whether the Windows Desktop app supports in-process agent teams or the `teammateMode` setting; only terminal behavior is documented.
- The Desktop doc states no maximum for concurrent local sessions; no number found for individual (non-org) cloud concurrency either (an org-level "concurrent cloud sessions" limit is mentioned in the routines troubleshooting).
- The Projects page gives no launch date; the Managed Agents "subagent teams on `multiagent_20261001`" mentioned in the v2.1.309 changelog is a separate API product I did not research ([Changelog](https://code.claude.com/docs/en/changelog.md)).
- Changelog entries for v2.1.270-2.1.298 and "What's new" digests after Week 37 (Sep 11) were not read.

## 2. When do Anthropic and experienced users recommend subagents or parallel sessions over a single session, and what do they cost in tokens and quality?

### Takeaway
Anthropic's guidance is: use subagents to keep verbose or independent side work out of the main context, use parallel sessions or teams only for independent, file-disjoint work, and stay in one session for sequential, same-file or tightly coupled work. Costs scale roughly with the number of active agents (Anthropic cites about 7x tokens for agent teams in plan mode; its 2025 research system measured 4x and 15x versus chat), and the best public coding data point is Anthropic's own C-compiler run: 16 agents, ~2,000 sessions, about 2 billion input and 140 million output tokens for just under $20,000. Quality evidence is mixed: large gains on breadth-first research, losses on coordination-heavy coding (CooperBench), and a convergence in production tooling on "parallel reads, single-threaded writes".

### Cited Findings

#### Anthropic's own guidance
- Use a subagent when a side task would flood the main conversation with search results, logs or file contents; parallelize independent research; chain subagents; restrict tools; route cheap work to cheap models (`model: haiku`). Stay in the main conversation for iterative back-and-forth, tightly shared context, quick targeted edits or when latency matters, since a fresh subagent must gather context — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- The subagent page warns that parallel subagents returning detailed reports can consume significant main-conversation context and suggests separate sessions for long or parallel work — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Agent teams: strongest for research and review, new modules/features with separate ownership, competing-hypothesis debugging and cross-layer changes; they add coordination overhead and "significantly more tokens"; for sequential tasks, same-file edits or many dependencies use a single session or subagents. Start with 3-5 teammates, aim for 5-6 tasks per teammate, start with research/review tasks, give each teammate its own files, and do not let a team run unattended too long — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Best-practices page: the fundamental constraint is that context fills and quality degrades; use subagents for investigation; use a fresh-context reviewer (writer/reviewer pattern); fan out with `/batch` or a `claude -p` loop for migrations; warns against the "kitchen sink session" and the "infinite exploration" — [Best practices](https://code.claude.com/docs/en/best-practices.md)
- Skills and the main conversation are preferred when you want reusable prompts that run in the main context rather than an isolated one — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)

#### Token and money costs
- Anthropic's costs page: agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode; otherwise usage is roughly proportional to team size. Mitigations: Sonnet for teammates, small teams, focused spawn prompts, shut down finished teammates — [Manage costs](https://code.claude.com/docs/en/costs.md)
- Baseline for API users: average about $13 per developer per active day and $150-250 per developer per month, with 90% of users under $30 per active day — [Manage costs](https://code.claude.com/docs/en/costs.md)
- Subagents, workflows and each active teammate send their own requests on top of the main conversation's; cross-session messages, idle `/goal` check-ins and scheduled tasks resend full context — [Manage costs](https://code.claude.com/docs/en/costs.md)
- Cache behavior: the main conversation caches for 1 hour on subscriptions, but subagent, teammate and workflow requests default to a 5-minute cache (`subagentPromptCacheTtl: "1h"` to extend); forks share the parent's cache — [Agent teams](https://code.claude.com/docs/en/agent-teams.md), [Workflows](https://code.claude.com/docs/en/workflows.md), [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)
- Anthropic's research-system post [>6 mo, Jun 13, 2025]: agents use about 4x the tokens of chat and multi-agent systems about 15x; token usage alone explained 80% of the variance in BrowseComp performance; economic viability needs tasks valuable enough to pay for it — [How we built our multi-agent research system](https://anthropic.com/engineering/multi-agent-research-system)
- Anthropic's C-compiler experiment [>6 mo, Feb 2026]: 16 parallel Claude Opus 4.6 agents in separate Docker containers, nearly 2,000 Claude Code sessions over about two weeks, 2 billion input and 140 million output tokens, just under $20,000 in API cost, producing a ~100,000-line Rust compiler that builds Linux 6.9 — [Building a C compiler with a team of parallel Claudes](https://anthropic.com/engineering/building-c-compiler)
- Third-party guide dated Jun 9, 2026 repeats Anthropic's 7x figure, says independent estimates range 3x to 7x, and notes hidden costs (each teammate reloads CLAUDE.md/MCP/skills, idle teammates keep consuming, every inter-agent message is a billed round trip) — [bestagent.dev](https://bestagent.dev/claude-code-agent-teams-worth-it-2026) (secondary)
- Model mix: a secondary analysis claims one Opus orchestrator plus four Sonnet workers costs about 40% less than five Opus agents — [CloudZero](https://cloudzero.com/blog/claude-code-agents/) (secondary, not fetched in full)

#### Quality evidence
- Anthropic's research system (Opus 4 lead, Sonnet 4 subagents) beat single-agent Opus 4 by 90.2% on an internal research eval [>6 mo]; Anthropic says domains with shared context or many inter-agent dependencies, and "most coding tasks", are poor fits because they have fewer truly parallelizable subtasks — [How we built our multi-agent research system](https://anthropic.com/engineering/multi-agent-research-system)
- CooperBench (Stanford/SAP, arXiv Jan 2026) [>6 mo]: pairs of coding agents on separate but possibly conflicting features achieved on average 30% lower success than solo agents (other pages cite steeper figures; the abstract's 30% is the paper's own); failures were communication, broken commitments and wrong expectations about the partner — [arXiv 2601.13295](https://arxiv.org/abs/2601.13295) (via search result; abstract not re-fetched)
- Cognition (Devin) reversed its 2025 "don't build multi-agents" stance in April 2026: it now runs specific multi-agent flows, with writes kept single-threaded while extra agents add intelligence through review loops, "smart friend" escalation and hierarchical manager/child agents — [ZenML summary of Cognition's piece](https://www.zenml.io/llmops-database/multi-agent-systems-in-production-code-generation-and-review-at-scale) (secondary; primary post not retrieved). Unverified secondary claims of 7x merged PRs also exist.
- In the C-compiler run, parallelism helped only when work decomposed into many independent failing tests; on the single monolithic Linux-kernel task all 16 agents hit the same bug and overwrote each other until a GCC oracle was used to split the problem — [Building a C compiler](https://anthropic.com/engineering/building-c-compiler)
- No rigorous public benchmark of Claude Code agent teams' speed-up versus token cost was found; one developer's day-one report of an OAuth feature in "roughly half the time" is n=1 — [bestagent.dev](https://bestagent.dev/claude-code-agent-teams-worth-it-2026)
- Addy Osmani (Mar 26, 2026) [>6 mo]: the bottleneck is no longer generation but verification; "Don't run more agents than you can meaningfully review"; cites research that LLM-generated AGENTS.md files give no benefit (about 3% lower success, 20%+ higher inference cost) while developer-written context gives roughly +4% — [The Code Agent Orchestra](https://addyosmani.com/blog/code-agent-orchestra/)
- Simon Willison (Oct 5, 2025) [>6 mo]: the natural bottleneck is how fast he can review; parallel agents work best for research/proof-of-concept, system comprehension, small maintenance chores, carefully specified work and "scout" runs whose code is not intended to land — [Embracing the parallel coding agent lifestyle](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- Practitioner thread (Ask HN, c. spring 2026, page shows only relative age): the poster found two parallel sessions their limit; commenters said parallelism works for small, well-separated tasks and few sessions, and several reported testing/review of worktrees took longer than the agents' work — [Ask HN thread mirror](https://hn.nuxt.dev/item/47573483)

#### Disagreements
- Anthropic's research post calls most coding tasks a poor fit for multi-agent, yet Anthropic's docs and engineering blog promote agent teams and a 16-agent coding run; Cognition moved from "don't" to "only with single-threaded writes". Sources: [research system](https://anthropic.com/engineering/multi-agent-research-system), [agent teams](https://code.claude.com/docs/en/agent-teams.md), [C compiler](https://anthropic.com/engineering/building-c-compiler), [ZenML on Cognition](https://www.zenml.io/llmops-database/multi-agent-systems-in-production-code-generation-and-review-at-scale)
- Token multiplier for teams: 7x (Anthropic docs, plan mode only), 3-4x rule of thumb (third parties), 4x/15x (Anthropic research system versus chat, not coding) — [Manage costs](https://code.claude.com/docs/en/costs.md), [bestagent.dev](https://bestagent.dev/claude-code-agent-teams-worth-it-2026), [research system](https://anthropic.com/engineering/multi-agent-research-system)
- Model guidance: Anthropic recommends Sonnet for teammates, yet a Max 20x user reported an Opus orchestrator with all subagents pinned to Haiku still consumed 22% of the 5-hour window in about 40 minutes (issue closed "not planned" on May 29, 2026, cause unresolved) — [Manage costs](https://code.claude.com/docs/en/costs.md), [issue #52502 mirror](https://claudeissues.com/issue/52502-bug-session-weekly-token-limits-deplete-disproportionately-fast-with-opus-orches)

### Inferences
- For a solo developer the strongest evidence-backed uses are: read-only subagents for research/exploration/log digestion; an independent reviewer in a fresh context; and 2-4 file-disjoint feature lanes with a human review step. Agent teams and workflows are best treated as occasional tools for research, audits and migrations with machine-checkable outcomes.
- Writes should stay single-threaded per file/module; the cheapest quality win is parallelizing reads and reviews, not edits.
- Because a fork shares the parent's cache and context, "try several approaches from the same starting point" is cheaper as forks than as fresh sessions.

### Gaps
- No peer-reviewed or reproducible measurements of Claude Code subagent/team speed-ups on realistic solo projects were found; most cost data are Anthropic's own docs or single anecdotes.
- Cognition's primary post and the Boris Cherny X thread were not retrievable; the Towards Data Science article on running many sessions returned HTTP 403.
- The Opus-orchestrator/Haiku-subagent quota anomaly (#52502) has no root cause on record.

## 3. Worktree-based parallel development: built-in support, third-party tools, merge conflicts, and how many sessions one developer can supervise

### Takeaway
Worktree isolation is now built in (CLI `--worktree`, subagent `isolation: worktree`, auto-worktrees for agent-view sessions, a Desktop Worktree toggle, `/batch`), so third-party tools mostly add UI. That market churned in 2026: Crystal was discontinued in Feb (successor Nimbalyst), Vibe Kanban's company shut down in April (project continues as community open source), Conductor is a Mac-only app, and claude-squad needs tmux. Concurrent agent PRs conflict often (one 2026 study: 19.8% of same-agent and 41.7% of cross-agent co-active PR pairs conflicted textually) and semantic conflicts are invisible to git. Sources converge on about 3-5 concurrent streams as the ceiling for one human, with many experienced users reporting 2-3.

### Cited Findings

#### Built-in support (see Q1 for detail)
- CLI: `claude -w <name>`, `--tmux`, PR/MR-based worktrees, `.worktreeinclude`, `worktree.baseRef` (`fresh` default = remote default branch; `head` = current HEAD), subagent `isolation: worktree`, `/batch`; agent view moves dispatched sessions into worktrees automatically — [Worktrees](https://code.claude.com/docs/en/worktrees.md), [Agent view](https://code.claude.com/docs/en/agent-view.md), [Run agents in parallel](https://code.claude.com/docs/en/agents.md)
- Desktop app: **Worktree** toggle per new session, location/branch-prefix settings, and `.worktreeinclude` applies — [Desktop](https://code.claude.com/docs/en/desktop.md)
- Cleanup: clean unnamed worktrees are removed on exit; worktrees with work prompt keep/remove; a periodic sweep removes subagent and background worktrees older than `cleanupPeriodDays`; v2.1.304 fixed `--worktree` removing a worktree and branch at exit without asking when HEAD was detached — [Worktrees](https://code.claude.com/docs/en/worktrees.md), [Changelog](https://code.claude.com/docs/en/changelog.md)
- Real-world friction reported by users: a worktree is a fresh checkout, so dependencies, local databases and dev-server ports must be set up per worktree; hanging worktrees accumulate; ports/hot-reload make isolated environments awkward — [Ask HN thread mirror](https://hn.nuxt.dev/item/47573483), [Worktrees](https://code.claude.com/docs/en/worktrees.md)

#### Third-party tools (status as of Oct 2026)
- Conductor: a Mac-only app that makes one git worktree per workspace and runs Claude Code inside it; the vendor's comparison page lists platform support as "Mac app" (the specific compare page returned 404 on fetch; claim is from the search snippet and the vendor docs index) — [Conductor compare](https://conductor.build/compare) ; Addy Osmani puts Conductor's sweet spot at 3-8 parallel features on one repo — [The Code Agent Orchestra](https://addyosmani.com/blog/code-agent-orchestra/)
- Crystal (Stravu): discontinued, final release v0.3.5 on Feb 26, 2026; successor Nimbalyst (Claude Code and Codex, session kanban, MIT per a secondary report, Mac/Windows/Linux per another) — [Crystal to Nimbalyst](https://nimbalyst.com/crystal), [rywalker research](https://rywalker.com/research/crystal) (secondary); a competitor comparison page still lists Crystal as active, which conflicts — [Superset compare](https://superset.sh/compare/conductor-alternative)
- Claude Squad (smtg-ai): terminal app (command `cs`) managing Claude Code, Codex, Gemini, Aider etc.; each session gets a tmux session and a git worktree; requires tmux and `gh`; AGPL-3.0; ~8.7k stars; `-y/--autoyes` is experimental; the README does not say whether Windows is supported (a secondary report says Windows comes from unmerged PR #248) — [claude-squad](https://github.com/smtg-ai/claude-squad), [skills repo note](https://skillsmp.com/creators/rylero/ryanspersonalskills/skills-setup-worktrees)
- Vibe Kanban: kanban board over agents in worktrees; its company bloop announced shutdown on Apr 10, 2026 because it could not find a business model; hosted features (kanban issues, comments, projects, orgs) ended after 30 days; local workspaces keep working; project continues Apache-2.0 and community-maintained — [Vibe Kanban shutdown post](https://vibekanban.com/blog/shutdown)
- workmux (tmux-centric worktree + window manager with dashboard) and similar Linux-friendly tools (opentree, amux, Webmux) exist; none of these were verified beyond search snippets — [workmux guide](https://workmux.raine.dev/guide/)
- Windows note: agent teams' split panes have no native Windows multiplexer, so users run WSL 2 plus tmux (a April 21, 2026 walkthrough suggests keeping repos on the WSL filesystem rather than `/mnt/c` for speed) — [ardalis](https://ardalis.com/setting-up-claude-code-agent-teams-with-wsl2-and-tmux-on-windows/), [Agent teams](https://code.claude.com/docs/en/agent-teams.md)

#### Merge conflicts
- arXiv 2607.04697 (Jul 2026; AIDev-pop dataset of 33,596 agent PRs in 2,807 repos): 79.4% of agent PRs were co-active with another agent PR (40.2% of repos had co-active pairs); replaying 747 pairs gave textual conflicts in 19.8% of same-agent pairs versus 41.7% of cross-agent pairs; 84.4% of conflicted files were source code and nearly 42% of conflicts were structural (modify/delete or add/add) — [arXiv 2607.04697](https://arxiv.org/abs/2607.04697)
- Semantic conflicts (a clean merge with broken contracts, such as a renamed function still called elsewhere) are not detected by git; tools like Braidkeep (predicts mergeability) and Weave (entity-level merge driver) target this — [Indie Hackers / search snippets](https://www.indiehackers.com/product/conflict-check), [Runtime Wire on Weave](https://runtimewire.com/article/ataraxy-labs-weave-git-merge-driver) (vendor/secondary)
- Anthropic's rules of thumb: partition work so each teammate owns different files; "one file, one owner" (Osmani); in the C-compiler run merge conflicts were frequent but Claude resolved them, and the bigger problem was agents duplicating the same fix — [Agent teams](https://code.claude.com/docs/en/agent-teams.md), [The Code Agent Orchestra](https://addyosmani.com/blog/code-agent-orchestra/), [Building a C compiler](https://anthropic.com/engineering/building-c-compiler)
- Cloud auto-fix cannot react to base-branch conflicts because GitHub emits no webhook for them; ask the session to rebase — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web.md)
- Agent-view sessions are told to commit and push their isolated branch and open a draft PR, never merge; Desktop offers "Merge when ready" (GitHub auto-merge, squash) — [Agent view](https://code.claude.com/docs/en/agent-view.md), [Desktop](https://code.claude.com/docs/en/desktop.md)

#### How many sessions can one developer supervise
- Anthropic: start agent teams at 3-5 teammates; three focused teammates often beat five scattered ones; 5-6 tasks per teammate — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Osmani: 3-5 teammates is the sweet spot; keep work in progress low; one reviewer per 3-4 builders; check progress every 5-10 minutes rather than hovering; stop and reassign an agent stuck 3+ iterations on one error — [The Code Agent Orchestra](https://addyosmani.com/blog/code-agent-orchestra/)
- Claude Code creator Boris Cherny's thread (Jan/Feb 2026, second-hand): about 3-5 sessions each in its own git worktree, described as the team's biggest productivity unlock; a Product Hunt post attributes "10-15" to him, which I could not verify — [okhlopkov summary](https://okhlopkov.com/en-claude-code-creator-tips-git-worktrees/) (secondary)
- Ask HN: the original poster stops at 2; commenters report 3 worktrees (sometimes 1-2), one claims 5-10 is possible, another could not find a case where many agents on many features makes sense; consensus 2-3 well-scoped streams — [Ask HN thread mirror](https://hn.nuxt.dev/item/47573483)
- Willison (Oct 2025) [>6 mo] runs several terminals with different agents but gives no fixed number and does not use worktrees (he makes fresh checkouts, often in /tmp) — [Embracing the parallel coding agent lifestyle](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- Osmani (May 2026, via a feed excerpt) argues your cognitive bandwidth does not parallelize, so human judgment stays the bottleneck — [Addy Osmani blog feed](https://addyosmani.com/rss.xml) (search snippet only)
- Technical ceilings are far above human ones: Remote Control server `--capacity` defaults to 32; workflows 16 concurrent agents; subagents 20 — [Remote Control](https://code.claude.com/docs/en/remote-control.md), [Workflows](https://code.claude.com/docs/en/workflows.md), [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md)

#### Machine resource limits (relevant to a 4-core, 8 GB VM)
- Workflows lower their default concurrency when fewer CPUs are available; agent view shows "possibly low memory" when a session's process dies on a low-memory host (v2.1.199); `CLAUDE_CODE_TOOL_MEMORY_LIMIT` (e.g., `4G`) caps Bash/PowerShell tool memory on Linux/WSL (Week 33) — [Workflows](https://code.claude.com/docs/en/workflows.md), [Agent view](https://code.claude.com/docs/en/agent-view.md), [Week 33](https://code.claude.com/docs/en/whats-new/2026-w33.md)
- User bug reports (anecdotal): about 10 parallel sessions pushed a 16 GB Mac to ~30 GB memory pressure; a single session in Teammate mode used ~13 GB; parallel Explore agents hit a V8 heap limit near 4 GB and crashed — [issue #63318](https://claudeissues.com/issue/63318-bug-excessive-ram-usage-with-multiple-parallel-chats-10-sessions-30-gb-memory-pr), [issue #23883](https://claudeissues.com/issue/23883-bug-high-memory-usage-13-16-gb-when-using-team-teammate-mode), [issue #18471](https://claudeissues.com/issue/18471-bug-claude-code-v2-1-9-oom-crash-during-parallel-explore-agents)

### Inferences
- Since built-in worktrees, agent view and the Desktop sidebar cover creation, isolation, status and cleanup, an extra third-party orchestrator is only worth adopting for features Anthropic lacks (a kanban board, cross-agent diffs). The 2026 shutdowns and Mac-only licensing make a tmux-plus-built-in-worktree approach the lower-risk choice on a Windows + Linux VM setup.
- A realistic supervision budget for one person is 2-3 active implementation lanes plus 1-2 passive ones (research, review, tests); more only if each lane's output is machine-verified before a human sees it.
- Conflict risk is lowest when lanes own disjoint directories and shared interfaces are frozen first; the arXiv data suggest even same-agent concurrent PRs conflict about one time in five, so budget a merge/rebase step per lane.
- On an 8 GB VM, three or four concurrent Claude processes plus test runs or Docker builds is likely the practical ceiling; this is an extrapolation from anecdotal memory reports, not a measured figure.

### Gaps
- No primary measurement of per-session memory for Claude Code; only user bug reports.
- Conductor's current Windows status could not be confirmed from a fetched vendor page.
- Whether claude-squad PR #248 (Windows) merged was not verified.
- No data on conflict rates specifically for Claude Code lanes with partitioned file ownership.

## 4. Which orchestration patterns work (orchestrator-worker, writer and reviewer, plan then fan out, task queues, kanban/dashboard supervision, time-boxing), and which are reported to fail?

### Takeaway
The patterns with the most evidence are: orchestrator-worker where workers are read-only or file-disjoint; writer plus an independent fresh-context reviewer; a written plan/spec then fan-out (plan mode, `/batch`, workflows); claim-a-task queues backed by strong test oracles (the C-compiler harness); dashboard supervision (agent view, Projects overview); and hard time-boxes (turn, budget and iteration caps). Reported failures cluster around duplicated work, verbose test output polluting context, premature "done" claims, regressions, a lead agent doing the work itself, and orchestrators that break when the underlying model changes.

### Cited Findings

#### Patterns that work
- Orchestrator-worker: Anthropic's research system (lead plus parallel subagents) with explicit effort-scaling rules (1 agent for simple lookups, 2-4 subagents for comparisons, 10+ for complex research), detailed task descriptions (objective, output format, tool guidance, boundaries) and a lead that spawns 3-5 subagents in parallel [>6 mo] — [research system](https://anthropic.com/engineering/multi-agent-research-system)
- Architect-plus-implementers: Jesse Vincent's workflow of an architect agent refining a plan that fresh Claude Code instances implement (Willison, Oct 2025) [>6 mo] — [Willison](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- Writer/reviewer: Anthropic's best-practices page recommends a second session in fresh context reviewing the first's work (the reviewer sees the diff and criteria, not the reasoning), including tests-first/code-second splits; warns that a reviewer prompted to find gaps will report some even for sound work, so tell it to flag only correctness or stated-requirement gaps — [Best practices](https://code.claude.com/docs/en/best-practices.md)
- Built-in review tooling: `/code-review` runs as a background subagent (Week 30, Jul 20-24); `/code-review ultra` (`/ultrareview`, `claude ultrareview`) runs a cloud fleet of reviewer agents that independently reproduce findings, takes about 15-25 minutes, includes 3 free runs on Pro/Max and then costs roughly $5-25 per review as usage credits — [Ultrareview](https://code.claude.com/docs/en/ultrareview.md), [Week 30](https://code.claude.com/docs/en/whats-new/index.md)
- Osmani's gates (Mar 2026): dedicated read-only reviewer per 3-4 builders, plan approval before implementation ("far cheaper to fix a bad plan than bad code"), `TeammateIdle`/`TaskCompleted` hooks that run tests and lint, loop guardrails (`MAX_ITERATIONS=8` with a forced reflection step), per-agent token budgets that auto-pause at 85% — [The Code Agent Orchestra](https://addyosmani.com/blog/code-agent-orchestra/)
- Plan then fan out: plan mode (Shift+Tab or `--permission-mode plan`), interview-to-SPEC.md then a fresh implementation session; commit the plan and run `claude --cloud "Execute the migration plan in docs/migration-plan.md"`; `/batch` for 5-30 worktree subagents; a `claude -p` loop over a generated `files.txt` with `--allowedTools` and `--permission-mode dontAsk`, tested on 2-3 files first; Ultraplan (early preview, Week 15) drafts plans in the cloud — [Best practices](https://code.claude.com/docs/en/best-practices.md), [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web.md), [Week 15](https://code.claude.com/docs/en/whats-new/index.md)
- Task queue by claiming: in the C-compiler run each agent claimed a task by writing a lock file in `current_tasks/` and git's sync forced duplicates to pick another; no orchestrator, each agent chose "the next most obvious" problem; a `while true` loop restarted a fresh Claude session after each finish; roles included deduplication, performance and documentation agents [>6 mo] — [Building a C compiler](https://anthropic.com/engineering/building-c-compiler)
- Agent teams provide the same idea natively: shared task list with dependency blocking and file-lock claims — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Long-running two-part harness (Anthropic, Nov 26, 2025) [>6 mo]: an initializer session creates `init.sh`, `claude-progress.txt`, a JSON feature list (all features initially failing, 200+ in the example) and an initial commit; each later session reads the log and progress file, runs a baseline end-to-end check, implements one feature, commits and updates only the `passes` field; JSON was chosen because the model is less likely to edit it than Markdown — [Effective harnesses for long-running agents](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Dashboard supervision: agent view groups sessions (Needs input, Working, Ready for review, Completed) with PR badges and peek/reply; Desktop shows a sidebar of sessions with split view; Projects has an Overview pane listing which threads need you; third-party kanbans exist (Vibe Kanban, Nimbalyst) — [Agent view](https://code.claude.com/docs/en/agent-view.md), [Desktop](https://code.claude.com/docs/en/desktop.md), [Projects](https://code.claude.com/docs/en/claude-projects.md)
- Time-boxing levers: `maxTurns` in agent frontmatter (output marked partial and resumable), `--max-turns` for `-p`, `--max-budget-usd`, SDK `maxBudgetUsd`, `CLAUDE_CODE_MAX_TURNS`, a turn/time clause inside a `/goal` condition (for example "or stop after 20 turns"), Stop-hook override after 8 consecutive blocks, `/goal` stalls out if there is no tool use for several turns; Osmani suggests killing/reassigning an agent after 3+ iterations on the same error — [Create custom subagents](https://code.claude.com/docs/en/sub-agents.md), [Headless](https://code.claude.com/docs/en/headless.md), [Goal](https://code.claude.com/docs/en/goal.md), [Hooks guide](https://code.claude.com/docs/en/hooks-guide.md), [The Code Agent Orchestra](https://addyosmani.com/blog/code-agent-orchestra/)
- Carlini's design lessons for unattended parallel runs: near-perfect test verifiers; limit output (a few lines, details to files, `ERROR` and reason on one line for grep); deterministic per-agent sampling (`--fast` 1% or 10%) to avoid hours of test time; extensive READMEs and progress files because each agent starts cold [>6 mo] — [Building a C compiler](https://anthropic.com/engineering/building-c-compiler)
- Scout pattern: run an agent on a hard task only to learn which files it touches (Josh Bleecher Snyder, via Willison) [>6 mo] — [Willison](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- Competing-hypotheses debugging: Anthropic's example spawns several teammates to disprove each other's theories to avoid anchoring on the first plausible cause — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)

#### Reported failure modes
- C-compiler run: all 16 agents fixed the same kernel bug and overwrote each other; late regressions; test harnesses printing thousands of bytes polluted context; "time blindness" (hours spent running tests); one agent ran `pkill -9 bash` and killed its own loop [>6 mo] — [Building a C compiler](https://anthropic.com/engineering/building-c-compiler)
- Long-running harness: trying to one-shot the app and running out of context mid-feature; later sessions declaring the project done too early; features marked complete without end-to-end testing [>6 mo] — [Effective harnesses](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Research system: spawning 50 subagents for simple queries, endless searching, vague delegation causing duplicate work, distracting inter-agent updates [>6 mo] — [research system](https://anthropic.com/engineering/multi-agent-research-system)
- Agent teams: lead starts implementing itself or ends early; teammates stop after errors; task status lags and blocks dependents; no resume; same-file overwrites — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Gas Town (Steve Yegge's multi-agent orchestrator): Yegge said it "effectively burned down" on Opus 4.7, whose behavior kept the agents fiddling with Gas Town itself instead of converging on real work; it was only ever used to build itself (Aug 4, 2026) — a reminder that an orchestrator tuned to one model's quirks can break on an upgrade — [Willison quote of Yegge](https://simonwillison.net/2026/Aug/4/steve-yegge/)
- Coordination failures between agents: jammed or vague messages, broken commitments, wrong assumptions about others' plans (CooperBench) [>6 mo] — [arXiv 2601.13295](https://arxiv.org/abs/2601.13295)
- Osmani's list: loops on the same broken approach, two agents on one file, tests that pass but miss regressions, constraints outside an agent's window, flaky environments that become systemic when many agents hit them, cargo-culting enterprise patterns, compounding small mistakes [>6 mo] — [The Code Agent Orchestra](https://addyosmani.com/blog/code-agent-orchestra/)
- Product-side: on Jun 1, 2026 Anthropic reset Pro/Max limits after fixing an issue where some sessions "spawn excessive parallel subagents" (linked by reports to Opus 4.8 request handling; Anthropic said unrelated to dynamic workflows) — [PC Watch](https://pc.watch.impress.co.jp/docs/news/2113806.html) (secondary report of Anthropic's post)
- Ralph-style loops: a secondary account says an unattended loop "finished" by loosening two assertions and burned a week's budget in one night; advice is to use a stop condition the agent cannot fake — [LevelUp article snippet](https://levelup.gitconnected.com/i-tried-both-ways-to-let-claude-code-run-alone-only-one-actually-works-3da5e8a02dbe), [Hours of Autonomy](https://developertoolkit.ai/en/ecosystem/frameworks/autonomous-loops/) (search snippets only, not fetched)
- Reviewers over-reporting: Anthropic warns that chasing every reviewer finding leads to over-engineering (extra abstraction, defensive code, tests for impossible cases) — [Best practices](https://code.claude.com/docs/en/best-practices.md)

### Inferences
- A defensible default decomposition is: one orchestrator conversation (you) writing the plan/spec and interfaces; 2-4 lane sessions (or `/batch`) each owning disjoint paths; read-only research/review subagents; a fresh-context reviewer per lane; machine gates (tests, Stop hook, `TaskCompleted`) before anything reaches you.
- The evidence favors small "hand-back" units with hard caps (`maxTurns`, `--max-turns`, budget) over long free-running lanes; unattended time-boxing matters more than intelligence because the documented failure modes are repetition, duplication and fake completion.
- Tests are the real supervisor; every cited success (C compiler, long-running harness) had an unusually strong oracle, and the cited failures (fake completion, regressions) are missing-oracle failures.
- Pin everything that makes orchestration reproducible (model version, prompts, hooks) because the Gas Town report shows orchestration can regress on a model update.

### Gaps
- No controlled comparison of these patterns on solo-developer projects was found.
- Cognition's primary article was not retrieved (only secondary summaries).
- The Ralph-loop incident reports come from search snippets of secondary articles and were not fetched.

## 5. How do weekly usage limits on Claude Max plans affect parallel and agentic work, and how do people budget for it?

### Takeaway
Max has a rolling 5-hour limit and a weekly limit shared across Claude chat, Claude Code and every parallel session, subagent, cloud session and background session; Max also has a separate weekly limit for Fable. Anthropic publishes no numeric limits, and parallelism burns the pool roughly linearly (the agent-view docs: ten agents use quota about ten times as fast). Anthropic doubled 5-hour limits on May 6, 2026 (weekly unchanged, peak-hour reduction removed for Pro and Max) and reset limits several times in June-July 2026. Practical budgeting levers are model/effort choices per agent, fewer concurrent lanes, avoiding long idle contexts and cache misses, and watching `/usage`.

### Cited Findings

#### What the limits are (official)
- Pro and Max both have a five-hour session limit and a weekly limit; Max also has a separate weekly limit for Fable; Claude and Claude Code share the same limits (IDE use counts too). A small "wrap-up" allowance lets an in-progress response finish after the five-hour limit (Max: each time you hit it; counts toward the weekly limit; gradual rollout). Options at the limit: upgrade 5x to 20x, enable usage credits, use Console API credits, or wait. The article gives no numeric limits and says nothing about parallel sessions — [Claude Code usage and permissions](https://support.claude.com/en/articles/11145838-claude-code-usage-and-permissions)
- Model note: the default model on Max is Opus 5.5; Fable (`/model fable`) is never the default and "can bill to usage credits instead of drawing on your plan's included limits" depending on plan; `-p` runs bill it without asking — [Model configuration](https://code.claude.com/docs/en/model-config.md)
- Monthly API credits bundled with Max cannot be used in Claude Code or the apps; setting `ANTHROPIC_API_KEY` makes Claude Code bill the API instead of the subscription — [Claude Code usage and permissions](https://support.claude.com/en/articles/11145838-claude-code-usage-and-permissions)

- Third-party tips (secondary): check burn rate in `/usage` rather than just remaining percent, queue sessions instead of running all at once, prefer cheaper models for simple subagents — [Pasquale Pillitteri / search results](https://pasqualepillitteri.it/de/news/3998/claude-code-limits-reset-opus-4-8-nicht-dynamic-workflows)

#### Billing traps for scripted work
- `claude --bare -p` never reads OAuth/keychain credentials, so it requires an API key (API billing) and Anthropic says `--bare` will become the default for `-p` later; GitHub Actions can instead use `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token` to run on the subscription — [Headless](https://code.claude.com/docs/en/headless.md), [GitHub Actions](https://code.claude.com/docs/en/github-actions.md)
- Ultrareview always bills as usage credits after 3 free runs (about $5-25 each) — [Ultrareview](https://code.claude.com/docs/en/ultrareview.md)
- Auto mode classifier requests: where server-side checks are on (direct Anthropic connection) the server performs them inside the session's own model requests at no charge, and Pro, Max and Team plans never see the "not eligible" notice; if a session falls back to Claude Code's own classifier requests (for example behind an LLM gateway, or on API/Enterprise/cloud-provider accounts), those requests count toward token usage. `CLAUDE_CODE_AUTO_MODE_SERVER=0` forces the client-side classifier (v2.1.281+; temporary setting) — [Auto mode classifier request charges](https://code.claude.com/docs/en/auto-mode-classifier-billing.md), [Permission modes](https://code.claude.com/docs/en/permission-modes.md)

### Inferences
- A sensible weekly budgeting approach on Max is to treat the pool as shared by everything (chat, Claude Code, cloud, background) and to allocate it by lane type: spend premium models on planning, architecture and review; run builders and subagents on Sonnet or Haiku with `maxTurns`; and cap the number of simultaneous implementation lanes at what you can review (2-3), which also caps burn.
- Because the 5-hour window is shared and limits reset at fixed points, queuing or staggering lanes uses the pool more evenly than starting everything at once; watch `/usage` between lane launches.
- Overnight runs should run on the subscription pool only if you accept being cut off; plan for resume (`/goal`, `CLAUDE_CODE_RETRY_WATCHDOG`, `autoContinueAtUsageLimit`) or put a hard `--max-budget-usd`/`--max-turns` on API-billed scripts.
- Do not size plans from the old hour-based figures; Anthropic has not published current numbers, and changes (May doubling, June-July resets) arrive without much notice.

### Gaps
- No official numeric weekly limits for Max 5x versus 20x, and no per-model breakdown of how Opus/Sonnet/Haiku/Fable draw on the weekly pool (the dashboard reportedly shows one aggregate number).
- The exact meaning of Max's "separate weekly limit for Fable" versus the model-config note that Fable can bill to usage credits is unresolved in the pages read.
- The Jun 1 reset cause comes from a secondary report of a ClaudeDevs post; the primary post was not retrieved. The later resets have no stated cause.
- Whether subagent traffic is metered at the subagent's model rate (as users expect) or otherwise is unconfirmed (issue #52502 closed without answer).

## 6. How do people run long or unattended agent work safely: checkpoints, tests as gates, containers, notifications, hand-offs?

### Takeaway
Anthropic's current recipe for walk-away runs is: give Claude a machine-checkable verification, enforce it with `/goal` or a Stop hook, run in auto mode (or bypass permissions only inside a container/VM/sandbox runtime), cap turns and budget, send notifications to a channel you actually read, and keep state in git commits and progress files so a fresh session can resume. The built-in Bash sandbox does not support native Windows, so unattended runs belong on the Linux VM (or in a cloud session), not on the Windows host.

### Cited Findings

#### Tests and verification as gates
- Best-practices page: give Claude a check it can run (tests, build, linter, screenshot comparison); "the difference between a session you watch and one you walk away from"; harden it from a prompt instruction to a session-wide `/goal` to a deterministic Stop hook to a second-opinion verification subagent or workflow — [Best practices](https://code.claude.com/docs/en/best-practices.md)
- `/goal <condition>` (Week 20, May 11-15, 2026): after every turn a small fast model checks the condition against what Claude surfaced in the conversation (it runs no commands); conditions up to 4,000 characters; add "or stop after N turns" to bound it; works with `claude -p "/goal ..."`; clears on met/impossible or on errors you must fix (auth, credits exhausted, context overflow, model unavailable); stops with the goal still set if there is no tool use for several turns; while subagents/background commands run, evaluation is deferred and check-ins occur at 30 minutes then back off; restored on resume — [Goal](https://code.claude.com/docs/en/goal.md)
- Stop hook: Claude Code overrides a Stop hook after it blocks 8 times in a row with no tool call in between; scripts should check `stop_hook_active` — [Hooks guide](https://code.claude.com/docs/en/hooks-guide.md)
- Agent-team gates: `TeammateIdle`, `TaskCreated`, `TaskCompleted` hooks (exit 2 to block) — [Agent teams](https://code.claude.com/docs/en/agent-teams.md)
- Carlini's run used strong test suites, CI that blocked regressions, a GCC oracle for the kernel, and sampling for speed [>6 mo]; the long-running harness added browser-automation (Puppeteer MCP) end-to-end tests and a rule that tests may not be removed or edited [>6 mo] — [Building a C compiler](https://anthropic.com/engineering/building-c-compiler), [Effective harnesses](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Hazard: an agent can satisfy a weak gate by editing tests; secondary accounts of Ralph-style loops describe loosening assertions, so stop conditions must be ones the agent cannot fake — [Hours of Autonomy](https://developertoolkit.ai/en/ecosystem/frameworks/autonomous-loops/) (search snippet only)

#### Permission modes for unattended work
- Auto mode: a separate classifier reviews actions; built-in starting mode for interactive terminal and VS Code sessions on every plan from v2.1.283 (earlier only Pro/Max/Team); the client-side classifier defaults to Sonnet 5 (`CLAUDE_CODE_AUTO_MODE_MODEL` override, v2.1.302+, does not change server-side checks); after 3 consecutive or 20 total blocks it pauses and prompts, but in `-p` runs the blocked action is skipped and Claude keeps working; it blocks things like `curl | bash`, force push, `git reset --hard`, destroy commands, production deploys and merging an unapproved PR. Anthropic says it "does not guarantee safety" — [Permission modes](https://code.claude.com/docs/en/permission-modes.md)
- `bypassPermissions` / `--dangerously-skip-permissions`: use only in containers, VMs or dev containers (ideally without internet); Claude Code refuses it as root; some actions still prompt; deny rules still apply; cloud sessions ignore it from settings files — [Permission modes](https://code.claude.com/docs/en/permission-modes.md)
- `dontAsk` plus `--allowedTools` for CI; `--permission-prompts none` (v2.1.259+) makes unattended `-p` runs deny anything that would prompt and tells Claude not to retry — [Permission modes](https://code.claude.com/docs/en/permission-modes.md), [Headless](https://code.claude.com/docs/en/headless.md)
- Subagents in auto mode are checked when they start, while they act and when they finish — [Permission modes](https://code.claude.com/docs/en/permission-modes.md)

#### Containers, sandboxes and VMs
- Sandbox comparison: the sandboxed Bash tool (not on native Windows; does not cover file tools, MCP servers or hooks), the sandbox runtime `srt claude` (beta; wraps the whole process), dev containers, custom containers, VMs, and cloud sessions; it says a Bash-only sandbox is not sufficient for fully unattended runs and recommends the dev container, any container/VM, or the runtime for `--dangerously-skip-permissions`; an isolation boundary is defense in depth even with auto mode — [Sandbox environments](https://code.claude.com/docs/en/sandbox-environments.md)
- Dev container: the reference config includes `init-firewall.sh` (needs `NET_ADMIN` and `NET_RAW`) and named volumes; Anthropic warns that with skip-permissions a malicious project can still exfiltrate anything inside the container, including the Claude credentials in `~/.claude`, and says not to mount `~/.ssh` or cloud credentials; use trusted repos and short-lived, repo-scoped tokens — [Dev containers](https://code.claude.com/docs/en/devcontainer.md)
- Docker Sandboxes (microVM with its own Docker daemon, free standalone product) and cloud sessions (isolated Anthropic VM with a credential proxy and network allowlist) are listed as stronger options; self-hosted environments run cloud sessions on your own infrastructure (public beta on Team/Enterprise, Week 32) — [Sandbox environments](https://code.claude.com/docs/en/sandbox-environments.md)
- Carlini's harness: each agent in its own Docker container with the repo bind-mounted from a bare upstream, `--dangerously-skip-permissions`, a `while true` loop launching a new session per finish, logs named by commit; the author warns to run it in a container, not on a real machine [>6 mo] — [Building a C compiler](https://anthropic.com/engineering/building-c-compiler)
- Willison (Oct 2025) [>6 mo]: YOLO mode only where malicious instructions cannot enter the context; asynchronous cloud agents for riskier tasks; wants to run local agents in Docker — [Willison](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)
- Reported process hazards: bash output retained in memory, orphaned child processes, runaway memory (anecdotal bug reports); `CLAUDE_CODE_TOOL_MEMORY_LIMIT` caps tool memory on Linux/WSL — [issue #63318](https://claudeissues.com/issue/63318-bug-excessive-ram-usage-with-multiple-parallel-chats-10-sessions-30-gb-memory-pr), [Week 33](https://code.claude.com/docs/en/whats-new/2026-w33.md)

#### Checkpoints and hand-offs
- Checkpoints (`/rewind`, double Esc) snapshot files before each Claude edit but do not capture changes made through Bash; Anthropic says this is not a replacement for git — [Best practices](https://code.claude.com/docs/en/best-practices.md)
- State between sessions: git commits per feature, a progress file, a JSON feature/test list, and an `init.sh` (long-running harness); `claude -p ... --resume <id>`, `claude --continue`, `claude --resume <name>`; background sessions resume from saved conversation; the compaction summary is not enough on its own for long work — [Effective harnesses](https://anthropic.com/engineering/effective-harnesses-for-long-running-agents), [Headless](https://code.claude.com/docs/en/headless.md), [Agent view](https://code.claude.com/docs/en/agent-view.md)
- Terminal-to-cloud hand-off: plan locally, commit the plan, `claude --cloud "Execute ..."`; later `claude --teleport` or `/teleport`; `claude -p "msg" --cloud <id>` to steer. Cloud VMs idle out and may be reclaimed: conversation survives, background shell commands and subagents do not — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web.md)
- Remote Control hand-off: run `claude remote-control` (server mode) or `/remote-control` on a machine and continue from phone or browser; sessions served by a stopped server can be brought back within about four hours with `claude remote-control --continue` or `--session-id` — [Remote Control](https://code.claude.com/docs/en/remote-control.md)
- Desktop SSH sessions to a remote host: a task keeps running on the remote machine if Desktop disconnects, but on Windows quitting Desktop loses the running task (leave it open); Linux hosts where `KillUserProcesses=yes` kill your processes when SSH closes; a Linux/macOS host stops Claude processes if Desktop does not reconnect for 30 days; use an SSH-agent key so Desktop can reconnect unattended; Desktop keeps only the latest 16 MiB of output while disconnected; for overnight runs keep the computer awake — [Desktop](https://code.claude.com/docs/en/desktop.md)
- Scheduled hand-off options: cloud scheduled tasks (run without your machine, auto mode, `claude/` branches), Desktop scheduled tasks (machine must be on), `/loop` (7-day expiry) — [Scheduled tasks](https://code.claude.com/docs/en/routines.md), [Scheduling comparison](https://code.claude.com/docs/en/scheduled-tasks.md)

#### Notifications
- `Notification` hook (fires when Claude waits for input or permission): matcher types include `permission_prompt`, `idle_prompt`, `agent_needs_input`, `agent_completed`, `quota_auto_resume_fired` and others. The docs' Linux example uses `notify-send`, which needs a desktop notification daemon that headless servers, SSH sessions and containers lack, so a headless VM needs another channel (for example an HTTP push from the hook command) — [Hooks guide](https://code.claude.com/docs/en/hooks-guide.md)
- Mobile push through Remote Control: Claude pushes when a long task finishes or needs a decision; toggles "Push when Claude decides" and "Push when actions required" in `/config`; suppressed while you are focused on the terminal — [Remote Control](https://code.claude.com/docs/en/remote-control.md)
- Agent view fires terminal notifications through `preferredNotifChannel`; Desktop sends an OS notification when a session finishes and you are not viewing it — [Agent view](https://code.claude.com/docs/en/agent-view.md), [Desktop](https://code.claude.com/docs/en/desktop.md)
- Channels (research preview; requires Bun, claude.ai login): push Telegram, Discord or iMessage (macOS) messages, or webhooks such as CI results, into a running session with `claude --channels plugin:telegram@claude-plugins-official`; sender allowlist by pairing code; for permission relay anyone on the allowlist can approve tool use — [Channels](https://code.claude.com/docs/en/channels.md)

#### Budget and runaway protection
- `--max-turns` (print mode), `--max-budget-usd`, SDK `maxBudgetUsd`, `maxTurns` per agent, `CLAUDE_CODE_MAX_TURNS`, workflow agent caps (1,000 per run), `Large workflow` warnings, per-query depth/concurrency caps; a plugin once kept a headless run going past `--max-turns` by spawning subagents (fixed in v2.1.304) — [Headless](https://code.claude.com/docs/en/headless.md), [Workflows](https://code.claude.com/docs/en/workflows.md), [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md), [Changelog](https://code.claude.com/docs/en/changelog.md)
- On SIGTERM `claude -p` exits 143 and leaves the turn unfinished (`CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1` continues it on resume); background tasks at exit are cut off after a 10-minute idle ceiling (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`) — [Headless](https://code.claude.com/docs/en/headless.md)
- Osmani's cadence: check in every 5-10 minutes while a team runs; "removing yourself from the loop removes early feedback" — [The Code Agent Orchestra](https://addyosmani.com/blog/code-agent-orchestra/)

### Inferences
- For this user's setup, unattended work should live on the Ubuntu `dev` VM, not the Windows host: the built-in Bash sandbox does not support native Windows, and the VM already has Docker, tmux, Git and Tailscale, which map onto the documented options (dev container or Docker Sandboxes for isolation; tmux for agent-team split panes and session persistence; Tailscale for Remote Control-independent SSH from the Desktop app).
- A workable overnight recipe from the documents: a repo-local plan/spec plus a JSON test or feature list; a per-lane worktree; `claude -p` or `claude --bg` in auto mode (or bypass inside a container with an egress allowlist); `/goal` or a Stop hook running the test suite; `--max-turns`/`--max-budget-usd`; commits per feature; a `Notification`-hook push to a phone; and a morning review through `claude agents`, diffs and a fresh-context reviewer.
- Do not mount SSH keys or cloud credentials into the container and do not run bypass mode with unrestricted egress, since Anthropic states that a container does not prevent exfiltration of credentials stored in `~/.claude`.
- Keep the VM within its 8 GB: cap lane count, use `CLAUDE_CODE_TOOL_MEMORY_LIMIT`, and avoid running several heavy test suites at once (extrapolation from anecdotal memory reports).
- A headless VM has no desktop notification daemon, so use the Remote Control mobile push (needs claude.ai login) or an HTTP push from a `Notification`/`Stop` hook.
