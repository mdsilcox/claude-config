# Memory and knowledge-vault management for Claude Code (state as of 2026-10-24)

*Conventions: "(>6 mo)" marks a claim dated before about 2026-04-24 that may be superseded. "Search summary" means the fact comes from a WebSearch result summary, not a page I fetched in full. Anything under Inferences is my own reasoning, built on the cited findings above it. Disagreements between sources are reported, not resolved.*

## 1. Current state of basic-memory, and how it compares with the other ways of giving Claude Code a vault

### Takeaway
basic-memory is at v0.24.1 (23 Oct 2026, AGPL-3.0): a local, file-first MCP server with a rebuildable SQLite index over plain Markdown. v0.24 made hybrid keyword plus semantic search always on and added read-only POSIX-style tools (cat, grep, ls, find, tail, man), checksum-guarded writes, temporal observations and schema tools, but index-integrity bugs (duplicate search rows, case-twin folders) were still open on 17-20 Oct 2026. The alternatives differ in kind: Obsidian REST/CLI routes need a running desktop Obsidian and offer keyword search; plain files plus Claude Code's own grep is the mechanism Anthropic itself describes; mem0/Graphiti/Letta are agent-owned stores with databases or LLM calls; native auto memory is per-repo and machine-local; Anthropic's API memory tool is an application-side feature. I found no head-to-head benchmark of these options for a Claude Code user.

#### basic-memory: features, with the version that introduced them
- Semantic vector search, hybrid keyword+vector fusion and the schema tools (`schema_infer`, `schema_validate`, `schema_diff`) arrived in v0.19 (Mar 2026, >6 mo, but still documented for v0.24). [Docs changelog](https://docs.basicmemory.com/raw/whats-new/changelog.md)
- v0.24 (Oct 2026): semantic search is always on and `semantic_search_enabled` is retired; default local embeddings are FastEmbed `BAAI/bge-small-en-v1.5` (384 dims), with OpenAI `text-embedding-3-small` or any OpenAI-compatible endpoint as options; `semantic_min_similarity` defaults to 0.55. [Semantic search](https://docs.basicmemory.com/raw/concepts/semantic-search.md), [Upgrade guide](https://docs.basicmemory.com/raw/whats-new/v0-24-upgrade.md)
- Hybrid merge: the stronger score is kept, a result found by both methods gets a 30% bonus, and a failed strict all-words query is retried as an any-word query. The page calls hybrid the default for CLI queries; boolean operators run as text. [Semantic search](https://docs.basicmemory.com/raw/concepts/semantic-search.md)
- Opt-in cross-encoder reranker (`reranker_enabled`, local `jinaai/jina-reranker-v1-tiny-en`): about +90 ms p50 on short notes; p95 on long transcript chunks rose from 420 ms to about 2.1 s; "improved quality" is claimed with no metric. [Semantic search](https://docs.basicmemory.com/raw/concepts/semantic-search.md)
- Initial index of a few hundred notes takes 1-3 minutes; "thousands" of notes are said to work, with no benchmark; Windows x86_64 and Linux are supported platforms; if the sqlite-vec extension cannot load, search silently falls back to keyword-only (`bm project info <name>` shows vector-runtime status). [Semantic search](https://docs.basicmemory.com/raw/concepts/semantic-search.md)
- Six read-only POSIX-style tools (`cat`, `grep`, `ls`, `find`, `tail`, `man`) are on by default in v0.24: `cat` reads a whole note, one heading section, a line range or a token budget; `grep(semantic=True)` ranks by meaning; `find` filters by metadata predicates such as `status=active` and projects frontmatter fields; projects act as mount points; hide with `bm config set enable_posix_tools false`. [v0.24 page](https://docs.basicmemory.com/raw/whats-new/v0-24.md), [Upgrade guide](https://docs.basicmemory.com/raw/whats-new/v0-24-upgrade.md)

[v0.24 page](https://docs.basicmemory.com/raw/whats-new/v0-24.md), [AI assistant guide](https://docs.basicmemory.com/raw/reference/ai-assistant-guide.md), [Upgrade guide](https://docs.basicmemory.com/raw/whats-new/v0-24-upgrade.md)

#### Alternative: Anthropic's native memory
- Auto memory: on by default in local sessions; notes are typed in a `type` frontmatter field (`user`, `feedback`, `project`, `reference`); stored at `~/.claude/projects/<project>/memory/`, shared by all worktrees of one repo; the first 200 lines or 25 KB of `MEMORY.md` load each session; topic files load on demand; machine-local, "not shared across machines"; controls are `autoMemoryEnabled`, `autoMemoryDirectory` and `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`; Claude skips what it can derive from the code or what CLAUDE.md already says. [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

### Inferences
- Treat basic-memory as the write and structure layer and keep reads pluggable. Claude Code can already read and grep the same folder natively with no prompts (via `--add-dir`), so the MCP's distinct value is revision-safe writes, schema validation, graph traversal (`build_context`), cross-project search and semantic recall. If only Claude Code is used, the MCP is optional for reading.
- For a headless Ubuntu VM, the Obsidian REST and CLI routes are a poor fit because both need the desktop app running; basic-memory and plain files work headless.
- Given the open Oct 2026 index bugs, pin v0.24.1 or later, run `bm doctor` and `bm status --json` after upgrades and syncs, and keep `bm reset --reindex` (rebuilds from the Markdown) as the documented repair path. Because the Markdown stays the source of truth, a corrupted index costs minutes, not data.
- mem0, Graphiti and Letta would add a second source of truth next to a vault that is fixed in place. Letta MemFS (git-backed Markdown, commit per edit, background "dreaming") is the closest design reference, not a replacement.
- Anthropic's API memory tool is not an access mechanism for the Claude Code CLI; its useful part is the pattern (view-first protocol, progress log), which a vault note can copy.
- Native auto memory cannot be the cross-project, cross-machine store: it is per repo and machine-local by Anthropic's own description.
- The README/docs naming mismatch suggests tool names may change; avoid hard-coding `bm_*` names in CLAUDE.md and refer to "the basic-memory search tool" instead.

## 2. How to structure notes for agent retrieval, and what the evidence says about semantic versus keyword search

### Takeaway
Write each note so that both grep and embeddings can land on it: a descriptive title and filename, a short summary paragraph first, headed sections, one-fact observation lines for decisions and pitfalls, explicit wikilinks, a small consistent frontmatter set (type, status, tags, dates) and a maintained index. The search evidence is mixed and comes from conversational-memory benchmarks, vendor tests and one May 2026 preprint: agentic grep matches or beats vector retrieval when the harness is good, while hybrid (BM25 plus embeddings) beat either alone in Anthropic's 2024 tests and in Cursor's tests. No study tests note granularity in a personal Markdown vault.

### Cited Findings

#### What basic-memory's index can use
- Notes are plain Markdown. Frontmatter holds `title`, `type` (any value), `tags`, `permalink` (stable, prefixed with the project name by default) and optional `created`/`modified` (used for recency ordering); other keys such as `status` are free-form and not built in; `locked: true` makes a note read-only to the note API; `bm_parse_semantics: false` makes a note graph-silent. [Knowledge format](https://docs.basicmemory.com/raw/concepts/knowledge-format.md)
- Observations are list items `- [category] content #tag`; relations are `- relation_type [[Target]]`; forward references are allowed and resolve when the target appears; wikilinks resolve by permalink, then title, then path, with a case-insensitive underscore/hyphen fallback only when it matches exactly one note. [Knowledge format](https://docs.basicmemory.com/raw/concepts/knowledge-format.md)
- The docs give no guidance on note length or atomicity; the closest statement is that observations are indexed individually so search can surface a specific fact. [Knowledge format](https://docs.basicmemory.com/raw/concepts/knowledge-format.md)
- Chunking: headers create section boundaries, observations and relations are indexed individually, prose is merged into chunks of about 900 characters with about 120 overlap. [Semantic search](https://docs.basicmemory.com/raw/concepts/semantic-search.md)
- `metadata_filters` supports equality, `$in`, `$gt/$gte/$lt/$lte`, `$between`, `$contains`, `$exists` and dotted nested keys; there is no `$ne`, `$nin`, `$regex` or top-level `$or`; strings match case-sensitively; a missing field never matches; filters apply to Markdown only; the page says richer frontmatter gives sharper search but prescribes no key set and points to schemas to enforce one. [Metadata search](https://docs.basicmemory.com/raw/concepts/metadata-search.md)
- Assistant rules in the docs: use exact titles in wikilinks so they resolve; update with `edit_note` instead of creating duplicates; if `write_note` reports "Similar existing notes", merge, link or keep. [AI assistant guide](https://docs.basicmemory.com/raw/reference/ai-assistant-guide.md)
- `write_note` rejects filename-convention twins in one folder (writing `project-plan.md` fails if `Project Plan.md` exists); `kebab_filenames` (default false) makes tool-created filenames kebab-case; `ensure_frontmatter_on_sync` (default true) adds derived `title` and `type` when missing; v0.24 backfills `permalink` into frontmatter. [Knowledge format](https://docs.basicmemory.com/raw/concepts/knowledge-format.md), [Configuration](https://docs.basicmemory.com/raw/reference/configuration.md), [Upgrade guide](https://docs.basicmemory.com/raw/whats-new/v0-24-upgrade.md)
- The docs say a project is the unit of isolation: relations cannot cross projects, and folders are "for you" because the graph ignores folder location; start with one project if unsure. [Projects and folders](https://docs.basicmemory.com/raw/concepts/projects-and-folders.md)

#### Index, hub and log pattern
- Karpathy's "LLM Wiki" idea file (4 Apr 2026, borderline >6 mo) has three layers: immutable raw sources, an LLM-owned wiki of Markdown pages, and a schema document (CLAUDE.md or AGENTS.md) that fixes conventions. `index.md` is a categorized catalog with one-line summaries that the LLM reads first; `log.md` is append-only with consistent prefixes so unix tools can parse it; at moderate scale (about 100 sources, hundreds of pages) the index works without embedding RAG, and a local search tool such as qmd (hybrid BM25/vector with LLM re-ranking) is suggested as it grows. "The cost of maintenance is near zero" is his argument, not a measured result. [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- The page-count thresholds (index alone under 100 pages, add search over about 150) come from a third-party commentary table that appears to be its own inference, not Karpathy's text. [Commentary gist](https://gist.github.com/acmerfight/1c26b29ef39c0acc20f2e6f1f84e025f)
- basic-memory v0.24 ships `bm wiki rebuild`, which generates `index.md` and `log.md` per folder and never overwrites hand-written ones (reports them as conflicts). [CLI reference](https://docs.basicmemory.com/raw/reference/cli-reference.md), [v0.24 page](https://docs.basicmemory.com/raw/whats-new/v0-24.md)
- Letta MemFS keeps a root `MEMORY.md` that lists directories with their own `MEMORY.md` index so the agent follows names to the right file. [MemFS docs](https://docs.letta.com/concepts/memfs)
- Anthropic: folder hierarchies, naming conventions and timestamps help agents judge purpose and relevance ("timestamps can be a proxy for relevance"). [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

#### Evidence on semantic versus keyword retrieval
- LongMemEval (ICLR 2025; submitted 14 Oct 2024, revised 4 Mar 2025; >6 mo): 500 questions testing information extraction, multi-session reasoning, temporal reasoning, knowledge updates and abstention; commercial assistants and long-context LLMs show a 30% accuracy drop on sustained interactions; the authors split memory design into indexing, retrieval and reading and propose session decomposition, fact-augmented key expansion and time-aware query expansion. [LongMemEval](https://arxiv.org/abs/2410.10813)
- Anthropic Contextual Retrieval (19 Sep 2024, >6 mo): top-20 chunk failure rate 5.7% baseline, 3.7% with contextual embeddings (-35%), 2.9% adding contextual BM25 (-49%), 1.9% adding reranking (-67%); embeddings plus BM25 beat embeddings alone because BM25 catches exact identifiers; a knowledge base under about 200,000 tokens (about 500 pages) can go straight into the prompt. [Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)
- Letta (12 Aug 2025, >6 mo): a LoCoMo conversation in one file plus file tools (`grep`, `search_files`, `open`, `close`) with GPT-4o mini scored 74.0% versus the 68.5% Mem0 reported for its best graph variant. `search_files` is semantic search and tool rules forced the agent to start with it; prompt tuning was minimal; the authors call LoCoMo a retrieval benchmark rather than a test of agentic memory, call Mem0's reported numbers "puzzling", and conclude that how well an agent uses a tool matters more than the retrieval mechanism. [Letta benchmark post](https://www.letta.com/blog/benchmarking-ai-agent-memory)
- "Is Grep All You Need? How Agent Harnesses Reshape Agentic Search" (arXiv 2605.15184, v1 preprint, 14 May 2026): 116-question LongMemEval sample; harnesses Chronos (custom), Claude Code, Codex and Gemini CLI; inline versus file-based tool results; grep generally beats vector retrieval in Experiment 1 and scores depend strongly on harness and tool-calling style; Experiment 2 adds growing amounts of unrelated history (results not visible on the abstract page). [arXiv abstract](https://arxiv.org/abs/2605.15184) A search summary of the PDF adds that inline grep beat inline vector in every harness-model pair and that file-based delivery can reverse or erase grep's advantage; the abstract page did not confirm those two details. [arXiv PDF](https://arxiv.org/pdf/2605.15184)
- Cursor (vendor, own benchmark, no independent replication found): adding semantic search to grep raised answer accuracy by about 12.5% on average (about 6.5% to 23.5% depending on model), online A/B tests showed fewer follow-ups, and grep plus semantic was best. [Cursor blog](https://cursor.com/blog/semsearch) (search summary)
- Reported but secondhand: early Claude Code used RAG with a local vector database and the team found agentic search worked better; a Hacker News commenter counters that grep misses vocabulary mismatch and does not suit millions of documents. [Medium write-up](https://medium.com/@jhanavibehl/code-retrieval-grep-rag-or-both-706cdefd0b70), [HN thread](https://hn.nuxt.dev/item/45439997)
- Secondary summaries describe the "Is Grep" paper as being about coding-agent tasks, while the arXiv abstract describes conversational long-memory QA. [DAIR summary](https://academy.dair.ai/papers/is-grep-all-you-need) contradicted by [arXiv abstract](https://arxiv.org/abs/2605.15184)

#### Disagreement to report
- Cursor's tests and Anthropic's 2024 contextual-retrieval results favor adding embeddings to keyword search; the May 2026 preprint and the Claude Code design favor agentic grep; Letta's "filesystem beats memory library" result actually used a semantic search tool. These are not resolved by the evidence I found.

### Inferences
- For a vault of hundreds to a few thousand notes, a hybrid default with grep still available is the safest reading: grep catches exact identifiers (error strings, package names, ids), embeddings catch vocabulary mismatch ("how did we pick the database" versus a note titled "storage-decision"). basic-memory already ships hybrid and also exposes `grep`.
- A note shape that serves both (my proposal, built on the cited chunking and filter behavior): descriptive kebab-case filename and title; frontmatter with `type`, `status`, `tags`, `project`, `created`, `updated` (and `supersedes`/`superseded_by`, see question 5); a two-to-three sentence summary directly under the title; `##` sections; and a short `## Observations` list only for decisions, pitfalls and rules, where one-fact lines are individually indexed. Long but well-headed notes still chunk cleanly at header boundaries, so atomicity matters most for titles and observations.
- Keep one `index.md` per top-level folder (generated by `bm wiki rebuild` or hand-written) plus hub notes per project or topic; this is the one structure that Karpathy, basic-memory and Letta independently converge on, and it costs the agent one read to orient.
- Because no independent evidence shows that the observation/relation syntax improves retrieval, apply it to new high-value notes instead of rewriting the existing vault; plain Markdown notes are still indexed.
- Use only positive `status` filters (for example `$in: ["active", "draft"]`) because there is no `$ne`; or keep archived notes out of the index (see question 5).

### Gaps
- No study tests atomic versus long notes, or headers versus none, for agent retrieval over a personal developer vault; the evidence is from conversation-memory benchmarks (LoCoMo, LongMemEval), code search or vendor tests.
- The Cursor post date and per-model detail were not retrieved, and the numbers are not independently replicated.
- The "Is Grep" accuracy numbers were not visible in what I fetched; it is a v1 preprint on 116 questions.
- The benefit of basic-memory's reranker is claimed without a metric; the benefit of observation/relation syntax for retrieval has no independent test.

## 3. What belongs in the vault versus CLAUDE.md, auto memory and project docs, and when the agent should search or write

### Takeaway
Anthropic's docs and basic-memory's docs converge on a layered split: CLAUDE.md (plus rules and skills) for short, always-true instructions and commands that Claude cannot infer, kept under about 200 lines; auto memory for small, machine-local, per-repo learnings that Claude writes itself; a searchable store (the vault) for deeper cross-project knowledge fetched on demand; hooks for anything that must happen every time. Practitioners add one central vault, a short CLAUDE.md that points to it, per-project progress logs and an inbox for raw capture. The evidence for the split is vendor documentation and blog posts, plus one 2026 study suggesting that bloated repository context files can hurt.

### Cited Findings

#### Anthropic's division of labor (current docs, Oct 2026; they cite Claude Code up to v2.1.309)
- Two complementary memory systems, both loaded each session and "treated as context, not enforced configuration"; to block an action regardless of what Claude decides, use a PreToolUse hook. CLAUDE.md is instructions you write; auto memory is notes Claude writes. [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Add to CLAUDE.md when Claude makes the same mistake a second time, a review catches something Claude should have known, you retype the same correction, or a new teammate would need the same context; multi-step procedures or single-area facts belong in a skill or a path-scoped rule. [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Target under 200 lines per CLAUDE.md; `@path` imports (max four hops) organize a file but do not reduce its context cost; contradictory instructions may be resolved arbitrarily; `/doctor prompt-audit` (v2.1.283+) reports outdated, broken-reference and conflicting instruction files. [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Include bash commands Claude can't guess, style rules that differ from defaults, test runners, repo etiquette, project-specific architectural decisions, environment quirks and gotchas; exclude anything derivable from code, standard conventions, detailed API docs ("link to docs instead"), frequently changing information, long tutorials and file-by-file descriptions; the test per line is "Would removing this cause Claude to make mistakes?" [Best practices](https://code.claude.com/docs/en/best-practices)
- Context cost: CLAUDE.md is in every request; skill descriptions load at start and bodies only when used; MCP loads tool names with deferred schemas; hooks cost nothing unless they return output; "put guardrails in hooks". [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- A project-root CLAUDE.md survives `/compact`; instructions given only in conversation do not. [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- A home-directory `@` import from a project CLAUDE.md triggers a one-time approval dialog; user-scope files (`~/.claude/CLAUDE.md`, `~/.claude/rules/`) load their imports without it (except in Cowork sessions). [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- `--add-dir` plus `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` also loads `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/rules/*.md` and `CLAUDE.local.md` from the added directory, so a vault can carry its own schema file. [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Auto memory is per repository, machine-local, limited to 200 lines or 25 KB of `MEMORY.md` at load, and skips facts derivable from the code. [Claude Code memory docs](https://code.claude.com/docs/en/memory)

#### basic-memory's own guidance
- Built-in memory is the short-term layer and basic-memory the long-term store; the page suggests saving a routing rule in the agent's memory so it checks basic-memory before answering about past work. [Versus built-in memory](https://docs.basicmemory.com/raw/concepts/vs-built-in-memory.md)
- For assistants: "Before answering questions about prior work or decisions, search first"; record important decisions, findings and context with `write_note` during the conversation; update existing notes with `edit_note`; there is no session-level active project, so ask once if ambiguous and then pass `project` on every call. [AI assistant guide](https://docs.basicmemory.com/raw/reference/ai-assistant-guide.md)
- The plugin's SessionStart briefing and PreCompact checkpoint do the read and save steps by hook; its skills cover orient, checkpoint, decide and remember. [Claude Code integration](https://docs.basicmemory.com/raw/integrations/claude-code.md) A wider skill set covers capture, continue, tasks, ingest, research, reflect, defrag, curate and lifecycle. [Agent skills](https://docs.basicmemory.com/raw/integrations/skills.md)

#### Hooks as the deterministic read and write triggers
- `SessionStart` fires on `startup`, `resume`, `clear`, `compact` and `fork`, accepts only `command` and `mcp_tool` handlers (`mcp_tool` hooks are skipped at launch because MCP servers are not up yet), and injects text through `hookSpecificOutput.additionalContext`. Injected text is capped at 10,000 characters (over the cap it is saved to a file and Claude sees a 2,000-character preview), is replayed rather than re-run on `--continue`/`--resume` so SHAs and timestamps can go stale, and should be written as factual statements because "text framed as system commands can trigger prompt-injection defenses". For static conventions the page recommends CLAUDE.md over a hook. [Hooks reference](https://code.claude.com/docs/en/hooks)
- `SessionEnd` has a 1.5-second default budget (raisable to 60 s with a per-hook `timeout`); command hooks accept `"async": true`; `PreCompact` can block compaction; `Stop` can add context. [Hooks reference](https://code.claude.com/docs/en/hooks)

#### Anthropic's multisession pattern (memory tool docs)
- An initializer session creates a progress log, a feature checklist and a reference to the startup script; each later session starts by reading them and ends by updating the log; work one feature at a time and mark it done only after end-to-end verification. When the memory tool is enabled the API injects "ASSUME INTERRUPTION: Your context window might be reset at any moment" and a view-memory-first protocol. [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

#### Practitioner patterns (blog-grade)
- Karpathy's pattern makes the schema document (CLAUDE.md or AGENTS.md) the place that defines ingest, query and lint workflows for the wiki. [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- Blog guides (search summary) mostly use one vault for all projects, a short CLAUDE.md (one suggests 200-300 lines), PARA folders, per-project progress logs and roadmaps, a `MEMORY.md` index, a raw inbox plus consolidated atomic notes, git versioning and (one guide) absolute-path wikilinks; one warns that a second brain fails when notes pile up and nobody re-reads them. [MindStudio guide](https://www.mindstudio.ai/blog/build-ai-second-brain-claude-code-obsidian), [Pillitteri guide](https://pasqualepillitteri.it/en/news/962/obsidian-claude-code-second-brain-persistent-memory), [CodeMeetAI](https://codemeetai.substack.com/p/how-to-build-a-second-brain-with), [Simonnet](https://cyrilsimonnet.substack.com/p/i-built-a-second-brain-with-claude), [lucasrosati repo](https://github.com/lucasrosati/claude-code-memory-setup)
- Hook-based capture is common: a tutorial describes a Stop hook that sends the transcript to Claude with a prompt asking for lessons, patterns and decisions and writes them to the vault; memem is a packaged local-first variant. [MindStudio hooks tutorial](https://www.mindstudio.ai/blog/self-evolving-claude-code-memory-obsidian-hooks), [memem](https://pypi.org/project/memem/)
- The guides are mostly personal write-ups and some point to paid guides; the search that surfaced them found no authoritative Anthropic documentation on vault conventions, so treat their folder layouts and line counts as individual preferences. [MindStudio guide](https://www.mindstudio.ai/blog/build-ai-second-brain-claude-code-obsidian), [Pillitteri guide](https://pasqualepillitteri.it/en/news/962/obsidian-claude-code-second-brain-persistent-memory) (search summary)

#### Evidence on context files
- ETH Zurich, "Evaluating AGENTS.md" (arXiv 2602.11988, Feb 2026, ICLR 2026; >6 mo): across coding agents and models, repository context files tended to reduce task success versus no context file and raised inference cost by over 20%; the authors conclude human-written files should describe only minimal requirements. [arXiv HTML](https://arxiv.org/html/2602.11988v1) Secondary coverage disagrees on exact numbers (one reads human-written files as +4% success with up to +19% cost) and a Jan 2026 study by Lulla et al. on efficiency paints a more nuanced picture. [Vaughan critique](https://codex.danielvaughan.com/2026/04/13/what-eth-zurich-paper-gets-wrong-right-about-agents-md/) (search summary)

#### Disagreement to report
- Recommended CLAUDE.md size: the official docs say under 200 lines; one blog guide suggests 200-300 lines. [Claude Code memory docs](https://code.claude.com/docs/en/memory) versus [MindStudio guide](https://www.mindstudio.ai/blog/build-ai-second-brain-claude-code-obsidian)
- Whether to keep auto memory on alongside an external memory: basic-memory's docs call them complementary; I found no source recommending turning it off, and no source testing contradictions between the two.

### Inferences
- A workable split (my proposal): user-level `~/.claude/CLAUDE.md` holds working style, writing defaults and a 3-4 line vault routing rule; each project's CLAUDE.md holds commands, layout, conventions and a pointer to that project's folder in the vault, kept under 200 lines and pruned with `/doctor`; repo docs (spec, ADRs, architecture) hold what must travel with the code and be reviewed in PRs, with only a summary note and link in the vault; the vault holds durable cross-project knowledge (decisions with rationale and rejected options, research reports, stack evaluations, reusable patterns, pitfalls, retros); skills hold procedures (including a vault skill that defines when to search and write); hooks hold only deterministic steps (sync, a digest under 10,000 characters).
- Auto memory can stay on as a low-stakes, per-repo scratchpad for corrections, but nothing important should live only there, because it is machine-local and invisible to the VM and other projects; promote anything reusable into the vault. The alternative of disabling it (`autoMemoryEnabled: false`) buys a single source of truth at the cost of losing cheap correction capture; the evidence does not decide this.
- Search triggers worth writing into the routing rule: before starting research or a stack choice; after a first failed attempt at a non-trivial error; on phrases like "have we done this before"; and before creating a note (to dedupe). Write triggers: a decision made, a research report finished, a reusable problem solved, a phase retro, or an explicit request.
- Prefer a reviewable write path for agent-authored notes (an `inbox/` folder or a permission prompt on write tools) over silent auto-capture; this serves both retrieval quality (less clutter) and the poisoning controls in question 6.
- The always-loaded surface (CLAUDE.md files, `MEMORY.md`, any SessionStart injection) should stay small; the ETH result and Anthropic's own "bloated CLAUDE.md causes Claude to ignore instructions" advice both point that way.

### Gaps
- No controlled evidence on vault-versus-CLAUDE.md splits; practitioner guidance is blog-grade and partly promotional.
- ETH study figures vary across secondary coverage and I did not read the full paper; it also tests repository context files, not a cross-project vault.
- No source tests whether auto memory plus an external memory produces contradictions.
- I found no Anthropic guidance on cross-project knowledge stores beyond `--add-dir`, imports and MCP.

## 4. Using one vault from a Windows desktop and a Linux VM (git, Syncthing, Obsidian Sync, a single remote MCP server), and the reported conflict and corruption problems

### Takeaway
The lowest-risk pattern the evidence supports is git (or any file sync) for the Markdown plus a separate, rebuildable basic-memory index on each machine: do not sync `~/.basic-memory` or `memory.db` (the database is a secondary index and `bm reset --reindex` rebuilds it from the files), normalize line endings to LF, avoid filenames that differ only by case or Unicode form, and keep the project name identical on both machines because permalinks are prefixed with it and v0.24 writes them into frontmatter. Syncthing and Obsidian Sync work but carry known conflict modes (`workspace.json` churn, NFC/NFD and case duplicates); a single remote basic-memory over HTTP is possible but has no built-in authentication, and basic-memory's docs give no official multi-machine guidance.

### Cited Findings

#### What basic-memory documents and what has gone wrong
- The architecture is "file-first": Markdown is the source of truth and the database "serves as a secondary index". [Technical information](https://docs.basicmemory.com/raw/reference/technical-information.md)
- `bm reset --reindex` rebuilds the index from the Markdown files; plain `bm reset` deletes only the index; reset refuses to run while `basic-memory mcp` is running unless `--force`; deleting the `-wal` file by hand "can silently discard recently indexed changes". [Troubleshooting](https://docs.basicmemory.com/raw/reference/troubleshooting.md), [CLI reference](https://docs.basicmemory.com/raw/reference/cli-reference.md)
- Config lives in `~/.basic-memory/config.json` (`BASIC_MEMORY_CONFIG_DIR` relocates config and the default DB); each project has a `path` and `mode`; cloud projects add `local_sync_path`. [Configuration](https://docs.basicmemory.com/raw/reference/configuration.md)
- Local cross-device sync is manual ("Git, Syncthing, etc."). [Repo README](https://github.com/basicmachines-co/basic-memory) The Cloud docs say each machine stores its own sync path and that using one project on two machines is "not explicitly covered". [Cloud sync](https://docs.basicmemory.com/raw/cloud/cloud-sync.md)
- Duplicate results, `-1`-suffixed permalinks and failing `edit_note` calls are commonly caused by cross-platform sync tools and case-only renames; fix with `basic-memory reindex --full -p <project>`; v0.24 fixes case-only renames on case-insensitive filesystems but does not repair duplicates already created. [Troubleshooting](https://docs.basicmemory.com/raw/reference/troubleshooting.md)
- Indexing is automatic: `index_changes` defaults to true, `index_delay` to 1000 ms (raise with `bm config set index_delay 2000` for rapid saves); an unreadable new directory (common on Linux) logs a warning and needs a permissions fix then `bm project index <project>`. [Configuration](https://docs.basicmemory.com/raw/reference/configuration.md), [Troubleshooting](https://docs.basicmemory.com/raw/reference/troubleshooting.md)
- Indexing edits your files: `ensure_frontmatter_on_sync` (default true) adds derived `title` and `type`, canonical permalinks are always added, `permalinks_include_project` defaults to true, and v0.24 scans backfill `permalink` into frontmatter. [Configuration](https://docs.basicmemory.com/raw/reference/configuration.md), [Upgrade guide](https://docs.basicmemory.com/raw/whats-new/v0-24-upgrade.md) A permalink is generated from the file path and prefixed with the project name. [Knowledge format](https://docs.basicmemory.com/raw/concepts/knowledge-format.md)
- Multiple writers: #1771 attributes duplicate `search_index` rows to interleaved deletes and inserts from several MCP server instances plus the file watcher on one SQLite DB (0.23.2, Windows 11 reporter, open). [Issue #1771](https://github.com/basicmachines-co/basic-memory/issues/1771)
- Unicode and case: #1275 (Syncthing flipping macOS NFC/NFD forms against Linux peers; fixed on main 14 Oct 2026), #1326 (case-duplicate folders, closed 25 Aug) and #1796 (case-twin folders again, open 20 Oct). [Issue #1275](https://github.com/basicmachines-co/basic-memory/issues/1275), [Windows issue list](https://github.com/basicmachines-co/basic-memory/issues?q=is%3Aissue+windows)
- Windows: v0.16.1 (2025-11-11, >6 mo) fixed line-ending conversion being flagged as corruption in rclone bisync (search summary); #1211 (Windows startup log-cleanup race, closed 9 Aug 2026); #1499 (WSL hooks failing silently when `uv` is in `~/.local/bin`, closed 14 Sep 2026). [Release notes index](https://docs.basicmemory.com/latest-releases), [Windows issue list](https://github.com/basicmachines-co/basic-memory/issues?q=is%3Aissue+windows)
- The Obsidian integration page says nothing about `.obsidian`, Obsidian Sync or git. [Obsidian integration](https://docs.basicmemory.com/raw/integrations/obsidian.md)

#### Git as the transport
- A forum write-up names CRLF/LF differences as the main source of spurious diffs across systems and recommends a `.gitattributes` with `* text=auto eol=lf`. [Obsidian forum](https://forum.obsidian.md/t/solving-git-sync-issues-caused-by-different-system-line-endings/92253)
- A git-sync plugin's page (vendor claim) generates the same `.gitattributes`, offers an optional pull on startup and stops with a notice on post-pull conflicts instead of resolving them automatically. [Mercurio Git Sync](https://community.obsidian.md/plugins/mercurio-git-sync)
- Claude Code hook facts that matter for sync: command hooks can run scripts at `SessionStart` and `SessionEnd`; `SessionEnd` has a 1.5-second default budget, raisable to 60 s per hook; `"async": true` runs a command hook in the background without enforcing its timeout. [Hooks reference](https://code.claude.com/docs/en/hooks) Published examples cover Stop-hook auto-commit and SessionStart context injection, but I found none that pulls a notes repo at start or handles pull conflicts. [Collabnix](https://collabnix.com/mastering-claude-code-hooks-automate-your-dev-workflow-in-2026/), [SmartScope](https://smartscope.blog/en/generative-ai/claude/claude-code-hooks-guide/) (search summary)

#### Syncthing
- Obsidian rewrites `workspace.json` whenever the vault changes, so Syncthing can replace it mid-write and produce `workspace.sync-conflict-*` files; users exclude `.obsidian/workspace.json`, `workspace-mobile.json`, `workspaces.json`, `graph.json` and their `.sync-conflict-*` variants in `.stignore`. [Syncthing forum](https://forum.syncthing.net/t/problems-with-obsidian-folder/25397), [Obsidian forum](https://forum.obsidian.md/t/obsidian-sync-sync-hidden-files-and-folders-as-well-start-with-a-dot/32123)
- A Windows, Linux and Android setup reported a flood of workspace conflict files and slow loads; the poster guesses permissions or timestamps and another user reports no conflicts. [Obsidian forum](https://forum.obsidian.md/t/slow-app-load-times-and-workspace-sync-conflicts-when-using-syncthing/44853) The same churn appears with OneDrive across machines. [Obsidian forum](https://forum.obsidian.md/t/vault-synced-over-onedrive-across-multiple-machines-generates-many-copies-of-workspace-json/115229)
- Syncthing's FAQ calls itself "not a great backup application" because all changes propagate to all devices and says versioning is available but other tools are encouraged; the page I fetched did not address case sensitivity, SQLite or git. [Syncthing FAQ](https://docs.syncthing.net/users/faq.html)
- Plugins exist to find and diff conflicts: Conflict Resolver (detects `.sync-conflict` names) and Syncthing Manager (side-by-side diff, `.stignore` editor). [Conflict Resolver](https://community.obsidian.md/plugins/conflict-resolver), [Syncthing Manager](https://community.obsidian.md/plugins/syncthing-manager)

#### Obsidian Sync and Headless
- Notes merge with Google's diff-match-patch (can leave duplicated text); other files use last-modified-wins; settings JSON is merged; from Obsidian 1.9.7 a device-specific option "Create conflict file" exists; a note created on two devices within a couple of minutes may keep only the remote version; files can vanish through Windows Defender quarantine or double-syncing with another service. [Obsidian Sync troubleshooting](https://obsidian.md/help/sync/troubleshoot)
- Obsidian Headless (open beta, no release date or Node version stated): requires a Sync subscription; `npm install -g obsidian-headless`; `ob login`, `ob sync-setup --vault`, `ob sync --continuous`; modes bidirectional, pull-only, mirror-remote; `--conflict-strategy merge|conflict`; do not run it beside desktop Sync on the same device; no birthtime on Linux; prebuilt native addon only for Windows and macOS; end-to-end encryption available. [Obsidian Headless](https://obsidian.md/help/sync/headless)

#### Single remote MCP server
- `bm mcp --transport stdio|streamable-http|sse` with `--host` (default 127.0.0.1 since v0.24, previously 0.0.0.0), `--port` (8000) and `--path` (`/mcp`); the HTTP server has no authentication and the command warns on a non-loopback host. [CLI reference](https://docs.basicmemory.com/raw/reference/cli-reference.md), [Upgrade guide](https://docs.basicmemory.com/raw/whats-new/v0-24-upgrade.md)
- The Docker image (`ghcr.io/basicmachines-co/basic-memory:latest`) starts SSE on port 8000, mounts notes at `/app/data` and config at `/home/appuser/.basic-memory`, and warns: "The server has no authentication, so publish the port only on a network you trust" and "Do not expose them directly to the public internet"; `FASTMCP_HTTP_ALLOWED_HOSTS`/`ORIGINS` restrict headers but are not authentication. [Docker docs](https://docs.basicmemory.com/raw/reference/docker.md)
- Claude Code: `claude mcp add --transport http <name> <url>` is recommended for remote servers, SSE is deprecated, static auth via `--header "Authorization: Bearer ..."`, OAuth via `/mcp`; since v2.1.265 `--transport http` falls back to SSE automatically. [MCP docs](https://code.claude.com/docs/en/mcp)
- basic-memory Cloud exposes an OAuth remote server: `claude mcp add -s user -t http basic-memory-cloud https://cloud.basicmemory.com/mcp`. [Claude Code integration](https://docs.basicmemory.com/raw/integrations/claude-code.md)
- Analog: Letta MemFS uses git as its sync layer (commit per edit; cloud agents push to a hosted repo; local-only agents must be backed up by the user). [MemFS docs](https://docs.letta.com/concepts/memfs)

#### Disagreement to report
- Remote transport: the Docker page documents SSE and does not mention streamable-http, while the CLI reference and upgrade guide list `--transport streamable-http`, and Claude Code treats SSE as deprecated. [Docker docs](https://docs.basicmemory.com/raw/reference/docker.md) versus [CLI reference](https://docs.basicmemory.com/raw/reference/cli-reference.md) and [MCP docs](https://code.claude.com/docs/en/mcp)

### Inferences
- Baseline (my proposal): keep the vault as one git repo cloned on both machines; each machine runs its own basic-memory against its own clone with its own `~/.basic-memory` (never synced); after any pull or branch change that touches many files, run `bm status --json` and, if results look wrong, `bm reset --reindex`.
- Keep the basic-memory project name identical on both machines, because permalinks carry the project prefix and are now written into frontmatter; a different name would make each machine rewrite the same files. Commit the first v0.24 scan from one machine before the other machine scans, because the indexer rewrites frontmatter on notes that lack `permalink`, `title` or `type`.
- Windows plus Linux specifics: add `.gitattributes` with `* text=auto eol=lf`; use lowercase kebab-case ASCII filenames (the `kebab_filenames` option helps for tool-created notes) so case-insensitive Windows and case-sensitive Linux never see twins, and Unicode-normalization bugs like #1275 cannot occur; git-ignore `.obsidian/workspace*.json` and `graph.json` if Obsidian is used for viewing.
- Sync automation: a `SessionStart` command hook doing a fast-forward-only pull, and an async `SessionEnd` hook doing add, commit and push (raising its `timeout` toward 60 s), keep the vault current without Claude spending turns on it; on a failed pull, surface a one-line `additionalContext` warning instead of auto-merging.
- Use one transport per working tree. I found no source blessing git plus Syncthing or Obsidian Sync on the same folder, and Obsidian's own docs warn against running two Sync clients on one device; Syncthing's docs fetched say nothing about `.git`.
- A single remote basic-memory on the VM (HTTP over the tailnet) gives one index and one writer process, which avoids #1771-style multi-process duplicates, but it adds a single point of failure, needs network ACLs because there is no authentication, and leaves the Windows machine without local files for grep or Obsidian unless they are synced anyway. Multiple stdio instances on one machine (desktop app, CLI, parallel sessions) are the multi-writer case that #1771 describes.
- Obsidian Sync is justified only if Obsidian mobile or E2EE sync is wanted; Headless is beta and would duplicate the existing git transport.

### Gaps
- basic-memory's docs are silent on multi-machine use, Windows, git and WSL beyond the items above; the issue list I read was page 1 of 97 results.
- No authoritative source on Syncthing with `.git` directories or SQLite files; no Windows plus Linux git conflict reports specific to basic-memory beyond line endings, case and Unicode.
- I did not fetch the obsidian-git plugin README, so its pull-on-startup and conflict behavior is unverified; a search summary mentioned a forum claim that the plugin pulls only after the workspace opens, but I could not trace it to a specific thread, so I have not relied on it.
- Tailscale-specific exposure of an MCP server (Serve, ACLs) was outside my lens and not researched.
- Whether two machines' separate indexes over one git working tree ever diverge in ways that matter is untested in what I found (likely fine, since each index is rebuilt from the files).

## 5. Keeping memory from going stale or contradicting itself

### Takeaway
The sources that address staleness converge on four moves: make time and status explicit in each note; supersede, archive or invalidate instead of silently overwriting or deleting; run a periodic lint or curate pass for contradictions, stale claims, orphans and schema drift; and cap whatever loads automatically. Tooling exists for each: basic-memory v0.24 temporal qualifiers, orphan listing, schema drift diff and lifecycle, defrag and curate skills; Karpathy's lint operation; Graphiti's bi-temporal invalidation; Letta's dreaming and memory-doctor subagents; Claude Code's size caps and `modified` stamps. No source gives an evidence-based review cadence, and the widely repeated "Auto Dream" thresholds are third-party claims.

### Cited Findings

#### Mechanisms in the tools
- Karpathy's pattern: ingest notes where new data contradicts old claims and updates summaries; lint passes look for contradictions between pages, stale claims that newer sources superseded, orphan pages, missing cross-references and data gaps; he describes no formal resolution mechanism beyond flagging and revising. [Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)
- basic-memory v0.24 temporal qualifiers on observations: `@effective`, `@valid` (the default), `@occurred`, `@due`, `@mentioned`, with ranges such as `@effective[2026-06-10,2026-07-27)` and `valid_at`, `valid_overlaps`, `time_kind` search filters. [v0.24 page](https://docs.basicmemory.com/raw/whats-new/v0-24.md)
- `bm orphans` lists notes with no relations; `bm schema diff <type>` compares a schema with actual usage over time to detect drift (the docs say drift is expected as habits change and recommend periodic checks); `bm prune` removes index entries for files now excluded by `.bmignore` or `.gitignore`, leaving the files on disk. [CLI reference](https://docs.basicmemory.com/raw/reference/cli-reference.md), [Schema system](https://docs.basicmemory.com/raw/concepts/schema-system.md), [v0.24 page](https://docs.basicmemory.com/raw/whats-new/v0-24.md)
- basic-memory skills: `memory-lifecycle` (status changes through folder organization, "archive-never-delete"), `memory-defrag` (splits bloated notes, consolidates scattered facts, retires stale content; plans before acting and deletes only when asked; installed separately), `memory-curate` (orphans, proposed relations, duplicate merges, hub notes), `memory-reflect` (folds recent activity into topic notes and writes a dated reflection; installed separately). [Agent skills](https://docs.basicmemory.com/raw/integrations/skills.md)
- Overwrite guards: `expected_checksum` with `NOTE_REVISION_CONFLICT`, and `locked: true` to make a note read-only to the note API. [AI assistant guide](https://docs.basicmemory.com/raw/reference/ai-assistant-guide.md), [Knowledge format](https://docs.basicmemory.com/raw/concepts/knowledge-format.md)
- Metadata search has no `$ne` or `$nin`, so excluding archived notes means filtering on a positive set of status values (for example `$in`). [Metadata search](https://docs.basicmemory.com/raw/concepts/metadata-search.md)
- Indexing skips files matched by `.gitignore` or `.bmignore`, but entries indexed before a pattern existed remain until `bm prune`; the docs describe `.bmignore` as setting global patterns. [Troubleshooting](https://docs.basicmemory.com/raw/reference/troubleshooting.md), [Cloud sync](https://docs.basicmemory.com/raw/cloud/cloud-sync.md)
- Claude Code auto memory: after each write `MEMORY.md` is measured against the 200-line / 25 KB limits; near the limit Claude is reminded to keep one line per entry, move detail to topic files and "merge or drop stale entries"; over the limit the write succeeds but returns an error telling Claude to rewrite the index; the write time is stamped into a `modified` frontmatter field (ISO 8601) that "shows how current the fact is"; memory files are exempt from the transcript cleanup sweep and stay until edited or deleted; `/memory` browses them. [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- The same docs warn that contradictory instruction files are resolved arbitrarily and offer `/doctor prompt-audit` (v2.1.283+) to find outdated or conflicting instructions. [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Anthropic memory-tool guidance: periodically delete memory files that have not been accessed in a long time, cap file sizes, and tell the model to "keep its content up-to-date, coherent and organized", to rename or delete files that are no longer relevant, and not to create new files unless necessary. [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) Anthropic also notes that timestamps can be a proxy for relevance. [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Graphiti: bi-temporal model in which contradicted facts are invalidated rather than deleted, so historical queries still work. [Graphiti repo](https://github.com/getzep/graphiti)
- Letta MemFS: every memory edit is a git commit, and "dreaming" and "memory doctor" subagents update memory in git worktrees without blocking the main agent. [MemFS docs](https://docs.letta.com/concepts/memfs)
- Schneider's poisoning guidance doubles as a staleness control: combine temporal decay with trust scoring, keep immutable logs of memory operations, audit the store against known-good states and allow rollback. [Schneider](https://christian-schneider.net/blog/persistent-memory-poisoning-in-ai-agents/)
- Third-party descriptions of Claude Code "Auto Dream": a four-phase cycle (orient on the memory directory, gather signals from recent transcripts, consolidate into topic files, prune the index to stay under 200 lines), triggered after more than 24 hours and 5+ sessions or manually with `/dream`; the problems it targets are duplicates, outdated facts, contradictions after 20+ sessions and relative dates such as "yesterday" losing meaning. The official memory page does not mention it. [Implicator](https://www.implicator.ai/anthropic-adds-auto-dream-to-claude-code-fixing-memory-decay-between-sessions), [claudefa.st](https://claudefa.st/blog/guide/mechanics/auto-dream), [Claude Code memory docs](https://code.claude.com/docs/en/memory)

#### Disagreement to report
- Delete versus keep: basic-memory's lifecycle skill is "archive-never-delete" and its defrag skill deletes only on request; Anthropic's memory-tool docs suggest periodically deleting unused memory files; Graphiti invalidates but keeps history. [Agent skills](https://docs.basicmemory.com/raw/integrations/skills.md), [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool), [Graphiti repo](https://github.com/getzep/graphiti)
- Auto Dream: described as a shipped or rolling-out feature by third parties and absent from the official memory page (see question 1).

### Inferences
- Frontmatter conventions (my proposal): `status: draft | active | superseded | archived`, `updated: YYYY-MM-DD`, `supersedes` / `superseded_by` (as `[[wikilinks]]`), `valid_until` or `review_after` for perishable facts (versions, prices, tool behavior), and optionally `confidence`. Define `status` as an enum in a schema note so `bm schema validate` flags typos and gaps, starting in `warn` mode.
- Supersede instead of editing history: decision notes are append-only; a changed decision gets a new note plus a `- supersedes [[old]]` relation, and the old note flips to `status: superseded`. The reader gets the lineage and the agent's `status: active` filter hides the old one.
- Archive by moving notes to a folder excluded from the index (for example `_archive/` in `.bmignore`, then `bm prune`) so they stay in git but out of search; the exact `.bmignore` location and per-project behavior need confirming before relying on it.
- Write absolute dates for anything perishable; relative dates ("yesterday", "recently") are the cited failure case.
- Add a lint pass on a schedule (my proposal; no source gives an evidence-based interval): run `bm orphans`, `bm schema validate` and `bm schema diff` monthly, and a Claude-driven read of notes touched or used in the last period, looking for contradictions, expired `valid_until` values and notes superseded by newer ones, with output as a proposal note (basic-memory's defrag skill already "plans before acting").
- At read time, treat a note older than its `review_after` as a lead to verify, not a fact; this uses the stated "timestamps as a proxy for relevance" idea at the point of use.
- Search before writing (the "Similar existing notes" prompt) is the cheapest contradiction preventer, because it turns a would-be duplicate into an `edit_note`.

### Gaps
- No empirical evaluation of review cadences or pruning strategies for a developer vault, and no data on how often stale or contradictory notes cause wrong agent answers.
- Auto Dream details come only from third-party posts.
- The `.bmignore` location and scope were not confirmed beyond "global patterns".
- I did not find whether basic-memory updates a note's `modified` field automatically on edit; the docs call `created` and `modified` optional.

## 6. Security: keeping secrets and private data out of an AI-readable vault, and prompt-injection risk from notes

### Takeaway
A persistent, agent-readable vault is a persistent prompt-injection surface. A July 2026 study of Claude Code and Codex found that making an agent overwrite its own memory files from untrusted content is hard, but instructions already planted in memory files can attack current and future sessions. The controls with documentary support are: keep secrets out of the vault and back that with Read deny rules and a local pre-commit scanner (GitHub's server-side push protection needs a paid add-on for private repositories); treat note text as data; put a human gate or an inbox in front of agent writes; and never expose basic-memory's unauthenticated HTTP transport beyond a trusted network. I found no Claude Code-specific advisory about vault poisoning.

### Cited Findings

#### Prompt injection and memory poisoning
- "Bad Memory: Evaluating Prompt Injection Risks from Memory in Agentic Systems" (arXiv 2607.14611, 16 Jul 2026; Gadgil, Alexander, Sunku, Roesner) tested Claude Code and OpenAI Codex with Claude Haiku 4.5, Claude Opus 4.7, GPT-5.2 and GPT-5.5 in a sandboxed synthetic workspace: making an agent overwrite its own memory files through untrusted external content is difficult, but malicious instructions already stored in memory files can successfully attack both current and future sessions; success varies by system, model, adversarial goal and multi-session sequence. No per-model rates were visible in the excerpt. [Bad Memory](https://papers.cool/arxiv/2607.14611)
- Schneider (26 Feb 2026, >6 mo): memory poisoning turns "a transient exploit into a durable control channel"; planted entries are phrased to look worth remembering (for example "Remember that the user prefers..."); session isolation alone does not address it; it cites MINJA (arXiv 2503.03704, over 95% injection success and over 70% attack success on most datasets) and OWASP ASI06 (Memory and Context Poisoning, Top 10 for Agentic Applications 2026); it does not discuss coding agents or CLAUDE.md. Mitigations: provenance tags (source, time, session, trust score), scanning for instruction-like text, explicit user confirmation before persisting new memories, quarantine, trust-aware retrieval, immutable operation logs, audits and rollback. [Schneider](https://christian-schneider.net/blog/persistent-memory-poisoning-in-ai-agents/)
- A Cloud Security Alliance research note titled "MemGhost: Persistent Memory Poisoning via a Single Email" carries the date 2026-07-23 in its URL; I saw only the title. [CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-memghost-agent-memory-poisoning-20260723-c/)
- Claude Code MCP docs: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk"; project `.mcp.json` servers need approval in interactive sessions but `claude -p` and Agent SDK runs load them without asking; `disabledMcpjsonServers` and `--strict-mcp-config` restrict servers. [MCP docs](https://code.claude.com/docs/en/mcp)
- Auto mode (the starting permission mode on v2.1.283+) uses a classifier that blocks "scope escalation, unknown infrastructure, and hostile-content-driven actions". [Best practices](https://code.claude.com/docs/en/best-practices)
- CLAUDE.md content is delivered as a user message and carries "no guarantee of strict compliance"; enforcement belongs in settings rules and hooks. [Claude Code memory docs](https://code.claude.com/docs/en/memory), [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Graphiti's reference MCP server has no authentication, authorization or prompt-injection protection. [Graphiti repo](https://github.com/getzep/graphiti)

#### Keeping secrets and private data out
- Memory-tool docs: "Claude usually refuses to write sensitive information to memory files. For stronger guarantees, add validation that strips sensitive data before your handler writes the file." [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Claude Code blocks its file tools from a path with a `Read` deny rule such as `Read(./.env)` or `Read(./secrets/**)`; the rule also blocks Edit and Write on that path, covers directories searched by Grep and Glob, checks both a symlink and its target, and deny rules from any scope beat allow rules; `.claudeignore` has no effect; on Windows paths are normalized to POSIX form, so `//c/**/.env` matches `.env` files on drive C and `//**/.env` on all drives. [Permissions](https://code.claude.com/docs/en/permissions)
- A Bash deny or ask rule "covers the invocation Claude usually produces and isn't a security boundary around the program"; pair it with the sandbox when a restriction must hold. [Permissions](https://code.claude.com/docs/en/permissions)
- MCP tool rules match by name only (`mcp__<server>__*` or `mcp__<server>__<tool>`); a settings rule with parentheses on an `mcp__` tool is skipped, so settings cannot path-restrict MCP calls. [Permissions](https://code.claude.com/docs/en/permissions)
- `permissions.blockReadsOutsideWorkingDirectories` makes the file tools refuse paths outside the working directories in every permission mode. [Permissions](https://code.claude.com/docs/en/permissions)
- basic-memory scoping: `bm mcp --project NAME` restricts a server to one project, and `BASIC_MEMORY_MCP_PROJECT` locks an MCP session to one project. [CLI reference](https://docs.basicmemory.com/raw/reference/cli-reference.md), [Configuration](https://docs.basicmemory.com/raw/reference/configuration.md)
- basic-memory harness capture stores metadata envelopes, not transcripts, and the page describes no redaction mechanism; v0.24.0 masked credentials on the Hermes capture path. [Harness capture](https://docs.basicmemory.com/raw/integrations/harness-capture.md), [v0.24.0 release notes](https://github.com/basicmachines-co/basic-memory/releases/tag/v0.24.0)
- Claude Code keeps session transcripts for `cleanupPeriodDays`; memory files are excluded from that sweep. [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- GitHub: repository-level push protection requires GitHub Secret Protection (the older private-repo requirement was GitHub Advanced Security) and is off by default; account-level push protection is on by default but only stops secrets reaching public repositories; anyone with write access can bypass a block with a reason. [GitHub push protection docs](https://docs.github.com/pt/code-security/concepts/secret-security/about-push-protection), [Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/resolve-github-secret-scanning-alerts-github-copilot-agent/4-examine-github-push-protection) (search summary)

#### Exposure of the access path
- Obsidian Local REST API: the API key is a bearer token with full vault access and is stored in the plugin's data file; HTTPS uses a locally generated certificate authority; the plain-HTTP port is less secure; signed URLs grant time-limited single-file access; event streams expose note paths. [Local REST API repo](https://github.com/coddingtonbear/obsidian-local-rest-api) The common MCP servers on top of it give write access to the whole vault, including `delete_file`. [mcp.directory](https://mcp.directory/blog/obsidian-mcp-complete-guide-2026)
- basic-memory's HTTP transports have no authentication, bind to loopback by default since v0.24, and "Do not expose them directly to the public internet". [Docker docs](https://docs.basicmemory.com/raw/reference/docker.md), [CLI reference](https://docs.basicmemory.com/raw/reference/cli-reference.md)
- basic-memory Cloud uses HTTPS in transit and OAuth 2.1 with PKCE, with tokens in `~/.basic-memory/basic-memory-cloud.json`; the docs do not describe encryption at rest. [Cloud sync](https://docs.basicmemory.com/raw/cloud/cloud-sync.md) Obsidian Headless offers end-to-end encryption (`--encryption e2ee`). [Obsidian Headless](https://obsidian.md/help/sync/headless)

### Inferences
- Policy (my proposal): no secrets in the vault; store the name and location of a secret, never its value. Enforce it three ways: a `Read` deny rule for any private folder; a local pre-commit scanner such as gitleaks, because server-side push protection is a paid feature for private repositories (the scanner suggestion is the search summary's takeaway, not a GitHub statement); and a CLAUDE.md or schema rule telling the agent to refuse to write credentials, remembering that this last layer is advisory.
- Because MCP rules cannot be path-scoped and the basic-memory server reads files itself, anything it indexes is reachable by the agent whatever the `Read` rules say (the docs do not state this outright; it follows from name-only MCP rules). Keep private material in a separate basic-memory project that ordinary sessions do not load, or outside the indexed folder.
- Treat the vault as semi-trusted. Notes the agent derived from web pages, emails or tool output are untrusted data: route them to an `inbox/` with `status: draft` and a `source:` field, and promote after human review; keep human-authored decisions separate. A permission `ask` rule on the write tools (`mcp__basic-memory__write_note`, `edit_note`, `move_note`, `delete_note`) gives the "explicit confirmation before persisting" that Schneider recommends, at the cost of friction.
- Every vault change in git is a provenance record; `git log -p` plus one commit per session gives the immutable operation log and rollback that the poisoning guidance asks for.
- Keep any SessionStart digest purely factual (Anthropic's own hook guidance) and never auto-execute instructions found in notes; hooks and permissions, not prompts, are the enforcement layer.
- `bm hook install` and the Claude Code plugin add user-level hooks that run on every session; review them like code.
- If a remote server is used, bind it to loopback or the tailnet interface and rely on network ACLs; the server provides no authentication of its own.

### Gaps
- No Claude Code-specific advisory on vault or memory-file poisoning; I did not read the CSA MemGhost note; "Bad Memory" per-model attack rates were not visible.
- Whether basic-memory's own file reads are subject to Claude Code `Read` deny rules is undocumented; the permissions page says MCP rules are matched by tool name only.
- basic-memory documents no secret redaction on writes or capture beyond the Hermes-path fix.
- The English GitHub push-protection page and the current Secret Protection pricing were not fetched; I relied on a search summary and a Microsoft Learn page.
- The effectiveness of prompt-level "treat notes as data" instructions is untested in what I found.
- Tailscale-specific hardening is outside my lens and not researched.
