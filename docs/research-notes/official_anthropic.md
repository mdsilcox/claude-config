## Inventory of every configuration surface and Anthropic's recommended use of each

### Takeaway
Claude Code now has about 20 extension and configuration surfaces; Anthropic's stated pattern is to start with CLAUDE.md, add surfaces only when a specific trigger recurs, and put anything that must happen every time in a hook or a permission rule rather than in prose. Most surfaces layer (CLAUDE.md and hooks add up, skills and subagents override by name, settings follow managed > command line > local > project > user).

### Cited Findings
**File and directory map (what lives where)**
- Project files committed to git: `CLAUDE.md` (or `.claude/CLAUDE.md`), `.claude/rules/*.md`, `.claude/settings.json`, `.mcp.json`, `.worktreeinclude`, `.claude/skills/<name>/SKILL.md`, `.claude/commands/*.md` (same mechanism as skills), `.claude/output-styles/*.md`, `.claude/agents/*.md`, `.claude/workflows/*.js`, `.claude/agent-memory/<name>/`. Not committed: `.claude/settings.local.json`, `CLAUDE.local.md`. User scope under `~/.claude/` (on Windows `%USERPROFILE%\.claude`): same folders plus `keybindings.json`, `themes/*.json`, `projects/<project>/memory/` (auto memory), and `~/.claude.json` (app state, account, personal-scope MCP servers) - [Explore the .claude directory](https://code.claude.com/docs/en/claude-directory)
- `CLAUDE_CONFIG_DIR` relocates every `~/.claude` path; Claude Desktop, VS Code and JetBrains also write to `~/.claude/`; transcripts under `~/.claude/projects/` are plaintext and swept after `cleanupPeriodDays` (default 30, minimum 1) - [Explore the .claude directory](https://code.claude.com/docs/en/claude-directory)
- `claude purge <path>` (formerly `claude project purge`, renamed in v2.1.288) deletes one project's local state with a dry-run option - [Explore the .claude directory](https://code.claude.com/docs/en/claude-directory)

**Memory (CLAUDE.md, CLAUDE.local.md, rules, imports, AGENTS.md, auto memory)**
- Four CLAUDE.md scopes, loaded broadest to most specific: managed policy (macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`, Linux/WSL `/etc/claude-code/CLAUDE.md`, Windows `C:\Program Files\ClaudeCode\CLAUDE.md`), user `~/.claude/CLAUDE.md`, project `./CLAUDE.md` or `./.claude/CLAUDE.md`, local `./CLAUDE.local.md` (gitignore it) - [Memory](https://code.claude.com/docs/en/memory)
- Files from the working directory and every parent load at launch and are concatenated (root first, so the file nearest the working directory is read last); subdirectory CLAUDE.md files load on demand when Claude reads or edits a file there - [Memory](https://code.claude.com/docs/en/memory)
- `@path/to/file` imports (relative to the importing file, max four hops deep); imports do not reduce context cost; block-level HTML comments are stripped before injection; `claudeMdExcludes` (any settings layer, arrays merge) skips files by glob - [Memory](https://code.claude.com/docs/en/memory)
- `.claude/rules/**/*.md` supports `paths:` frontmatter (the only field read) for path-scoped loading; `~/.claude/rules/` holds user-level rules that load before project rules; rules directories accept symlinks - [Memory](https://code.claude.com/docs/en/memory)
- AGENTS.md: since v2.1.277 (2026-09-18) Claude reads `AGENTS.md` only when no `CLAUDE.md`/`CLAUDE.local.md` exists in or above the working directory; `/config` > "Project instructions" values `claude-md-or-agents-md` (default), `claude-md-and-agents-md`, `claude-md`, `managed-only`; or write `@AGENTS.md` inside CLAUDE.md - [Memory](https://code.claude.com/docs/en/memory); [Changelog](https://code.claude.com/docs/en/changelog)
- Auto memory: Claude writes `~/.claude/projects/<project>/memory/MEMORY.md` plus topic files (types `user`, `feedback`, `project`, `reference`); first 200 lines or 25KB of MEMORY.md load each session; on by default locally; toggle in `/memory` (`autoMemoryEnabled`), `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, relocate with `autoMemoryDirectory`; machine-local, shared across worktrees of one repo - [Memory](https://code.claude.com/docs/en/memory)
- Subagents can keep their own memory via the `memory` frontmatter field (`user`, `project`, or `local` scope) - [Subagents](https://code.claude.com/docs/en/sub-agents)

**Skills** - [Skills](https://code.claude.com/docs/en/skills)
- Locations: `~/.claude/skills/`, `.claude/skills/`, nested `<subdir>/.claude/skills/`, plugin `skills/` (namespaced `/plugin:skill`), and claude.ai-account skills synced one-way into `~/.claude/skills/synced/` (opt out with `syncClaudeAiSkills: false`). Name collisions: enterprise > personal > project.
- Frontmatter: `name`, `description`, `when_to_use` (description plus when_to_use truncated at 1,536 characters in the listing), `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools` (pre-approves for the invoking turn only), `disallowed-tools`, `model`, `effort`, `context: fork`, `agent`, `background`, `hooks`, `paths`, `shell`, `metadata`.
- Keep SKILL.md under about 500 lines; after auto-compaction only the first 5,000 tokens of each invoked skill are re-attached within a 25,000-token total budget (most recent first).
- `` !`command` `` injection runs before Claude sees the skill (disable with `disableSkillShellExecution`); `skillOverrides` (`on`, `name-only`, `user-invocable-only`, `off`) hides skills without editing them; `/skill-doctor` (v2.1.252+) reports context cost and usage per skill.
- Bundled skills: `/doctor` (alias `/checkup`; `/doctor prompt-audit` v2.1.283+), `/run`, `/verify`, `/run-skill-generator`, `/claude-api`, `/code-review` (alias `/review`), `/debug`, `/loop`, `/batch`, `/simplify`, `/workflow-authoring`, `/skill-doctor`, `/fewer-permission-prompts`; a custom skill named `verify` or `simplify` makes Claude run it before each non-doc, non-test commit (v2.1.286+).
- `.claude/commands/x.md` and `.claude/skills/x/SKILL.md` both create `/x`; if both exist the skill wins.

**Subagents** - [Subagents](https://code.claude.com/docs/en/sub-agents)
- Built-ins: Explore (read-only, skips CLAUDE.md), Plan, general-purpose, claude (default for dispatched background sessions), statusline-setup (Sonnet), claude-code-guide (Haiku).
- Files: managed > `--agents` JSON > `.claude/agents/` > `~/.claude/agents/` > plugin `agents/`; hot-reloaded. Fields: `name`, `description` (required), `tools`, `disallowedTools`, `model` (`sonnet`, `opus`, `haiku`, `fable`, full ID, `inherit`), `permissionMode`, `maxTurns`, `autoCompactWindow` (v2.1.296+), `skills` (fully preloaded), `mcpServers`, `hooks`, `memory`, `background`, `omitClaudeMd` (v2.1.271+), `effort`, `isolation: worktree`, `color`, `initialPrompt`.
- Model resolution: per-invocation parameter, then frontmatter `model`, then `CLAUDE_CODE_SUBAGENT_MODEL`, then the main model (`CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` forces one model, v2.1.257+).
- Subagents spawned by Claude run in the background by default; fork mode (inherits the full conversation) is on by default in interactive sessions since v2.1.232; nesting depth default is three (v2.1.219+); concurrency default is 20 (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`); a non-fork subagent does not inherit conversation history, invoked skills, auto memory or output style.

**Hooks** - [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Handler types: `command`, `http`, `mcp_tool`, `prompt` (single-turn LLM check), `agent` (multi-turn, experimental, 60 s default timeout, up to 50 turns). Event list: SessionStart, Setup, UserPromptSubmit, UserPromptExpansion, PreToolUse, PermissionRequest, PermissionDenied, PostToolUse, PostToolUseFailure, PostToolBatch, Notification, MessageDisplay, SubagentStart/Stop, TaskCreated/Completed, Stop, StopFailure, TeammateIdle, InstructionsLoaded, ConfigChange, CwdChanged, DirectoryAdded, FileChanged, WorktreeCreate/Remove, PreCompact/PostCompact, PreModelSwitch/PostModelSwitch, Elicitation/ElicitationResult, SessionEnd.
- Exit code 2 blocks (stderr goes to Claude); exit 0 with JSON gives structured control; `if` field uses permission-rule syntax (tool events only); a PreToolUse `deny` holds even in `bypassPermissions`; a Stop hook is overridden after 8 consecutive blocks (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`); `onFailure: "block"` added v2.1.295; hooks run in non-interactive shells so profile `echo` output corrupts JSON; Windows needs Git Bash or the `"args": []` exec form.
- Locations: `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed settings, plugin `hooks/hooks.json`, skill frontmatter, subagent frontmatter; `/hooks` browses them; `disableAllHooks`, `allowManagedHooksOnly` to restrict.

**Settings hierarchy** - [Settings](https://code.claude.com/docs/en/settings)
- Precedence, highest first: managed settings, command line (`--settings`), `.claude/settings.local.json`, `.claude/settings.json`, `~/.claude/settings.json`. List keys such as `permissions.allow` merge across files; a deny at any level wins. Env vars are not a level (per-pair rules). `/status` shows loaded sources; `claude doctor` lists rejected entries. Settings files are strict JSON (no comments); use `"$schema": "https://json.schemastore.org/claude-code-settings.json"`.
- `defaultMode` values `auto` and `bypassPermissions` are ignored from project and local settings; set them in user settings or pass `--permission-mode` - [Settings](https://code.claude.com/docs/en/settings); [Permission modes](https://code.claude.com/docs/en/permission-modes)

**Permission modes** - [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Six modes: `default` (UI label Manual; alias `manual`), `acceptEdits`, `plan`, `auto`, `dontAsk` (never in the Shift+Tab cycle; CLI only), `bypassPermissions`. Shift+Tab cycles; `--permission-mode`, `permissions.defaultMode`, `disableAutoMode`, `disableBypassPermissionsMode` control availability.
- Built-in starting mode: `auto` in terminal and VS Code since v2.1.283; `claude -p` and the Agent SDK start in `default` since v2.1.302.

**Auto mode** - [Permission modes](https://code.claude.com/docs/en/permission-modes); [Configure auto mode](https://code.claude.com/docs/en/auto-mode-config)
- A separate classifier reviews actions; pauses after 3 consecutive or 20 total blocks; drops broad allow rules on entry (`Bash(*)`, wildcarded interpreters, `Agent`, `Monitor`); tune with `autoMode.environment`, `allow`, `soft_deny`, `hard_deny` (include `"$defaults"`), `autoMode.classifyAllShell`; `/auto-mode-setup`; `claude auto-mode defaults|config|critique|reset`; classifier model override `CLAUDE_CODE_AUTO_MODE_MODEL` (v2.1.302+). `autoMode` is read only from user settings, managed settings or `--settings`, never from project files.

**Sandbox** - [Sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing)
- Seatbelt on macOS, bubblewrap + socat on Linux/WSL2, native Windows not supported. Enable with `/sandbox` or `sandbox.enabled`; key settings `autoAllowBashIfSandboxed`, `failIfUnavailable`, `allowUnsandboxedCommands`, `filesystem.allowWrite|denyWrite|denyRead|allowRead`, `network.allowedDomains|deniedDomains`, `excludedCommands`, `credentials`. Open runtime: `@anthropic-ai/sandbox-runtime`.

**Plugins, marketplaces, mods** - [Plugins overview](https://code.claude.com/docs/en/plugins/overview); [Anthropic's marketplaces](https://code.claude.com/docs/en/plugins/anthropic-marketplaces); [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)
- A plugin is a directory with `.claude-plugin/plugin.json` bundling skills, agents, hooks, MCP servers, LSP servers, output styles, themes, monitors, workflows. Install scopes user/project/local. Official marketplace `claude-plugins-official` is auto-added on first interactive run; community (`claude-community`) and demo (`claude-code-plugins`) are opt-in. Enabled plugins add their skill/agent descriptions to every turn; official plugins show a "Context cost" estimate.
- Settings: `enabledPlugins`, `extraKnownMarketplaces`; commands `/plugin`, `claude plugin install|uninstall|update|enable|disable|validate|eval`, `/reload-plugins`, `--plugin-dir` (folders, `.zip`), `--plugin-url`. `claude plugin eval` (v2.1.269) scores a plugin against test cases with a no-plugin baseline.
- Mods (v2.1.287, 2026-10-01): plugins whose JS/TS handlers run inside Claude Code and can draw panes, add `/commands`, and rewrite or answer tool calls and prompts; not sandboxed, run with user permissions; some built-ins (`cc-plugin-agents-md`, `cc-plugin-diff`, `cc-plugin-you-should-know`) are mods.

**MCP** - [MCP](https://code.claude.com/docs/en/mcp)
- Scopes: local (default, in `~/.claude.json` per project), project (`.mcp.json`, committed), user (`~/.claude.json`); precedence local > project > user > plugin > claude.ai connectors. `claude mcp add --transport http|sse|stdio --scope ... --env ... --header ...`, `claude mcp login|logout|list|get|remove`, `/mcp`. `.mcp.json` supports `${VAR}` and `${VAR:-default}` expansion.
- Tool search is on by default (names and server instructions load; schemas deferred); `ENABLE_TOOL_SEARCH` values `true`, `false`, `auto`, `auto:N`; per-server `"alwaysLoad": true`. Output warning at 10,000 tokens, default cap 25,000 (`MAX_MCP_OUTPUT_TOKENS`). MCP tasks (beta, v2.1.304+) background tool calls over two minutes.

**Output styles, status line, checkpoints, plan mode**
- Output styles: Default, Proactive, Concise (v2.1.237), Explanatory, Learning, or custom `~/.claude/output-styles/*.md` / `.claude/output-styles/*.md` with `keep-coding-instructions`; `/output-style` or `outputStyle` setting (case-sensitive) - [Output styles](https://code.claude.com/docs/en/output-styles)
- Status line: `statusLine` setting (`type: "command"`, `command`, `padding`, optional `refreshInterval` in seconds, `hideVimModeIndicator`); script gets JSON on stdin including `model`, `context_window.used_percentage`, `cost.total_cost_usd`, `effort.level`, `rate_limits.five_hour|seven_day.used_percentage` and `resets_at` (Pro and Max only), `workspace`, `worktree`, `prompt_cache` - [Status line](https://code.claude.com/docs/en/statusline)
- Checkpoints: every turn-starting prompt creates one (100 most recent kept); `/rewind` or Esc Esc offers restore code, restore conversation, restore both, summarize from here, summarize up to here; tracks only Claude's file-edit tools (not Bash-only changes, not subagent edits) - [Checkpointing](https://code.claude.com/docs/en/checkpointing)
- Plan mode: Shift+Tab, `/plan`, or `--permission-mode plan`; approval options include "Yes, and use auto mode"; Ctrl+G edits the plan; the plan file is re-injected after compaction - [Permission modes](https://code.claude.com/docs/en/permission-modes); [Context window](https://code.claude.com/docs/en/context-window)

**Parallel and background work** - [Run agents in parallel](https://code.claude.com/docs/en/agents)
- Five approaches: subagents, agent view (research preview, `claude agents`, `claude --bg`, `/bg`), agent teams (experimental, off by default, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), Projects (cloud, public beta on Pro and Max), dynamic workflows. Support tools: worktrees (`claude --worktree <name>`), cross-session messaging (v2.1.224), `/batch` (5 to 30 worktree-isolated subagents).
- Background sessions auto-move into their own worktree before editing (`worktree.bgIsolation: "none"` disables) - [Agent view](https://code.claude.com/docs/en/agent-view)

### Inferences
- A solo developer needs only a small subset day to day: CLAUDE.md, a handful of skills, `.claude/settings.json` permissions, 2 to 4 hooks, one or two custom subagents, and LSP plugins; the rest (agent teams, mods, managed settings, gateways) is team or enterprise machinery.
- Because `~/.claude` is shared by the CLI, the Desktop Code tab, VS Code and JetBrains on the same machine, one user-level configuration on Windows serves both of the user's local surfaces; the Ubuntu `dev` VM needs its own `~/.claude` (or a synced repo of it) since cloud and remote machines do not read the Windows user files.
- A from-scratch layout that follows only the cited recommendations: user scope = a short `~/.claude/CLAUDE.md` (personal preferences), `~/.claude/settings.json` (model, effort, status line, `permissions.defaultMode: "auto"`, deny rules for secrets, a notification hook), a few personal skills and subagents; project scope = a concise committed `CLAUDE.md` (commands, conventions, gotchas), `.claude/settings.json` (allow/ask/deny rules, format-on-edit and protected-file hooks, LSP plugin enablement), `.claude/rules/` with `paths:` for language-specific guidance, skills for multi-step procedures, and `.claude/settings.local.json` for personal overrides; add agent teams, mods, managed settings or gateways only if a specific trigger appears. This is a synthesis (inference), not an Anthropic-published template.

## Where Claude Code runs: Desktop app, web/cloud, Remote Control, mobile, scheduled tasks, GitHub Actions, headless mode, Agent SDK

### Takeaway
Every surface except Desktop-on-Windows sandboxing and a few research previews is available to a Max subscriber; local surfaces (CLI, Desktop, VS Code) share the same `~/.claude` files, while cloud sessions read only the cloned repo's committed config plus account-synced items. Remote Control and Desktop SSH sessions are the official ways to reach a home-lab VM; `claude -p --bare` is the recommended automation entry point.

### Cited Findings
- Desktop app Code tab reads the same settings files as the CLI; environments are Local, Cloud, SSH and WSL; each session can run in its own worktree under `<project>/.claude/worktrees/`; panes for chat, diff, Browser, Terminal, Files, Plan, Tasks, subagent, iOS Simulator (macOS); panes can pop out into their own window (Week 37); preview servers are configured in `.claude/launch.json`; `dontAsk` is CLI-only; `/desktop` (alias `/app`) hands a CLI session to Desktop on macOS or x64 Windows; `/resume` in Desktop picks up CLI sessions (Week 35) - [Desktop](https://code.claude.com/docs/en/desktop); [Commands](https://code.claude.com/docs/en/commands); [What's new index](https://code.claude.com/docs/en/whats-new/index)
- Desktop SSH sessions: remote must be Linux/macOS x86_64 or arm64 with an SFTP subsystem, home not mounted `noexec`, about 1 GB free under `~/.claude/remote/`; Desktop uses `~/.ssh/config` (OpenSSH 7.6+) and installs a helper plus Claude Code on the remote automatically; with Desktop v2.31226.0+ a task keeps running after disconnect; a Claude-account sign-in can expire and stop it; plugins are not available in WSL or cloud sessions; computer use is a research preview for Pro and Max - [Desktop](https://code.claude.com/docs/en/desktop)
- Cloud sessions ("Claude Code on the web"): Pro, Max, Team, and Enterprise premium seats; run on Anthropic-managed VMs (or self-hosted environments); count toward plan limits with no separate VM charge; GitHub required for cloning and PRs; `claude --cloud "task"` (old `--remote` is a deprecated alias), `claude --teleport` / `/teleport` pull a session back; `/web-setup` connects GitHub using your `gh` token; auto-fix watches a PR for CI failures and review comments (`/autofix-pr`); user and local settings are not read in cloud sessions - [Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web); [Settings](https://code.claude.com/docs/en/settings)
- Cloud scheduled tasks (formerly routines, research preview): triggers are schedule, API (`/fire` endpoint with a bearer token and beta header `experimental-cc-routine-2026-04-01`) and GitHub events; created at claude.ai/code/routines or with `/schedule`; expressions more frequent than hourly are rejected; limits of 100 scheduled runs per hour per account; branches pushed with a `claude/` prefix; runs start in auto mode; session-scoped alternatives are `/loop` and Desktop scheduled tasks - [Scheduled tasks](https://code.claude.com/docs/en/routines)
- Remote Control (`claude remote-control` server mode, `claude --remote-control`, `/remote-control` or `/rc`): Pro, Max, Team, Enterprise; API keys, Bedrock/Vertex/Foundry, and custom `ANTHROPIC_BASE_URL` are not supported; outbound HTTPS only; server mode defaults to 32 concurrent sessions and `--spawn same-dir|worktree|session`; recommended to start inside `tmux` or `screen` on a remote machine; requires a full-scope `claude auth login`, not a `claude setup-token` / `CLAUDE_CODE_OAUTH_TOKEN` token; out of research preview and shown as a device card in the mobile Code tab (Week 34) - [Remote Control](https://code.claude.com/docs/en/remote-control); [What's new index](https://code.claude.com/docs/en/whats-new/index)
- Mobile: no separate app; the Claude iOS/Android Code tab reaches cloud sessions, Projects, Remote Control sessions and Dispatch (Pro and Max); push notifications when Remote Control is active; bypass permissions cannot be selected from the app - [Mobile](https://code.claude.com/docs/en/mobile)
- GitHub Actions: `anthropics/claude-code-action@v1`; `/install-github-app` or manual setup; secrets `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`); interactive mode (`@claude`) versus automation mode (`prompt` input); `claude_args` passes CLI flags such as `--max-turns`, `--model`, `--allowedTools`; run a skill or plugin via `plugin_marketplaces` / `plugins` inputs; separate managed "Code Review" product for Team and Enterprise - [GitHub Actions](https://code.claude.com/docs/en/github-actions)
- Headless: `claude -p`, `--output-format text|json|stream-json`, `--json-schema`, `--allowedTools`, `--permission-mode`, `--permission-prompts none` (v2.1.259+), `--max-budget-usd`, `--continue` / `--resume`, `--no-session-persistence`; `--bare` skips hooks, skills, plugins, MCP, auto memory and CLAUDE.md, uses only `ANTHROPIC_API_KEY` or `apiKeyHelper`, and "will become the default for `-p` in a future release"; piped stdin capped at 10MB - [Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- Agent SDK (Python and TypeScript; formerly Claude Code SDK) exposes the same tools, loop, hooks, subagents, MCP, permissions, sessions, skills and plugins; third parties may not offer claude.ai login, so use API keys; do not brand an SDK product "Claude Code"; Managed Agents is the hosted alternative - [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

- For the Windows 11 + Max + Ubuntu `dev` VM + Tailscale setup, the documented paths are: Desktop SSH sessions (Tailscale hostname in `~/.ssh/config`), or `claude remote-control` in tmux on the VM driven from the phone or claude.ai/code. ## What does Anthropic recommend for user-level versus project-level CLAUDE.md, its length, what to leave out, and how to maintain it?

### Takeaway
Keep every CLAUDE.md under about 200 lines, containing only facts Claude cannot infer from the code (commands, conventions that differ from defaults, gotchas); put personal preferences in `~/.claude/CLAUDE.md` or `CLAUDE.local.md`, team conventions in the committed project file, and move procedures to skills and file-specific rules to `.claude/rules/` with `paths:`. Maintain it like code and prune it, because a bloated file makes Claude ignore real instructions.

### Cited Findings
- Add to CLAUDE.md when Claude makes the same mistake a second time, a code review catches something Claude should have known, you retype the same correction, or a new teammate would need the same context; keep it to "build commands, conventions, project layout, 'always do X' rules" - [Memory](https://code.claude.com/docs/en/memory)
- Target "under 200 lines per CLAUDE.md file"; longer files consume more context and reduce adherence; imports organize but do not reduce cost; a file over 4 MiB is skipped entirely; on-demand files (subdirectory CLAUDE.md, path-scoped rules) are truncated at 40,000 characters on a 200K window and 150,000 to 200,000 characters on a 1M window (enforced from v2.1.309) - [Memory](https://code.claude.com/docs/en/memory)
- Include: bash commands Claude can't guess, style rules that differ from defaults, test instructions and runners, repo etiquette, architectural decisions, environment quirks, gotchas. Exclude: anything Claude can infer from code, standard conventions, detailed API docs (link instead), frequently changing information, long tutorials, file-by-file descriptions, self-evident advice - [Best practices](https://code.claude.com/docs/en/best-practices)
- Test for each line: "Would removing this cause Claude to make mistakes?"; if Claude ignores a rule the file is probably too long; use "IMPORTANT" emphasis on a single line at most; "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly" - [Best practices](https://code.claude.com/docs/en/best-practices)
- Write verifiable instructions ("Use 2-space indentation", "Run `npm test` before committing", "API handlers live in `src/api/handlers/`") and avoid contradictions across CLAUDE.md, nested files and rules - [Memory](https://code.claude.com/docs/en/memory)
- User-scope file is for personal preferences across all projects (code styling preferences, personal tooling shortcuts); project file is team-shared instructions; `CLAUDE.local.md` is for sandbox URLs and test data; the Steering post's rule is to put personal preferences in user-level files and keep project-level files for team-wide preferences specific to that codebase - [Memory](https://code.claude.com/docs/en/memory); [Steering Claude Code (2026-06-18)](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- A gitignored `CLAUDE.local.md` exists only in the worktree where created; share personal instructions across worktrees by importing a file from home (`@~/.claude/my-project-instructions.md`), which triggers a one-time approval dialog for project-level files but not for user-scope files - [Memory](https://code.claude.com/docs/en/memory)
- CLAUDE.md is delivered as a user message after the system prompt, "there's no guarantee of strict compliance"; to block an action regardless, use a PreToolUse hook; for system-prompt-level text use `--append-system-prompt` (better for scripts); project-root CLAUDE.md survives `/compact` (re-read from disk), conversation-only instructions do not - [Memory](https://code.claude.com/docs/en/memory)
- Maintenance tools: `/init` generates a starter (`CLAUDE_CODE_NEW_INIT=1` gives an interactive flow covering CLAUDE.md, skills, hooks); `/memory` lists loaded files; `/context` verifies what loaded; `/doctor` proposes cuts for derivable content (directory layouts, dependency lists, architecture overviews); `/doctor prompt-audit` (v2.1.283+) flags instructions written for older models, dead file references and contradictions; `InstructionsLoaded` hook logs what loads and why - [Memory](https://code.claude.com/docs/en/memory)
- Steering post (2026-06-18, Anthropic staff author): "Keep CLAUDE.md under 200 lines, give it an owner, and review changes to it like code"; root file holds always-on facts, a path-scoped rule beats a nested CLAUDE.md for a cross-cutting concern - [Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Large-codebase blog (2026-05-14): root file should hold pointers and critical gotchas, with subdirectory files for local conventions; review configuration every three to six months and after major model releases; retire rules and hooks that compensate for old model limits; anti-pattern: reusable expertise in CLAUDE.md instead of a skill - [How Claude Code works in large codebases](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)
- Large-codebase docs: layer a short root file plus per-directory files; a Stop hook can read the transcript and propose CLAUDE.md updates; revisit after model releases - [Monorepo and large codebase setup](https://code.claude.com/docs/en/large-codebases)
- Compounding practice from the Claude Code team: after a correction, end with "Update your CLAUDE.md so you don't make that mistake again"; tag `@claude` on PR review comments via the GitHub Action to add rules; one engineer keeps a notes directory per task/project and points CLAUDE.md at it - [Claude Code power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips)
- If CLAUDE.md sets commit or PR rules, turn off Claude Code's built-in git instructions with `includeGitInstructions` and set text with the `attribution` setting to avoid competing guidance - [Memory](https://code.claude.com/docs/en/memory)
- Auto memory complements, not replaces, CLAUDE.md: it records user/feedback/project/reference notes Claude can't derive from the repo; MEMORY.md is capped at 200 lines / 25KB at load; edit or delete freely; `modified` timestamps are recorded - [Memory](https://code.claude.com/docs/en/memory)
- Claude Code also works in non-code folders such as a notes vault; `.claude/` and CLAUDE.md coexist with other tools' config directories - [Common workflows](https://code.claude.com/docs/en/common-workflows)
- Subagents load CLAUDE.md (full hierarchy, including AGENTS.md) at startup, except Explore, Plan and agents with `omitClaudeMd`; auto memory and output style are not passed to non-fork subagents - [Subagents](https://code.claude.com/docs/en/sub-agents)

### Inferences
- Anthropic's own rules imply a split for a solo developer: `~/.claude/CLAUDE.md` for cross-project preferences only (writing style, tool preferences), each repo's CLAUDE.md for commands/conventions/gotchas, and everything procedural in skills. Because project CLAUDE.md is the cheapest onboarding for subagents (they read it automatically), keeping it accurate matters more than keeping it long.
- A multi-hundred-line global file contradicts the "under 200 lines per file" and "would removing this cause mistakes" guidance; `/doctor prompt-audit` is the sanctioned way to audit a legacy file for stale, model-era-specific instructions.
- `autoMemoryDirectory` (absolute path) plus `--add-dir` with `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` would let a vault folder act as memory/context, but Anthropic documents these only as generic options, not as a vault pattern.

### Gaps
- Anthropic does not publish a recommended split between user-level CLAUDE.md and `~/.claude/rules/` beyond "personal preferences"; no stated line-count target for user-level files separate from the 200-line rule.
- `/dream` is listed under Memory in the Help Center quick reference but is not documented on any page I read.

## When does Anthropic say to use a skill versus a subagent versus a slash command versus a hook versus an MCP server versus a plugin?

### Takeaway
Anthropic's rule: CLAUDE.md for always-on facts, rules (`paths:`) for scoped conventions, skills for reusable knowledge and invocable workflows, subagents for context isolation, hooks for anything that must happen every time, MCP for external systems, and plugins purely as the packaging and distribution layer. Slash commands are no longer a separate surface (merged into skills).

### Cited Findings
- Feature table: CLAUDE.md = persistent context; output style = role/tone/format; skill = reusable instructions and workflows; subagent = isolated execution returning a summary; dynamic workflow = script running many subagents; cross-session messaging; code intelligence (LSP); MCP = external services; hook = automation on events; artifact = shareable page; plugins are "the packaging layer" - [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- "Build your setup over time" triggers: convention wrong twice -> CLAUDE.md; same prompt typed repeatedly -> user-invocable skill; playbook pasted a third time -> skill; copying data from a tab Claude can't see -> MCP; reading many files to find symbols -> code intelligence plugin; side task floods the conversation -> subagent; want something every time -> hook; second repo needs same setup -> plugin - [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Skill vs subagent: skills are reusable content that adds to the main window; subagents are isolated workers with a separate window; they combine (`skills:` preload in a subagent, `context: fork` for a skill) - [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Hook vs skill: hooks "fire on its event without Claude deciding", cost zero context unless they return output; a skill's outcome "can vary"; "Put guardrails in hooks... If a rule must hold every time, make it a hook rather than a prompt instruction" - [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- MCP vs skill: MCP gives tools and data access; skills give knowledge about using them; they combine (MCP connection plus a skill documenting the schema) - [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Layering: CLAUDE.md files are additive; skills and subagents override by name (managed > user > project for skills; managed > CLI flag > project > user > plugin for subagents); MCP servers local > project > user; hooks merge and all fire - [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Context cost: CLAUDE.md = every request; output styles = every request; skills = descriptions every request, body on use; MCP = tool names only until used (tool search); subagents = isolated; hooks = zero unless output returned; `disable-model-invocation: true` removes a skill's description from context entirely - [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Custom commands merged into skills: `.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` both create `/deploy`; skills add supporting files, invocation control and auto-loading - [Skills](https://code.claude.com/docs/en/skills)
- Use `disable-model-invocation: true` for side-effect workflows (deploy, commit) you want to trigger manually; use `allowed-tools` to pre-approve the tools a skill needs for that turn - [Best practices](https://code.claude.com/docs/en/best-practices); [Skills](https://code.claude.com/docs/en/skills)
- Subagent vs main conversation: use the main conversation for iterative back-and-forth, shared-context phases, quick targeted changes and latency-sensitive work; use subagents to keep verbose output out of context, enforce tool/permission limits, or run self-contained work; `/btw` is the lighter option for side questions - [Subagents](https://code.claude.com/docs/en/sub-agents)
- Subagent vs dynamic workflow: with subagents "Claude decides turn by turn what runs next"; in a workflow "the script decides" and intermediate results live in script variables; use workflows when a job outgrows a handful of subagents or findings need cross-checking - [Extend Claude Code](https://code.claude.com/docs/en/features-overview); [Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Rules vs CLAUDE.md vs skills: rules load every session or when matching files open; skills load on demand; path-scoped rule preferred over nested CLAUDE.md for cross-cutting concerns - [Extend Claude Code](https://code.claude.com/docs/en/features-overview); [Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Steering post decision rules: always-on facts -> CLAUDE.md; "every time X, always do Y" -> hook; hard prohibitions -> hooks and permissions, with managed settings the only org-wide enforcement; multi-step procedures -> skills; isolated side work -> subagent; output styles "sparingly"; the post does not cover MCP and mentions plugins only briefly - [Steering Claude Code](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Plugins: skills, subagents, hooks and MCP "all work on their own, without a plugin"; use a plugin to package several of them, reuse across repositories, or distribute versioned releases; enabled plugins add context and processes to every session - [Plugins overview](https://code.claude.com/docs/en/plugins/overview)
- Mods vs hooks vs skills vs MCP: pick a mod only when you need to draw in the interface, add a custom command, or rewrite an event inside Claude Code; use a settings hook for a script you already have; a skill when you keep pasting instructions; MCP when Claude must reach an external system - [Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)
- Output style vs CLAUDE.md: CLAUDE.md = what Claude should know; output style = how it responds; neither is enforced - [Extend Claude Code](https://code.claude.com/docs/en/features-overview); [Output styles](https://code.claude.com/docs/en/output-styles)
- MCP vs CLI: "Prefer CLI tools when available" (`gh`, `aws`, `gcloud`, `sentry-cli`) because they add no per-tool listing; disable unused MCP servers; tool search is default so idle MCP tools are cheap - [Manage costs](https://code.claude.com/docs/en/costs); [Best practices](https://code.claude.com/docs/en/best-practices)
- Anti-patterns named by Anthropic: reusable expertise in CLAUDE.md instead of a skill, prompts for behavior that should be a hook, setups left tribal instead of packaged as plugins, building MCP connections before basic configuration works, exploration and editing in the same session - [How Claude Code works in large codebases (2026-05-14)](https://claude.com/blog/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start)
- Skills design (Oct 2025, possibly superseded in details): three-level progressive disclosure (metadata always, body when relevant, linked files as needed); start from evaluation; keep names and descriptions sharp because they drive triggering; install skills only from trusted sources - [Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
- Hooks have a sibling for judgment calls: `prompt` hooks (single LLM call) and `agent` hooks (multi-turn verification with tools, experimental); `/goal` is "a wrapper around a session-scoped prompt-based Stop hook" - [Hooks guide](https://code.claude.com/docs/en/hooks-guide); [Goal](https://code.claude.com/docs/en/goal)

### Inferences
- A hook-over-prose posture is Anthropic's consistent answer to "Claude ignored my rule": moving mandatory behaviors (formatting after edits, blocking edits to `.env`, test gate before stop) from CLAUDE.md into hooks and permission rules is the sanctioned fix.
- For the user's languages, the highest-value plugins are LSP plugins (`pyright-lsp`, `clangd-lsp`, `csharp-lsp`), because Anthropic names them as reducing file reads and catching type errors post-edit; they work in terminal sessions only, not cloud sessions.

### Gaps
- No official page gives a single numeric threshold for when to extract a skill versus a subagent beyond the "third time" and "keeps flooding context" triggers.
- Anthropic's guidance on when to prefer an MCP server over a CLI is limited to the cost-page recommendation; no decision table found.

## Which workflows does Anthropic recommend (explore-plan-code-commit, test-driven, visual iteration, verification, writer/reviewer, headless automation), and what does it say about planning and specs?

### Takeaway
Anthropic's top recommendation is to give Claude a way to verify its own work (tests, build, screenshot, a `/goal` condition, or a Stop hook), then explore in plan mode, plan, implement, and commit; for big features, have Claude interview you into a SPEC.md and implement in a fresh session. Independent review (fresh subagent or second session) and parallel worktree sessions are the recommended scaling patterns, with agent teams and dynamic workflows reserved for work that truly splits.

### Cited Findings
- "Give Claude a way to verify its work" is the first best-practice: a check Claude can run (tests, build exit code, linter, fixture diff, browser screenshot); gating options in rising strength: in the prompt, a `/goal` condition, a Stop hook, a verification subagent or workflow; ask for evidence (test output, screenshot) not assertions; run `/verify` yourself afterward - [Best practices](https://code.claude.com/docs/en/best-practices)
- Four-phase workflow: Explore (plan mode), Plan (Ctrl+G to edit the plan), Implement, Commit; "If you could describe the diff in one sentence, skip the plan"; planning pays off for uncertain approach, multi-file changes or unfamiliar code - [Best practices](https://code.claude.com/docs/en/best-practices)
- Specific prompts: scope the task, point to sources and existing patterns, describe symptom, location and what "fixed" looks like; example "write a failing test that reproduces the issue, then fix it" - [Best practices](https://code.claude.com/docs/en/best-practices)
- Spec workflow: prompt Claude to interview you with the `AskUserQuestion` tool on technical implementation, UI/UX, edge cases, tradeoffs, write `SPEC.md`, then "start a fresh session to execute it"; good specs name files and interfaces, state what is out of scope, and end with an end-to-end verification step - [Best practices](https://code.claude.com/docs/en/best-practices)
- Visual iteration: paste a screenshot, ask Claude to implement, screenshot the result and list differences; the Chrome extension (Claude in Chrome, GA Week 27) and the Desktop Browser pane / `.claude/launch.json` previews let Claude verify web changes; `/verify` and `/run` build and drive the real app - [Best practices](https://code.claude.com/docs/en/best-practices); [Desktop](https://code.claude.com/docs/en/desktop); [Skills](https://code.claude.com/docs/en/skills)
- Test-driven: "have one Claude write tests, then another write code to pass them"; Security Engineering used pseudocode first, then TDD with periodic check-ins (Jul 2025, possibly superseded) - [Best practices](https://code.claude.com/docs/en/best-practices); [How Anthropic teams use Claude Code](https://claude.com/blog/how-anthropic-teams-use-claude-code)
- Writer/Reviewer: "A fresh context improves code review since Claude won't be biased toward code it just wrote"; reviewer subagent sees only the diff and criteria; tell the reviewer to flag only correctness/requirement gaps to avoid over-engineering; bundled `/code-review` runs as a background subagent (July 2026) - [Best practices](https://code.claude.com/docs/en/best-practices); [What's new Week 30](https://code.claude.com/docs/en/whats-new/2026-w30)
- Team practice: one Claude writes a plan, a second reviews it "as a staff engineer"; when things go wrong, re-plan rather than patch; append `/simplify` after changes to run parallel reuse/quality/efficiency review - [Claude Code power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips)
- Parallelism ladder: worktree CLI sessions (3 to 5 at once per the power-user tips), Desktop worktree checkbox, cross-session messaging, cloud sessions, agent view, agent teams (experimental, start with 3 to 5 teammates, 5 to 6 tasks each, partition by file ownership), `/batch` for migrations - [Best practices](https://code.claude.com/docs/en/best-practices); [Agent teams](https://code.claude.com/docs/en/agent-teams); [Claude Code power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips)
- Agent teams are "experimental and disabled by default"; use for research/review, new modules, competing-hypothesis debugging, cross-layer work; "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective"; cost "approximately 7x more tokens than standard sessions when teammates run in plan mode" - [Agent teams](https://code.claude.com/docs/en/agent-teams); [Manage costs](https://code.claude.com/docs/en/costs)
- Dynamic workflows (shipped Week 22, 2026-05-25 to 05-29; available on all paid plans, on Pro turn on in `/config`): Claude writes a JS script using `agent()`, `parallel()`, `pipeline()`; up to 16 concurrent agents by default (max 256), 1,000 agents per run; quality patterns include adversarial verification and loop-until-done; save with `s` in `/workflows`; trigger with the `ultracode` keyword or `/effort ultracode`; the authors caution that parallelism and specialization "have to earn their coordination cost" - [Dynamic workflows](https://code.claude.com/docs/en/workflows); [A harness for every task (2026-06-02)](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)
- `/goal <condition>`: a fresh small model checks the condition after every turn; condition up to 4,000 characters; include "or stop after 20 turns" to bound it; goal clears on met, impossible, or unrecoverable error; works in `-p` and Desktop - [Goal](https://code.claude.com/docs/en/goal)
- Fan-out and headless: loop `claude -p` over a file list with `--allowedTools` and `--permission-mode dontAsk`; test on 2 to 3 files first; `claude -p --permission-mode auto`; pipe data in (`cat error.log | claude -p "..."`) - [Best practices](https://code.claude.com/docs/en/best-practices); [Headless](https://code.claude.com/docs/en/headless)
- Scheduling: `/loop` (session-scoped), Desktop scheduled tasks, cloud scheduled tasks (`/schedule`), GitHub Actions; "be explicit about what success looks like" because scheduled runs cannot ask questions - [Common workflows](https://code.claude.com/docs/en/common-workflows)
- Long-running harness research: a planner expands 1 to 4 sentences into a spec, a generator builds, a separate skeptical evaluator tests the running app with Playwright against hard-threshold criteria; the author found agents lenient when grading their own work, so an external evaluator gives the generator something concrete to iterate against; retro game maker example: solo run 20 minutes and $9 versus full harness 6 hours and $200; with Opus 4.6 the sprint construct was dropped and evaluation moved to a single end pass - [Harness design for long-running application development (2026-03-24)](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Long-running agents across context windows (2025-11-26, possibly superseded): initializer agent creates `init.sh`, `claude-progress.txt`, an initial commit and a JSON feature list with `passes` flags; coding agent does one feature at a time, commits, and starts each session by reading progress/git log and running a basic end-to-end test; use browser automation for end-to-end checks - [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- 16 parallel Claudes built a C compiler (2026-02-05): bare git upstream, a Docker container per agent, `current_tasks/` lock files for claiming work, no orchestrator, tests as a near-perfect verifier, progress notes for fresh contexts; nearly 2,000 sessions, about 2B input / 140M output tokens, just under $20,000; failure mode: all agents hit the same kernel bug and overwrote each other until a known-good oracle (GCC) split the work - [Building a C compiler with a team of parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler)
- Context-pollution tip from that work: print few lines, log details to files, put "ERROR" and reason on one line for grep, give a `--fast` sampling option - [Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)
- Common failure patterns: kitchen-sink session, correcting over and over (after two failed corrections `/clear` and rewrite the prompt), over-specified CLAUDE.md, trust-then-verify gap, infinite exploration; "Sometimes you should let context accumulate... Sometimes you should skip planning" - [Best practices](https://code.claude.com/docs/en/best-practices)
- Team prompts for rigor: "Grill me on these changes and don't make a PR until I pass your test", "Prove to me this works", "Knowing everything you know now, scrap this and implement the elegant solution" - [Claude Code power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips)
- Use Claude as codebase Q&A for onboarding (ask what you would ask a senior engineer) - [Best practices](https://code.claude.com/docs/en/best-practices)

### Inferences
- The minimum viable "autonomous" loop on current features is: SPEC.md from an interview, fresh session in plan mode, `/goal` with a test/lint/exit-code condition (or a Stop hook), then `/code-review` in a background subagent before commit; this matches Anthropic's three escalation levels for verification.
- Agent teams and the 16-agent compiler pattern are justified by Anthropic only when tasks are independent and a near-perfect verifier exists; for single-developer app work, worktree sessions plus `/batch` or a dynamic workflow cover most parallelism at lower coordination cost.

### Gaps
- Anthropic has no page that prescribes test-driven development as a first-class workflow; TDD appears only as examples.
- Planning/spec guidance beyond the interview prompt is thin; no official template for SPEC.md was found.

## What permission, sandbox and settings configuration does Anthropic recommend for safety with low friction (deny rules for secrets, allowlists, auto mode, sandbox)?

### Takeaway
Anthropic's low-friction stack is: auto mode as the default starting mode, plus narrow allow rules for known-safe commands, deny rules for secrets and destructive commands, hooks for hard guardrails, and the sandbox (Linux/macOS/WSL2 only) for filesystem and network isolation; `bypassPermissions` is for isolated containers or VMs only. Deny rules are evaluated first at every scope and cannot be overridden.

### Cited Findings
- Rule order is deny, then ask, then allow, first match wins, regardless of specificity; a deny at any scope beats allows at others; managed settings are highest and cannot be overridden even by `--allowedTools` - [Permissions](https://code.claude.com/docs/en/permissions)
- Syntax: `Tool` or `Tool(specifier)`; Bash wildcards put `*` after the subcommand (`Bash(npm run *)`, `Bash(git commit *)`); a trailing ` *` also matches the bare command; `Bash(git * main)` style leading wildcards are warned about; deny rules can match tool parameters (`Agent(model:opus)`, `Bash(run_in_background:true)`); a bare tool-name deny removes the tool from context - [Permissions](https://code.claude.com/docs/en/permissions)
- Bash rule limits: `Bash(git push *)` does not match `git -C . push`; for a hard check use a PreToolUse hook; permission rules are "enforced by Claude Code, not by the model" - [Permissions](https://code.claude.com/docs/en/permissions); [Auto mode config](https://code.claude.com/docs/en/auto-mode-config)
- Secrets: example deny rules `Read(./.env)`, `Read(./.env.*)`, `Read(./secrets/**)` in committed `.claude/settings.json`; these stop file tools and commands that name the file (e.g. `cat .env`) but not `grep -r` over a directory; the sandbox closes that gap because it adds Read deny paths to what sandboxed commands can't read; deny rules don't cover subprocesses that open files themselves - [Example settings](https://code.claude.com/docs/en/settings-example); [Monorepo and large codebase setup](https://code.claude.com/docs/en/large-codebases)
- Sandbox recommended configuration: `sandbox.enabled`, `failIfUnavailable: true`, `allowUnsandboxedCommands: false`, `network.allowedDomains` (github.com, registry.npmjs.org, pypi.org, files.pythonhosted.org), `filesystem.denyRead` (`~/.ssh`, `~/.aws`, `~/.gnupg`), `credentials` deny/mask for `GITHUB_TOKEN`, `NPM_TOKEN`; default boundaries: writes to the working directory and temp, reads of most of the machine (including `~/.ssh`) unless denied; protected paths (`.claude/settings*`, `.claude/hooks`, `.mcp.json`, shell rc files, `.git/hooks`, `.git/config`) always write-denied - [Sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing)
- Sandbox platforms: macOS Seatbelt, Linux and WSL2 bubblewrap + socat (Ubuntu 24.04+ may need an AppArmor profile for bubblewrap), "Native Windows: Not supported", WSL1 not supported; the sandbox covers only shell commands, not Read/Edit/Write, WebFetch, MCP or hooks; not a complete boundary (domain fronting, Unix sockets like docker.sock) - [Sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing); [Advanced setup](https://code.claude.com/docs/en/setup)
- Sandbox and permissions are complementary: with default `autoAllowBashIfSandboxed: true` sandboxed Bash runs without prompts even in Manual mode; Anthropic's own measurement (Oct 2025, possibly superseded): "sandboxing safely reduces permission prompts by 84%" - [Sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing); [Beyond permission prompts](https://www.anthropic.com/engineering/claude-code-sandboxing)
- Auto mode is the built-in starting mode in terminal and VS Code since v2.1.283 (changelog also records v2.1.284 for interactive and VS Code sessions with no mode configured); requires Opus 4.6+, Sonnet 4.6+, Haiku 5.5 or a Fable model on the Anthropic API; classifier default Sonnet 5; "does not guarantee safety" - [Permission modes](https://code.claude.com/docs/en/permission-modes); [Changelog](https://code.claude.com/docs/en/changelog)
- Auto mode blocks by default: `curl | bash`, sending sensitive data to external endpoints, production deploys, force push, `git reset --hard`, `terraform destroy`, merging unapproved PRs, disabling CI checks, printing live credentials, tampering with session transcripts; allows by default: local file ops, installing from lock files, pushing to the current repo's branches (except deploy-target branch names), read-only HTTP - [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Add human checkpoints inside auto mode with `permissions.ask` (`Bash(git push *)`, `Bash(gh pr create *)`), which the classifier cannot override; use `permissions.deny` for never-run actions; spoken boundaries ("don't push") can be lost to compaction - [Configure auto mode](https://code.claude.com/docs/en/auto-mode-config)

## What is Anthropic's guidance on context management (/clear, /compact, auto-compaction, context editing, large windows, subagent isolation, model and effort choice)?

### Takeaway
Anthropic treats the context window as the primary constraint: clear between unrelated tasks, compact with focus instructions at natural breaks, delegate verbose work to subagents, keep CLAUDE.md small, and pick model and effort once at session start because switching mid-session rebuilds the prompt cache. 1M-token windows are now native on most current models, and Opus 5.5 is the default for Max with `medium` default effort.

### Cited Findings
- "Claude's context window fills up fast, and performance degrades as it fills"; use `/clear` between unrelated tasks, run `/compact <instructions>` (or add a "Compact instructions" section to CLAUDE.md), use `/btw` for side questions, `Esc Esc`/`/rewind` > "Summarize from here / up to here" for partial compaction - [Best practices](https://code.claude.com/docs/en/best-practices); [Manage costs](https://code.claude.com/docs/en/costs)
- After two failed corrections on one issue, `/clear` and restart with a better prompt; use `/rename` before `/clear` then `/resume` to return - [Best practices](https://code.claude.com/docs/en/best-practices); [Manage costs](https://code.claude.com/docs/en/costs)
- What survives compaction: system prompt and output style, project-root CLAUDE.md and unscoped rules (re-read from disk), auto memory, skill descriptions (v2.1.304+), plan file, up to five recently read files (over 5,000 tokens come back as path references), invoked skill bodies (5,000 tokens each, 25,000 total), background tasks keep running, `SessionStart` hooks matching `compact` re-run; path-scoped rules and nested CLAUDE.md are summarized away until re-triggered - [Explore the context window](https://code.claude.com/docs/en/context-window)
- Auto-compact window: `autoCompactWindow` setting, `/autocompact 500k`, `claude --autocompact`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, per-model via `modelSettings` (v2.1.288+); accepted 100K to 1M tokens; models with a native 1M window compact at about 967K by default, Opus/Sonnet 4.6 without `[1m]` at 200K - [Model configuration](https://code.claude.com/docs/en/model-config)
- Idle compaction (v2.1.299, 2026-10-14): conversations over 200K tokens that sit idle about 54 minutes are compacted; disable with `"idleCompaction": false` (needs v2.1.290+) or `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` - [Changelog](https://code.claude.com/docs/en/changelog); [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Extended context: native 1M window on Fable 5.1/5, Sonnet 5 and later, Haiku 5.5, Opus 4.7 and later; Opus 4.6 and Sonnet 4.6 need the `[1m]` suffix (Max includes Opus 4.6 1M; Sonnet 4.6 1M requires usage credits); `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` forces 200K - [Model configuration](https://code.claude.com/docs/en/model-config)
- Subagents "run in separate context windows and report back summaries"; `/btw` has full context but no tools and doesn't enter history; forks inherit the parent conversation and cache - [Best practices](https://code.claude.com/docs/en/best-practices); [Subagents](https://code.claude.com/docs/en/sub-agents)
- Engineering principles (Sep 2025, possibly superseded in product details): context rot and finite "attention budget"; smallest set of high-signal tokens; just-in-time retrieval and progressive disclosure; compaction, structured note-taking, and sub-agent architectures that return condensed 1,000 to 2,000 token summaries - [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Compaction versus resets: compaction can leave "context anxiety" on Sonnet 4.5, while Opus 4.5 "largely removed that behavior", so later harnesses used automatic compaction only - [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Offload to hooks and skills: a PreToolUse hook can rewrite `npm test` to show only failures; a skill gives knowledge so Claude doesn't explore; MCP tool search keeps idle MCP tools cheap; `/context` and `/skill-doctor` show what is consuming space - [Manage costs](https://code.claude.com/docs/en/costs)
- Model aliases: `default`, `best`, `fable`, `sonnet`, `opus`, `haiku`, `sonnet[1m]`, `opus[1m]`, `opusplan`; on the Anthropic API `opus` = Opus 5.5, `sonnet` = Sonnet 5.5, `haiku` = Haiku 5.5; default for Pro, Max, Team, Enterprise and API is Opus 5.5 (v2.1.280, 2026-09-22); Fable models are never default and may bill to usage credits; `ANTHROPIC_DEFAULT_MODEL` sets the starting model - [Model configuration](https://code.claude.com/docs/en/model-config); [Changelog](https://code.claude.com/docs/en/changelog)
- Effort levels `low`, `medium`, `high`, `xhigh`, `max` (plus the separate `ultracode` setting); defaults `medium` on Opus 5.5, Sonnet 5.5, Haiku 5.5, `xhigh` on Opus 4.7, and `high` on other effort-capable models; guidance: `low` quick steps, `medium` day-to-day with clear scope, `high` where verification matters, `xhigh` deeper reasoning, `max` hard autonomous problems and "can overthink"; `ultrathink` in a prompt boosts one turn; `/effort` saves a level per model, `s` applies to the session only - [Model configuration](https://code.claude.com/docs/en/model-config)
- Caching consequences: each model has its own cache so `/model` mid-session re-reads everything uncached; changing effort keeps the cache on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 via API key or subscription; default TTL is one hour for the main conversation on a subscription within plan usage and five minutes otherwise (`promptCacheTtl`, `subagentPromptCacheTtl`); `/cd` preserves cache; `/rewind` hits an earlier cache entry; "Pick your model and effort level at the top of a session, then save `/compact` for natural breaks" - [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- Cost and limits: enterprise average about $13 per developer per active day and $150 to $250 per month; Max/Pro have a five-hour session limit and a weekly limit shared with Claude chat, plus a separate weekly limit for Fable on Max; `/usage` attributes plan usage to skills, subagents, plugins, MCP servers and gives fix recommendations (`f` to apply, v2.1.305+); `autoContinueAtUsageLimit` resumes after reset - [Manage costs](https://code.claude.com/docs/en/costs); [Use Claude Code with your Pro or Max plan](https://support.claude.com/en/articles/11145838-using-claude-code-with-your-pro-or-max-plan)
- Usage drivers in long sessions: long context re-read each turn, cache misses after a break, scheduled tasks and `/loop`, cross-session messages, `/goal` check-ins (at most three idle check-ins), subagents and workflows each sending their own requests, teammates, and compaction itself; sending a subagent to Sonnet or Haiku lowers cost - [Manage costs](https://code.claude.com/docs/en/costs)
- Quality incident (Anthropic postmortem, 2026-04-23): the default effort was lowered from `high` to `medium` on 2026-03-04 and reverted 2026-04-07; a caching bug that dropped prior reasoning ran 2026-03-26 to 2026-04-10 (fixed v2.1.101) and likely drained limits faster; a verbosity cap in the system prompt hurt coding quality by 3% on a broader eval (2026-04-16 to 04-20) - [An update on recent Claude Code quality reports](https://www.anthropic.com/engineering/april-23-postmortem)
- The Claude Code team: "Opus with thinking for everything" because less steering and better tool use make it faster overall; `/effort max` per session for hard debugging; `/effort auto` available - [Claude Code power user tips](https://support.claude.com/en/articles/14554000-claude-code-power-user-tips)
- Status line fields to watch context live: `context_window.used_percentage` (input tokens only), `exceeds_200k_tokens`, `rate_limits.five_hour` and `seven_day` percentages and reset times (Pro/Max only), `prompt_cache` (hit ratio, warm/cold) - [Status line](https://code.claude.com/docs/en/statusline); [Prompt caching](https://code.claude.com/docs/en/prompt-caching)

### Inferences
- For a Max subscriber, the weekly limit (and the separate Fable limit) is the binding constraint rather than cost; the actionable levers are `/clear` discipline, keeping CLAUDE.md small, using Sonnet/Haiku for subagents, avoiding agent teams and large workflows unless justified, and watching the status-line `rate_limits` and `/usage` recommendations.
- Anthropic's defaults changed twice in 2026 (effort default reverted in April; newer models default to `medium`), so any effort level hard-coded in old settings may now be overriding a better default.

### Gaps
- "Context editing" (automatic clearing of old tool results) is mentioned only indirectly ("clearing old tool results from context" as an expected cache rebuild); no user-facing setting for it was found.
- Support page gives no numeric Max 5x/20x allowances; community figures are outside this lens. The Max-specific article (support.claude.com article 11014257) returned HTTP 404, so only the "Use Claude Code with your Pro or Max plan" article was read.

### Inferences
- The pace is roughly 10 to 15 minor releases per month with two or three model launches per quarter; features move from "research preview" to default within 2 to 5 months (auto mode: March preview, August default for subscribers, September default for all), so setups built on January habits are likely stale.
- Several 2026 habits Anthropic has since deprecated or defaulted differently (explicit todo tools, hard-coded effort level, `--sandbox` on remote control, project-level `defaultMode: "bypassPermissions"`) are worth removing from a from-scratch design.
