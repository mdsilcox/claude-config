# Empirical evidence: what makes AI coding agents more or less effective (status 2026-10-24)

Grading key used throughout. Evidence type: **RCT** = randomized controlled trial; **CTRL** = controlled experiment or benchmark ablation; **QE** = quasi-experiment on observational data (for example difference-in-differences); **OBS** = observational or descriptive mining study; **SURVEY** = self-report; **VENDOR** = numbers published by the company that sells the model or tool, usually on undisclosed internal evals (conflict of interest); **ANEC** = case study or anecdote; **SECONDARY** = number seen only in a secondary write-up, not confirmed in the primary source. Strength: strong, moderate, weak. "Older model" marks results on models released before about late 2025 (pre Claude 4.5 / GPT-5.x) that may not transfer to the current Claude 5.5 generation (Opus 5.5 released 2026-09-22, Sonnet 5.5 2026-09-28, Haiku 5.5 2026-10-07). Most 2026 items are arXiv preprints that are not yet peer reviewed. Sources are cited inline in parentheses.

## 1. Do repository context files (AGENTS.md, CLAUDE.md) measurably help or hurt, and which content matters?

### Takeaway
Three controlled 2026 studies agree that context files move task success by only a few points, and two of them found no correctness benefit for Claude Code specifically (Sonnet 4.5, Sonnet 4.6). Files do reliably change behavior and cost: agents obey them (more testing, more exploration, use of the tools they name). LLM-generated files raised cost about 20-23% while slightly lowering success; developer-written files gave about +4% success on average; and the one study measuring speed found a developer-written AGENTS.md cut median runtime about 29%. Named commands and tools, and warnings about expensive operations, change behavior measurably; codebase overviews and text that duplicates existing docs do not help.

### Cited Findings
- **[CTRL, moderate; preprint, ICLR 2026 poster]** Gloaguen, Mündler, Müller, Raychev, Vechev (ETH Zurich / LogicStar.ai), "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?", submitted 2026-02-12. Compared no file vs LLM-generated vs developer-written context files on SWE-bench Lite (300 tasks, repos without context files) and a new AGENTbench (138 tasks from 12 Python repos that ship developer-written files), using Claude Code + Sonnet 4.5, Codex + GPT-5.2 and GPT-5.1 mini, and Qwen Code + Qwen3-30B ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)).
- Same study, success: LLM-generated files changed success by -0.5% (SWE-bench Lite) and -2% (AGENTbench) on average per Section 4.2; the abstract says about -3% on AGENTbench (internal inconsistency in the paper). Developer-written files gave about +4% on average and improved every agent **except Claude Code**. Exact per-agent rates are only in a figure ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)).
- Same study, cost: LLM-generated files added 2.45 and 3.92 steps per task and raised cost about 20% and 23% (Lite, AGENTbench); developer-written files added 3.34 steps and up to 19% cost. Claude Code + Sonnet 4.5 on AGENTbench: 40.7 steps / $1.15 (no file), 46.5 / $1.33 (LLM file), 45.3 / $1.30 (human file). GPT-5.2 reasoning tokens rose 14-22% with LLM files ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)).
- Same study, behavior: agents generally follow the instructions; with a file they run more tests and search, read and write more files. Named tools get used: `uv` about 1.6 uses per task when mentioned vs under 0.01 when not; repo-specific tools about 2.5 vs under 0.05 ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)).
- Same study, overviews and redundancy: 8 of 12 developer files and 95-100% of files generated by Sonnet 4.5, GPT-5.2 and Qwen contained a codebase overview, yet files did not reduce the steps before the agent first touched the files the PR changed, so the authors conclude they are not effective overviews. When all other documentation was removed from the repos, LLM-generated files improved performance by 2.7% and beat developer-written files (Claude Code excluded), which suggests generated files mostly duplicate existing docs. Stronger models did not write better files. Recommendation: omit LLM-generated files for now; human-written files should hold only minimal requirements such as repo-specific tooling ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)).
- **[CTRL, moderate for efficiency, silent on correctness; workshop paper]** Lulla, Mohsenimofidi, Baltes, Galster, Zhang, Treude, "On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents" (2026-01-23, v2 2026-03-30, JAWs 2026). Paired with/without design, Codex CLI with gpt-5.2-codex, 124 small merged PRs (at most 100 changed lines and 5 files) from 10 repos that already had one root AGENTS.md. With the file: median wall-clock 98.6 s to 70.3 s (-28.6%), mean -20.3%; median output tokens -16.6% (mean -20.1%); both significant (Wilcoxon, p<0.05). Input, cached and total tokens: no significant change. Correctness was not measured (only a manual sanity check of 50 outputs). Mean savings exceed median savings, so the file mainly trims a few expensive runs ([arXiv 2601.20404](https://arxiv.org/html/2601.20404v2)).
- **[CTRL, weak to moderate; single-author preprint, small n]** Khatri, "Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories" (2026-07-28). Claude Code (claude-sonnet-4-6) and Codex CLI (gpt-5.5), 17 real tasks from 3 Python repos, three strategies (none, always-on, selective), 3 repeats, 288 runs scored with the original PR's gold tests. Context strategy did not measurably change correctness for either agent; equivalence testing bounds the effect to about 10-15 pp; the real AGENTS.md never turned a near-miss into a pass; failures were mostly implementation skill (design, pattern choice, exact wiring) rather than missing repo knowledge ([arXiv 2607.27250](https://arxiv.org/abs/2607.27250)).
- **[SECONDARY]** Per-condition numbers for Khatri as reported by a summary of the paper: Claude Code 53.3% (none) / 55.6% (always-on) / 55.6% (selective); Codex 58.8% / 56.9% / 52.9%; minimum detectable effect about 30 pp. One file section did matter for efficiency: a warning that the full test suite is slow cut blind full-suite runs from 3.67 to 1.67 per cell and wall-clock time by about 24% on one repo. Per-task difficulty correlated across the two agents at Spearman ρ = 0.75, with about 40% of tasks in different difficulty bands per agent, which the author offers as an explanation of contradictory prior results ([summary of Khatri 2026](https://codex.danielvaughan.com/2026/08/06/do-context-files-help-coding-agents-agents-md-ablation-study-codex-cli-correctness-vs-efficiency/); headline claims confirmed in [arXiv 2607.27250](https://arxiv.org/abs/2607.27250)).
- **[OBS, describes content, not effect]** "Agent READMEs: An Empirical Study of Context Files for Agentic Coding" (2025-11): 2,303 context files from 1,925 repos (Claude Code, Codex, Copilot). Implementation details appear in 69.9%, architecture in 67.7%, build and run commands in 62.3%, security and performance requirements in 14.5% each; files are long and hard to read ([arXiv 2511.12884](https://arxiv.org/abs/2511.12884v1)). Related descriptive studies of 253 CLAUDE.md files ([arXiv 2509.14744](https://alphaxiv.org/overview/2509.14744v1)) and 466 AGENTS.md files ([arXiv 2510.21413](https://arxiv.org/abs/2510.21413v4)) find shallow structure and no settled conventions.
- **Conflict:** Lulla et al. find a developer-written AGENTS.md makes Codex faster and cuts output tokens ([arXiv 2601.20404](https://arxiv.org/html/2601.20404v2)), while Gloaguen et al. find developer-written files add steps and up to 19% cost ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)). They differ in agent, task size (tiny PRs vs benchmark issues) and metric (wall-clock and output tokens vs dollar cost including input); neither study resolves the other.

### Inferences
- For Claude Code, the context file is a behavior and efficiency lever, not a capability lever: two independent studies on Sonnet 4.5 and 4.6 found no correctness gain, and the best-case average gain for other agents is about +4%.
- Content with measured behavioral effect: exact tool and command names (agents then use them) and warnings about expensive or slow operations (fewer blind full-suite runs). Content with no measured benefit: codebase overviews, anything duplicated from README or docs, and auto-generated files.
- Because agents follow file instructions literally, every unconditional "always do X" rule is paid for on every task (more tests, more exploration, +19-23% cost in one study), whether or not the task needs it.

### Gaps
- No study varies context-file length or rule count directly, so there is no measured "optimal length".
- No study covers Opus-class or Claude 5.x models, multi-hour sessions, nested or per-directory files, or imported files.
- All three controlled studies use Python repos; nothing on C++/C# modding, browser games or FastAPI/HTMX specifically.

## 2. How does instruction-following degrade with instruction count, instruction length and context fill, and what is known for recent Claude models?

### Takeaway
Simple, checkable instructions are followed almost perfectly by Claude 4-class models up to about 100 at once (about 95%), then decline to about 68-82% at 250 and 40-53% at 500, with omissions dominating and earlier instructions favored. Separately, longer inputs degrade reasoning even with perfect retrieval (13.9-85% drops within advertised windows), focused prompts beat full ones for every model tested, and long agent trajectories and compaction add their own failure modes (agents overwriting correct code, losing constraints). Vendor-reported long-context retrieval for newer Claude models is far better (Opus 4.6: 76% on an 8-needle 1M-token test vs 18.5% for Sonnet 4.5), but there is no independent instruction-count benchmark for Claude 4.5+ or 5.x.

### Cited Findings
- **[CTRL, moderate; synthetic task; NeurIPS 2025]** IFScale, Jaroslawicz et al. (Distyl AI), "How Many Instructions Can LLMs Follow at Once?" (2025-07-15). Task: write a business report that includes N exact keywords, N = 10 to 500, 20 models. Best at 500: gemini-2.5-pro 68.9%, o3-high 62.8% ([arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)).
- Same study, Claude accuracy at 100 / 250 / 500 instructions: claude-3.7-sonnet 94.8 / 72.9 / 52.7; claude-opus-4 94.6 / 67.9 / 44.6; claude-opus-4 with thinking 81.8 / 81.5 / 52.1; claude-sonnet-4 94.4 / 77.2 / 42.9; claude-sonnet-4 with thinking 94.8 / 80.0 / 39.9; claude-3.5-haiku 43.4 / 16.6 / 8.5. At 10-50 instructions most Claude models score 98-100% ([arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)).
- Same study, patterns: reasoning models (gemini-2.5-pro, o3) show threshold decay; gpt-4.1 and claude-3.7-sonnet linear decay; claude-3.5-haiku and llama-4-scout exponential decay to a 7-15% floor. Models favor earlier instructions (primacy bias peaks around 150-200 instructions); omission errors outnumber wrong-variant errors about 4-7 to 1 for Claude 4 models; thinking gave only moderate gains at high density; latency for claude-opus-4 rose from 24.9 s at 10 instructions to 147 s at 500 ([arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)).
- **[CTRL, moderate; NeurIPS 2025 D&B]** AgentIF (Qi et al., Tsinghua / Zhipu): 707 human-annotated instructions from 50 real agentic applications, averaging about 1,723 words and 11.9 constraints each; current models "generally perform poorly", especially on complex constraint structures and tool specifications ([arXiv 2505.16944](https://arxiv.org/html/2505.16944v1)). **[SECONDARY]** an aggregator lists the best instruction-level success near 60% ([benchmarklist](https://benchmarklist.com/benchmarks/agentif/)). Older models.
- **[CTRL, moderate; vendor research by a retrieval-database company, possible conflict of interest]** Chroma "Context Rot" (2025-07-14): 18 models including Claude Opus 4, Sonnet 4, Sonnet 3.7, Sonnet 3.5, Haiku 3.5. Performance falls with input length even on simple tasks; it falls faster when the question is semantically far from the answer; distractors hurt more as length grows; logically coherent haystacks hurt more than shuffled ones; on LongMemEval every model scored higher with a focused ~300-token prompt than the full ~113k-token prompt. Claude models hallucinated least because they abstain, and Sonnet 4 / Opus 4 showed the largest focused-vs-full gap from that caution ([Chroma](https://www.trychroma.com/research/context-rot)).
- **[CTRL, moderate; EMNLP-era 2025 paper, older models]** Du et al., "Context Length Alone Hurts LLM Performance Despite Perfect Retrieval" (2025-10-06): 5 models including Claude 3.7 Sonnet and GPT-4o on math, QA and coding (HumanEval). Performance dropped 13.9% to 85% as input length grew, well within claimed windows, even when the irrelevant tokens were whitespace or fully masked. Mitigation (have the model recite the evidence first) gave up to +4% for GPT-4o on RULER ([arXiv 2510.05381](https://arxiv.org/html/2510.05381v1)).
- **[CTRL, strong but old models]** "Lost in the Middle" (Liu et al., 2023, TACL 2024): accuracy is highest when relevant information is at the start or end of the context and lowest in the middle ([arXiv 2307.03172](https://arxiv.org/abs/2307.03172)).
- **[VENDOR via SECONDARY]** Claude Opus 4.6 (2026-02) reportedly scored 76% on MRCR v2 8-needle at 1M tokens vs 18.5% for Sonnet 4.5, and 93% at 256k; I could not confirm these against Anthropic's system card ([NYU Shanghai RITS summary](https://rits.shanghai.nyu.edu/ai/anthropic-releases-claude-opus-4-6-with-1m-token-context-window); [letsdatascience](https://letsdatascience.com/news/anthropic-releases-claude-opus-46-update-80aaa28b)). MRCR measures retrieval, which Du et al. show is not the same as reasoning over long input.
- **[OBS on trajectories, moderate; preprint]** "Coherence Collapse: Diagnosing Why Code Agents Fail After Reaching the Right Code" (Kim et al., 2026-03-25, v2 2026-05-26): 16,758 trajectories, 3 agent scaffolds (SWE-Agent, OpenHands, LiveSWEAgent), 7 models. On SWE-Agent and OpenHands, 60-69% of failures by capable models reached and edited the correct functions but still produced a wrong patch; the largest theme was agents overwriting or thrashing correct code; in 5 cases a gold-identical patch existed mid-trajectory and was later destroyed. An edit-commit checkpoint recovered all 5; a consensus variant gave +3.0 pp Pass@1 on GPT-5 (p=0.08, not significant) ([arXiv 2603.24631](https://arxiv.org/abs/2603.24631)). **[SECONDARY]** a search summary reported a 63.7% collapse rate in the longest trajectory quartile vs 21.7% in the shortest; not confirmed in the abstract.
- **[CTRL, weak; preprint, abstract has no numbers]** Min et al., "Towards Reliable Context Compression for Long-Horizon Agents" (2026-08-06, v2 2026-10-14), AppWorld: compression weakens the influence of recent interactions and increases blocked actions, repeated exploration and run-to-run instability ([arXiv 2608.06503](https://arxiv.org/abs/2608.06503)).
- **[SECONDARY, weak]** A "governance decay" preprint (arXiv 2606.22528, not verified) is reported to find constraint violations rising from 0% with the policy in context to 30% after compaction, and 38% when the summary dropped the constraint ([blog summary](https://codex.danielvaughan.com/2026/07/03/governance-decay-self-compacting-agents-context-compaction-safety-constraints-codex-cli-constraint-pinning/)).
- **[OBS, weak; single practitioner, no controls]** LangWatch analysis of 2,451 sessions and 873 compactions suggests compacting around 250k-450k tokens and that very large windows add cost without clear benefit ([LangWatch](https://langwatch.ai/research/finding-the-optimal-context-window)).

### Inferences
- There is an instruction budget. For simple checkable rules, Claude 4-class models are near-perfect up to about 100 and degrade beyond 150-250; real agentic constraints are harder than keyword inclusion (AgentIF), so the practical budget for behavioral rules is likely much lower. User rules also share the window with the harness's own system prompt and tool descriptions.
- Order matters: primacy bias and lost-in-the-middle both favor putting the few critical rules first.
- Omission is the dominant failure, so rules that must never be broken are better enforced mechanically (hooks, tests, linters) than by prose.
- Context fill degrades reasoning independent of retrieval, and compaction can drop constraints and execution state. This supports fresh sessions per task, keeping logs and large files out of the main context, and re-stating critical constraints after compaction.

### Gaps
- No independent instruction-count or long-context reasoning benchmark for Claude 4.5, 4.6, 5 or 5.5 was found; the newest Claude models in IFScale and Chroma are Opus 4 / Sonnet 4 (mid-2025).
- No public controlled study of Claude Code's own auto-compaction or of how adherence to CLAUDE.md changes as a session's context fills.
- IFScale and Chroma use synthetic tasks; transfer to coding-agent rules is assumed, not measured.

## 3. Multi-agent vs single-agent: failure taxonomies, token multipliers, when parallelism pays, merge conflicts, coordination overhead

### Takeaway
The best controlled evidence (Google, Dec 2025, non-coding tasks, matched token budgets) shows multi-agent setups help on decomposable parallel work (+81% on a finance task) but hurt on sequential planning (-39% to -70%), average about -3.5% overall, add 58-515% coordination overhead, and offer diminishing or negative returns once a single agent already scores above about 45%. Vendors report large wins for breadth-first research and scanning (Anthropic +90.2% on research; 266 vs 21 vulnerabilities found), at 4-15x the tokens, while their coding swarms show falling merge rates as agent count rises, conformity, and resource exhaustion. In GitHub data, co-active PR pairs from different agent tools conflict about twice as often as pairs from the same tool (41.7% vs 19.8%). Vendor-practitioners converge on read-only subagents and hierarchical planner/worker designs; parallel writers and flat swarms do poorly.

### Cited Findings
- **[CTRL, strong design; not coding tasks]** Kim et al. (Google Research, Google DeepMind, MIT), "Towards a Science of Scaling Agent Systems" (2025-12-17; Google blog 2026-01): 180 configurations, 15,750 runs, matched token budgets; models from GPT-5, Gemini 2.x and Claude Sonnet 3.7 / 4.0 / 4.5; benchmarks Finance-Agent, BrowseComp-Plus, PlanCraft, WorkBench. Multi-agent vs single-agent: Finance-Agent centralized +80.8%; PlanCraft every variant worse, -39.0% (hybrid) to -70.1% (independent); BrowseComp-Plus -35% (independent) to +9.2% (decentralized); WorkBench -1.2% to +5.7%; mean -3.5% (95% CI about -18.6% to +25.7%) ([arXiv 2512.08296](https://arxiv.org/html/2512.08296v2); [Google Research blog](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)).
- Same study, mechanics: error amplification relative to a single agent is 17.2x for independent agents, 7.8x decentralized, 5.1x hybrid, 4.4x centralized; coordination overhead 58% (independent) to 285% (centralized) and 515% (hybrid); turns 3.6-6.2x; success per 1K tokens falls from 67.7 (single agent) to 13.6 (hybrid); tool-heavy tasks suffer most from overhead; coordination gains turn negative once the single-agent baseline exceeds about 45% (β ≈ -0.404, p<0.001). A fitted model picked the best architecture for 87% of held-out configurations ([arXiv 2512.08296](https://arxiv.org/html/2512.08296v2)).
- **[VENDOR, moderate; undisclosed internal eval]** Anthropic, "How we built our multi-agent research system" (2025-06-13): Opus 4 lead with Sonnet 4 subagents beat single-agent Opus 4 by 90.2% on an internal research eval. Agents use about 4x the tokens of chat and multi-agent systems about 15x. On BrowseComp, token usage alone explained 80% of performance variance (95% with tool-call count and model choice). Parallel tool calling cut research time up to 90%. Anthropic states coding is a poorer fit: "most coding tasks involve fewer truly parallelizable tasks than research", and domains where agents must share context or have many dependencies are poor fits ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).
- **[VENDOR experiments, moderate to weak; mostly no single-agent control; some unreleased models]** Anthropic Frontier Red Team, "Patterns and problems in multiagent systems" (2026-08-13). Vulnerability hunting: a coordinating 45-agent swarm found 266 vulnerabilities in a 27M-token run vs 21 for independent parallel agents in 6.5M tokens; restricted to the core directories both covered, tokens per vulnerability were comparable, and only 12 findings overlapped. Game-building swarms: the fraction of PRs merged fell as agent count rose from 10 to 80, steeply for Sonnet 4.6 and Opus 4.6 (876 and 980 PRs opened at 80 agents, few merged); prompts and role structures made little difference; the games were poor. Conformity: 18 of 30 agents picked the same branch name. Hidden-profile task: groups of four reached the best option in 17-36% of episodes for most models (about 85% for the strongest) vs a solo ceiling near 100%. A job-queue run produced 2.4 million job requests and accepted 117 jobs ([Anthropic](https://www.anthropic.com/research/multiagent-systems)).
- **[OBS taxonomy plus small interventions, moderate; older models]** Cemri et al. (UC Berkeley), "Why Do Multi-Agent LLM Systems Fail?" (MAST, v2 2025-04-22): 200+ traces from 7 frameworks, 14 failure modes, human inter-annotator kappa 0.88. Shares: specification issues 41.77%, inter-agent misalignment 36.94%, task verification 21.30%. Top modes: step repetition 17.14%, reasoning-action mismatch 13.98%, failing to ask for clarification 11.65%, disobeying the task spec 10.98%, unaware of termination conditions 9.82%. For ChatDev, better role specs gave +9.4% and an added high-level verification step +15.6%; authors conclude better base models alone will not fix these failures ([arXiv 2503.13657v2](https://arxiv.org/html/2503.13657v2)).
- **[OBS, moderate; short preprint]** Xu, Subramanian, Karthik, "AI Agent Pull Requests on GitHub: Frequency, Structure, and Merge Conflict Rates" (2026-07-06): 33,596 agent-authored PRs in 2,807 repos. 40.2% of repos had agent PR pairs open at the same time, covering 79.4% of agent PRs; only 0.5% of co-active pairs came from two different agent tools. Replaying three-way merges for 747 pairs: textual conflicts in 41.7% of cross-agent pairs vs 19.8% of same-agent pairs (non-overlapping 95% CIs); 84.4% of conflicted files were source code; about 42% of conflicts were structural (modify/delete, add/add). Note "same agent" means the same agent product, not one orchestrated session ([arXiv 2607.04697](https://arxiv.org/abs/2607.04697)). **[SECONDARY]** The AgenticFlict dataset (AIware 2026) reportedly measured a 27.67% merge-conflict rate over 107K+ AI-authored PRs ([summary](https://news.creeta.com/en/multi-agent-worktree-merge-train-2026/)).
- **[VENDOR case study, weak to moderate; conflict of interest]** Cursor, "Scaling long-running autonomous coding" (2026-01-14): with flat coordination through a shared file and locks, 20 agents slowed to the effective throughput of 2-3; optimistic concurrency made agents risk-averse; a planner/worker hierarchy with a judge and fresh starts each cycle worked; a dedicated integrator role "created more bottlenecks than it solved". GPT-5.2 was a better planner and long-run worker than GPT-5.1-Codex, and Opus 4.5 "tends to stop earlier and take shortcuts". A browser was built in about a week (1M+ lines, about 1,000 files); periodic fresh starts were still needed against drift. No quality evaluation or single-agent baseline ([Cursor](https://cursor.com/blog/scaling-agents)).
- **[VENDOR case study, weak to moderate]** Anthropic (Carlini), "Building a C compiler with a team of parallel Claudes" (2026-02): 16 parallel agents, no orchestrator, lockfiles plus git, about 2,000 Claude Code sessions, about $20,000 API cost, 2 billion input and 140 million output tokens, producing a roughly 100k-line Rust C compiler that builds Linux 6.9 on x86, ARM and RISC-V and passes the GCC torture tests. Task had an unusually strong test oracle ([Anthropic](https://anthropic.com/engineering/building-c-compiler)).
- **[VENDOR opinion, weak; few numbers]** Cognition, "Multi-Agents: What's Actually Working" (2026-04-22), revising its 2025 "Don't Build Multi-Agents" stance: read-only subagents (search, code context) are the common working pattern; a clean-context coder/reviewer loop is a "notable improvement" (unquantified); a strong-model "smart friend" helps in hard cases, but a weaker primary model capped quality; parallel writers make conflicting implicit decisions; unstructured swarms are "mostly a distraction". Devin Review catches about 2 bugs per Devin-written PR, about 58% severe (no method or baseline given) ([Cognition](https://cognition.com/blog/multi-agents-working)).
- **[OBS, weak; from search snippet]** SWE Atlas reports that some frontier models rarely delegate even when they can (subagent invoked in about 1% of Gemini 3.1 Pro trials, 0.3% of Gemini 3 Flash) ([arXiv 2605.08366](https://arxiv.org/pdf/2605.08366)).
- **Conflicting academic results on coding:** AgentForge reports a multi-agent framework at 40.0% on SWE-bench Lite, +26 pp over its own single-agent baseline (likely weak baseline) ([arXiv 2604.13120](https://arxiv.org/pdf/2604.13120)); an empirical comparison of seven agent frameworks reports single-agent systems more effective for software development, with the multi-agent framework showing the longest trajectories from coordination overhead (single-vs-multi claim from search snippet, not confirmed in the abstract) ([arXiv 2511.00872](https://arxiv.org/abs/2511.00872)); SWE-Dev found simple Self-Refine gives a better performance/cost balance than workflow-heavy systems like ChatDev ([arXiv 2505.16975](https://arxiv.org/pdf/2505.16975)).

### Inferences
- Parallel agents pay off when the work splits into independent, mostly read-only or separately verifiable pieces (research, search, scanning separate areas, many independent fixes with a strong oracle). They lose on sequential, tightly coupled, tool-heavy work and when one agent already does reasonably well, which describes most solo feature work.
- If parallelism is used, centralized or hierarchical control contains error amplification (4.4x vs 17.2x for independent agents), and disjoint file scopes reduce textual conflicts; worktrees move conflicts to merge time rather than removing them.
- Specification and verification failures make up most multi-agent failures (about 63% combined in MAST), so a clear spec and an explicit verification step matter more than adding agents.
- The widely quoted "-39% to -70% on sequential tasks" comes from PlanCraft (a Minecraft crafting-planning benchmark), not from coding; the "about 2x merge conflicts" figure compares PRs from different agent products in GitHub, not orchestrated lanes in one repo. Both transfer to coding lanes only by analogy.

### Gaps
- No controlled single-agent vs multi-agent study on real coding tasks with Claude Code subagents or agent teams was found.
- I found no primary source for a measured comparison of "grouping coupled files under one agent" vs "file-by-file parallel agents" (a figure of 44-60% extra cost for the latter could not be traced).
- Semantic conflicts (clean merges that break behavior) between parallel agents are not quantified anywhere I found.

## 4. Test-first work, self-verification loops, second-agent review, and planning before implementation

### Takeaway
The best-supported lever is an external, trustworthy oracle: given correct human-written tests, an agentic workflow resolved 88.8% (SWE-bench Lite) and 94.3% (Verified) of tasks, whereas agent-written tests on their own did not change resolution rates (0 to -2.6 pp) but shifted token use by up to about 49%. Self-repair is bottlenecked by feedback quality; feedback from a stronger model or a human helps much more (1.58x more repairs with human feedback, older models), and LLM judges favor their own outputs, which supports a different-model or clean-context reviewer. In the field, though, most AI review comments are rejected (56.3%). There is no controlled evidence on "plan mode" itself; the closest evidence is Anthropic's advisor pattern (+2.7 pp, -11.9% cost, vendor) and failure taxonomies where specification problems are the largest failure class (41.8%).

### Cited Findings
- **[CTRL, moderate; EACL 2026; tests are an oracle, so an upper bound]** TDFlow: with human-written tests supplied, the test-driven agentic workflow reached 88.8% on SWE-bench Lite and 94.3% on SWE-bench Verified; the authors argue writing good reproduction tests is the main remaining obstacle ([ACL Anthology](https://preview.aclanthology.org/ingest-eacl/2026.eacl-long.70)).
- **[CTRL, old]** Cognition's 2024 SWE-bench report: giving Devin the final unit tests raised its pass rate to 23% on 100 sampled tasks vs 13.86% overall (not comparable to standard results) ([Cognition](https://cognition.ai/post/swe-bench-technical-report)).
- **[CTRL, moderate; preprint]** Chen et al., "Rethinking the Value of Agent-Generated Tests for LLM-Based Software Engineering Agents" (2026-02-08), mini-SWE-agent on SWE-bench Verified with six models (claude-opus-4.5 resolved 74.4%, gemini-3-pro 74.2%, gpt-5.2 71.8%). Test-writing rates were similar for resolved and unresolved tasks (Opus 4.5: 84.4% vs 78.9%); gpt-5.2 wrote tests in only 0.6% of tasks yet resolved 71.8%. Prompting models to write or not write tests changed resolved counts by 0, -1.0%, -2.6% and -1.8%; 83.2% of tasks kept the same outcome. Discouraging tests cut input tokens 33-49% and API calls 25-35% for two models; encouraging them raised GPT-5.2 output tokens 19.8% ([arXiv 2602.07900](https://arxiv.org/html/2602.07900v1)).
- **[CTRL, old models, strong design; ICLR 2024]** Olausson et al., "Is Self-Repair a Silver Bullet for Code Generation?": once repair cost is counted, self-repair gains are often modest; the bottleneck is the model's feedback on its own code; feedback from a stronger model gives substantially larger gains, and an experienced programmer's feedback raised GPT-4's repaired programs 1.58x ([arXiv 2306.09896](https://arxiv.org/abs/2306.09896v4)).
- **[CTRL, old models; ICLR 2024]** Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet": intrinsic self-correction without external feedback does not reliably improve and can degrade reasoning ([arXiv 2310.01798](https://arxiv.org/abs/2310.01798)).
- **[CTRL, moderate; NeurIPS 2024; summarization, not code]** Panickssery, Bowman, Feng, "LLM Evaluators Recognize and Favor Their Own Generations": self-recognition ability correlates linearly with self-preference bias, and fine-tuning experiments support a causal link ([arXiv 2404.13076](https://arxiv.org/pdf/2404.13076)).
- **[OBS, moderate; field data]** Lin, Liang, Thongtanunam, Tantithamthavorn, "Is Agentic Code Review Helpful? Mining Developers' Feedback to CodeRabbit Reviews in the Wild" (2026-07-03): 31,073 review comments with developer feedback on 10,191 PRs in 239 repos; 36.4% accepted, 7.3% discussed, 56.3% rejected, mostly as false positives, redundant, out of scope, or misaligned with developer intent; a lightweight classifier predicted rejection at up to 76% F1 ([arXiv 2607.03316](https://arxiv.org/abs/2607.03316)).
- **[CTRL benchmark, ICLR 2026]** CR-Bench: review agents tuned to find all hidden issues show a low signal-to-noise ratio, so resolution rates alone mislead ([ICLR 2026](https://www.iclr.cc/virtual/2026/10017268)). **[VENDOR-sponsored, conflict of interest]** a Signal65 report produced with a vendor rates CodeRabbit at 95.88% precision ([Signal65](https://signal65.com/wp-content/uploads/2026/03/Signal65-Insights_Evaluating-AI-Code-Review-Tools.pdf)).
- **[VENDOR observation, weak]** Anthropic's Sonnet 5.5 launch (2026-09-28): on FrontierCode, Sonnet 5.5 scored lower at Max effort (46.2%) than at Xhigh (52.1%) because Max more often ran the code-review skill, which splits review across many subagents ([Anthropic](https://www.anthropic.com/claude-sonnet-5-5)).
- **[OBS, weak; 30 tasks, one framework]** Tokenomics (Salim et al., Concordia, 2026-01-20): in ChatDev with a GPT-5 reasoning model, the iterative code-review stage consumed 59.4% of tokens on average, and input tokens were 53.9% of all tokens ([arXiv 2601.14470](https://arxiv.org/abs/2601.14470)).
- **[OBS + intervention, older models]** MAST: adding a high-level verification step to ChatDev gave +15.6% on its ProgramDev benchmark; verification failures are 21.3% of multi-agent failures ([arXiv 2503.13657v2](https://arxiv.org/html/2503.13657v2)). Coherence Collapse: an edit-commit checkpoint recovered every case where an agent had produced the gold patch and then destroyed it ([arXiv 2603.24631](https://arxiv.org/abs/2603.24631)).
- **[VENDOR, moderate; single vendor eval with a confound]** Anthropic, "The advisor strategy" (2026-04-09): Sonnet 4.6 executor consulting an Opus advisor scored +2.7 pp on SWE-bench Multilingual over Sonnet alone and cut cost per task 11.9% (5 trials of 300 problems; solo Sonnet used adaptive thinking, the advisor run used thinking off plus a suggested coding prompt). Haiku 4.5 with an Opus advisor scored 41.2% on BrowseComp vs 19.7% alone. Each advice returns about 400-700 tokens; the executor decides when to ask ([Claude blog](https://claude.com/blog/the-advisor-strategy)).
- **Planning, no controlled evidence found:** searches found no controlled ablation of "plan before code" or plan mode for coding agents in 2025-2026. Cursor's guidance cites a University of Chicago study that experienced developers are more likely to plan before generating code (a behavioral correlation, not an effect on agent output) ([Cursor](https://cursor.com/blog/agent-best-practices)). A reported ESEM 2026 study mined 85 agent plan files and proposes a readiness checklist (descriptive; seen only in a blog) ([summary](https://codex.danielvaughan.com/2026/08/09/agent-plans-task-oriented-artifacts-codex-cli-plan-mode-implementation-steps-file-locations-validation/)).

### Inferences
- Tests help most when they encode the human's intent and are trustworthy (written or approved by the human, or pre-existing). Mandating that the agent write more tests is mostly a cost lever on SWE-bench-style tasks; the value of test-first work likely comes from the human-checked spec the tests represent, not from the agent's test writing.
- Fast, specific verification commands (a quick test subset, type check, lint) are cheap wins; the slow-suite warning in Section 1 is one measured example.
- Same-model, same-context self-review adds little new information. A clean-context or different-model reviewer is better supported (feedback-quality bottleneck, self-preference bias), but its output should be triaged: in the field about half of AI review comments are rejected, and fanning review across many subagents raised cost and lowered one benchmark score.
- Planning evidence is indirect: specification problems are the largest failure class, a strong-model advisor at decision points helped a cheaper executor, and planning-heavy sequential work suffers when split across agents. This points to one short plan or spec produced in a single context (ideally by the strongest model), not elaborate multi-agent planning.

### Gaps
- No RCT or controlled study of test-driven development with modern coding agents vs a standard workflow; no measurement of Claude Code's plan mode.
- No vendor-independent production measurement of a general AI reviewer's precision and recall was found; review evidence on second-model vs same-model is indirect (older models, non-code tasks).
- Nothing specific to C++/C# game mods, where builds and tests are often slow or absent.

## 5. Productivity evidence: METR's RCT (2025) and 2026 follow-ups, DORA, large surveys; which conditions predicted gains or losses?

### Takeaway
The only RCT on experienced developers in their own large repos (METR, early-2025 tools) found a 19% slowdown despite a perceived 20% speedup. METR's late-2025 follow-up points to small speedups (point estimates 4-18% faster, intervals include zero), but METR calls the data unreliable because 30-50% of developers withheld tasks they would not do without AI. 2026 self-reports are large (median 1.4-2x value, 3x speed) yet METR's own staff reported the lowest gains, and METR's analysis of Claude Code transcripts gives only a soft upper bound (1.5-13x). Org-level survey data (DORA 2025) tie AI to higher throughput but lower stability, and a difference-in-differences study of Cursor adoption found a two-month velocity spike with persistent rises in static-analysis warnings (+30%) and complexity (+42%) that predicted later slowdowns.

### Cited Findings
- **[RCT, strong design, small n, older tools]** METR, "Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity" (2025-07-10): 16 experienced developers, 246 real tasks in mature repos they knew well, mostly Cursor Pro with Claude 3.5/3.7 Sonnet. AI-allowed tasks took 19% longer (95% CI about +2% to +39%); developers forecast a 24% speedup and afterwards believed AI had sped them up 20%. METR's listed likely contributors: over-optimism, high familiarity with the repos, large complex repos, low AI reliability (developers accepted under 44% of generations) and implicit repo context ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); [arXiv 2507.09089](https://arxiv.org/abs/2507.09089)).
- **[RCT with serious selection problems, weak]** METR, "We are Changing our Developer Productivity Experiment Design" (2026-02-24): second study from August 2025 with 57 developers (10 returning, 47 new), 143 repos, 800+ tasks, pay cut from $150 to $50 per hour. METR reports "a speedup of -18%" for returning developers (CI -38% to +9%) and -4% for new ones (CI -15% to +9%), where negative means less time with AI. 30-50% of surveyed developers said they withheld tasks they did not want to do without AI; time logging broke down when developers ran agents concurrently. METR thinks developers are probably more sped up in early 2026 than in early 2025 but calls the data "only very weak evidence" of the size ([METR](https://metr.org/blog/2026-02-24-uplift-update/)). METR's Feb-Mar 2026 risk report summarizes the RCT as "small (~4-20%) productivity benefits", likely an underestimate ([METR risk report](https://metr.org/blog/2026-05-19-frontier-risk-report/)). Secondary coverage has misreported the -18% as a slowdown or as a reversal; treat third-party summaries cautiously ([Rob Bowley](https://blog.robbowley.net/2026/04/04/metrs-developer-productivity-research-2026-update/)).
- **[OBS, weak; soft upper bound]** METR transcript analysis (2026-02-17): 5,305 Claude Code transcripts from 7 METR staff in January 2026; an LLM judge estimated time a skilled engineer would need without AI. Daily time-savings factors ranged about 1.5x-13x (per-person 2.11x-11.62x); higher agent concurrency was associated with higher factors (causality not established). The judge was validated on only 34 human estimates with typical error of 2-3x, and METR stresses this is not a productivity multiplier ([METR](https://metr.org/notes/2026-02-17-exploratory-transcript-analysis-for-estimating-time-savings-from-coding-agents/)).
- **[SURVEY, weak; convenience sample, about 2% response]** METR survey (2026-05-11, fielded Feb-Apr 2026): 349 technical workers, half regularly using Claude Code. Median self-reported value change 1.4x-2x, speed 3x; perceived value rose from 1.3x (Mar 2025) to 2x (Mar 2026). Larger perceived gains went with heavier use, more AI experience, using Claude Code or Codex, and working at startups; METR staff reported the lowest gains. METR notes its 2025 RCT found developers overestimated AI's effect by about 40 pp ([METR](https://metr.org/blog/2026-05-11-ai-usage-survey/)).
- **[SURVEY, moderate size, correlational]** DORA 2025 "State of AI-assisted Software Development" (2025-09-23): nearly 5,000 respondents; 90% use AI at work; over 80% believe it raised their productivity; 30% report little or no trust in AI-generated code. AI adoption now relates positively to delivery throughput and product performance (unlike the prior year) but negatively to delivery stability; DORA frames AI as an amplifier of existing team conditions and reports that internal platform quality correlates with realizing AI's value ([Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)).
- **[QE, moderate; MSR 2026; early-agent era]** He, Miller, Agarwal, Kästner, Vasilescu (CMU), "Speed at the Cost of Quality" (v3 2026-01-26): 806 repos that adopted Cursor (mostly Aug 2024 to Mar 2025) vs 1,380 propensity-matched controls, staggered difference-in-differences. Lines added +281% in month 1 and +48% in month 2, then no significant gain; overall lines added +28.6%, commits not significant. Static-analysis warnings +30.3% and cognitive complexity +41.6% (the text elsewhere says 25%), both persistent. A 100% increase in complexity predicted a 64.5% drop in lines added the next month; warnings, a 50.3% drop ([arXiv 2511.04427](https://arxiv.org/html/2511.04427v3)).
- **[SURVEY, large, self-selected]** Stack Overflow 2025: 84% use or plan to use AI tools (51% of professionals daily); 46% distrust AI accuracy vs 33% who trust it (3% highly); 66% cite "almost right, but not quite" solutions and 45% say debugging AI code takes longer; about 31% use agents; 52% report a positive productivity effect, 69% of agent users say agents raised productivity ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/ai)). 2026: 48% trust AI when they can easily validate its answers, 16% for most tasks that are not important decisions; coding assistants or agents are the top AI use case (66%) ([Stack Overflow 2026](https://survey.stackoverflow.co/2026/ai)).
- **[RCT, older autocomplete-era tools; for contrast]** GitHub Copilot lab RCT: 55.8% faster on a small, well-defined task (n=95) ([arXiv 2302.06590](https://arxiv.org/abs/2302.06590)); three field experiments at Microsoft, Accenture and a Fortune 100 firm (4,867 developers): +26.08% completed tasks ([SSRN 4945566](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=4945566)); Google internal RCT: about 21% faster on an enterprise task (n=96, wide CI) ([arXiv 2410.12944](https://arxiv.org/abs/2410.12944)).

### Inferences
- Perceived speedup is not evidence of speedup: the one well-controlled measurement found perception wrong by about 40 pp. A solo developer redesigning a setup should measure outcomes (time to merged change, rework, defects) rather than trust feel.
- Conditions associated with losses: deep familiarity with a large, mature codebase and a high quality bar (METR 2025), low acceptance of generations, and unchecked growth of complexity and warnings (Cursor DiD). Conditions associated with gains: well-defined tasks (lab RCTs), heavier and more experienced use of agentic tools (METR survey, correlational), agent concurrency (METR transcripts, correlational), and strong surrounding platform and practices (DORA, correlational).
- Speed gains that add complexity are partly repaid later (complexity increases predicted later velocity losses), so quality gates (lint, static analysis, tests) are part of keeping the productivity gain.

### Gaps
- No clean 2026 RCT of agentic tools (Claude Code, Codex) on experienced developers exists; METR is redesigning its study.
- No evidence specific to solo developers on hobby or small projects, game mods, or home-lab workflows.

## 6. Model selection (Opus vs Sonnet vs Haiku, including subagents) and thinking or effort budgets

### Takeaway
Model capability tends to beat extra token budget (Anthropic: upgrading model beat doubling budget). Vendor data for the Claude 5.5 family show Sonnet 5.5 matching or beating Opus 5.5 on some agentic coding evals at half the price, with Opus described as stronger on open-ended work; Haiku 5.5 trails far behind on hard coding (39.2% vs 70.6% on Terminal-Bench 4.0) but is positioned for subagent search and summary. More effort is not monotonically better: default (medium) Opus 5.5 matched max on one coding eval, Sonnet 5.5 scored lower at Max than Xhigh, and an earlier study found "overthinking" trajectories resolve fewer SWE-bench issues. A cheap executor with a strong advisor improved quality and cost in vendor tests. Benchmark numbers need caution: SWE-bench Verified is contaminated and partly flawed per OpenAI's audit, and difficulty is agent-specific.

### Cited Findings
- **[VENDOR, 2026-09-22]** Claude Opus 5.5: Terminal-Bench 4.0 66.4% (xhigh effort), FrontierCode 1.1 54.4% (max) and 54.6% at default medium effort, CursorBench 4.0 57.8% (max) vs 52.5% (medium). Default-effort Opus 5.5 "beats Opus 5 at max effort for about a fifth of the cost" on Terminal-Bench 4.0; overall "uses fewer tokens per task, which nets out to a 40% drop in costs". Price $4 / $20 per million input / output tokens, cache reads $0.20. Terminal-Bench 4.0 standard error about ±2.6 points ([Anthropic](https://www.anthropic.com/claude-opus-5-5)).
- **[VENDOR, 2026-09-28]** Claude Sonnet 5.5: Terminal-Bench 4.0 70.6% (vs 10.3% for Sonnet 5), FrontierCode 52.1% (xhigh) and 46.2% (max), CursorBench 55.5%. At low effort it exceeds Sonnet 5's best CursorBench score for under a tenth of the cost per task; "costs up to 30% less per task than its predecessor". Anthropic says it "complements Opus 5.5 best when running at lower effort settings" and that Opus "remains clearly stronger at complex, open-ended work requiring sustained judgment". Price $2 / $10 ([Anthropic](https://www.anthropic.com/claude-sonnet-5-5)).
- **[VENDOR, 2026-10-07]** Claude Haiku 5.5: Terminal-Bench 4.0 39.2% (Haiku 4.5: 0.0%), FrontierCode 46.4%; $0.10 / $0.50 per million tokens for prompts up to 100k; positioned for summaries, compaction, queries, classification and as a subagent beside Opus and Sonnet, with Sonnet and Opus recommended for complex agentic coding; first Haiku with adjustable effort ([Anthropic](https://www.anthropic.com/claude-haiku-5-5)).
- **[VENDOR, 2025-06, older models]** Anthropic: "upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7"; the research system used an Opus lead with Sonnet subagents ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).
- **[VENDOR, 2026-04]** Advisor strategy: Sonnet + Opus advisor +2.7 pp on SWE-bench Multilingual with -11.9% cost per task; Haiku + Opus advisor 41.2% vs 19.7% on BrowseComp ([Claude blog](https://claude.com/blog/the-advisor-strategy)). Cognition reports the inverse caveat: pairing a weaker primary with a strong "smart friend" was "not good enough" because quality was capped by the primary ([Cognition](https://cognition.com/blog/multi-agents-working)).
- **[VENDOR via SECONDARY, 2025-11, older model]** Anthropic reported that Opus 4.5 at medium effort matched Sonnet 4.5's best SWE-bench Verified score with 76% fewer output tokens, and at high effort beat it by 4.3 pp with 48% fewer tokens ([Cline blog quoting Anthropic](https://cline.bot/blog/anthropics-claude-opus-4-5-is-live-in-cline)).
- **[CTRL, moderate; older models]** Cuadron et al., "The Danger of Overthinking" (2025-02): 4,018 OpenHands trajectories on SWE-bench Verified; higher overthinking scores correlate with lower resolution, reasoning models overthink more, and simply picking the candidate with the lower overthinking score improved performance by almost 30% while cutting compute cost 43% ([arXiv 2502.08235](https://arxiv.org/pdf/2502.08235)). Related: "Inverse Scaling in Test-Time Compute" (Anthropic Fellows and others, 2025-07) found longer reasoning lowers accuracy on several non-coding task families ([arXiv 2507.14417](https://arxiv.org/abs/2507.14417)).
- **[OBS, moderate; preprint]** Bai et al. (incl. Brynjolfsson, Pentland), "How Do AI Agents Spend Your Money?" (2026-04-24, v3 2026-10-02): eight frontier models on SWE-bench Verified; accuracy often peaks at intermediate token cost then plateaus; Kimi-K2 and Claude Sonnet 4.5 used over 1.5 million more tokens on average than GPT-5 on the same tasks ([arXiv 2604.22750](https://arxiv.org/abs/2604.22750)).
- **[VENDOR anecdote, weak; older models]** Cursor found GPT-5.2 a better planner and long-run worker than GPT-5.1-Codex and that Opus 4.5 "tends to stop earlier and take shortcuts"; it now picks the best model per role ([Cursor](https://cursor.com/blog/scaling-agents)).
- **[CTRL]** IFScale: enabling thinking on Claude Opus 4 helped at 250-500 instructions (81.5% vs 67.9% at 250) but not for Sonnet 4 at 500 (39.9% vs 42.9%), and raised latency ([arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)).
- **[CTRL]** Khatri: per-task difficulty correlates only ρ = 0.75 across Claude Code and Codex, with about 40% of tasks in different difficulty bands, so which agent or model wins depends on the task ([SECONDARY summary](https://codex.danielvaughan.com/2026/08/06/do-context-files-help-coding-agents-agents-md-ablation-study-codex-cli-correctness-vs-efficiency/)).
- **[VENDOR audit, moderate]** OpenAI, "Why we no longer evaluate SWE-bench Verified" (2026-02): of 138 audited hard tasks, 59.4% had material problems in tests or problem statements (35.5% required unstated implementation details, 18.8% tested unrequested functionality), and GPT-5.2, Claude Opus 4.5 and Gemini 3 Flash could reproduce some original fixes from memory; OpenAI recommends SWE-bench Pro, where top scores were about 23% vs about 70% on Verified (figures via secondary coverage of the post) ([OpenAI](https://openai.com/en/index/why-we-no-longer-evaluate-swe-bench-verified); [Decrypt](https://decrypt.co/359012/openai-benchmark-measure-ai-coding-supremacy-contaminated)). **[SECONDARY]** a May 2026 audit reportedly found SWE-bench Pro graders mis-graded about a third of trials ([Decrypt](https://decrypt.co/359012/openai-benchmark-measure-ai-coding-supremacy-contaminated)).
- **[CTRL, not coding]** Google scaling study: multi-agent gains vanish once a single agent exceeds about 45% on a task, so stronger single models reduce the payoff of orchestration ([arXiv 2512.08296](https://arxiv.org/html/2512.08296v2)).

### Inferences
- Default to a strong mid-tier model (Sonnet-class) for implementation and the strongest model (Opus-class) for planning, ambiguous design, long-horizon or high-stakes work; vendor data show the Sonnet/Opus gap on standard coding evals is small in the 5.5 generation, and Sonnet beats Opus on one of them.
- Use Haiku-class models for read-only subagent work (search, summarization, classification, compaction), not for hard implementation; the 31-point Terminal-Bench gap is large.
- Effort: start at the default and raise it for hard tasks; max effort is not reliably best (equal or worse on two of the vendor's own coding evals) and overthinking correlates with failure. Spend is better directed at a stronger model than at more tokens on a weaker one.
- Because difficulty is agent-specific and SWE-bench Verified is compromised, the user's own small eval set (a handful of real tasks from their projects) is a better guide than leaderboard deltas of a few points.

### Gaps
- No independent (non-vendor) evaluation of Opus 5.5, Sonnet 5.5 or Haiku 5.5 on agentic coding was found; all 5.5 numbers are Anthropic's, on new benchmark versions (Terminal-Bench 4.0, FrontierCode 1.1) with no history.
- No controlled study of Claude Code subagent model choice (for example Haiku vs Sonnet explore subagents) on real coding outcomes.
- **[SECONDARY, weak]** METR task time horizons reportedly reached about 12 hours (50% success) for frontier models by May 2026 with doubling every few months, and METR says measurements above 16 hours are unreliable; figures seen only on prediction-market pages ([Manifold](https://manifold.markets/event/best-metr-time-horizons-in-2026)).

## 7. Memory, retrieval, skills and tool loading: what helps?

### Takeaway
Curated, human-written procedural knowledge helps (curated skills +16 pp on average, but only about +4.5 pp in software engineering), while self-generated skills and LLM-generated context files do not help. Loading tools and knowledge on demand beat always-on loading in vendor tests (tool search raised tool-selection accuracy from 49% to 74% for Opus 4; memory plus context editing gave +39% on an agentic search eval), and focused context beats full context in independent tests. No empirical evidence was found on cross-project Markdown memory vaults for coding agents.

### Cited Findings
- **[CTRL, moderate; NeurIPS 2026]** SkillsBench (2026-02): tasks run with no skills, curated skills and self-generated skills. Curated skills raised average pass rate by +16.2 pp (arXiv) or +16.4 pp (NeurIPS version), varying by domain from about +4.5 pp in software engineering to +51.9 pp in healthcare; 16-18 of 84-86 tasks got worse with skills. Self-generated skills gave no benefit on average (about -1.3 pp per the NeurIPS listing) ([hyper.ai abstract of arXiv 2602.12670](https://hyper.ai/en/papers/2602.12670); [NeurIPS 2026](https://neurips.cc/virtual/2026/poster/139353)). **[SECONDARY]** reported pass rates 40.6% curated, 24.3% none, 21.0% self-generated, with self-generated tested only on Claude Code and Codex ([Engineer's Codex](https://www.engineerscodex.com/skillsbench-ai-generated-skills)).
- **[CTRL]** Consistent with this, LLM-generated AGENTS.md files slightly lowered success and raised cost, and stronger models did not write better ones ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1)).
- **[VENDOR, 2025-09]** Anthropic context management: memory tool plus context editing improved an internal agentic-search eval by 39% over baseline, context editing alone by 29%; in a 100-turn web-search eval, context editing let agents finish workflows that otherwise hit context exhaustion while cutting token use 84% ([Anthropic](https://www.anthropic.com/news/context-management)).
- **[VENDOR, 2025-11; contested]** Anthropic Tool Search Tool: on MCP tool-selection evals, accuracy rose from 49% to 74% for Opus 4 and from 79.5% to 88.1% for Opus 4.5 with deferred, on-demand tool loading; a large tool library that would consume tens of thousands of tokens up front shrinks to about 500 tokens plus the 3-5 tools found ([Anthropic](https://anthropic.com/engineering/advanced-tool-use)). A competitor's test with 2,792 tools reported only 34% accuracy for Anthropic's tool search vs 94% for its own product (conflict of interest on both sides) ([Stacklok](https://stacklok.com/blog/stackloks-mcp-optimizer-vs-anthropics-tool-search-tool-a-head-to-head-comparison/)).
- **[VENDOR, illustrative example, not an eval]** Anthropic's "Code execution with MCP" (2025-11) describes calling tools from code instead of loading definitions and results into context, with an example falling from about 150,000 to 2,000 tokens (98.7%) ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)).
- **[VENDOR, 2025-06]** A tool-testing agent that rewrote a flawed MCP tool description cut task completion time 40% for later agents using it ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).
- **[CTRL]** Focused prompts (~300 tokens of relevant history) beat full ~113k-token prompts for all 18 models on LongMemEval ([Chroma](https://www.trychroma.com/research/context-rot)).

### Inferences
- Knowledge that helps is curated by a human and procedural (how to do X in this project), loaded when relevant; knowledge the agent writes for itself, or that restates what is already in the repo, does not measurably help and costs tokens.
- Always-on tool and MCP definitions are a context cost with an accuracy penalty as the tool count grows; on-demand loading (deferred tools, skills with short descriptions) is the better-supported default.
- The gain from skills is smallest in software engineering (+4.5 pp), so for coding the main value of skills is likely consistency and efficiency in repeated project procedures rather than raw success.

### Gaps
- No empirical study of cross-project memory stores (Markdown vaults, MCP memory servers) for coding agents was found; any benefit is unmeasured.
- No independent comparison of agentic search (grep/glob) vs embedding retrieval for Claude Code was found in this search.
- No independent replication of Anthropic's memory and context-editing numbers.

## 8. Cost and token usage: what drives it?

### Takeaway
Agentic coding uses about 1000x the tokens of code chat, dominated by input tokens (re-reading context), with up to 30x variance between runs of the same task and accuracy that plateaus at intermediate spend; models cannot predict their own costs. Multi-agent setups multiply this (about 15x chat; 58-515% coordination overhead), review loops can dominate pipeline tokens (59% in one study), and habits induced by instructions (writing tests, extra exploration) shift token use by 20-50% without changing outcomes.

### Cited Findings
- **[OBS, moderate; preprint]** Bai et al. (2026-04-24, v3 2026-10-02), eight frontier models on SWE-bench Verified: agentic tasks use about 1000x more tokens than code reasoning or chat; input tokens drive most cost; runs on the same task differ by up to 30x in total tokens; more tokens do not mean higher accuracy (often peaks at intermediate cost); models predict their own token use poorly (correlation at most 0.39) and underestimate it ([arXiv 2604.22750](https://arxiv.org/abs/2604.22750)).
- **[VENDOR]** Agents use about 4x the tokens of chat; multi-agent systems about 15x ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).

### Inferences
- On a subscription with weekly limits, the main levers are fewer re-read input tokens (short always-loaded context, focused sessions, avoiding big pastes), fewer parallel agents, and avoiding instruction-induced rituals (unconditional test writing, exhaustive exploration, multi-agent review on every change).
- Because cost variance per task is up to 30x and models cannot predict their own spend, hard caps and checkpoints on long autonomous runs are a reasonable safeguard (inference; not directly tested).

### Gaps
- No published measurement of how Claude subscription usage limits map to tokens, so plan-level budgeting cannot be grounded empirically here.
- No study isolates the token effect of Claude Code features (subagents, skills, hooks) on real projects.

## 9. What configuration choices does the evidence support?

### Takeaway
The evidence favors a lean, human-written context file with exact commands and warnings; a small, front-loaded instruction set with mechanical enforcement of must-follow rules; focused sessions; single-agent work by default with read-only or hierarchical delegation only for parallelizable work; trustworthy, fast verification; triaged review by a fresh-context or different model on risky changes; strong-model planning; default effort; and on-demand loading of curated skills and tools. Each implication below is tied to its evidence and grade, and several rest on vendor or indirect evidence.

### Cited Findings
- The specific evidence for each implication is cited in Sections 1-8; key anchors: context files ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v1), [arXiv 2601.20404](https://arxiv.org/html/2601.20404v2), [arXiv 2607.27250](https://arxiv.org/abs/2607.27250)); instruction count ([arXiv 2507.11538](https://arxiv.org/html/2507.11538v1)); context length ([Chroma](https://www.trychroma.com/research/context-rot), [arXiv 2510.05381](https://arxiv.org/html/2510.05381v1)); multi-agent ([arXiv 2512.08296](https://arxiv.org/html/2512.08296v2), [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system), [arXiv 2607.04697](https://arxiv.org/abs/2607.04697)); verification ([TDFlow](https://preview.aclanthology.org/ingest-eacl/2026.eacl-long.70), [arXiv 2602.07900](https://arxiv.org/html/2602.07900v1), [arXiv 2306.09896](https://arxiv.org/abs/2306.09896v4)); review ([arXiv 2607.03316](https://arxiv.org/abs/2607.03316), [arXiv 2404.13076](https://arxiv.org/pdf/2404.13076)); models and effort ([Anthropic Opus 5.5](https://www.anthropic.com/claude-opus-5-5), [Anthropic Sonnet 5.5](https://www.anthropic.com/claude-sonnet-5-5), [arXiv 2502.08235](https://arxiv.org/pdf/2502.08235)); skills and tools ([SkillsBench](https://hyper.ai/en/papers/2602.12670), [Anthropic tool search](https://anthropic.com/engineering/advanced-tool-use)); productivity ([METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/), [arXiv 2511.04427](https://arxiv.org/html/2511.04427v3)).

### Inferences
1. **CLAUDE.md: short, hand-written, operational.** Include exact build, test, lint and run commands, required tools (for example `uv`), warnings about slow or dangerous operations, and non-obvious gotchas; leave out codebase overviews, architecture essays and anything already in README or docs; do not keep unedited auto-generated (/init-style) output. Evidence: generated files -0.5% to -3% success and +20-23% cost; overviews did not speed navigation; named tools get used about 100x more often; a slow-test warning cut blind full-suite runs by more than half; no correctness gain for Claude Code in two studies (CTRL, moderate; Sections 1 and 7).
2. **Treat instructions as a scarce budget.** Aim for dozens of high-value rules, not hundreds; put the critical ones first; phrase rules as conditional ("when touching X, run Y") rather than unconditional rituals; enforce must-never rules with hooks, tests or linters rather than prose. Evidence: adherence about 95% at 100 simple instructions then steep decline, omission-dominated, primacy bias; agents obey rules literally at a token cost (CTRL, moderate; Sections 1-2).
3. **Keep the working context focused.** One task per session, delegate broad read-only exploration to subagents that return short summaries, keep large logs and files out of the main context, and re-state critical constraints after compaction. Evidence: length alone degrades reasoning 13.9-85%; focused beats full prompts for every model; failures concentrate in long trajectories with agents overwriting correct code; compaction can drop constraints (CTRL moderate for length effects; weak or secondary for compaction; Section 2).
4. **Single agent by default; parallelize only independent work.** Use parallel or multi-agent setups for breadth-first, read-heavy or independently verifiable tasks; when writing in parallel, use one coordinator, disjoint file scopes and isolated worktrees, and expect merge conflicts and 4-15x token use. Evidence: -39% to -70% on sequential planning, gains only on decomposable tasks, error amplification 4.4x centralized vs 17.2x independent, coordination overhead 58-515%, cross-tool PR conflicts 41.7% vs 19.8%, vendor swarms with falling merge rates (CTRL strong but non-coding; OBS; VENDOR; Section 3).
5. **Invest in trustworthy, fast oracles over agent test rituals.** Provide or approve the key tests yourself (test-first where the spec is clear), give the agent a fast check command, and do not require "write more tests" unconditionally. Evidence: 88.8-94.3% resolution with human-written tests; agent-written test volume did not change outcomes but changed tokens up to 49%; self-repair limited by feedback quality (CTRL, moderate; Section 4).
6. **Review with fresh eyes, then triage.** For risky diffs, use a reviewer in a clean context, ideally a different or stronger model, and treat its findings as candidates (about half of AI review comments are rejected in the field); avoid fanning review out to many subagents by default. Evidence: stronger-model and human feedback beat self-feedback; self-preference bias; 56.3% rejection rate; Sonnet 5.5 scored lower at Max when review was split across subagents; review loops consumed 59% of tokens in one pipeline (CTRL older models; OBS; VENDOR; Section 4).
7. **Plan once, with the strongest model, in one context.** For multi-step changes, have the strongest model write a short plan or spec and resolve ambiguities before implementation; for cheap executors, an advisor-style consult at decision points. Evidence is indirect: specification failures are the largest multi-agent failure class (41.8%); advisor +2.7 pp at -11.9% cost (vendor); no controlled plan-mode study exists (OBS, VENDOR, weak; Section 4).
8. **Match models to roles and validate on your own tasks.** Opus-class for planning and open-ended or long-horizon work; Sonnet-class for most implementation; Haiku-class for search, summary and compaction subagents. Evidence: vendor 5.5 numbers (Sonnet close to or above Opus on some coding evals at half the price; Haiku 31 points behind on Terminal-Bench 4.0); model upgrades beat doubling token budgets; task difficulty is agent-specific (VENDOR; CTRL weak; Section 6).
9. **Start at default effort; raise it selectively.** Evidence: default-effort Opus 5.5 equaled max on one coding eval at much lower cost, Sonnet 5.5 scored lower at Max than Xhigh, overthinking correlated with failure in SWE-bench trajectories, accuracy plateaus at intermediate token spend (VENDOR; CTRL older models; OBS; Section 6).
10. **Curate skills by hand and load tools on demand.** Write skills for repeated project procedures yourself; do not rely on agent-written skills or memory notes as a performance lever; keep always-loaded MCP servers few and prefer deferred tool loading. Evidence: curated skills +16 pp overall but +4.5 pp in software engineering; self-generated skills about -1.3 pp; tool search 49% to 74% accuracy (vendor, contested) (CTRL; VENDOR; Section 7).
11. **Measure, do not trust the feeling of speed, and guard quality.** Track a few outcome measures for your own work and keep static analysis and complexity checks in the loop. Evidence: perceived vs measured productivity off by about 40 pp in the RCT; Cursor adoption raised warnings 30% and complexity 42%, which predicted later slowdowns; DORA links AI to lower stability (RCT; QE; SURVEY; Section 5).

### Gaps
- Most implications rest on Python issue-resolution benchmarks, mid-2025 to early-2026 models, or vendor evaluations; none was tested on solo game modding (C++/C#), browser games, or long multi-day solo projects.
- No study measures an end-to-end "lean vs heavy" Claude Code configuration on the same project, which is the comparison the redesign most needs; a small personal A/B on real tasks would be the only direct evidence available.
