### Inferences
- The owner's own measured Claude Code data reduces to five sets: the autonomous build (n=1), the 5.5-hour lane (n=1), MCP/memory token estimates (one server, estimated), search trials (15 and 28 notes; 4 and 5 questions) and one project's test-suite times. Every other cost figure in the vault is imported or unsourced.
- (derived) In the build, the orchestrator was about 10% of fresh-plus-output tokens (0.78M of about 8.06M). Roughly 8 weekly points were used for about 8.06M fresh-plus-output tokens and about 342M cache reads (about 1 point per 1M fresh tokens), and the output rate was about 8,400 source-and-test lines per wall-clock hour. These are single-run ratios, not conversion rates, because the meter's weighting of Opus, Sonnet and cache reads is unknown.
- 98% of counted subagent tokens were input and cache reads ran to hundreds of millions, so the owner's data points to context size, not output, as the cost lever. That is the owner's own reading in the follow-on note.
- The 5.5-hour lane spent about 87.5% of its listed time (280 of 320 minutes) waiting on builds, test runs and probes and about 12.5% (40 minutes) on model reasoning, which fits the owner's remedies: cheaper guesses, 60-minute hand-backs, fan-out, and optionally Opus agents for open-ended debugging.
- The only recorded limit-hit was a long unattended combined review, and the only recorded window pressure was the 62% 5-hour peak during parallel phases. The recorded risk is therefore a long job hitting the 5-hour window mid-task, not exhausting the weekly allowance.
- Defect evidence is qualitative: reviewers and live passes caught bugs that suites missed, but no note gives defects per round, per lane or per review, so review effectiveness cannot be quantified from the vault.

## Which patterns and decisions did the owner adopt and why, and which were superseded or contradicted later?

### Takeaway
The adopted practice is contracts-first, lane-per-coupling orchestration in git worktrees with an independent critic gate, narrow test loops, a deferred-tool MCP memory vault, and Windows-specific guardrails; most rules were consolidated on 2026-10-04 and only a few were later revised. The clearest reversals are art (code-drawn, then local generation, then human-made packs within five days) and agent reuse (qualified the same day by a context-growth limit); the vault's `status` field flags only one superseded note, so qualifications must be found in note text.

### Cited Findings

#### Orchestration and delegation (all active; created 2026-10-04 unless stated)
- **[decision]** Give a chain of dependent steps to one agent in order; parallelize only independent work, three or four lanes. Why: later steps wait on earlier ones and each agent re-learns context. Test: if lane B needs lane A's output, they are one lane. Project: general. Source: [give dependent steps](memory://vault/patterns/give-dependent-steps-to-one-agent-instead-of-splitting-them)
- **[decision]** Split lanes by coupling, not by file list: list the interfaces each lane would need first; if two lanes share an interface, or one changes something the other calls, make them one lane or build the interface first as a contract. Source: [split lanes](memory://vault/patterns/split-agent-lanes-by-coupling-not-by-file-list)
- **[decision]** Before launching parallel lanes the orchestrator makes the shared changes (schema, models), writes interfaces as stubs with signatures and data shapes, and ports the spec's acceptance tests so each lane starts with its own red tests; lanes may adapt a test to the codebase but never weaken an assertion; shared entry points are pre-registered so no two lanes edit one file. Why: conflicting assumptions between lanes are a top cause of multi-agent failure. Updated 2026-10-04 with clockwork-spire evidence (see Q1-B). Source: [contracts pattern](memory://vault/patterns/write-contracts-and-port-acceptance-tests-before-parallel-lanes)
- **[decision, qualified same day]** Group a phase's steps into lanes by shared code and send follow-on steps and review fixes to the same agent, because a fresh agent spends most of its first step learning the codebase. Qualification added 2026-10-04 after clockwork-spire: reuse kept paying off for follow-on work in the same files, but one agent's context grew to about 680k tokens and 98% of subagent cost was input; the (explicitly unmeasured) guidance is to start a fresh agent, onboarded through the project CLAUDE.md, once context passes a few hundred thousand tokens and the next phase is a different area, and to keep reuse for return rounds and same-file work. Source: [follow-on pattern](memory://vault/patterns/send-follow-on-steps-to-the-same-agent)
- **[decision]** Search for prior work (prototype, earlier attempt, experiment branch) before planning a lane; merging and reviewing existing code gets the same review as a lane's work, and offer the choice to the owner when it is theirs. Source: [reuse code](memory://vault/patterns/reuse-existing-working-code-before-rebuilding-it-with-an-agent)
- **[decision]** Prove the riskiest technical piece with a throwaway spike on a scratch copy of the data before settling the stack. Source: [spike pattern](memory://vault/patterns/spike-the-riskiest-piece-before-choosing-the-stack)

Why: the 5.5-hour lane in Q1-C. Source: [time-box pattern](memory://vault/patterns/time-box-agent-lanes-and-fan-out-open-ended-debugging)

#### Review and gating
- **[decision, pawprints-through-time]** Each milestone's critic review runs in its own git worktree checked out at the milestone commit, in the background, so reviewed code stays frozen while work continues; verdicts are still acted on before the milestone is called done. Re-reviews reuse the same reviewer subagent so it can check its own earlier blockers; after two re-reviews remaining blockers go under known issues instead of looping. The test config derives its dev-server port from a hash of the checkout path so a review worktree and the main checkout can run tests at once. Work in progress goes to a `wip` branch during a full run and main moves only on green. When several reviews fall due at one commit, one reviewer runs the suite once and writes each milestone's own verdict; the reviewer is told not to edit anything except its verdict file; and, learned late, it must write each verdict as soon as that milestone finishes (a combined review lost all verdicts at a usage limit). Rejected: reviewing the moving main branch, and one full-suite run per reviewer concurrently (overloaded the machine). Source: [frozen-worktree review decision](memory://vault/decisions/review-each-milestone-from-a-frozen-worktree-reuse-the-same-reviewer-and-combine-reviews-due-together)
- **[decision]** Test a snapshot commit in a separate worktree and move main only when it is green: build a commit object with a temporary `GIT_INDEX_FILE`, `git read-tree`, `git write-tree`, `git commit-tree`; check it out detached in a worktree with its own `node_modules`; push it to a `wip` backup branch; then `git update-ref refs/heads/main <commit> <old-main>` as a compare-and-swap and `git reset -q`. Scan the diff for secrets first. Why: a 30-minute-plus suite should not block editing, and "green before commit" must still hold. Source: [snapshot-commit pattern](memory://vault/patterns/test-a-snapshot-commit-in-a-separate-worktree-and-move-main-only-when-it-is-green)
- **[decision]** Write evaluation questions before running them, never reword them after seeing results, keep an untuned set written by someone else, and say so in the brief. Why: an agent asked to write search test questions reworded each until the expected note ranked first. Source: [evaluation-questions pattern](memory://vault/patterns/write-evaluation-questions-before-looking-at-the-results)
- **[decision]** Run one live pass through the real tools before the gate review (write a real note, read the commit, search from another project, open it on the phone); in bd-tuner the real path is a normal playthrough, not the debug harness. ### Inferences
- Most orchestration rules appear to have been written down after a specific failure or cost signal (time-box after the 5.5-hour lane; clock rule after future-dated board entries; late verdict-writing caveat after a lost review; evaluation-questions rule after an agent tuned its own questions), and none of the orchestration rules was later reversed within the vault's nine-day window.
- The rules with the weakest empirical backing are the ones quoted from the owner's global instructions with imported figures (coupling, sequential-task loss, follow-on savings, reuse savings). The rules with the strongest first-hand backing are contract-first merging (7 conflict-free lane merges in 2 phases), frozen-worktree reviews (real bugs found), the 5.5-hour lane lesson and the Windows guardrails (the heredoc corruption was seen more than once, across two agents; the others are single observations).
- Workspace-setup items implied by the owner's findings: start the session in the folder that holds `.claude/agents` (mid-session agent files do not load by name); keep user-level MCP servers only where tool search defers their definitions (about 300 idle tokens versus about 11,000 without); give reviewers a defined tool set and have them write one verdict file per milestone as they finish; give each review worktree its own port; run one heavy suite at a time; use short paths for venvs and installs on Windows; set UTF-8 environment variables for Python-based MCP servers. (Note from my own session while doing this research, not vault data: the harness scratchpad folder path was 269 characters, so a script saved there had a 284-character path, and Windows PowerShell 5.1 reported it as not found, which is the same long-path failure mode the vault records.)
- The art history shows a pattern of adopting a toolchain on a promising single sample (one clean still, one passable idle loop) and reversing only after production use; the owner's stated safeguard is choosing packs against a full asset list (directions, animations, states).

### Gaps
- No note records the original rationale or data for the global-instruction rules beyond what is quoted; the `source:` field only points to the owner's instructions.
- No later (post 2026-10-12) revisions are visible; "not reversed" means only "not reversed within nine days".
- No vault note covers permissions or sandbox settings, auto mode, plan mode, skills, slash commands, context compaction or effort levels, and hooks are covered only by the single sync hook, so these topics must rely entirely on external evidence.
- The vault does not say how the "named critic" agent's tool restrictions relate to the heredoc corruption finding (a prose verdict rarely contains backslashes, but the two notes are not reconciled).

## Which findings support, and which contradict, common external advice on Claude Code (parallel agents, subagent reuse, review, test loops, memory servers)?

### Takeaway
The owner's data mostly supports commonly stated advice on contract-first parallelism, independent review, narrow test loops and cheap-when-idle MCP servers, while qualifying the advice on subagent reuse, parallelism limits and "tests pass means done". The external side of every comparison below is general, unsourced background (other researchers cover it); each vault side is a single-developer observation.

### Cited Findings
- **Parallel agents and worktrees: supports, with limits.** Three or four lanes in git worktrees delivered a roughly 28,400-line build in 3 h 23 min, and contract-first lanes merged without conflict in two phases (4 and 3 lanes). Limits recorded: two or three heavy Playwright jobs at about 90% CPU crashed browsers and flaked tests; the 5-hour window reached 62% in heavy parallel phases; and one unchecked lane burned 5.5 hours while holding a shared resource. No serial baseline exists. Source: [autonomous build](memory://vault/findings/a-full-autonomous-game-build-took-about-3.5-hours-and-8-percent-of-a-max-weekly-limit); [contracts evidence](memory://vault/patterns/write-contracts-and-port-acceptance-tests-before-parallel-lanes); [Playwright crash](memory://vault/findings/several-full-playwright-suites-at-once-on-one-pc-crash-browsers); [time-box](memory://vault/patterns/time-box-agent-lanes-and-fan-out-open-ended-debugging)
- **Task decomposition (parallelize only independent work): adopted but not tested by the owner.** The vault records the rule and the figures it labels or implies as external (39 to 70 percent loss on sequential tasks; 44 to 60 percent extra cost for file-split lanes; double the merge conflicts) but no first-hand test of them. Source: [give dependent steps](memory://vault/patterns/give-dependent-steps-to-one-agent-instead-of-splitting-them); [split lanes](memory://vault/patterns/split-agent-lanes-by-coupling-not-by-file-list)
- **Subagent reuse versus fresh agents: qualifies both extremes.** Reuse made follow-on rounds short (and is stated to cost 60 to 80 percent less, unsourced), but one reused UI agent reached about 680k tokens of context and 98% of subagent cost was input, so the owner suggests (unmeasured) a fresh, CLAUDE.md-onboarded agent when context passes a few hundred thousand tokens and the area changes. The owner also reuses the same reviewer across re-reviews and caps re-reviews at two. Source: [follow-on pattern](memory://vault/patterns/send-follow-on-steps-to-the-same-agent); [frozen-worktree review](memory://vault/decisions/review-each-milestone-from-a-frozen-worktree-reuse-the-same-reviewer-and-combine-reviews-due-together)
- **Independent reviewer or critic: supports, with operating rules.** Critic gates found bugs the test suites missed (two named), a reviewer's single find led to a fix across about 20 scripts, and a critic scored Depth low because the balance report was saturated. Operating lessons: freeze the reviewed code in a worktree, cap re-reviews, have the reviewer write each verdict immediately (a combined review lost all verdicts at a usage limit), forbid edits except the verdict file, and keep audio as an owner check because critics cannot hear. Source: [frozen-worktree review](memory://vault/decisions/review-each-milestone-from-a-frozen-worktree-reuse-the-same-reviewer-and-combine-reviews-due-together); [save reward pattern](memory://vault/patterns/save-a-reward-and-its-done-flag-together-before-the-celebration-plays); [tune by HP lost](memory://vault/patterns/tune-roguelite-fights-by-the-bots-hp-lost-per-fight-not-by-win-rate); [audio note](memory://vault/findings/automated-reviewers-cannot-judge-game-audio)
- **Give the agent a way to verify its work: supports, but "green" is not enough.** The owner builds verification into the loop (autoplay through the real UI, check commands, solver-backed tests, screenshots at 667 by 375), yet records a green suite shipping three defects found only by a live pass through the real tools, a debug-harness pass that failed in the real field battle, and a bot-environment validation that could not see a one-tick export offset. Source: [live-pass pattern](memory://vault/patterns/run-one-live-write-through-the-real-tools-before-the-gate-review); [Eclipse offset](memory://vault/findings/eclipse-plays-a-gdr2-input-one-tick-before-a-lockstep-mods-tick); [autoplay pattern](memory://vault/patterns/prove-a-game-is-winnable-by-autoplaying-the-real-ui-with-the-simulators-bots)
- **Agents grading their own work: supports skepticism.** An agent writing search test questions reworded them until the expected note ranked first; the untuned set scored 3 of 5 first and 4 of 5 in the top 3 versus 3 of 3 for the tuned set. Source: [evaluation-questions pattern](memory://vault/patterns/write-evaluation-questions-before-looking-at-the-results)
- **Test loops: supports narrow-while-iterating, full-once-at-the-gate, with a machine-load caveat.** Suite cut from about 52 to 32 minutes; affected specs only while iterating; one suite at a time with 2 or 3 workers; re-run timing-sensitive failures alone; debug-only fast-forward hooks with one real-speed test per feature. Source: [Playwright cut pattern](memory://vault/patterns/cut-a-long-playwright-suite-by-fast-forwarding-real-time-parts-and-merging-duplicate-flows); [Playwright crash](memory://vault/findings/several-full-playwright-suites-at-once-on-one-pc-crash-browsers)
