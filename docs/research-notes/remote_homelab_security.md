## 1. Windows-native vs WSL2 vs a remote Linux VM: tradeoffs and what Anthropic supports

### Takeaway
Anthropic supports all three (native Windows, WSL2, and a remote Linux machine driven from the Desktop app over SSH), but the built-in OS sandbox exists only on Linux, macOS and WSL2: native Windows, including a Windows machine used as an SSH target, runs commands unsandboxed. So the Windows desktop fits Windows-only toolchains (C++/C# mods) under prompts or auto mode, while the Linux VM (or WSL2) is the place for anything unattended, sandboxed, or run with bypass-permissions.

### Cited Findings

**What Anthropic supports**
- The setup page lists three Windows options: native Windows (requires nothing, Git for Windows optional, sandboxing "Not supported"), WSL 2 (sandboxing "Supported", recommended for "Linux toolchains or sandboxed command execution"), and WSL 1 (sandboxing "Not supported") | [Setup docs](https://code.claude.com/docs/en/setup)
- System requirements: macOS 13+, Windows 10 1809+ or Server 2019+, Ubuntu 20.04+, Debian 10+, Alpine 3.19+; 4 GB+ RAM; x64 or ARM64; shell Bash, Zsh, PowerShell or CMD | [Setup docs](https://code.claude.com/docs/en/setup)
- The sandbox page says native Windows is "Not supported. Claude Code runs commands unsandboxed there", WSL1 is not supported (error text `Sandboxing requires WSL2`), and WSL2 is supported | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- For "Work on a native Windows host" the sandbox-environments page recommends "A container or VM, or run the Bash sandbox inside WSL2" | [Sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- Desktop app Code tab environments: Local, Cloud, SSH (remote Linux, macOS or Windows machine), and WSL (a WSL 2 distribution) | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Windows as an SSH *target* needs Desktop v2.31226.0+ and Microsoft's OpenSSH Server. Anthropic says Windows remotes "get less testing than Linux ones", Claude runs unsandboxed there, the terminal does not open for Windows-path folders such as `C:/projects/app`, worktrees are forced into `<project-root>/.claude/worktrees/`, and the helper may keep running after a session ends | [Desktop docs](https://code.claude.com/docs/en/desktop)
- A dedicated VM "provides the strongest separation" and is Anthropic's pick for evaluating untrusted code; the same page lists cloud sessions as the no-infrastructure alternative (needs a subscription plus GitHub, or `claude --cloud` to upload a local repo) | [Sandbox environments](https://code.claude.com/docs/en/sandbox-environments)

**Native Windows: shell, hooks and tool quirks**
- With Git for Windows installed, the Bash tool runs in Git Bash and the PowerShell tool is available alongside it (on by default for claude.ai and Console accounts; `CLAUDE_CODE_USE_POWERSHELL_TOOL=1/0` toggles it for other providers). Without Git for Windows, only the PowerShell tool is used. Override the Git Bash location with `CLAUDE_CODE_GIT_BASH_PATH` | [Setup docs](https://code.claude.com/docs/en/setup)
- PowerShell tool limits during its preview: profiles are not loaded, sandboxing is not supported on Windows, it runs with process-scope `-ExecutionPolicy Bypass`, and `grep`/`rg`/`git diff` exit code 1 can display as an error even when it is a normal result | [Tools reference](https://code.claude.com/docs/en/tools-reference)
- Silent gotcha: a scoped `Bash` deny rule turns the PowerShell tool off without a warning unless you set `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` or add a scoped `PowerShell(...)` rule. Hooks that inspect shell commands should match `Bash|PowerShell`, not `Bash` alone | [Tools reference](https://code.claude.com/docs/en/tools-reference)
- Hooks: a command hook can opt into PowerShell with `"shell": "powershell"`. On Windows without Git Bash, a failed or timed-out hook "blocking because Git Bash wasn't found" blocks the tool call. Git Bash can source your profile (for example via `BASH_ENV`) and anything the profile prints pollutes the hook's JSON stdout | [Tools reference](https://code.claude.com/docs/en/tools-reference), [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Permission-rule paths are normalized to POSIX form on Windows (`C:\Users\alice` becomes `/c/Users/alice`), so a `.env` deny rule must be written `//c/**/.env` (one drive) or `//**/.env` (all drives) | [Permissions docs](https://code.claude.com/docs/en/permissions)
- Security page warns against enabling WebDAV or letting Claude Code touch `\\*` paths on Windows, because WebDAV can trigger network requests that bypass the permission system | [Security docs](https://code.claude.com/docs/en/security)
- Desktop on Windows does not read PowerShell profiles; set `PATH` in user or system environment variables and restart Desktop | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Terminal quirks: Windows Terminal supports Shift+Enter with no setup; on Windows a Backspace that arrives as `^H` is read as Ctrl+Backspace unless `CLAUDE_CODE_BS_AS_CTRL_BACKSPACE=0` | [Terminal config](https://code.claude.com/docs/en/terminal-config)
- Credential storage: macOS Keychain, Linux a file with mode 0600, Windows a file that inherits the user-profile ACLs | [Security docs](https://code.claude.com/docs/en/security)
- Updates: native installs auto-update in the background; WinGet (`winget upgrade Anthropic.ClaudeCode`), Homebrew, apt, dnf and apk installs do not. Windows binaries are signed "Anthropic, PBC"; manifests are GPG-signed from v2.1.89 | [Setup docs](https://code.claude.com/docs/en/setup)

**WSL2 specifics**
- Desktop WSL sessions need WSL 2 (WSL 1 unsupported), an installed distro and `git` inside it. The Claude Code process, tools and git run inside the distro with Linux paths. Use them when the repo lives in the distro filesystem, because working on those files from Windows goes through a network filesystem that is "slow and breaks file watching". Limits: no plugins, terminal and connectors may be missing, file pane is view-only, attachments may be image-only, "Merge when ready" is disabled, trust is per distro and folder | [Desktop in WSL](https://code.claude.com/docs/en/desktop-wsl), [Desktop docs](https://code.claude.com/docs/en/desktop)
- If the project sits under `/mnt/c`, search can return fewer results (cross-filesystem read penalty) while `claude doctor` still says OK. Anthropic's fixes: use narrower searches, move the project to `/home/...`, or use native Windows instead | [Troubleshooting](https://code.claude.com/docs/en/troubleshooting)
- v2.1.299 (Oct 2026) fixed sandboxed commands failing on WSL2 with `bwrap: Can't mkdir /mnt/c/Program Files/ClaudeCode` | [Changelog](https://code.claude.com/docs/en/changelog)
- WSL2 VM defaults (Microsoft doc updated 2026-10-16): memory = 50% of Windows RAM, swap = 25% of memory, `networkingMode` default NAT (mirrored needs Windows 11 22H2+), `localhostForwarding` true, `autoMemoryReclaim` default `dropCache`; settings live in `%UserProfile%\.wslconfig` and need `wsl --shutdown` to apply; systemd needs `[boot] systemd=true` in `/etc/wsl.conf` | [Microsoft WSL config](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)

**The Windows host edition**
- This research session's environment block reports "Windows 11 Home 10.0.26200". Search-surfaced forum and Microsoft Q&A threads say WSL2 can run on Windows 11 Home (with Virtual Machine Platform and Windows Hypervisor Platform enabled) but full Hyper-V, including Hyper-V Manager, is not available there; a search-surfaced Claude Code GitHub issue (#31991) is about Cowork, a different Claude Desktop feature that needs Hyper-V, being blocked on Home | [Search-surfaced: Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/3888158/wsl2-stopped-working-suddenly-hcs-e-hyperv-not-ins), [Search-surfaced: Elevenforum](https://www.elevenforum.com/t/win11-home-wsl2-working-but-hyper-v-not-fully-installed-so-cant-run-a-vm.26064/latest), [Search-surfaced: GitHub #31991](https://github.com/anthropics/claude-code/issues/31991)
- Docker's local Sandboxes on Windows list "Windows 11" plus the Windows Hypervisor Platform feature (`Enable-WindowsOptionalFeature -Online -FeatureName HypervisorPlatform -All`) | [Docker Sandboxes install](https://docs.docker.com/ai/sandboxes/install.md)

**Disagreements and tensions in the sources**
- Troubleshooting says to consider native Windows when files sit on `/mnt/c`; the Desktop WSL page says to keep the repo inside the distro and run the session there. Both agree the repo and the tool should be on the same side of the VM boundary, but they recommend opposite fixes | [Troubleshooting](https://code.claude.com/docs/en/troubleshooting), [Desktop in WSL](https://code.claude.com/docs/en/desktop-wsl)

### Inferences
- Suggested split (mine): Linux VM for FastAPI/HTMX apps, Docker Compose work, browser games that build on Linux, and every unattended run; native Windows only for MSVC/.NET game-mod builds that need Windows toolchains; WSL2 on the desktop is optional and mainly useful as a place to get the sandbox on the Windows machine for non-Windows-toolchain repos.
- On native Windows nothing OS-level contains a runaway or injected session, so it relies on permission prompts, auto mode, deny rules, git, and the user not enabling bypass there. Setting `permissions.disableBypassPermissionsMode: "disable"` in the Windows *user* settings is a documented way to lock oneself out of bypass (the docs say it works from any scope); see section 3.
- Because deny rules written for Bash do not cover PowerShell, a Windows deny list should be mirrored for `PowerShell(...)` and hooks should match both tools.
- If using WSL2, keep repos under `/home/<user>` and cap the VM in `.wslconfig` rather than letting it take 50% of RAM.

### Gaps
- No Anthropic or independent benchmark comparing native-Windows and WSL2 Claude Code performance; only the `/mnt/c` caveat above.
- Not verified whether a Windows 11 Home machine can run Docker's local Sandboxes (requires Windows Hypervisor Platform; Home availability of that feature was only seen in forum reports).
- The docs do not say whether the Claude Code CLI inside WSL2 (as opposed to the Desktop WSL session) has the plugin, terminal and connector gaps.

## 2. Using the remote Linux VM: Desktop SSH, Remote Control, tmux over SSH, VS Code Remote-SSH, and long or unattended runs

### Takeaway
There is no single best path. The Desktop app's SSH environment is the most integrated way to drive the VM from Windows and its remote helper keeps a task alive through SSH drops, but with a Claude account sign-in it is explicitly not reliable overnight, and on Windows quitting Desktop loses the running task. For real unattended work the documented pattern is the CLI inside tmux (or `claude --bg` background sessions) on the VM, optionally with Remote Control for phone steering; Remote Control under systemd is still rough in practice.

### Cited Findings

**Desktop app SSH environments**
- Setup: environment selector > New environment > SSH tab > Add SSH connection; fields are name, `user@host` or an `~/.ssh/config` Host alias, port, optional key, and a remote worktree folder | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Linux/macOS target requirements: x86_64 or arm64, glibc 2.17+ or musl, an SSH server with the SFTP subsystem (`Subsystem sftp`), `MaxSessions` above 1 (OpenSSH default is 10), a shell that runs commands sent over SSH, and about 1 GB per connecting user under `~/.claude/remote/` on a non-`noexec` mount. Desktop installs a helper plus Claude Code there on first connect | [Desktop docs](https://code.claude.com/docs/en/desktop)
- The helper "runs the session, which lets Claude keep working if your SSH connection drops" (Desktop v2.31226.0+). Sleep, network loss, or quitting Desktop does not stop the task, but it ends if it finishes, needs you, or hits a limit | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Limits while disconnected: with a Claude-account sign-in "don't count on a task to run overnight" because Desktop renews the task's sign-in only while Desktop is running and connected (can expire in "a few minutes"); remote restart ends the task; Linux hosts with systemd-logind `KillUserProcesses=yes` (exempt via `KillExcludeUsers`) kill it on logout; logind `StopIdleSessionSec` can log out idle terminals, and Desktop's terminal shares the SSH connection on macOS/Linux clients; a new helper version can replace the helper and end a running task; after 30 days without a connection the helper stops and ends all Claude Code processes under it; helper keeps a 16 MiB buffer of recent output | [Desktop docs](https://code.claude.com/docs/en/desktop)
- **Windows client gotcha:** "Desktop on Windows: you don't get the running task back, because Desktop never rejoins after a quit", and the docs advise not quitting Desktop on Windows during a long task. On macOS/Linux clients Desktop can rejoin the process | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Tools that fail while Desktop is disconnected: worktree edit checks on some setups (wait ~30 s then fail), connectors (fail after ~30 s), folder-restriction checks (wait up to 10 min), new workflows (wait up to 10 min). MCP servers that Claude Code starts on the remote host keep working; servers from `claude_desktop_config.json` do not when Desktop is disconnected | [Desktop docs](https://code.claude.com/docs/en/desktop)
- To cut interruptions Anthropic suggests: auto mode, allow rules in the remote `~/.claude/settings.json`, a `PermissionRequest` hook, a `Notification` hook with `permission_prompt`, a `Stop` hook (and `StopFailure` for API errors), all configured on the remote machine. Some actions are never auto-approved even in bypass mode, so a task can still wait forever | [Desktop docs](https://code.claude.com/docs/en/desktop)
- "Test the remote machine": start a short task, quit Desktop mid-task, reopen well after it should be done. Use a login that works without a prompt (key in an SSH agent), also for jump hosts. For a task that must run while the computer is asleep or off, use a cloud session | [Desktop docs](https://code.claude.com/docs/en/desktop)
- SSH config handling: the documented section "Use your SSH configuration" is scoped to macOS and Linux (Desktop runs the system OpenSSH client, v1.37937.0+, OpenSSH 7.6+, honoring `HostName`, `User`, `IdentityFile`, `CertificateFile`, `ProxyJump`, `ProxyCommand`). For Windows the retrievable text only says a "built-in SSH client" is used in some cases, for example a Microsoft Store install or "a Windows computer without Microsoft's OpenSSH 9.4 or later" | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Desktop gives `ssh` 30 s unless `ConnectTimeout` is set; host-approval prompts must be answered within 45 s; `ForwardAgent`, `ForwardX11`, `LocalForward`, `RemoteForward`, `DynamicForward` and `Tunnel` are not applied to Desktop's connection | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Ports and browser: Claude "can't open your app in the Browser pane in SSH sessions"; forward a port yourself with `ssh -N -L 3000:localhost:3000 devbox`; if you see `administratively prohibited` the admin must enable `AllowTcpForwarding` | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Git and GitHub: set up `git` and `gh` on the remote yourself (Desktop doesn't install `gh`), "Merge when ready" is disabled in SSH sessions. Proxy and CA settings must go in the remote `~/.claude/settings.json` (`NODE_EXTRA_CA_CERTS`, not `SSL_CERT_FILE`) | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Desktop sends an OS notification when a session finishes and you are not viewing it | [Desktop docs](https://code.claude.com/docs/en/desktop)

**Remote Control (RC)**
- What it is: a window (claude.ai/code, iOS/Android Claude app) onto a Claude Code process that keeps running on your machine; "Your local Claude Code session makes outbound HTTPS requests only and never opens inbound ports". Session transcript is stored on Anthropic servers while connected; not available to ZDR/HIPAA orgs | [Remote Control docs](https://code.claude.com/docs/en/remote-control)
- Requirements: Pro, Max, Team or Enterprise plan; API keys are not supported; must be signed in with `/login` or `claude auth login`; not available with Bedrock/Vertex/Foundry or when `ANTHROPIC_BASE_URL` is not api.anthropic.com; unavailable if `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` or `DISABLE_GROWTHBOOK` is set; long-lived tokens from `claude setup-token` / `CLAUDE_CODE_OAUTH_TOKEN` "can't establish Remote Control sessions" | [Remote Control docs](https://code.claude.com/docs/en/remote-control)
- Start modes: `claude remote-control` (server mode, many sessions from one process), `claude --remote-control "name"` / `--rc` (interactive plus remote), `/remote-control` or `/rc` inside a session (also in Desktop and VS Code). Flags include `--name`, `--spawn same-dir|worktree|session`, `--capacity N` (default 32), `--permission-mode`, `--continue`/`--session-id` (v2.1.200+). `--sandbox`/`--no-sandbox` were removed from `claude remote-control` in v2.1.300; enable sandboxing in settings instead | [Remote Control docs](https://code.claude.com/docs/en/remote-control), [Changelog](https://code.claude.com/docs/en/changelog)
- Persistence: "If you run `claude` from a terminal on a remote machine, start it inside `tmux` or `screen`". A stopped server's sessions can be brought back with `claude remote-control` / `--continue` for about four hours; in server mode an extended network outage makes the process give up after roughly 10 minutes and exit, while an interactive session keeps retrying | [Remote Control docs](https://code.claude.com/docs/en/remote-control)
- Workspace trust: in an untrusted directory `claude remote-control` asks `Trust <directory>? [y/N]`; when stdin/stdout is not a terminal it fails with `Workspace not trusted`. Trust is never saved for the home directory | [Remote Control docs](https://code.claude.com/docs/en/remote-control)
- Phone features: attach images or files from phone or browser (files are downloaded to the machine and passed as `@` references), commands such as `/model`, `/effort`, `/compact`, `/usage` work remotely, `/plugin` and `/resume` are local-only. Server mode also takes `--chrome` (v2.1.273+) for Chrome on the host machine | [Remote Control docs](https://code.claude.com/docs/en/remote-control)
- Optional Trusted Devices (beta): on Pro/Max you can require device enrollment plus a sign-in no older than 18 hours (Face ID, Touch ID, Windows Hello or passkey) before anyone can view or steer RC sessions | [Remote Control docs](https://code.claude.com/docs/en/remote-control)
- Disable with `disableRemoteControl`; auto-connect via `remoteControlAtStartup` (a `true` in project settings is ignored) | [Remote Control docs](https://code.claude.com/docs/en/remote-control)
- **Practitioner reports on RC as a service (anecdotal):** GitHub #87413 (Claude Code v2.1.233 then v2.1.234, Linux, systemd user unit plus tmux; opened Aug 17, closed "not planned" Sep 21, 2026) says there is no non-interactive consent flag, so units pipe `echo y |`; one commenter on Ubuntu Server 26.04 ran a piped-`y` system unit across 43 starts and 11 reboots without a consent failure; another case lost its link/QR after restart because a new environment ID was created; the `-c` window (~4 h) does not cover reboots | [GitHub #87413 via claudeissues.com](https://claudeissues.com/issue/87413-remote-control-on-always-on-machines-three-reproducible-edges-consent-vs-service). Other search-surfaced reports: with no PTY a systemd `Type=simple` unit exited immediately in v2.1.210 (#77751), and `claude -p` under a service account exited 0 silently when the OS user had not completed interactive onboarding (#95217, Sept 2026) | [Search-surfaced: claudeissues.com results](https://claudeissues.com/issue/77751-bug-claude-remote-control-collapses-into-an-implicit-print-mode-and-exits-immedi)

**CLI in tmux over SSH (practitioner pattern)**
- Andrew Leech (Apr 20, 2026; at the 6-month edge): Pixel 5 with Termux → Tailscale → Eternal Terminal (ET, port 2022) → tmux → Claude Code on a home Linux server; ~40 named tmux sessions across three machines, some alive since January; plain SSH "drops connections constantly" on mobile, mosh "lacks proper scrollback and has rendering problems with Claude Code's TUI", ET reconnects transparently; alias `clauded='claude --dangerously-skip-permissions'` accepted because sessions run in git-tracked project dirs; no notifications mentioned | [Anecdote: alelec blog](https://notes.alelec.net/posts/claude-code-from-anywhere/)
- Search-surfaced homelab write-ups describe the same shape: a dedicated Proxmox VM for Claude Code, reconnect over SSH and reattach tmux, WireGuard or Tailscale for access, ZFS snapshots with sanoid for rollback, and an isolated NAT bridge for the workload VMs | [Search-surfaced: homelab spec](https://adyrem.duckdns.org/git/adyrem/homelab/src/commit/069ad6afac2556ccec63e2e46d78b279807caf16/homelab-requirements.md), [Search-surfaced: OpenReplay guide](https://blog.openreplay.com/remote-box-agentic-coding-setup/)
- tmux settings Anthropic documents so Shift+Enter, desktop notifications and progress reach the outer terminal: `set -g allow-passthrough on`, `set -g focus-events on`, `set -s extended-keys on`, `set -as terminal-features 'xterm*:extkeys'` | [Terminal config](https://code.claude.com/docs/en/terminal-config)

**Background sessions (`claude --bg`, agent view)** (research preview)
- Background sessions run under a separate supervisor, so they "keep working after you close agent view, your shell, or your terminal". `claude --bg "task"`, `/bg`, `claude agents`, `claude attach <name>`, `claude logs`, `claude stop`, `claude daemon status`. SSH disconnects are not addressed explicitly. Machine shutdown stops sessions; sessions under 48 h old then show failed | [Agent view docs](https://code.claude.com/docs/en/agent-view)
- Idle sessions (finished or waiting, unattached for about an hour) have their process stopped to save memory and resume on next reply; pin with Ctrl+T to keep running; each session uses subscription quota independently | [Agent view docs](https://code.claude.com/docs/en/agent-view)
- Permission handling: permission dialogs and sandbox prompts cannot be answered from the peek panel (attach instead); bypass mode needs the bypass disclaimer accepted in `~/.claude/settings.json` or it is ignored; dispatched sessions are isolated in their own worktree; `claude agents --json` gives `state`/`status`/`waitingFor` for scripting | [Agent view docs](https://code.claude.com/docs/en/agent-view)
- Network/proxy variables must go in `settings.json` `env`, not the shell, because the shared supervisor inherits whichever shell started it first; the `processWrapper` setting can prefix the supervisor and workers with a launcher | [Network config docs](https://code.claude.com/docs/en/network-config)

**Headless mode and scheduled jobs**
- `claude -p "..."` with `--output-format json|stream-json`, `--allowedTools`, `--permission-mode`, `--continue/--resume`, `--max-budget-usd`; since v2.1.302 `-p` with no mode set starts in Manual (calls needing approval are denied); `--permission-prompts none` (v2.1.259+) denies anything that would prompt; SIGTERM exits 143 and skips the in-flight turn | [Headless docs](https://code.claude.com/docs/en/headless), [Permission modes](https://code.claude.com/docs/en/permission-modes)
- `--bare` skips hooks, skills, MCP, CLAUDE.md and "doesn't use your subscription login" (needs `ANTHROPIC_API_KEY` or `apiKeyHelper`); Anthropic says it will become the default for `-p` | [Headless docs](https://code.claude.com/docs/en/headless)
- `claude -p` shows no trust dialog and, without `--bare`, runs a repo's project hooks and `.mcp.json` servers even in a never-trusted folder; for untrusted repos use `--bare`, `--setting-sources user`, or `--settings '{"disableAllHooks": true}'` | [Permissions docs](https://code.claude.com/docs/en/permissions), [Headless docs](https://code.claude.com/docs/en/headless)
- `claude setup-token` creates a long-lived token for CI (`CLAUDE_CODE_OAUTH_TOKEN`), usable for model requests but not Remote Control | [Env vars](https://code.claude.com/docs/en/env-vars), [Remote Control docs](https://code.claude.com/docs/en/remote-control)
- systemd specifics: `loginctl enable-linger USER` spawns the user manager at boot and keeps it after logout so non-logged-in users can run long-running services | [systemd loginctl](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html)
- Install on the VM via signed apt repo (stable or latest channel) or native installer; package-manager installs do not self-update; native installer auto-updates and keeps only the two newest versions plus the active one | [Setup docs](https://code.claude.com/docs/en/setup)

**VS Code Remote-SSH**
- Extension needs VS Code 1.94+; in a window connected to WSL, an SSH host or a dev container the docs tell you to edit `~/.claude/settings.json` on that remote system, implying the extension and its config live on the remote side. `/remote-control` works from the VS Code prompt | [VS Code docs](https://code.claude.com/docs/en/vs-code), [Remote Control docs](https://code.claude.com/docs/en/remote-control)
- Remote-SSH Linux host needs glibc 2.28+, kernel 4.18+, libstdc++ 3.4.25+, `tar`, `curl` or `wget`; Ubuntu 20.04+ supported; Alpine not supported for Remote-SSH | [VS Code Linux prerequisites](https://code.visualstudio.com/docs/remote/linux)
- Memory: the official prerequisites page gives no RAM figure. A search-surfaced forum answer quotes 1 GB minimum and 2 GB / 2 cores recommended for the remote host, and reports that opening a whole filesystem root or heavy TypeScript IntelliSense can exhaust RAM on small hosts; a VS Code issue reports remote high CPU and OOM only on versions newer than 1.120.0 | [Search-surfaced: Cursor forum](https://forum.cursor.com/t/remote-server-access-causes-high-memory-usage-and-system-freeze/175132), [Search-surfaced: microsoft/vscode#324188](https://github.com/microsoft/vscode/issues/324188)

**Auth and credentials on the VM**
- Credentials live under `~/.claude` (token, settings, history) and `~/.claude.json`; a dev container warning says a malicious project can exfiltrate "anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`". Avoid mounting `~/.ssh` or cloud credential files; prefer repo-scoped or short-lived tokens | [Dev container docs](https://code.claude.com/docs/en/devcontainer)
- Headless login: if the browser callback cannot reach the machine, copy the code from the browser and paste it at the `Paste code here if prompted` prompt | [Dev container docs](https://code.claude.com/docs/en/devcontainer)
- `/heapdump` writes a `.heapsnapshot` to `~/Desktop` (home dir if none) that "contains every string in the process, including your full conversation and credentials"; never share or leave it around | [Troubleshooting](https://code.claude.com/docs/en/troubleshooting)
- Sandbox credential handling (v2.1.221+): `sandbox.credentials` can `deny` files/env vars or `mask` them so a command only sees a sentinel and the proxy substitutes the real token for allowed hosts; masking needs `network.tlsTerminate` and is honored only from user, managed or `--settings` scope | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing)

**Clipboard, images, browser testing**
- Over SSH, `/copy` and fullscreen selection send OSC 52 to the local terminal (some terminals ignore it: iTerm2 needs "Applications in terminal may access clipboard", macOS Terminal.app does not support it); `/copy` also writes the text to a file and prints the path as a fallback; `CLAUDE_CODE_DISABLE_MOUSE=1` on the remote hands selection back to the terminal | [Troubleshooting](https://code.claude.com/docs/en/troubleshooting)
- Inside the sandbox, `xclip`/`pbcopy`/`wl-copy` may not reach the clipboard; use `/copy` | [Troubleshooting](https://code.claude.com/docs/en/troubleshooting)
- Images: no documented way to paste a Windows-clipboard image into a CLI session over SSH was found. The documented route is attaching photos or files from the phone or browser in an RC session (Claude sees photos directly; other files are downloaded to the machine and passed as `@` references) | [Remote Control docs](https://code.claude.com/docs/en/remote-control). In the other direction, the VS Code docs say Claude can send files to you in an RC-connected session with the `SendUserFile` tool (v2.1.295+) | [VS Code docs](https://code.claude.com/docs/en/vs-code). Whether the Desktop app's attachment menu works in SSH sessions was not confirmed.
- Headless Chromium under the Linux sandbox: Chromium needs `--no-sandbox` or an `excludedCommands` entry, or `sandbox.allowNestedUserNamespaces` (v2.1.305, "disables a security boundary") | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing), [Changelog](https://code.claude.com/docs/en/changelog)

**Disagreements and tensions**
- Anthropic's RC page recommends running a remote CLI inside tmux/screen, while Anthropic's agent-view page offers a supervisor-based alternative; neither states which is better for SSH drops. The Desktop page recommends against relying on its SSH mode for overnight tasks with a Claude-account sign-in, while the Windows-quits-lose-the-task limit is stated only for Desktop on Windows.
- Practitioner (Leech) found mosh poor for Claude Code's TUI; I found no source arguing the opposite, but also no Anthropic guidance on mosh.

### Inferences
- Likely best fit for this setup (mine): (a) daily interactive work through the Desktop SSH environment to `dev` using a key held by the Windows ssh-agent and a Tailscale MagicDNS hostname; (b) for overnight or multi-hour runs, SSH to the VM, start `tmux`, run `claude auth login` once on the VM (full-scope login), then `claude --remote-control` (or `claude remote-control --spawn worktree --capacity 2`) so the phone can steer; (c) for scripted jobs use `claude -p --permission-mode ... ` from a systemd timer with a `setup-token` credential, remembering it cannot do RC and `--bare` needs an API key.
- Because Desktop-on-Windows loses the task when quit and renews a Claude-account sign-in only while connected, treat Desktop SSH as the interactive tool, not the overnight tool. Keep Desktop's integrated terminal idle and run your own commands from a separate SSH login (Anthropic's own advice) so logind idle logout does not take the connection down.
- Do not point Tailscale SSH `check` mode at the path Desktop uses: Desktop reconnects only where it can log in without a prompt (and approvals must land inside 45 s), while `check` mode forces periodic browser re-authentication. Plain OpenSSH keys over the tailnet, or Tailscale SSH in `accept` mode, avoid that conflict. (Inference from [Tailscale SSH docs](https://tailscale.com/kb/1193/tailscale-ssh) and the Desktop limits above; not tested.)
- RC under systemd is possible but unsupported in practice; tmux (optionally launched by a systemd user unit with `loginctl enable-linger`) gives a PTY and sidesteps the TTY and consent issues.
- Because Desktop does not forward the ssh-agent, Git on the VM needs its own credential. A narrow deploy key or fine-grained, repo-scoped token for the VM follows Anthropic's "repository-scoped or short-lived tokens" advice and limits what a compromised session can push.
- For browser testing, forward the app port to the Windows browser, or run headless Playwright/Chromium on the VM (needs a sandbox exception); Claude-in-Chrome style tools run on the machine that has Chrome, not on the VM.

### Gaps
- Not found: what ssh executable and config handling the Windows Desktop app uses for SSH environments (docs retrievable cover macOS/Linux; Windows may use a built-in client). Worth a 5-minute test with `ssh -V` and a `Host dev` alias.
- Not found: whether Desktop SSH sessions leave a long-lived credential on the VM or only a short-lived token (the "renews only while connected" language suggests the latter).
- Not found: an official systemd recipe, or a supported non-interactive consent flag, for Remote Control; evidence is limited to closed GitHub issues and search-surfaced reports.
- Not found: official guidance on mosh/Eternal Terminal; only the one practitioner report.
- Not found: authoritative VS Code Remote-SSH memory numbers; only forum hearsay.
- Not found: how to paste images into a CLI session over SSH from Windows Terminal.

## 3. Sandboxing and isolation: built-in sandbox, devcontainers, Docker Sandboxes, bypass-permissions, Proxmox snapshots

### Takeaway
Anthropic's own guidance is layered: the built-in Bash sandbox (bubblewrap on Linux) is a convenience and defense layer but is explicitly not enough for fully unattended runs; bypass-permissions or unattended auto mode belongs inside a container, a VM, or the sandbox runtime, running as a non-root user, ideally with an egress allowlist. A dedicated VM with Proxmox snapshots is the strongest option Anthropic names for untrusted code, but snapshots roll back everything on the VM and are not backups.

### Cited Findings

**Built-in sandbox on Linux (and where it is missing)**
- Platforms: macOS (Seatbelt), Linux and WSL2 (bubblewrap for filesystem, socat for the network relay, optional seccomp filter blocking Unix sockets); not native Windows, not WSL1. It is **off by default**, **fail-open** unless `failIfUnavailable: true`; built on the open-source `@anthropic-ai/sandbox-runtime` | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- Install: `sudo apt-get install bubblewrap socat`; `/sandbox` shows missing dependencies; restart Claude Code after installing. On Ubuntu 24.04+, AppArmor can block bubblewrap's user namespaces: check `sysctl kernel.apparmor_restrict_unprivileged_userns`; if it returns 1, add an AppArmor profile for `/usr/bin/bwrap` that includes `userns,` and reload AppArmor. v2.1.310 improved `/sandbox` and the startup warning to name this restriction | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing), [Changelog](https://code.claude.com/docs/en/changelog)
- Defaults: writes limited to the working directory, per-user temp dir and `--add-dir` dirs; reads of "most of the machine, including `~/.ssh` and `~/.aws/credentials`"; no direct network route (traffic goes through a local proxy with an initially empty `allowedDomains`); env vars inherited unless `credentials.envVars` or `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- Key settings: `sandbox.enabled`, `failIfUnavailable`, `autoAllowBashIfSandboxed` (default true), `allowUnsandboxedCommands` (default true; set false so a failed command cannot be retried with `dangerouslyDisableSandbox`), `excludedCommands`, `filesystem.allowWrite/denyWrite/denyRead/allowRead`, `network.allowedDomains/deniedDomains/strictAllowlist (v2.1.219+)/allowLocalBinding/allowUnixSockets`, `credentials.files/envVars`, and the weaker-mode switches `enableWeakerNestedSandbox` (containers without a fresh /proc) and `allowNestedUserNamespaces` (v2.1.305) | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- What it does **not** cover: typed `!` commands, hooks, MCP servers, status line, LSP and `apiKeyHelper` run outside the sandbox; Read/Edit/WebFetch/WebSearch are governed by permission rules, not the sandbox; writes to `$PATH` dirs or shell rc files can lead to code execution outside it | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- Known incompatibilities and limits: `docker` (use `excludedCommands`, which run with full access), `jest` with watchman, rootless Podman/Buildah, Chromium without `--no-sandbox`; UDP, QUIC/HTTP3 and ICMP are blocked; plain `ssh` and most DB drivers ignore proxy variables and fail even for allowed hosts; the proxy does not inspect TLS so domain fronting can reach non-allowlisted hosts and broad allows like `github.com` enable exfiltration; allowing `/var/run/docker.sock` grants host access | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- The `docker` group "grants root-level privileges to the user", so any Claude session that can run `docker` is root-equivalent on the VM; Docker's rootless mode is the documented alternative | [Docker post-install docs](https://docs.docker.com/engine/install/linux-postinstall/)
- Recent fixes show this layer is still being hardened: v2.1.309 fixed sandboxed Bash running shell startup files outside the sandbox and write denies not lifting on Linux when a background command outlived the session; v2.1.304 fixed `denyRead` globs containing brackets | [Changelog](https://code.claude.com/docs/en/changelog)
- Search-surfaced advisories: CVE-2026-25725 (bubblewrap sandbox did not protect a missing `.claude/settings.json`, fixed in 2.1.2), CVE-2026-25724 (deny rules not enforced through symlinks, fixed in 2.1.7), CVE-2026-39861 (symlink-assisted sandbox escape, fixed in 2.1.64) | [Search-surfaced: GitLab advisory CVE-2026-25725](https://advisories.gitlab.com/npm/@anthropic-ai/claude-code/CVE-2026-25725/), [CVE-2026-25724](https://advisories.gitlab.com/pkg/npm/@anthropic-ai/claude-code/CVE-2026-25724), [CVE-2026-39861](https://advisories.gitlab.com/npm/@anthropic-ai/claude-code/CVE-2026-39861/)
- Anthropic's launch post (Oct 20, 2025, **>6 mo**) claimed sandboxing "safely reduces permission prompts by 84%" in internal use and that filesystem plus network isolation are both required; it is vendor-measured and the sandbox runtime was a beta research preview | [Anthropic engineering blog](https://www.anthropic.com/engineering/claude-code-sandboxing)

**Sandbox runtime (`srt`) for the whole process**
- `npm install -g @anthropic-ai/sandbox-runtime`, then `srt claude` wraps the entire Claude Code process (file tools, MCP servers and hooks included) in the same Seatbelt/bubblewrap isolation. Config in `~/.srt-settings.json`; default is no network and writes only to a few runtime paths; allow your project dir, `~/.claude`, `~/.claude.json`, `/tmp`, plus `api.anthropic.com`, `claude.ai`, `platform.claude.com`. On Linux the deny list is built once at launch, so nested repos created later (`git init`, `git clone`) are not covered. Research preview; config format may change | [Sandbox environments](https://code.claude.com/docs/en/sandbox-environments)

**Anthropic's own selection guide**
- The bash sandbox on its own "constrains only shell commands, so it is not sufficient for fully unattended runs in either mode" (bypass or auto). Always run `--dangerously-skip-permissions` "inside a container, a VM, or the sandbox runtime". Auto mode's classifier "is a per-action control, not an isolation boundary" but isolation is not required with it the way it is with bypass | [Sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- Bypass details: deny rules still apply in every mode; allow rules have no effect; protected-path writes are allowed; the CLI refuses to start in bypass as root (or under sudo) on Linux/macOS unless inside a recognized sandbox; `--restricted` sessions (v2.1.248+) refuse it; the docs say bypass "offers no protection against prompt injection or unintended actions" and recommend containers/VMs "without internet access" running as non-root; admins can block it with `permissions.disableBypassPermissionsMode: "disable"` and a user can set it in their own settings | [Permission modes](https://code.claude.com/docs/en/permission-modes), [Permissions docs](https://code.claude.com/docs/en/permissions)
- In Desktop, bypass is behind **Settings > Claude Code > Allow bypass permissions mode** for Pro/Max users; cloud sessions do not offer bypass | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Auto mode (Anthropic engineering post, Mar 25, 2026, **>6 mo**): two-stage classifier on Sonnet 4.6 seeing only user messages and tool calls; measured false-positive 0.4% (n=10,000 real internal calls), false-negative 17% on 52 real overeager actions and 5.7% on 1,000 synthetic exfiltration attempts; Anthropic calls 17% "the honest number" and says auto mode is not a drop-in replacement for human review on high-stakes infrastructure | [Anthropic auto mode post](https://www.anthropic.com/engineering/claude-code-auto-mode). Docs: auto mode "reduces permission prompts but does not guarantee safety"; three consecutive or 20 total blocks pause it; by default it blocks `curl | bash`, force pushes, prod deploys and sending sensitive data out, but allows reading `.env` and sending credentials to their matching API | [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Auto mode is the built-in starting mode for terminal and VS Code sessions since v2.1.283; `-p` runs start in Manual since v2.1.302; `"auto"` or `"bypassPermissions"` as `defaultMode` in *project* settings is ignored | [Permission modes](https://code.claude.com/docs/en/permission-modes), [Security docs](https://code.claude.com/docs/en/security)

**Reference devcontainer**
- Claude Code installs into any devcontainer via the feature `ghcr.io/anthropics/devcontainer-features/claude-code:1.0` (pins the script, not the CLI; the CLI auto-updates unless `DISABLE_AUTOUPDATER=1`). Persist login with a named volume on `~/.claude` plus `CLAUDE_CONFIG_DIR` set to the same path. `/etc/claude-code/managed-settings.json` inside the image takes highest precedence | [Dev container docs](https://code.claude.com/docs/en/devcontainer)
- The reference container (`anthropics/claude-code/.devcontainer`: `devcontainer.json`, `Dockerfile`, `init-firewall.sh`) is "a working example rather than a maintained base image"; the firewall needs `NET_ADMIN` and `NET_RAW`; `--dangerously-skip-permissions` is acceptable because it runs non-root with the egress limit, but "dev containers do not prevent a malicious project from exfiltrating anything accessible inside the container" | [Dev container docs](https://code.claude.com/docs/en/devcontainer)
- From an automated read of `init-firewall.sh` (verify against the source): iptables plus an ipset, default policy DROP, allows GitHub ranges from `api.github.com/meta`, registry.npmjs.org, api.anthropic.com, sentry.io, statsig.com and VS Code endpoints (resolved once at start), allows the whole /24 of the default gateway, allows outbound DNS and SSH to anywhere, IPv4 only (no ip6tables), verifies by expecting example.com to fail. Weaknesses noted: IP-based allowlist goes stale on CDNs, allowing all of GitHub is an exfiltration path (attacker repos or gists), IPv6 left open | [init-firewall.sh](https://github.com/anthropics/claude-code/blob/main/.devcontainer/init-firewall.sh) (analysis is a model summary of the script)
- Trail of Bits publishes a stricter per-project `claude-code-devcontainer` for audits and untrusted repos, and `dropkit` for disposable cloud droplets with Tailscale | [Trail of Bits config](https://github.com/trailofbits/claude-code-config)

**Hardened plain Docker (Agent SDK guide)**
- Anthropic's example for a container-run agent: `--cap-drop ALL`, `--security-opt no-new-privileges`, a custom seccomp profile, `--read-only`, `tmpfs` for `/tmp` and home with `noexec`, `--network none` plus a mounted Unix socket to a host-side proxy that enforces allowlists and injects credentials, `--memory 2g --cpus 2 --pids-limit 100`, `--user 1000:1000`, code mounted read-only, never `~/.ssh`/`~/.aws`/`~/.config` | [Secure deployment guide](https://code.claude.com/docs/en/agent-sdk/secure-deployment)
- Isolation ladder from the same guide: sandbox runtime (good, very low overhead, same kernel, no TLS inspection), Docker (setup dependent), gVisor (excellent, medium/high overhead: simple syscalls ~2x slower, file-I/O-heavy workloads up to 10-200x slower), VMs such as Firecracker or QEMU (excellent, high overhead) | [Secure deployment guide](https://code.claude.com/docs/en/agent-sdk/secure-deployment)

**Docker Sandboxes (`sbx`)**
- Docker's `sbx` CLI runs agents in a per-session **microVM with its own kernel and private Docker daemon**; local sandboxes are free (cloud sandboxes are pay-as-you-go). Architecture post dated Apr 16, 2026; an earlier launch post is Jan 30, 2026 (**>6 mo**); the older "Docker Desktop sandboxes" page is marked deprecated | [Docker landing](https://docs.docker.com/ai/sandboxes/), [Docker architecture post](https://www.docker.com/blog/why-microvms-the-architecture-behind-docker-sandboxes/), [Search-surfaced: Docker Desktop sandboxes (deprecated)](https://docs.docker.com/ai/sandboxes/docker-desktop.md)
- Linux requirements: Ubuntu 24.04+ (derivatives not supported), x86-64 or arm64, **KVM enabled** (`lsmod | grep kvm`, user in the `kvm` group) and, inside a VM, **nested virtualization**; install via `curl -fsSL https://get.docker.com | sudo SBX=1 sh` or `REPO_ONLY=1` then `apt install docker-sbx`; `sbx login` uses Docker OAuth. No RAM/CPU/disk figures are stated | [Docker Sandboxes install](https://docs.docker.com/ai/sandboxes/install.md)
- Security defaults: all outbound TCP (HTTP, HTTPS, SSH) blocked unless an allow rule exists (`sbx policy ls`), UDP/ICMP blocked, no credentials unless supplied via `sbx secret` or env vars and then injected by a host-side proxy ("The agent cannot read the raw credential values"); the current directory is mounted read-write with `sbx run` (agent can modify any file there including hidden files and Git hooks); the agent has sudo and full write access inside the VM; host Docker daemon is not reachable | [Docker sandboxes security defaults](https://docs.docker.com/ai/sandboxes/security/defaults.md)
- Proxmox side: nested virtualization needs `options kvm-intel nested=Y` (or `kvm-amd nested=1`) on the PVE host and the guest CPU type set to host (`qm set <vmid> --cpu host`); VMs with nesting active cannot be live-migrated; without hardware extensions nested KVM runs "roughly 10x slower or more" | [Proxmox nested virtualization](https://pve.proxmox.com/wiki/Nested_Virtualization)
- A search-surfaced summary of Docker release notes says Droid OAuth credentials are proxy-managed (tokens stay on the host), but no equivalent statement was found for Claude Code subscription OAuth | [Search-surfaced: sbx release notes](https://newreleases.io/project/github/docker/sbx-releases/release/v0.35.0-rc3)

**Practitioner positions on bypass**
- Trail of Bits runs Claude Code with `--dangerously-skip-permissions` (alias `claude-yolo`) on hosts and says "the sandbox is what keeps the agent from doing damage", while noting built-in `/sandbox` still leaves `~/.ssh` and `~/.aws` readable and recommending the devcontainer for stronger read/write isolation; it adds deny rules for those paths and says "Hooks are not a security boundary" | [Trail of Bits config](https://github.com/trailofbits/claude-code-config)
- Leech runs bypass on a home server in git-tracked project dirs with no extra isolation mentioned | [Anecdote: alelec blog](https://notes.alelec.net/posts/claude-code-from-anywhere/)
- Real-world precedent that AI CLIs with permissive flags are a post-compromise tool: in the Nx "s1ngularity" npm attack (Aug 2025, **>6 mo**) malware drove installed Claude, Gemini and Q CLIs to help find secrets; JFrog's write-up does not name the flag, other vendors report `--dangerously-skip-permissions`/`--yolo`/`--trust-all-tools`; GitGuardian counted 2,349 leaked credentials across 1,079 systems | [JFrog](https://research.jfrog.com/post/nx-supply-chain-attack-targets-ai-tool-users/), [Search-surfaced: GitGuardian](https://blog.gitguardian.com/the-nx-s1ngularity-attack-inside-the-credential-leak/)

**Proxmox snapshots and rollback**
- Commands: `qm snapshot <vmid> <name>` (add `--vmstate 1` on a running VM to also save device state and RAM into a volume on the state storage), `qm rollback <vmid> <name>`, `qm delsnapshot <vmid> <name>`. Rollback "destroys the current VM state (even if running) and disks"; with saved RAM the VM resumes live. PVE pauses vCPUs and flushes pending I/O at the QEMU block layer to keep multiple disks consistent. Source is a **proposed documentation patch dated 2026-07-14** on the pve-devel list, not the published manual | [pve-devel docs patch](https://lore.proxmox.com/all/20260714142629.277917-5-f.ebner@proxmox.com/)
- Storage support (Proxmox wiki table): ZFS, LVM-thin, BTRFS, Ceph RBD, CephFS yes; Directory/NFS/CIFS only with qcow2 images; LVM, iSCSI and FC/SAS get snapshots as volume chains since Proxmox VE 9. Internal qcow2 snapshots on file storage block a running VM while created or deleted, can take minutes or hours on large disks, and perform poorly on NFS | [Proxmox storage wiki](https://pve.proxmox.com/wiki/Storage)
- Search-surfaced guide verified on PVE 8.4.9 / QEMU 9.2.0 says snapshots are not backups because they sit on the same storage as the VM, recommends thin LVM or ZFS, and notes RAM state costs space; forum text says the guest agent triggers fsfreeze/fsthaw for consistent disk state | [Search-surfaced: ComputingForGeeks](https://computingforgeeks.com/proxmox-vm-snapshots/)
- PVE firewall: disabled by default; levels datacenter/node/VM; per-NIC firewall flag also required; rules take IPs, ranges, IP sets and aliases only, **no FQDN filtering**; the nftables-based `proxmox-firewall` is a tech preview (REJECT becomes DROP for guests); Proxmox advises opening an SSH session first and allowing ports 8006 and 22 to avoid lockout (the fetched page was labeled version 9.2.13) | [Proxmox firewall docs](https://pve.proxmox.com/pve-docs/chapter-pve-firewall.html)
- Search-surfaced homelab spec: a dedicated NAT bridge (vmbr2) for Claude Code workload VMs with no route to the LAN unless required; ZFS snapshots via sanoid, daily kept 7 days and weekly kept 4 weeks | [Search-surfaced: homelab spec](https://adyrem.duckdns.org/git/adyrem/homelab/src/commit/069ad6afac2556ccec63e2e46d78b279807caf16/homelab-requirements.md)

**Disagreements**
- Anthropic: bash sandbox alone is "not sufficient for fully unattended runs"; always put bypass inside container/VM/`srt`. Trail of Bits: runs bypass on the host with `/sandbox` doing the safety work (and uses devcontainers for untrusted code). Both are shown; they differ on whether the host sandbox suffices for trusted code.
- Anthropic's docs describe `excludedCommands: ["docker compose *"]` as a normal pattern, yet the same page says excluded commands run with full access and that socket access grants host access; the docs give no safer Docker-in-sandbox pattern.
- Auto mode: Anthropic reports a 17% false-negative rate on real overeager actions; Anthropic's own security page makes auto the *default* starting mode. Reported side by side without resolution.

### Inferences
- Layering that fits this homelab (mine, built from the cited pieces): (1) treat the dev VM itself as the blast-radius boundary and run Claude Code as a dedicated unprivileged user with no `sudo` and **not in the `docker` group**; (2) enable the built-in sandbox with `failIfUnavailable: true` and `allowUnsandboxedCommands: false`, a short `allowedDomains` list, and `denyRead` for credential dirs; (3) for bypass or truly unattended runs use a per-project devcontainer or `srt claude` as non-root with the egress allowlist, and keep Docker access out of it; (4) snapshot before risky runs.
- Docker Compose is the main tension: the sandbox blocks `docker`, `excludedCommands` runs it unsandboxed, and the `docker` group is root. Options are to let Claude edit and have the user (or a small, separately owned wrapper) run `docker compose`, to run rootless Docker for the agent user, or to accept `docker compose *` as an excluded command knowingly. No source prescribes one.
- A sketch of settings built only from documented keys (untested; verify key names in the settings reference, which I did not fetch): `sandbox.enabled`, `sandbox.failIfUnavailable`, `sandbox.allowUnsandboxedCommands: false`, `sandbox.filesystem.denyRead` for `~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.git-credentials`, `~/.docker/config.json`, `sandbox.network.allowedDomains` limited to `api.anthropic.com`, the package indexes and the git host, `sandbox.network.strictAllowlist: true`, plus `env.CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` and `env.CLAUDE_CODE_TOOL_MEMORY_LIMIT`.
- Docker Sandboxes (`sbx`) are a poor fit for an 8 GB, 4-core guest that already runs Compose services: they need nested KVM on Proxmox (`--cpu host`, `nested=Y`), a second kernel and private Docker daemon inside the 8 GB, and their handling of a Max-plan login is unconfirmed. They fit better on the Windows desktop if Windows Hypervisor Platform is available.
- A dedicated agent VM is cleaner than snapshotting the shared dev VM: rollback reverts every disk, including the user's Docker volumes and any concurrent work, so keep irreplaceable data off it (git remotes, Proxmox Backup Server) or use a separate, disposable VM for bypass runs. Take snapshots without `--vmstate` on an 8 GB guest to avoid an 8 GB state volume per snapshot (the state volume holds the RAM). Because the user wants to be asked before data deletion and network/firewall changes, `qm delsnapshot`, rollback and any PVE firewall change should each be explicit approval points.
- Proxmox's firewall cannot allowlist domains; per-domain egress needs Claude's sandbox proxy, the devcontainer firewall, or a forward proxy (for example Squid) on the VM or network.

### Gaps
- Docker Sandboxes with a Claude subscription (Max) login: whether OAuth tokens stay host-side is unconfirmed; RAM/CPU/disk requirements not stated; Windows 11 Home compatibility unverified.
- The `init-firewall.sh` analysis is a model-generated summary of the script; the script itself should be read before relying on those details.
- No source fetched for Proxmox template/clone (`qm clone`) workflows or Proxmox Backup Server; the clone idea above is from general knowledge, not from a cited page.
- Primary advisory pages for the three 2026 CVEs were not opened (search-surfaced only).
- No measurement of bubblewrap sandbox overhead on a 4-core VM (Anthropic's table only says "very low").

## 4. Security baseline: permissions and secrets, MCP and plugin vetting, prompt injection, egress control, Tailscale and SSH, exposed ports

### Takeaway
Experts converge on defense in depth: deny rules for secrets plus the OS sandbox (deny rules alone do not stop Bash), a project-trust discipline (repo files can run code), minimal egress, short-lived scoped credentials, vetted MCP servers and plugins, a private Tailscale-only network with tagged ACLs, and no public ports. No single control is trusted: Anthropic, Trail of Bits and Simon Willison all say filters and hooks are not boundaries.

### Cited Findings

**Permissions and secrets**
- Deny rules are enforced in every mode including bypass; any scope's deny beats allow; `Read(...)` deny covers pasted images and @-mentioned directories and applies to symlink targets. `.claudeignore` "has no effect": use `Read` deny rules. Path anchors: `//abs/path`, `~/home`, `./rel`; a bare `Read(.env)` matches any `.env` under the working directory; use `Read(//**/.env)` for the whole filesystem | [Permissions docs](https://code.claude.com/docs/en/permissions), [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Bash deny rules are not a security boundary: `Bash(curl *)` does not stop `/usr/bin/curl` or `sh -c 'curl ...'`; `Bash(git push *)` does not stop `git -C . push`. Anthropic points to sandbox network isolation and PreToolUse hooks for real enforcement | [Permissions docs](https://code.claude.com/docs/en/permissions)
- Wrapper stripping is limited (`timeout`, `time`, `nice`, `nohup`, `stdbuf`, bare `xargs`); runners like `npx`, `docker exec`, `devbox run` are not stripped, so `Bash(devbox run *)` allows anything after `run` | [Permissions docs](https://code.claude.com/docs/en/permissions)
- Trail of Bits' recommended deny list: Read/Edit denies for `~/.ssh/**`, `~/.gnupg/**`, `~/.aws/**`, `~/.azure/**`, `~/.kube/**`, `~/.docker/config.json`, `~/.npmrc`, `~/.npm/**`, `~/.pypirc`, `~/.gem/credentials`, `~/.git-credentials`, `~/.config/gh/**`, and Edit denies for shell rc files; their caveat: without `/sandbox`, deny rules cover only built-in tools, not Bash | [Trail of Bits config](https://github.com/trailofbits/claude-code-config)
- Anthropic's secure-deployment guide lists files to keep out of any mount: `.env`, `~/.git-credentials`, `~/.aws/credentials`, gcloud ADC, `~/.azure`, `~/.docker/config.json`, `~/.kube/config`, `.npmrc`, `.pypirc`, service-account JSON, `*.pem`, `*.key` | [Secure deployment guide](https://code.claude.com/docs/en/agent-sdk/secure-deployment)
- `permissions.blockReadsOutsideWorkingDirectories` (v2.1.257) stops reads outside the working directories even in bypass; `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` strips credentials from subprocess environments and, on Linux, forces every command (including `!` shell mode) into the sandbox | [Permission modes](https://code.claude.com/docs/en/permission-modes), [Sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- The recommended credential pattern is a proxy outside the agent boundary that injects keys so the agent never sees them; for git, route through a tool or proxy that holds the credential. Anthropic's cloud sessions use this design (GitHub credentials never enter the VM; a proxy restricts pushes) | [Secure deployment guide](https://code.claude.com/docs/en/agent-sdk/secure-deployment), [Security docs](https://code.claude.com/docs/en/security)
- Deny-rule bypass reports: a vendor write-up (Adversa, via secondary news) says a 50-subcommand analysis cap let a denied `curl` run when preceded by 50 harmless commands; one account says it was fixed in v2.1.90, another says no official confirmation. Current docs say deny and ask rules apply when any subcommand matches, including nested ones | [Search-surfaced: letsdatascience](https://letsdatascience.com/news/claude-code-bypasses-deny-rules-exposing-vulnerability-681de690), [Permissions docs](https://code.claude.com/docs/en/permissions)

**Repo trust, hooks and MCP**
- Check Point Research (Feb 25, 2026, **>6 mo**; all patched): a cloned repo's project config could run commands or leak API keys before the trust prompt. Hooks in `.claude/settings.json` (fixed Aug 26, 2025), `enableAllProjectMcpServers`/`enabledMcpjsonServers` auto-approving `.mcp.json` servers (CVE-2025-59536, fixed Sep 22, 2025), and `ANTHROPIC_BASE_URL` in project settings redirecting API traffic including the key (CVE-2026-21852, fixed Dec 28, 2025, now network is deferred until trust is accepted). Advice: update, inspect `.claude/`, `.vscode/` before opening, review config changes like source | [Check Point Research](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)
- Today's rule: project `permissions.allow` rules and `additionalDirectories` apply only after the trust dialog, but project hooks, the `env` block and helper commands are used even when only a parent folder is trusted and in `claude -p` (never trusted); `.mcp.json` servers connect without asking in `-p`. Mitigations: `--bare`, `--setting-sources user`, `disableAllHooks` via `--settings`, `disabledMcpjsonServers` | [Permissions docs](https://code.claude.com/docs/en/permissions)
- Trail of Bits sets `enableAllProjectMcpServers: false` because `.mcp.json` lives in git and a compromised repo could ship malicious MCP servers; also pins `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` | [Trail of Bits config](https://github.com/trailofbits/claude-code-config)
- Anthropic "does not security-audit or manage any MCP server", reviews connectors only against listing criteria, and encourages writing your own or using trusted providers; plugins can add MCP servers, so `.mcp.json` review does not show every server | [Security docs](https://code.claude.com/docs/en/security)
- Hooks, MCP servers, plugin monitors and `apiKeyHelper` run outside the sandbox with your privileges | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing), [Sandbox environments](https://code.claude.com/docs/en/sandbox-environments)
- Snyk ToxicSkills (scan as of Feb 5, 2026, **>6 mo**): of 3,984 skills from ClawHub and skills.sh, 13.4% (534) had at least one critical issue (malware distribution, prompt injection, exposed secrets) and 36.82% had some flaw; a later podcast page mentions 76 malicious skills (unverified) | [Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)
- Teams can allowlist channel plugins and MCP via managed settings; `ConfigChange` hooks can audit or block settings changes mid-session | [Channels docs](https://code.claude.com/docs/en/channels), [Security docs](https://code.claude.com/docs/en/security)

**Prompt-injection defenses**
- Built in: network-fetching commands (`curl`, `wget`) are not auto-approved; WebFetch usually summarizes the page with a separate model call; command parsing asks before anything it cannot fully analyze; auto mode strips tool results from the classifier's input and adds a prompt-injection probe on tool outputs; pasted text is marked as possibly containing instructions Claude should only follow if the typed message asks | [Security docs](https://code.claude.com/docs/en/security), [Permission modes](https://code.claude.com/docs/en/permission-modes), [Anthropic auto mode post](https://www.anthropic.com/engineering/claude-code-auto-mode), [Terminal config](https://code.claude.com/docs/en/terminal-config)
- Anthropic's own list for untrusted content: review commands, avoid piping untrusted content into Claude, verify changes to critical files, use VMs for scripts and tool calls touching external services | [Security docs](https://code.claude.com/docs/en/security)
- Framework: the "lethal trifecta" (Simon Willison, Jun 16, 2025, **>6 mo**) is private data plus untrusted content plus external communication; his advice is to avoid the combination entirely, calling ~95%-effective guardrails "very much a failing grade" | [Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/). Anthropic's secure-deployment guide links to it | [Secure deployment guide](https://code.claude.com/docs/en/agent-sdk/secure-deployment)
- Heads-up on doc claims: a vendor blog's "90.5% safety bypass" figure for Claude Code was surfaced by search but could not be verified against its source paper, so it is not used here | [Search-surfaced: secure.com](https://www.secure.com/news/claude-code-safety-bypass-trusted-channel-injection)

**Egress control**
- Required endpoints (network-config docs): `api.anthropic.com`, `claude.ai`, `platform.claude.com` (OAuth exchange and refresh), `downloads.claude.ai` (installer/updates), `registry.npmjs.org` (plugins, npx MCP, npm installs), `mcp-proxy.anthropic.com` (claude.ai connectors; disable with `ENABLE_CLAUDEAI_MCP_SERVERS=false`), `github.com` (plugin marketplaces), `raw.githubusercontent.com` (changelog), `storage.googleapis.com`, `code.claude.com`, `bridge.claudeusercontent.com` (Claude in Chrome); optional Datadog intake hosts for telemetry/error reports, disabled by `DISABLE_TELEMETRY` / `DISABLE_ERROR_REPORTING` or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`. Claude Code does not support SOCKS proxies | [Network config docs](https://code.claude.com/docs/en/network-config)
- Caution: `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` also disables feature-flag fetching, which turns off Remote Control, and auto-updates (Trail of Bits advises against it for the latter reason); `DISABLE_TELEMETRY`/`DO_NOT_TRACK` alone keep RC available on v2.1.283+ unless Trusted Devices is required | [Env vars](https://code.claude.com/docs/en/env-vars), [Remote Control docs](https://code.claude.com/docs/en/remote-control), [Trail of Bits config](https://github.com/trailofbits/claude-code-config)
- Built-in sandbox egress: domain allowlist via local proxy, `strictAllowlist` to deny instead of prompt (v2.1.219+), per-command extra hosts in auto mode (v2.1.271+), loopback/link-local/metadata-resolving hostnames refused (v2.1.284), IPv6 needs brackets (v2.1.229). Limits: no TLS inspection, domain fronting, broad allows are exfil paths | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- Stronger options: `--network none` plus a Unix-socket proxy (Squid, Envoy, mitmproxy, LiteLLM named), or a TLS-terminating proxy; Node `fetch()` ignores `HTTP_PROXY` by default (`NODE_USE_ENV_PROXY=1` on Node 24+) | [Secure deployment guide](https://code.claude.com/docs/en/agent-sdk/secure-deployment)
- Devcontainer firewall limits listed in section 3 (IPv4 only, GitHub ranges, SSH and DNS open) | [init-firewall.sh](https://github.com/anthropics/claude-code/blob/main/.devcontainer/init-firewall.sh)
- Proxmox firewall has no FQDN rules | [Proxmox firewall docs](https://pve.proxmox.com/pve-docs/chapter-pve-firewall.html)

**Tailscale and SSH**
- Tailscale default policy for a new tailnet is allow-all; ACLs are deny-by-default once defined (an empty `acls` section denies everything); ACLs and grants are the two models, edited in the admin console, GitOps or API (page validated Jan 5, 2026) | [Tailscale ACLs](https://tailscale.com/kb/1018/acls)
- Tailscale SSH: Tailscale takes over port 22 on the Tailscale IP, authenticates with WireGuard node keys, leaves OpenSSH config untouched; the server must be Linux (or macOS open-source variant), enabled with `tailscale set --ssh`; policy `ssh` rules use `action: accept|check` (check re-authenticates via the IdP, default `checkPeriod` 12 h, range 1 min to 168 h, or `always`), `dst` cannot use a port, tagged devices cannot originate check-mode rules; restarting `tailscaled` ends active SSH sessions; access changes take effect within seconds and end sessions no longer allowed; not suited to shared multi-user machines; page validated Jan 5, 2026 | [Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh)
- Tailscale Funnel exposes a service to the **public internet** (beta; ports 443/8443/10000; needs the `funnel` node attribute, default target `autogroup:member`); Serve is tailnet-only; a single port is either one or the other (page validated Jan 20, 2026) | [Tailscale Funnel](https://tailscale.com/kb/1223/funnel)
- OpenSSH baseline (Mozilla guidelines, undated, © 2017, **>6 mo**): `PasswordAuthentication no` (and block passwords in PAM too), `PermitRootLogin No`, `AuthenticationMethods publickey`, `LogLevel VERBOSE`, ED25519 keys preferred | [Mozilla OpenSSH guidelines](https://infosec.mozilla.org/guidelines/openssh)
- Desktop SSH needs SFTP and `AllowTcpForwarding` enabled (for the port-forward workaround); the host-key advice is to keep `StrictHostKeyChecking` and a real `known_hosts`, because `UserKnownHostsFile=/dev/null` plus accept-new means nothing records the key | [Desktop docs](https://code.claude.com/docs/en/desktop)

**Exposed ports**
- Docker published ports bypass ufw: Docker routes container traffic in the `nat` table before ufw's INPUT/OUTPUT chains, "effectively" ignoring ufw rules; nftables backend is experimental | [Docker packet filtering](https://docs.docker.com/engine/network/packet-filtering-firewalls/). (Docker's page extract did not cover the `127.0.0.1:` publish syntax or the DOCKER-USER chain; those are standard Docker features but not confirmed from this page.)
- Remote Control opens no inbound ports; Desktop's browser access is by a user-run `ssh -L` | [Remote Control docs](https://code.claude.com/docs/en/remote-control), [Desktop docs](https://code.claude.com/docs/en/desktop)

**Disagreements and caveats**
- Hooks: Anthropic recommends PreToolUse hooks to inspect full command text; Trail of Bits says "Hooks are not a security boundary -- a prompt injection can work around them" and uses them as guardrails. Same facts, different weight.
- Whether Adversa's 50-subcommand deny bypass is fixed: one secondary source says fixed in v2.1.90, another has no confirmation.
- Anthropic's auto-mode default allows reading `.env` and sending credentials to their matching API; Trail of Bits and Anthropic's own sandbox guidance still treat `.env` and credentials as files to deny.

### Inferences
- Minimal baseline for this user (mine): (1) deny Read/Edit on credential paths and `.env` files in *user* settings on both machines, mirrored for `PowerShell(...)` on Windows; (2) sandbox with deny-read on the same paths on the VM; (3) `enableAllProjectMcpServers: false` and a habit of reading `.claude/`, `.mcp.json` and `.vscode/` of any cloned repo before opening; (4) `--bare` or `--setting-sources user` for any `claude -p` on a repo you did not write; (5) no long-lived cloud or SSH keys on the VM: a repo-scoped deploy key or fine-grained token, and no ssh-agent forwarding into agent sessions; (6) one Anthropic login on the VM that you can revoke ("Sign out everywhere"), with Trusted Devices on if the phone is used for RC; (7) MCP servers: only self-written or from providers you trust, enabled per project; plugins treated like npm packages.
- Tailscale (mine, from the cited default-allow behavior): tag the VM (for example `tag:dev`) and write an explicit policy so only the user's own devices reach `tag:dev` on 22 and the app ports; leave Funnel off (restrict the `funnel` node attribute); keep sshd key-only with root login off and no LAN or WAN exposure; use `tailscale serve` for private access to dev servers instead of publishing ports.
- On Docker: bind published ports to loopback or the Tailscale address rather than relying on ufw; set per-service memory limits (section 5).
- Per-domain egress for the VM is only enforceable by Claude's sandbox proxy, a container firewall, or a forward proxy. For a solo developer, the sandbox `allowedDomains` list plus `strictAllowlist` is the cheapest, and `devcontainer` firewall or `--network none` plus proxy is the strongest.

### Gaps
- Primary advisories for CVE-2026-25724/25725/39861 and Adversa's original deny-bypass report were not opened.
- Tailscale grants-vs-ACL best-practice guidance, tag syntax and the `tests` block were not retrieved (the fetched page lacked them).
- No source fetched on ssh-agent forwarding risk, `AllowUsers`/`ListenAddress` tuning, or fail2ban; Mozilla's page does not cover them.
- No MCP-server-specific audit statistics found (Snyk data is about skills).
- Docker `127.0.0.1:port:port` publishing and `DOCKER-USER` chain not confirmed from the fetched page.
- Claude Code OpenTelemetry/monitoring docs (audit trail) were not fetched.

## 5. Resource limits on an 8 GB VM: memory per session, concurrency, Docker limits, swap

### Takeaway
Anthropic documents a 4 GB minimum and a 2.5 GB heap warning but gives no per-session figure; field reports range from about 110-180 MB to 700-900 MB per process at rest, with many leak reports reaching multiple GB, and MCP servers multiply the cost per session. On a shared 8 GB VM plan for two or three concurrent sessions at most, cap tool memory and Docker services explicitly, and keep swap (preferably compressed) plus an early OOM killer as a safety net.

### Cited Findings

**Official numbers and knobs**
- System requirement: 4 GB+ RAM. A "critical memory usage warning" appears when a session's heap passes 2.5 GB; remedy is `/compact` or restart and `claude --continue`; `/heapdump` writes diagnostics (the snapshot contains conversation and credentials); `claude --safe-mode` disables plugins/MCP/hooks to test whether they cause usage | [Setup docs](https://code.claude.com/docs/en/setup), [Troubleshooting](https://code.claude.com/docs/en/troubleshooting)
- `CLAUDE_CODE_TOOL_MEMORY_LIMIT` (Linux and WSL, v2.1.233+) caps memory for Bash, PowerShell and Monitor commands via a memory cgroup, one cap shared by all of a session's commands; the kernel kills a command that cannot stay under it without naming the cap; if cgroup setup fails commands run uncapped (see `claude --debug`); `CLAUDE_CODE_TOOL_MEMORY_CGROUP_EXCLUDE` (v2.1.246+) can extend the cap to MCP servers, LSP, hooks, plugins, helpers and child agents (`none` caps every kind) | [Tools reference](https://code.claude.com/docs/en/tools-reference)
- Subagent limits: `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (default 20, v2.1.217+) and `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (default 3); `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP` (v2.1.193+) controls the reaping of background shells under critical memory pressure after 30 minutes idle | [Env vars](https://code.claude.com/docs/en/env-vars)
- Background sessions: idle unattached sessions are stopped after about an hour; the row notes `possibly low memory` when a process exits before starting on a low-memory host; the supervisor can stop idle sessions to free memory | [Agent view docs](https://code.claude.com/docs/en/agent-view)
- Remote Control server mode defaults to `--capacity 32` concurrent sessions | [Remote Control docs](https://code.claude.com/docs/en/remote-control)
- Memory-related fixes in the latest builds: v2.1.299 (growth under heavy debug logging), v2.1.300 (high memory after resuming a cloud or RC session with many subagents), v2.1.304 (lower memory in long or resumed conversations), v2.1.310 (lower memory for non-interactive sessions compacting very large transcripts) | [Changelog](https://code.claude.com/docs/en/changelog)

**Field measurements (anecdotes, all from bug reports; treat as ranges)**
- GitHub #61425 (v2.1.148, opened May 22, closed "not planned" Jun 21, 2026): title claims ~700 MB RSS per idle CLI, but the `ps` output in the same report shows 498,324 KB and 371,756 KB (about 487 and 363 MiB) | [Anecdote: #61425](https://claudeissues.com/issue/61425-bug-excessive-memory-usage-700-mb-rss-per-cli-instance)
- GitHub #88524 (v2.1.237, macOS 15, 16 GB, ~15 MCP servers, opened Aug 21, 2026, still open): 13 concurrent sessions at roughly 110-180 MB RSS each (the reporter says this undercounts compressed idle heaps) yet the machine thrashed swap; a commenter measured about 560 MB per session process (10 sessions = 5,604 MB) and 1,606 MB for 11 MCP sidecar trees from one never-invoked plugin; archiving an idle session freed ~390 MB; Desktop sessions are not evicted until the app exits | [Anecdote: #88524](https://claudeissues.com/issue/88524-memory-scales-linearly-with-open-sessions-on-macos-idle-chats-never-release-ram)
- Search-surfaced reports: fresh session ~860 MB RSS (Mar 2026), WSL2 session ~990 MB after a minute, and leak reports reaching 4.6 GB in six minutes (v2.1.100, Linux), 12.6 GB in about 12 minutes (v2.1.143, WSL2), 10 GB+ in long Opus 4.7 1M-context sessions, and 18-23 GB with ~1,000 skill files | [Search-surfaced results](https://claudeissues.com/issue/60534-memory-leak-in-long-running-session-rss-grows-to-12-gb-within-minutes-v2-1-143-w), [#57987](https://claudeissues.com/issue/57987-memory-usage-grows-to-10gb-in-long-sessions-with-opus-4-7-1m-context), [#22427](https://claudeissues.com/issue/22427-memory-leak-in-active-sessions-with-many-skills-23gb-ram-after-30min)
- Conflict in the evidence: #61425's headline (700 MB) vs its own `ps` data (363-498 MB); #88524's 110-180 MB per session vs the commenter's 560 MB per session; reports differ by OS, version, MCP count and session age.

**Docker, systemd, swap**
- Docker: `--memory` is the hard cap (minimum 6m); `--memory-swap` equal to `--memory` disables swap for the container; `--memory-reservation` is a soft limit; `--cpus` caps CPU; on memory shortage the kernel kills processes, Docker lowers the daemon's OOM priority but not containers', so containers are more likely to be killed; do not rely on `--oom-kill-disable` without `-m` | [Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)
- Compose: `deploy.resources.limits` accepts `memory`, `cpus` and `pids`, with `reservations` as guarantees; the page does not say whether they are enforced outside Swarm | [Compose deploy reference](https://docs.docker.com/reference/compose-file/deploy/)
- Anthropic's container example uses `--memory 2g --cpus 2 --pids-limit 100` for an agent container | [Secure deployment guide](https://code.claude.com/docs/en/agent-sdk/secure-deployment)
- systemd: `MemoryHigh=` throttles (preferred main control), `MemoryMax=` is a hard cap that invokes the OOM killer inside the unit, `MemorySwapMax=` caps swap, `ManagedOOMMemoryPressure=kill` hands the unit to systemd-oomd; `Delegate=` controls whether user services get controllers | [systemd resource-control](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)
- earlyoom: userspace daemon polling up to 10 times a second; acts when both available RAM and free swap fall below 10% (SIGTERM, escalating to SIGKILL at half), because the kernel OOM killer "waits too long" and swaps out other things first; `apt install earlyoom`; `--prefer`/`--avoid` regexes via `/etc/default/earlyoom` | [earlyoom README](https://github.com/rfjakob/earlyoom)
- zram: compressed RAM block device usable as swap (`mkswap`, `swapon`); sizing beyond about 2x RAM is rarely useful given ~2:1 compression; idle overhead about 0.1% of disk size | [Kernel zram docs](https://docs.kernel.org/admin-guide/blockdev/zram.html)
- Overhead of isolation layers: bubblewrap sandbox runtime "very low", Docker "low", gVisor medium/high, VMs high; Docker Sandboxes add a microVM plus private Docker daemon with no stated memory figures | [Secure deployment guide](https://code.claude.com/docs/en/agent-sdk/secure-deployment), [Docker Sandboxes install](https://docs.docker.com/ai/sandboxes/install.md)
- Other memory consumers: Desktop's remote helper uses about 1 GB of disk per user; VS Code Remote-SSH server memory is unquantified in official docs (see section 2) | [Desktop docs](https://code.claude.com/docs/en/desktop)

### Inferences
- Rough budget for 8 GB (mine, unverified by measurement): reserve about 1.5-2 GB for OS, page cache and Tailscale/Docker daemon; the user's Compose services take whatever they take (cap each with a memory limit); leave roughly 3-4 GB for Claude. At 0.4-0.9 GB per idle session and 1.5-2.5 GB when active with MCP servers or builds, that is about two interactive sessions plus one background job. More than three concurrent sessions needs measuring with `ps -o rss`.
- Practical controls: set `CLAUDE_CODE_TOOL_MEMORY_LIMIT` to about 2G so a runaway build or test is killed instead of the VM; lower `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (for example 2-3) and pass `--capacity` 2 for RC server mode; keep MCP servers few and per-project because each session spawns its own sidecars; restart (`claude --continue`) when the 2.5 GB warning appears; put the whole Claude user in a systemd slice with `MemoryHigh` (throttle) and a higher `MemoryMax`; add zram swap (about 2-4 GB) plus earlyoom with `--avoid` for sshd/tailscaled/dockerd and `--prefer` for `claude` or its builds; and set `mem_limit`/`deploy.resources.limits.memory` on every Compose service.
- Because `claude --bg` stops idle processes after about an hour and resumes on reply, background sessions are a cheap way to hold many conversations without holding their RAM; pin only the ones that must keep running.
- Avoid running Docker Sandboxes, headless Chromium, VS Code Remote-SSH server and several Claude sessions at once on this VM; pick at most two of those at a time.

### Gaps
- No official per-session RSS figure; all numbers are anecdotal bug reports across different OSes and versions, none measured on Ubuntu Server with the v2.1.30x builds.
- No authoritative figure for headless Chromium/Playwright, VS Code server, or Docker Sandboxes memory on this class of VM.
- Not confirmed whether Compose enforces `deploy.resources` without Swarm (older `mem_limit` attribute not covered on the fetched page).
- Not verified whether `CLAUDE_CODE_TOOL_MEMORY_LIMIT` works when the session is started by Desktop's remote helper, or on a VM without a delegated memory cgroup for the user.

## 6. Notifications and monitoring for long runs

### Takeaway
Claude Code has several built-in routes (Notification and Stop hooks, terminal notifications, Remote Control mobile push, Desktop OS notifications, Channels for Telegram/Discord), and the hook route is the one that works on a headless VM because hooks run outside the sandbox and can curl a push service. ntfy is the common community choice but has no official integration; self-hosting it behind Tailscale needs an upstream relay for instant iOS delivery.

### Cited Findings

**Hooks (works on any host, including the remote VM)**
- `Notification` hook fires when Claude is waiting for input or permission; types include `permission_prompt` (after the prompt has waited about 6 s), `idle_prompt` (Claude finished about 60 s ago and you have not typed), `agent_needs_input`, `agent_completed`, `auth_success`, elicitation types and `quota_auto_resume_*`. `Stop` fires whenever Claude finishes responding (not at task completion, and not on user interrupts); API errors fire `StopFailure` with types such as `rate_limit`, `overloaded`, `authentication_failed`, `billing_error`, `max_output_tokens` | [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Command hooks run outside the sandbox, so a `curl` in a hook is not limited by the sandbox allowlist | [Sandboxing docs](https://code.claude.com/docs/en/sandboxing)
- `notify-send` needs a desktop notification daemon, which "headless servers, SSH sessions, and most containers don't have"; the Windows example uses `powershell.exe` and opens a message box that can appear behind the terminal; under WSL `powershell.exe` must be on PATH through interop | [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- For Desktop SSH sessions Anthropic tells you to configure the `Notification`, `Stop`, `StopFailure` and `PermissionRequest` hooks in `~/.claude/settings.json` **on the remote machine** | [Desktop docs](https://code.claude.com/docs/en/desktop)
- Subtleties: a `Stop` hook that blocks is overridden after eight consecutive blocks; check `stop_hook_active` | [Hooks guide](https://code.claude.com/docs/en/hooks-guide)

**Terminal and OS notifications**
- Desktop notifications are sent by default only from Ghostty, Kitty and iTerm2 (and reach the local machine over SSH); elsewhere set `"preferredNotifChannel": "terminal_bell"` or use a hook; inside tmux set `allow-passthrough on`; iTerm2 needs "Send escape sequence-generated alerts" enabled | [Terminal config](https://code.claude.com/docs/en/terminal-config)
- Terminals implementing the OSC 7501 Program Status Protocol can show working/waiting/done (v2.1.295+; not inside tmux and not for background sessions) | [Terminal config](https://code.claude.com/docs/en/terminal-config)
- Claude Desktop sends OS notifications when a session finishes and you are not viewing it | [Desktop docs](https://code.claude.com/docs/en/desktop)

**Remote Control mobile push**
- While RC is active Claude can push to the phone, typically when a long task finishes or it needs a decision; you can also ask in the prompt ("notify me when the tests finish"). Enable in `/config`: "Push when Claude decides" and "Push when actions required". Troubleshooting: `No mobile registered` means open the Claude app; iOS Focus modes and Android battery optimization can delay delivery. `CLAUDE_CLIENT_PRESENCE_FILE` (v2.1.181+) suppresses pushes while a marker file exists, to be managed by a screen-lock listener. Pushes are skipped while you are focused in the connected terminal | [Remote Control docs](https://code.claude.com/docs/en/remote-control), [Env vars](https://code.claude.com/docs/en/env-vars)

**Channels (Telegram, Discord, iMessage)** (research preview)
- A channel is an MCP server that pushes events into a running session and can reply two-way. Official plugins for Telegram, Discord and iMessage (macOS only); require Bun, claude.ai or Console API-key auth (not Bedrock/Vertex/Foundry), `claude --channels plugin:telegram@claude-plugins-official`, pairing code plus `/telegram:access policy allowlist`; events only arrive while the session is open, so an always-on setup needs a background process or persistent terminal; channels that implement permission relay let allowlisted senders approve or deny tool use remotely; Team/Enterprise need `channelsEnabled`; Pro/Max opt in per session with `--channels`; flags and protocol may change | [Channels docs](https://code.claude.com/docs/en/channels)
- Dispatch (message a task from the phone to Desktop on your computer) and Scheduled tasks (CLI, Desktop, cloud) are the other "away from the terminal" triggers Anthropic lists | [Remote Control docs](https://code.claude.com/docs/en/remote-control)

**ntfy and community tools**
- Common pattern: a `Stop` hook that `curl`s a topic on ntfy.sh; one-way, and public topics are readable by anyone who guesses the name, so reserve a topic or self-host. A gist filters to sessions longer than 30 s; `claude-push` and `claude-remote-approver` use a `PermissionRequest` hook with ntfy Allow/Deny buttons for two-way approval; Pushary is a paid ($9.99/mo) alternative | [Search-surfaced: gist](https://gist.github.com/iboss-ptk/3c036277237f4e483447a9f450244e58), [claude-push](https://github.com/coa00/claude-push), [claude-remote-approver](https://github.com/yuuichieguchi/claude-remote-approver), [Pushary](https://pushary.com/claude-code-notifications)
- Self-hosting ntfy: `auth-default-access: deny-all` with an `auth-file`, user tokens via `ntfy token add` (prefix `tk_`, up to 60 per user, tokens currently grant full account access), `behind-proxy: true` behind a reverse proxy. iOS needs `upstream-base-url: https://ntfy.sh` so the self-hosted server sends only a poll request (message ID) through ntfy.sh to Firebase/APNs; without it delivery "can take hours" (about 20-30 minutes when the phone is in use). Android uses Firebase via the ntfy.sh app or alternatives; messages are cached in memory for 12 hours unless a cache file or database is configured | [ntfy config docs](https://docs.ntfy.sh/config/)

**Monitoring unattended work**
- `claude agents --json [--all]` lists background sessions with `state` (`working`, `blocked`, `done`, `failed`, `stopped`), `status` and `waitingFor`; `claude logs <name>` prints recent output; Notification hook types `agent_needs_input` and `agent_completed` cover background sessions; footer shows `← N agents` or `← N done` | [Agent view docs](https://code.claude.com/docs/en/agent-view)
- `--output-format stream-json` emits `system/api_retry` events and `permission_denied` messages; `--output-format json` includes `total_cost_usd` (client-side estimate); `--max-budget-usd` caps spend; v2.1.305 added `CLAUDE_CODE_RETRY_WATCHDOG_USAGE_LIMIT_RECHECK_MS` for unattended retry mode | [Headless docs](https://code.claude.com/docs/en/headless), [Changelog](https://code.claude.com/docs/en/changelog)
- Anthropic points to OpenTelemetry metrics for usage monitoring and `ConfigChange` hooks for audit | [Security docs](https://code.claude.com/docs/en/security)

**Disagreements**
- Search-surfaced guides present ntfy.sh as "free and easy" while the ntfy docs themselves say public topics are open and iOS instant delivery of a self-hosted server depends on the public ntfy.sh relay; both are true but pull in opposite directions for a privacy-minded tailnet-only setup.

### Inferences
- A layered setup (mine): (1) Remote Control push for "done" and "needs a decision" when RC is on; (2) `Notification` (matcher for `permission_prompt` and `idle_prompt`), `Stop` and `StopFailure` hooks on the VM that curl a self-hosted or token-protected ntfy topic, optionally skipping sessions shorter than about 30 seconds; (3) Desktop's own OS notification for interactive sessions; (4) optional Telegram channel if two-way chat is wanted. Because hooks run unsandboxed, ntfy does not need to be added to the sandbox allowlist.
- Hook command quality matters: keep the payload static or minimal (no secrets), rate-limit, and match the notification types with a regex matcher (check in `/hooks` that it parsed).
- For the user's tailnet-only preference, a self-hosted ntfy reachable only over Tailscale is private but, on an iPhone, still needs the ntfy.sh upstream relay for instant push (the relay sees only message IDs); on Android the foreground-service or Firebase options apply. If the phone already has the Claude app, RC push may remove the need for ntfy for the "done" case.
